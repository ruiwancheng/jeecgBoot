# 回归测试使用指南（业务人员版）

> **本文给业务人员看**。教你怎么和 AI 配合，把"系统功能到底有没有问题"这件事搞清楚。
>
> **核心思路**：你**不懂技术**没关系，AI 帮你读技术细节 + 出报告，**你只需要做一件事 — — 看到失败的地方时，亲自到系统里走一遍，告诉 AI 到底是不是真的 bug**。

---

## 一、什么时候需要做回归测试

| 场景 | 举例 |
|---|---|
| 🔄 **系统大改动后** | 加了新功能、删了旧功能、改了数据库结构 |
| 📦 **发版前** | 准备给客户升级前，要确保老功能没被搞坏 |
| 🐛 **修了一个 bug 之后** | 担心改 A 坏 B（这种情况最常见）|
| 📅 **每周/每月例行** | 防止代码越改越坏，定期体检 |

**简单说**：只要代码动了，都该做一次回归。

---

## 二、整个流程 4 步走

```
第 1 步：跑测试（AI 自动，30-60 分钟）
   ↓ 产出"回归报告"
第 2 步：业务人员复核（你！30-60 分钟）
   ↓ 告诉 AI 哪些是真的 bug
第 3 步：误判复盘（AI 自动，5 分钟）
   ↓ 防止下次又踩同样的坑
第 4 步：bug 派发修复（AI 自动，1-3 天）
   ↓ 工程师改代码
```

**整套流程约 1-2 天**（其中 90% 时间在跑测试 + 工程师改代码，**你只需投入 30-60 分钟复核**）。

## 三、详细步骤（业务人员视角）

### 📋 第 1 步：跑回归测试

**对 AI 说**：
```
跑回归测试
```
或者更精确：
```
/test-regression
```

**AI 做什么**：
- 自动起 30+ 个测试（API + 浏览器）
- 30-60 分钟跑完
- 产出一份"回归报告"（HTML 或 Markdown）
- 报告里会列出：哪些测试通过 ✅，哪些失败 ❌

**你做什么**：
- 等 AI 跑完（不用盯）
- 收到 AI 提示"报告已生成"

**小贴士**：
- 报告通常在 `harness/.regression-runs/20260807-XXXXXX/regression-report.md`
- AI 自己会记住最新一次报告的位置，不用你记
- 失败越多越正常（1-3 个不算事）

---

### 📋 第 2 步：你来复核（**最重要的一步！**）

**对 AI 说**：
```
开始复核
```
或者：
```
/regression-review
```

**AI 做什么**：
- 给你列出失败的测试清单
- 解释每个失败是什么（用业务语言，不用技术术语）
- 告诉你**去系统的哪个页面 + 做什么操作**可以验证

**你做什么 — — 4 件事**：

#### ① 拿到 AI 给的清单

AI 会告诉你类似：
> "测试 4.1 失败：盘点页面 E2E
> 怀疑原因：账面对不上账
> 验证步骤：登录系统 → 库存管理 → 盘点 → 创建盘点单 → 看账面数量"

#### ② 打开系统，按 AI 说的步骤亲自走一遍

**这就是关键！** 你要像平时用系统一样，亲自点进去看：
- 账面数量对不对？
- 操作能成功吗？
- 页面显示正常吗？

#### ③ 告诉 AI 你的判断

**用自然语言告诉 AI 就行**，例如：

```
"4.1 盘点页面的账面数量对，我看到的就是 15，业务上这样是对的，
  不是 bug，是测试用的数据残留"
```

或者：

```
"4.1 抽屉打不开，点了查看追溯后空白页，这是真 bug，
  严重度 P1，前端工程师小王去修"
```

或者：

```
"4.6 库存预警页面没有搜索框，
  这是优化点不是 bug，慢慢做就行，
  P2 排期，前端工程师老李"
```

**4 种判断 + 句式**（直接念就行）：

| 你的判断 | 念这句话 |
|---|---|
| ✅ **误判**（不是 bug，是测试方法错了或数据残留）| "4.X 是误判，因为 XXX" |
| 🔴 **真 bug**（系统真的坏了）| "4.X 是真 bug，因为 XXX，严重度 P0/P1/P2，负责人 XXX" |
| 🟡 **要优化**（不是 bug，但功能不完善）| "4.X 是要优化，因为 XXX，安排到下个迭代" |
| ❓ **看不准**（让 AI 派另一个 AI 再查）| "4.X 我拿不准，让另一个 AI 复核下" |

#### ④ 重复 ②-③ 直到所有失败都判断完

不用怕判断错 — AI 会记录你的判断，并写进报告。

---

### 📋 第 3 步：误判复盘（AI 自动）

**对 AI 说**：
```
复盘误判
```
或者：
```
/regression-retro
```

**AI 做什么**：
- 把这次的所有"误判"分类（5 大类）
- 改测试代码，避免下次踩同样的坑
- 写规则文档

**你做什么**：
- 不用管，AI 自动做
- 5 分钟内完成

**为什么要做这步**：
- 防止下次回归又发现 30+ 误判（浪费时间）
- 让测试更精准

---

### 📋 第 4 步：bug 派发修复（AI 自动）

**对 AI 说**：
```
派发 bug 修复
```
或者：
```
/regression-decompose
```

**AI 做什么**：
- 把"真 bug"按严重度分 3 档：
  - **P0 阻塞**：24 小时内必须修（如：核心功能全挂）
  - **P1 主流程**：1 周内修（如：主要业务不能跑）
  - **P2 优化**：2 周内修（如：体验问题）
- 给每个 bug 写好"如何修"的说明
- 派给对应工程师（前端/后端）

**你做什么**：
- 看一眼 AI 的派发清单
- 确认严重度合理
- 等工程师修完

## 五、你需要知道的事

### 关于"AI 误判"（正常现象）

- 回归报告里 30%+ 是**误判**（不是真 bug），正常！
- 常见原因：
  - 测试用的数据残留
  - 业务上没这功能（测试多加的）
  - 测试期望值与业务实际不符
  - 报告生成器误归类

- **不用担心误判多** — 这就是为什么要你复核

### 关于"严重度"

| 等级 | 含义 | 处理时效 |
|---|---|---|
| **P0 阻塞** | 核心功能全挂，客户用不了 | 24 小时 |
| **P1 主流程** | 主要业务不能跑（如：不能下单、不能盘点）| 1 周 |
| **P2 优化** | 体验问题、不影响主功能 | 2 周 |
| **P3 无需跟进** | 误判或小问题 | 不跟进 |

**怎么判断严重度**（你不是工程师也能判断）：

- **P0**：客户付款后钱扣了但订单没生成；盘点后账面全乱了
- **P1**：某个常见场景走不通；数字对不上
- **P2**：页面某个按钮没的；颜色/字体不好看
- **P3**：建议性反馈

### 关于"责任人"

- 你**不需要知道**谁负责哪个模块
- 告诉 AI "前端 bug" 或 "后端 bug" 即可，AI 会找对人
- AI 找不到时会问你

### 关于"复核时间"

- **8 个失败测试**约需 **30-60 分钟**复核
- 重点看：**P0/P1** 的（影响业务的）
- P2/P3 可以快速过

## 六、常见问题

### Q1：我看系统时发现不了 AI 说的问题？

A：可能 AI 给的步骤不够细。告诉 AI：
```
"我没看到这个问题，AI 重新查一下，给我更具体的步骤"
```

### Q2：我看系统时发现是测试方法错了，不是真 bug？

A：太好了！这就是误判。直接说：
```
"4.X 是误判，因为 XXX"
```

### Q3：测试有几十个失败，一个一个看不完怎么办？

A：先看 P0/P1（约 2-3 个），P2/P3 可以快速过：
- P0/P1：必须亲自到系统里走一遍
- P2/P3：可以只看 1-2 个，其他批量说"信任 AI 判定"

### Q4：我不确定一个测试是误判还是真 bug？

A：直接说"拿不准"，AI 会派另一个 AI 再查：
```
"4.X 我拿不准，让另一个 AI 复核"
```

### Q5：AI 改的测试代码会不会影响业务？

A：不会。AI 改的是**测试代码**（测业务的代码），不是业务代码本身。
- 测试代码改完，下次回归更准
- 业务代码只有工程师能改

### Q6：什么时候跑回归？

| 时机 | 建议 |
|---|---|
| 大改动后 | 必跑 |
| 修一个 bug 后 | 必跑（防改 A 坏 B）|
| 每周/每月 | 建议跑 |
| 客户升级前 | 必跑 |
| 平时小修小补 | 看情况 |

## 九、最常见的 5 个误判场景（2026-08-07 经验）

> 这些场景下次大概率还会出现，看到心里有数：

1. **测试用旧数据残留** — 测试用的物料在 dev DB 还有库存，账面看起来不对
2. **业务页面没这功能** — 比如 basic-codeRule 页面没设计"导出"，但测试加了导出断言
3. **业务页面已废弃** — 比如 batch-ledger 已被"批次追溯"替代，但测试还在测
4. **URL/文件名错位** — 测试访问 `/project/mes/purchase/ledger`，但业务叫"库存台账"
5. **报告生成器误归类** — 所有 traceabilityBatch 都被打上"Connection Refused"标签

**遇到这些场景放心说"是误判"** — AI 已经知道怎么改。

# 第二部分：覆盖率管理 + 自主进化

> **本部分讲的是"4 步流程"之外的"周边能力"**：

## 十一、怎么查看测试覆盖率（"哪些功能还没测过"）

**对 AI 说**：
```
看看现在测了哪些
```
或者：
```
/coverage
```

**AI 给你看的报告**（示例）：

| 维度 | 已覆盖 | 总数 | 覆盖率 |
|---|---|---|---|
| 页面（38 个）| 36 | 38 | 95% |
| 接口（180 个）| 145 | 180 | 80% |
| 业务链路 | 9 | 12 | 75% |

**+ 缺口清单**（按优先级）：

```
🔴 P0 — 完全没测过的模块（必须补）：
- 客户地址子模块（7 个接口，0 次调用）
- 客户联系人子模块（7 个接口，0 次调用）

🟡 P1 — 部分覆盖：
- 销售发票（写入路径覆盖不足）
- 采购发票（写入路径覆盖不足）

🟢 P2 — 已基本覆盖：
- 物料管理（55 次调用，覆盖率 100%）
```

**你做什么**：
- 看"🔴 P0"清单 → 这些是下次要补的
- 告诉 AI"补这些"即可

## 十二、怎么增加测试用例提升覆盖率（"补测试"）

### 场景 A：补某个模块的测试

**对 AI 说**：
```
给客户地址子模块补测试
```
或者：
```
/add-tests basic customerAddress
```

**AI 做什么**：
- 自动读 Controller 代码（找所有接口）
- 自动读前端页面（找所有按钮/操作）
- 自动生成测试用例（CRUD + 异常路径 + 权限）
- 写入 `harness/e2e/mes/basic-customerAddress.spec.ts` + `harness/tests/modules/basic-customerAddress.test.js`
- 跑通测试
- git commit

**输出示例**：

```markdown
## /add-tests basic customerAddress 完成

新增：
- harness/e2e/mes/basic-customerAddress.spec.ts（7 tests）
- harness/tests/modules/basic-customerAddress.test.js（10 tests）

覆盖：7/7 接口 = 100%

验证：
- spec: 7 passed
- module: 10 passed

commit: <hash>
```

### 场景 B：补某个业务流程的测试（如"销售→出库→收款"）

**对 AI 说**：
```
给销售出库收款流程补测试
```
或者：
```
/add-tests sales 链路 sales-receipt-flow
```

AI 会模拟真实业务跑一遍（创建销售单 → 出库 → 收款），验证数据流通畅。

### 场景 C：新功能上线时补测试

**对 AI 说**：
```
新加了生产领料功能，给它补测试
```
或者：
```
/add-tests manufacturing productionPicking
```

### 场景 D：批量自动生成（适合新模块）

**对 AI 说**：
```
为新模块 demo 仓库管理生成测试
```
或者：
```
/gen-tests demo 仓库管理
```

AI 会**重新生成**（覆盖旧文件）该模块所有 API + E2E 测试。

## 十三、怎么让 AI 自主学习进化（"系统越用越聪明"）

> **AI 也有"记笔记"和"升级"机制**。每次跑回归、每次出 bug、每次复盘，AI 都会**自动累积经验**到知识库，下次不会犯同样的错。

### 13.1 三层学习机制

```
第 1 层：经验库（learnings/）
   ↓ 每次跑回归 / 出 bug / 复盘 都写一条经验
第 2 层：规则化（rules/）
   ↓ AI 自动把"反复出现的经验"总结成规则
第 3 层：自动改进（autonomous）
   ↓ 每周 AI 自动跑一次，检查"还有哪些经验没规则化"
```

### 13.2 你能用的 3 个命令

#### 命令 1：`/learn` — 提取本次会话经验

**对 AI 说**：
```
记一下今天的经验
```
或者：
```
/learn
```

**AI 做什么**：
- 回顾本次会话
- 提取 1-3 条可复用经验
- 写入 `.claude/memory/learnings/`
- 格式：`[日期] [类别] 标题 | 触发条件 | 处理方式`

**例**：
```
2026-08-07 learnings/2026-08-07-orchestration-taskid-required.md
  - 标题: Orca 派工 taskId 必填
  - 触发: 派发任务给独立 AI 工人
  - 处理: 必须用 task-create + dispatch，不能直接 terminal send
```

#### 命令 2：`/auto-learn` — 检查知识库健康度

**对 AI 说**：
```
检查下知识库
```
或者：
```
/auto-learn
```

**AI 给你看的报告**：

```
=== /auto-learn 报告 ===

📚 learnings 清单 (12 条)
  2026-08-07 orchestration-taskid-required ✅→rules/
  2026-08-07 regression-double-review ✅→rules/
  ...

🛡️ 规则覆盖率: 9/12 (75%)
  已覆盖: 派工协议、回归测试、误判模式...
  未覆盖: SQL 注入、状态机、性能测试

📊 速查表: 18 条模式, 覆盖 8 个模块
  新增建议: stock 模块缺速查表

🔄 待进化: 3 条 learnings 未规则化
```

**你做什么**：
- 看"未覆盖"项 → 决定要不要补
- 决定"yes, evolve" → AI 帮规则化

#### 命令 3：`/evolve` — 让 AI 自动升级（高阶）

**对 AI 说**：
```
让 AI 自己升级下
```
或者：
```
/evolve
```

**AI 做什么**（**重要：会修改规则文件**）：
1. 读所有 learnings
2. 对比现有规则
3. 输出"建议改进清单"（逐项确认）
4. 你确认后 → AI 改 `code-style.md` / `audit-classification.md` / `frontend.md` 等
5. 改完跑 harness-check 验证

**典型输出**：
```
1. [高] "派工协议 taskId 必填" → 写入 commands/dev/delegate.md
2. [中] "误判 5 大类" → 写入 rules/testing.md
3. [低] "精度 4 位通用规则" → 写入 code-style.md
确认: 1,2,3 / all / none
```

你回 `1,2,3` 或 `all` 即可。

## 十四、完整的"开发 → 上线 → 维护"工作流

```
新功能开发
   ↓ /new-module <新模块>   （自动生成模块骨架）
   ↓ /add-tests <模块>     （自动生成测试）
   ↓ 工程师写代码
   ↓ /test-regression        （跑回归）
   ↓ /regression-review      （你复核）
   ↓ /regression-retro        （AI 复盘误判）
   ↓ /regression-decompose    （AI 派发 bug）
   ↓ 工程师修代码
   ↓ /test-regression        （再跑回归）
   ↓ /learn                   （AI 提取经验）
   ↓ /auto-learn              （AI 检查知识库）
   ↓ /evolve                  （AI 自主升级规则）
   ↓ 上线
```

**这套流程的目的**：让 AI 系统**越用越聪明**，每次跑回归都能发现新的误判模式、新的 bug 规律，下次不再犯。
