# [2026-08-07] [docs] 给业务人员写文档的"业务语言"原则

**触发条件**：写给业务人员（不懂技术）的文档 — — 使用指南 / 操作手册 / SOP / FAQ 等。

**处理方式**：

## 1. 核心原则：业务动作 > 技术术语

业务人员**不懂技术**，他们关心的是"**我做什么**"和"**AI 做什么**"，不是 API / 端点 / worker_done 这些技术概念。

**翻译对照表**：

| ❌ 技术术语 | ✅ 业务语言 |
|---|---|---|
| `regression-test slice 4.1` | 测试 4.1 失败 |
| `regression-report.js` | 回归报告 |
| `expect(received).toBe(20)` | 账面数量对不上账 |
| `5s timeout` | 操作超时（页面没响应）|
| `Connection Refused` | 页面打不开 |
| `worker_done 被拒` | AI 任务交付失败 |
| `task-create + dispatch` | （业务人员无需知道）|
| `harness/.regression-runs/XXX/` | 报告位置（AI 自己记）|
| `endpoint / API / 端点` | 功能（如果非要用，叫"操作"）|
| `git commit / push` | （业务人员无需知道）|
| `覆盖率 80%` | 测了 80% 的功能 |
| `P0 阻塞 / P1 主流程` | 24h / 1 周 / 2 周（**直接用时间**）|

## 2. 文档结构（按业务人员"做事流程"组织）

不要按技术架构组织，按**业务人员一天/一周做的事**组织：

```markdown
❌ 技术架构组织：
  第一章：系统概述
  第二章：架构设计
  第三章：API 规范
  第四章：测试框架
  第五章：报告生成

✅ 业务人员做事流程：
  第一章：什么时候需要做回归测试
  第二章：整个流程 4 步走
  第三章：详细步骤（业务人员视角）
  第四章：反馈模板（直接复制）
  第五章：你需要知道的事
  第六章：常见问题
```

## 3. 必备 4 个元素

业务人员文档必含：

### 元素 1：**自然语言命令清单**

不要让业务人员记 `/test-regression` 这种命令，让他们说自然语言：

```markdown
| 场景 | 你对 AI 说的话 |
|---|---|
| 跑回归测试 | "跑回归测试" |
| 你复核 | "开始复核" |
| AI 复盘 | "复盘误判" |
| 派发修复 | "派发 bug 修复" |
```

**AI 自己会翻译**成 `/test-regression` 等命令，业务人员无需知道。

### 元素 2：**复制粘贴模板**

业务人员不想"造句"，给模板直接套：

```markdown
## 反馈模板

### 模板 A：误判（不是 bug）
"4.X <哪个测试> 是误判，因为 <你在系统里看到的情况>"

### 模板 B：真 bug
"4.X <哪个测试> 是真 bug，因为 <问题>，严重度 P0/P1/P2，负责人 <谁>"
```

### 元素 3：**业务判断标准**

业务人员不知道怎么定 P0/P1/P2，给具体业务例子：

```markdown
| 等级 | 业务例子 |
|---|---|
| P0 | 客户付款后钱扣了但订单没生成；盘点后账面全乱了 |
| P1 | 某个常见场景走不通；数字对不上 |
| P2 | 页面某个按钮没的；颜色不好看 |
| P3 | 建议性反馈 |
```

### 元素 4：**"我不需要知道"声明**

明确告诉业务人员"哪些是 AI 做的 / 你不需要懂"：

```markdown
你不需要：
- ❌ 懂技术
- ❌ 用命令行
- ❌ 改代码
- ❌ 记命令（AI 自己会）

你只需要：
- ✅ 打开浏览器看系统
- ✅ 在对话窗口跟 AI 说话
- ✅ 30-60 分钟做业务复核
```

## 4. 写作风格 5 条铁律

### 铁律 1：**句子短，主语明确**

```markdown
❌ "本指南将阐述回归测试的整个生命周期，包括测试执行、报告生成、误判分类、修复派发等环节"
✅ "回归测试 4 步走：① 跑测试 ② 你复核 ③ AI 复盘 ④ 派发修复"
```

### 铁律 2：**用"你"不用"用户"**

```markdown
❌ "用户需要登录系统查看"
✅ "你打开系统，点 X 按钮，看 Y 是否正确"
```

### 铁律 3：**业务例子 > 抽象描述**

```markdown
❌ "高严重度意味着阻塞核心业务流程"
✅ "客户付款后钱扣了但订单没生成 → P0"
```

### 铁律 4：**避免双重否定 + 条件句**

```markdown
❌ "如果你没看到 AI 说的问题，那么可能是 AI 给的步骤不够细"
✅ "看不到？让 AI 重新给具体步骤"
```

### 铁律 5：**可视化优于文字**

```markdown
❌ "回归测试 4 步流程，依次为：第一步跑测试，第二步复核，第三步复盘，第四步派发"
✅ 用流程图 + 表格：
```

## 5. 速查表放在文档头部（业务人员先看这个）

```markdown
# 文档标题
> 给业务人员用。先看速查表，需要细节再往下读。

## ⚡ 速查表（30 秒看完）

| 场景 | 你说什么 |
|---|---|
| 跑测试 | "跑回归测试" |
| 复核 | "开始复核" |
| 误判 | "4.X 是误判，因为 XXX" |
| 真 bug | "4.X 是真 bug，...负责人 X" |
| 派发 | "派发 bug 修复" |

## 详细步骤（5 分钟看完）
...
```

## 6. 章节字数控制

| 章节类型 | 字数上限 |
|---|---|
| 速查表 | 1 页 A4（< 500 字）|
| 单一命令说明 | < 300 字 |
| 详细步骤 | < 1500 字 |
| FAQ | 每条 < 100 字 |
| 总文档 | < 10 页 A4（< 5000 字）|

**如果写超了，说明应该拆成多个文档**。

## 7. 实际案例对比

### ❌ 错误示例（技术语言）

```markdown
## /regression-review 工作流

1. 解析报告
   ```bash
   grep -E "^### 4\." harness/.regression-runs/$RUN_ID/regression-report.md
   ```

2. 抽取 failed 切片
   ```bash
   grep -A 10 "测试位置：" harness/.regression-runs/$RUN_ID/regression-report.md
   ```

3. 委派独立 AI 复核
   ```bash
   orca orchestration task-create --spec "..."
   ```

4. 合并双源复核结果
   ...
```

**问题**：业务人员看到 1-4 步全是 bash 命令，直接放弃。

### ✅ 正确示例（业务语言）

```markdown
## 你来复核（最重要的一步！）

**对 AI 说**：开始复核

**AI 做什么**：
- 给你列出失败的测试清单
- 解释每个失败是什么
- 告诉你去系统的哪个页面 + 做什么操作可以验证

**你做什么 — — 4 件事**：

1. 拿到 AI 给的清单（AI 会说"4.1 失败，怀疑原因 XXX"）

2. 打开系统，亲自走一遍（按 AI 说的步骤点进去看）

3. 告诉 AI 你的判断（用自然语言）：
   - "4.1 是误判"（不是 bug）
   - "4.1 是真 bug，严重度 P1"（系统坏了）
   - "4.1 是要优化"（不是 bug，但不完善）

4. 重复 1-3 直到所有失败都判断完
```

**好处**：业务人员看到 1-4 步都是"我做什么"，AI 做什么用 1 行带过。

## 8. 文档自检清单

写完业务人员文档后，对照这个清单自检：

- [ ] 业务人员看完能在 5 分钟内上手
- [ ] 没有命令 / API / 代码 / 端点等术语（或者已翻译）
- [ ] 每个步骤都有"你做什么"和"AI 做什么"
- [ ] 反馈模板可直接复制粘贴
- [ ] 有"严重度"业务例子（不只是 P0/P1/P2 抽象）
- [ ] 速查表在文档头部
- [ ] 总字数 < 5000 字
- [ ] 至少 1 个"我不需要懂"声明

## 9. 适用文档类型

- ✅ 使用指南 / 用户手册
- ✅ SOP（标准操作流程）
- ✅ FAQ
- ✅ 操作指南
- ✅ 培训文档
- ❌ 技术架构文档（用技术语言）
- ❌ API 文档（用技术语言）
- ❌ 代码注释（用代码语言）
