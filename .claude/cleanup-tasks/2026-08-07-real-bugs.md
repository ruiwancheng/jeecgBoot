## B1 · purchase-mesCostLog 权限码注册（P0 阻塞）

### 业务名
**采购成本日志 /list 端点权限码缺失，导致整接口 500 不可用**

### 用户路径
- 路径：访问任何采购成本日志相关页面（如 `/project/mes/purchase/costLog`）
- 操作步骤：
  1. 登录系统（任意有权限的账号）
  2. 调 `GET /mes/purchase/mesCostLog/list?pageNo=1&pageSize=10`
  3. 期望：返回 200 + 成本日志列表
- 实际：返回 500 + 报错 `Subject does not have permission [mes:purchase:costLog:list]`
- 影响范围：**所有**采购成本日志功能不可用

### 验收标准
- [ ] 数据库 `sys_permission` 表新增权限码 `mes:purchase:costLog:list`（code + name + perms + perms_type='1'）
- [ ] 权限码与 `MesCostLogController` 的 `@PreAuthorize` 注解 / `RequiresPermissions` 注解一致
- [ ] 跑回归 `purchase-mesCostLog.test.js` 全部通过（1.1 list 200 即可）
- [ ] 业务人员实测：调 `/mes/purchase/mesCostLog/list` 返回 200 + records

### 依赖
- 数据库初始化脚本：需新增 INSERT INTO sys_permission SQL
- `MesMenuRegistry.java`：检查是否需要新增 menu + 关联 perm
- 后端：检查 `MesCostLogController` 的权限注解

### 风险
- **medium**：新增权限码可能涉及菜单注册、角色绑定
- 需同步检查 `mes:purchase:costLog:queryById` / `queryAll` / `exportXls` 等其他权限码是否齐全

### 工作量
- **small**（约 30 分钟）
  - DB INSERT: 5 分钟
  - 重启后端生效: 5 分钟
  - 跑回归验证: 20 分钟

### Rollback
- 直接 DELETE FROM sys_permission WHERE perms = 'mes:purchase:costLog:list'
- 重启后端即可

## B2 · other-stock-in 后端精度丢失（P1 主流程）

### 业务名
**其他入库 totalAmount 计算时 4 位小数被强制截断为 2 位，财务核算精度丢失**

### 用户路径
- 路径：`/project/mes/stock/other-in`（其他入库页面）
- 操作步骤：
  1. 登录系统
  2. 进入"其他入库" → "新增入库单"
  3. 选物料（如 LOCAL-M，movingAvgCost=18.6765）
  4. 选仓库 + 输入数量
  5. 保存（系统自动预填移动平均成本 + 计算 totalAmount）
  6. 调 `GET /mes/stock/otherIn/list` 查落库单据
- 预期：`totalAmount = 18.6765`（保留 4 位小数）
- 实际：`totalAmount = 18.68`（被截断为 2 位小数，丢失 0.0035）

### 验收标准
- [ ] 数据库 `c_mes_other_stock_in_item.amount` 字段精度从 `decimal(18,2)` 改为 `decimal(18,4)`
- [ ] 后端 `MesOtherStockInServiceImpl.java:190` 的 `setScale(2, ...)` 改为 `setScale(4, ...)`
- [ ] 同样修复以下文件中所有 `setScale(2, ...)`（系统性问题）：
  - `MesOtherStockInServiceImpl.java:190` — `item.setAmount(...).setScale(2, HALF_UP)`
  - `MesStocktakeServiceImpl.java:216` — `ii.setAmount(...).setScale(2, HALF_UP)`
  - `MesStocktakeServiceImpl.java:244` — `oi.setAmount(...).setScale(2, HALF_UP)`
  - `MesStocktakeServiceImpl.java:313` — `item.setDiffAmount(...).setScale(2, HALF_UP)`
  - `MesOtherStockOutServiceImpl.java:132` — `lockedAmount.setScale(2, HALF_UP)`
- [ ] 跑回归 `8.2-stocktake` + `e2e-purchase-sales` 中 other-stock-in 全部通过
- [ ] 业务人员实测：新增入库单 totalAmount 保留 4 位小数

### 依赖
- 数据库迁移：字段精度调整（需检查现有数据无影响）
- 多个 service 文件批量修改（需回归 stocktake + other-stock-in + other-stock-out）

### 风险
- **high**：数据库字段精度调整可能影响现有数据；批量改 setScale 可能影响其他财务计算
- 需先备份数据库，确认现有 amount 字段都是 2 位精度（不会出现 3/4 位精度数据）
- 需业务人员确认：财务核算是否真的需要 4 位精度（vs 2 位 + 单独 unit_cost 4 位）

### 工作量
- **medium**（约半天）
  - DB migration + 数据备份 + 字段调整: 1 小时
  - 5 个 service 文件批量改 setScale: 1 小时
  - 跑 stocktake + other-stock-in + other-stock-out 回归: 2 小时
  - 业务人员实测验证: 1 小时

### Rollback
- DB migration 回滚：`ALTER TABLE c_mes_other_stock_in_item MODIFY amount decimal(18,2);`
- service 文件 git revert
- 重新跑回归确认恢复

### Owner
后端工程师

### 关联
- 报告：`harness/.regression-runs/20260807-032053/regression-report.md#4.2 + #4.8`
- 测试日志：`harness/.regression-runs/20260807-032053/logs/8.3.attempt-1.log` + `e2e-purchase-sales.attempt-1.log`
- 业务复核原文：业务人员实测 totalAmount 4 位小数 vs 2 位小数

### 派发脚本
```bash
git checkout -b fix/amount-precision-4

# 1. 数据库迁移
mysql -u root -p jeecg-boot <<EOF
ALTER TABLE c_mes_other_stock_in_item MODIFY amount decimal(18,4);
ALTER TABLE c_mes_other_stock_out_item MODIFY amount decimal(18,4);
ALTER TABLE c_mes_stocktake_item MODIFY amount decimal(18,4);
ALTER TABLE c_mes_stocktake_item MODIFY diff_amount decimal(18,4);
EOF

# 2. 批量改 setScale（5 个文件）
sed -i 's/setScale(2, java.math.RoundingMode.HALF_UP)/setScale(4, java.math.RoundingMode.HALF_UP)/g' \
  jeecg-boot/jeecg-boot-module/project-mes/src/main/java/org/jeecg/modules/mes/stock/service/impl/MesOtherStockInServiceImpl.java \
  jeecg-boot/jeecg-boot-module/project-mes/src/main/java/org/jeecg/modules/mes/stock/service/impl/MesOtherStockOutServiceImpl.java
# 其他 stocktake 文件手动检查

# 3. 重新编译后端
cd jeecg-boot && mvn clean package -pl jeecg-boot-module/project-mes -am -DskipTests

# 4. 重启后端 + 跑回归
cd .. && python harness/scripts/resilient_regression.py resume --run-dir 20260807-032053 --retry-failed
```
