## 共识风险

## 🔴 P0 共识（4 项）

| # | 问题 | 检出 Agent | 说明 |
|---|------|-----------|------|
| **P0-1** | **抽盘行 book_qty 后端未校验** | 产品2号, 研发3号 | `calcAndSaveItems` 接受客户端传入的 `book_qty`，未与 `c_mes_inventory.current_qty` 交叉验证。通过 API 可传任意值 → diffQty 被篡改 → 盘亏出库扣除错误库存量。修复：`calcAndSaveItems` 中 FOR UPDATE 读库存行并校验 `bookQty` 必须等于 `current_qty`（仅限非全盘行）。 |
| **P0-2** | **`calcAndSaveItems` 未清除 `generatedInId`/`generatedOutId`** | 测试2号, 研发2号 | `item.setId(null)` 只重置了 id。编辑盘点单时可通过 `items[].generatedInId='fake'` 注入伪造的关联单号。需加 `item.setGeneratedInId(null); item.setGeneratedOutId(null);`。 |
| **P0-3** | **`updateWithItems` 未重置 `generatedInId`/`generatedOutId`** | 测试2号 | 同上——编辑状态清空已有关联单号（草稿编辑后重新审核，旧关联无效）。 |
| **P0-4** | **全盘快照只读 `current_qty > 0`** | 产品2号, 测试1号 | `snapshotByWarehouse SQL: WHERE i.current_qty > 0` — 账面数为 0 的物料被排除！如果实盘发现"库位里其实有 5 个物料" → 不会出现在明细中 → 盘盈无法录入。修复：移除 `> 0` 条件，改为快照所有有库存记录的物料。 |
