## 事务边界分析

### 审核事务图谱 🔴 P0
```
stocktakeService.audit(id) @Transactional ← 事务 T1 (盘点 + 出入库单 + 库存)
  ├─ selectByIdForUpdate 锁盘点单
  ├─ auditWithGuard CAS '1'→'2' 原子守卫
  ├─ queryWithItems 读明细（行锁已获取，明细稳定）
  ├─ 逐差异行:
  │   ├─ otherStockInService.saveWithItems(inDoc) ← 同一事务 T1（REQUIRED传播）
  │   │   ├─ validate + calculate amounts
  │   │   ├─ save/duplicateKey/resurrect → c_mes_other_stock_in
  │   │   └─ saveItems → c_mes_other_stock_in_item
  │   ├─ otherStockInService.audit(inDoc.getId()) ← 同一事务 T1
  │   │   ├─ selectByIdForUpdate (入库单)
  │   │   ├─ auditWithGuard CAS '1'→'2'
  │   │   ├─ updateMovingAvgCostOnStockIn → 物料成本表 FOR UPDATE + 成本日志
  │   │   └─ stockIn → 库存表 FOR UPDATE + 台账 INSERT
  │   └─ itemMapper.updateById 回写 generated_in_id ← 同一事务 T1
  └─ (同盘亏 side)
```

**分析：** 
- 所有操作在同一个大事务中 ✅
- Spring AOP `REQUIRED` 传播：盘点 audit 和出入库 audit 合并 ✅
- **任一子步骤抛异常 → 整个事务回滚** ✅
- 但存在 BUG：出入库单的 `auditWithGuard` 成功后，库存操作失败 → 回滚 → 无法恢复 `auditWithGuard` 之前的状态（因为 CAS 原子更新已经提交在同一事务中） → **同一事务中 CAS 更新和库存操作原子化，事务回滚全部撤销** ✅

**澄清：MySQL InnoDB 事务回滚会恢复 CAS 更新的值。CAS 更新 `SET status='2' WHERE id=X AND status='1'` 在事务回滚后恢复为 '1' ✅**

### ⚠️ generated_in/out_id 回写时序

```java
// L167-170:
otherStockInService.saveWithItems(inDoc);
otherStockInService.audit(inDoc.getId());
inCode = inDoc.getCode();
for (MesStocktakeItem item : inLines) {
    item.setGeneratedInId(inDoc.getId());
    itemMapper.updateById(item);
}
```

**分析：** `generatedInId` 的回写在 `saveWithItems`+`audit` 之后，仍在同一事务内。如果 `updateById` 失败：
- 出入库单已审核（CAS+库存+台账）
- 盘点单需回滚 → 所有三步都回滚 ✅

回写失败 = 事务回滚 → 盘点审核失败 → 出/入库单的 CAS 也回滚 = **库存未动 = 一致性保障** ✅

### 🔴 P0：回写与出入库审计在同一事务中，但依赖 itemMapper.updateById 成功

**问题：** `itemMapper.updateById(item)` — 如果此调用失败（网络连接断开/并发冲突），整个事务回滚。但：
- 盘点单 CAS 已执行 → 回滚 → CAS 恢复 '1'
- 出入库单已审核（CAS+库存）→ 回滚 → 库存恢复

**但注意：** `MesOtherStockInServiceImpl.audit()` 本身在**独立的** `@Transactional` 中。通过 Spring 代理调用时传播为 `REQUIRED` → 和外层盘点 audit 合并。回滚时 InnoDB 恢复状态。✅

### 事务大小评估

全盘 500 个物料：
- 盘盈 20 + 盘亏 10 = 2 张出/入库单
- 1 大事务：盘点 CAS + 20 行仓库 FOR UPDATE + 30 行库存 FOR UPDATE + 30 行台账 INSERT

事务大小约 60-90 行 DML + 2 次移动平均成本计算。单次约 500ms-2s。可接受。
