# 11_测试牛马3号_性能压测

> 审计对象：MES 盘点单模块
> 审计日期：2026-07-28

## N+1 查询分析

### 全盘快照 ✅
```sql
SELECT i.material_id, i.current_qty, m.moving_avg_cost
FROM c_mes_inventory i
LEFT JOIN c_mes_material m ON i.material_id = m.id
WHERE i.warehouse_id = #{warehouseId} AND i.current_qty > 0
```
1 条 SQL 完成全仓快照。500 行 → ~50ms ✅

### 抽盘逐行拉库存 🔴 P1
```ts
// onMaterialChange: 每选一个物料调一次 inventory API
const res = await queryInventoryList({ materialId, warehouseId, pageNo:1, pageSize:1 });
```
20 个物料 = 20 次 HTTP 请求 → ~2-3 秒。抽盘物料数 ≤ 20 可接受，但 50+ 时会感觉卡。

### 列表查询 ✅
```java
service.page(new Page<>(pageNo, pageSize), qw);
```
1 SQL，无 N+1 ✅

### 按 ID 查询 ✅
```java
baseMapper.selectById(id);            // 1 SQL
itemMapper.selectList(qw);            // 1 SQL
```
2 SQL 固定 ✅

### 🟡 审核中生成出入库的 SQL 放大

审核 500 物料的盘点单 → 差异行 30：
```
盘点 audit:        1 UPDATE(CAS) + 1 SELECT(items) + 2 saveWithItems + 2 audit
入库 saveWithItems: 1 INSERT/UPDATE + N INSERT(items) = 1 + 15 (盘盈行)
入库 audit:         1 SELECT(locks) + 1 UPDATE(CAS) + N×SELECT_FOR_UPDATE + N×upsertDelta + N×ledger + N×costLog
                    = 1 + 1 + 15×(3~4) = ~50 DML
出库 saveWithItems: 同上镜像 ≈ 1 + 15
出库 audit:         同上无成本日志 = 1 + 1 + 10×(2~3) = ~25 DML
---
总计 ≈ 100-120 DML 在一个事务中
```

事务大小约 120 条 DML + 2 次物料成本计算。单次事务时间 ~500ms-2s。低频操作（日个位数）→ 可接受 ✅

## 索引分析
```sql
PRIMARY KEY (id),              ✅
UNIQUE INDEX uk_stocktake_code_del (code, del_flag), ✅
INDEX idx_item_take_id (take_id) ✅
```

| 查询 | 索引 | 评估 |
|------|------|:--:|
| 列表 ORDER BY create_time DESC | **无索引** | 🔴 P1 |
| 按 code 查重 | uk_stocktake_code_del | ✅ |
| FOR UPDATE id | PRIMARY KEY | ✅ |
| 子表按 take_id | idx_item_take_id | ✅ |

## 🔴 P1：`create_time` 列缺索引
```sql
-- queryPageList: ORDER BY create_time DESC
```
与 OtherStockIn/Out 同样的模式。建议加 `INDEX idx_create_time (create_time)`。

## 结论
全盘快照性能优秀（单 SQL）。1 P1（create_time 索引缺失）、1 P1（抽盘逐行拉库存）。
