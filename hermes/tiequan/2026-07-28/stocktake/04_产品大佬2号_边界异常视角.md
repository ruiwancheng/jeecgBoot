## 并发安全

### 盘点单审核+编辑并发 ✅
```java
// audit(): selectByIdForUpdate → CAS '1'→'2'
// updateWithItems(): selectByIdForUpdate → FOR UPDATE 锁住主表 → 互斥
```
盘点审核和编辑互斥 ✅

### 盘点单审核+删除并发 ✅
```java
// audit(): selectByIdForUpdate, CAS
// removeWithItems(): selectByIdForUpdate, status='1' 守卫
```

### 审核中生成出入库单的并发 🔴 P1
```java
// audit() L167-168:
otherStockInService.saveWithItems(inDoc);
otherStockInService.audit(inDoc.getId());
```
出/入库单的 `saveWithItems` 和 `audit` 在盘点审核的同一事务中，出/入库单的 `auditWithGuard` CAS 是原子操作。但 `saveWithItems` 中 `catch DuplicateKeyException` — 如果编码规则发重号，会抛异常导致整盘审核回滚。概率低但不对用户友好。

**建议：** 出/入库单 code 生成应该在事务外或加 `RETRY`，或直接用 `INSERT IGNORE`+固定 id 的预生成策略。

## 快照一致性

### 账面快照时点 vs 审核时点
假设：
- 创建时账面=100（`snapshotTime = T1`）✓ 快照正确
- 审核时实际库存=90（期间 10 被出库）
- 实盘=95

审核结果：
- `diffQty = 95-100 = -5`（盘亏 5）
- 生成出库单 qty=5
- 最终库存 = 90-5 = 85（而非期望的实盘 95）

**口径衡量：** 前端 alert 已提示"审核差异以此为准，期间出入库不影响本次盘点"✅。这是设计决策，非 bug。但 85≠95 会让不理解的用户困惑。

**风险：** 审核后需要二次盘点 — V1 无锁仓下仅靠文档提示。🟡 P2（可接受的 V1 约束）。

### 抽盘手工行的 book_qty 前端信任问题 🔴 P1
```typescript
// StocktakeDrawer.vue L117-122
const res: any = await queryInventoryList({ materialId: matId, warehouseId: wh, pageNo: 1, pageSize: 1 });
const row = res?.records?.[0];
updateItem(i, 'bookQty', row ? Number(row.current_qty) : 0);
```

**问题：** 前端从 inventory API 拉 `current_qty` 作为 `book_qty`，但：
1. API `queryInventoryList` 不保证快照一致性 — 选中物料 A 时读一次、选 B 再读一次，两次间隔可能数分钟
2. `pageSize=1` 只能拿到一条记录，如果同物料多仓库有数据可能取错
3. 用户可以**篡改 book_qty**（InputNumber 组件是只读的 `<span>` — 等等，检查代码）

```html
<template #bookQty="{ record }">
  <span>{{ record.bookQty }}</span>   <!-- 只读 ✅ -->
</template>
```
book_qty 前端只读 ✅，但 `actualQty` 可修改 ✅（这正是用户需要的）。

**但抽盘的信任问题不在前端：** 前端提交 `items` 数组，其中 `book_qty` 是客户端传的。后端 `calcAndSaveItems` **无条件信任入参**：

```java
if (item.getBookQty() == null) throw new JeecgBootException("明细行账面数量不能为空");
```

**没有校验"book_qty 必须等于当时库存"** — 调用方可以传任意 book_qty。

**攻击向量：** 
- 正常抽盘：选物料 A → onMaterialChange 自动填 book_qty = 当前库存
- 恶意（绕过前端）：直接 POST 数据，`book_qty=9999999` → 后端接受 → `diffQty = actualQty - 9999999` → 生成巨大的盘亏出库单 → 审核后扣除数万库存 ❌

**修复：** 后端 `calcAndSaveItems` 中校验抽盘行的 `book_qty` **必须等于** 当前 `c_mes_inventory.current_qty`（对指定 material+warehouse）。对全盘快照行不用校验（后端自己取的）。🔴 P0

## 逆向操作

### V1 无红冲 🟡
- 审核后不可反审核 — 只能走普通出入库手动调整
- 单据删除：仅草稿可删 — 审核后永久不可删

**业务风险：** 审核后发现实盘数填错（如盘亏 10 填成 100）→ 生成巨大出入库单 → **无法逆转**。需要业务人员手动创建盘盈入库单对冲。🟡 P2（V1 设计决策，需文档明确）

## 临界值

| # | 场景 | 预期 | 实际 |
|---|------|------|:--:|
| CL-1 | actual_qty = null | 审核拦截 | ✅ L139 抛异常 |
| CL-2 | actual_qty < 0 | 前端 InputNumber min=0 拦截 | ✅ 前端+`if (item.getActualQty() != null)` 只计算差异不抛异常 |
| CL-3 | 全仓物料为空 | 提示"该仓库无库存物料" | ✅ L68 |
| CL-4 | unit_cost = null | 后端 `BigDecimal.ZERO` 兜底 | ⚠️ 差异金额=0 静默 — 审核不拦截？L139 只查 actualQty 未查 unitCost |

**CL-4 分析：** 审核时会生成出入库单，入库单 `audit()` 中 `updateMovingAvgCostOnStockIn` 检查 `unitCost > 0` 才联动成本 — 0 成本入库会跳成本更新，符合设计预期。✅

## 结论
1 P0（抽盘 book_qty 后端未校验服务器端数据）、1 P1（出入库单编码重号无重试）、2 P2（V1 无红冲/快照偏差文档）。并发设计优秀（FOR UPDATE + CAS 三层）。

**风险汇总：1 P0 / 1 P1 / 2 P2**
