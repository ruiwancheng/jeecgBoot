# 08_研发大牛3号_并发安全视角审计

> 审计对象：MES 盘点单模块
> 审计日期：2026-07-28

## 并发场景分析

### 场景 1：并发审核盘点单 ✅
```
T1: audit(id) → FOR UPDATE 锁 → CAS '1'→'2' 成功
T2: audit(id) → FOR UPDATE 等待 T1 → T1 释放 → CAS '1'→'2' → 失败（已是'2'）
```
FOR UPDATE + CAS 双保险 ✅

### 场景 2：审核+编辑并发 ✅
```
T1: audit(id) → FOR UPDATE
T2: updateWithItems(id) → FOR UPDATE → 等待 T1 释放 → 读 status='2' → 报错
```

### 场景 3：审核中的库存并发
盘点审核 → 生成出/入库单 → `audit()` → `stockIn/stockOut` → `selectForUpdate(materialId, warehouseId)` 加行锁

**分析：** 如果盘点审核期间另有出入库操作同时进行：
- 盘点出库单 `audit` → `stockOut` → FOR UPDATE 锁库存行
- 另一个 `stockIn` → FOR UPDATE 等待同库存行 → T1 释放后执行

**两个操作不会交错，库存准确性保证。** ✅

## 快照时点偏差（业务性）

### 🔴 P0：全仓快照不加锁 + 审核期间出入库 → 快照过期

```sql
-- snapshotByWarehouse: 普通 SELECT，不加锁
SELECT i.material_id AS materialId, i.current_qty AS bookQty, m.moving_avg_cost AS unitCost
FROM c_mes_inventory i LEFT JOIN c_mes_material m ...
WHERE i.warehouse_id = #{warehouseId} AND i.current_qty > 0
```

**时序分析：**
1. `snapshotByWarehouse` 读库存 → 物料 A 账面=100
2. 另一事务 `stockOut(material A, qty=5)` → 库存=95
3. 盘点审核 → diff=实盘-100 → 调整

**这是否为 P0？** orca 评审明确说"全盘快照不应使用 FOR UPDATE"（P1 建议）。V1 设计决策 = V1 不锁仓。前端 alert 提示已有。🟡 P2（设计决策，非 bug）。

### 🔴 真正的 P0：抽盘行 book_qty 客户端提供+后端不验证

这是产品2号也发现的同一个问题，但这里从并发视角看：

```
攻击者同时提交：
POST /add { takeType:'2', items:[{ materialId:'M1', bookQty:9999999.9999, actualQty:1, unitCost:0 }] }
  → diffQty = 1-9999999.9999 = -9999998.9999
  → 生成出库单 qty=9999998.9999
  → 审核 → stockOut 尝试扣除 9999998.9999
    → 如果库存不足：抛异常，事务回滚（安全 ✅）
    → 如果库存够（攻击者先入库了大量库存）：库存被大量扣除 ❌
```

**严重性：** 如果攻击者"正常入库 10000 + 盘点抽盘 book_qty 填 20000" → diff=-10000 → 出库 10000 → 库存清零。虽然后端不验证 book_qty，但需要"先入库真库存"的前提 — 漏洞利用成本高但不是不可利用。🔴 P0

### 🟡 并发风险：回写 generated_in/out_id 使用逐行 updateById

```java
// L170: 逐行回写
for (MesStocktakeItem item : inLines) {
    item.setGeneratedInId(inDoc.getId());
    itemMapper.updateById(item);
}
```

30 行差异 → 30 次 UPDATE。如果中间某行失败 → 事务回滚 ✅—所有 30 行回滚。但 `updateById` 更新整行（非单字段），会覆盖 `actualQty` 等值。在事务内且在 audit 之后 → 明细数据已稳定，覆盖的是相同值 → 没问题 ✅

## 幂等性

### auditWithGuard 幂等 ✅
```sql
UPDATE ... SET status='2' ... WHERE id=#{id} AND status='1'
```
第二次调用返回 0 → 抛异常，不生成入库单 ✅

### 出入库单生成幂等 ⚠️
同一盘点单的 audit 不会生成重复出/入库单（因为 CAS 守卫）。但如果网络重试导致 audit 被调两次：
1. 第一次：CAS 成功 → 生成凭证 → commit
2. 第二次：CAS 失败 → 异常

结果：重复调用安全，不会二次生成凭证 ✅

## 结论
并发设计稳固（FOR UPDATE + CAS + 事务保护），1 P0（抽盘 book_qty 信任问题，并发视角同产品2号）和 1 P2（快照不加锁偏差为设计决策）。

**风险汇总：1 P0 / 0 P1 / 1 P2**
