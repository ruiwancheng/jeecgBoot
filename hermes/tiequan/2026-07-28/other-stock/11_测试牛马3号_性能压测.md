## N+1 查询分析

### 列表查询

```java
// Controller.queryPageList
QueryWrapper<MesOtherStockIn> qw = QueryGenerator.initQueryWrapper(entity, req.getParameterMap());
return Result.ok(service.page(new Page<>(pageNo, pageSize), qw));
```

- 单次 SQL（MyBatis-Plus `page`）✅
- 无子查询、无循环 ✅

### 按 ID 查询（含明细）

```java
// ServiceImpl.queryWithItems
MesOtherStockIn e = baseMapper.selectById(id);       // SQL #1
LambdaQueryWrapper<MesOtherStockInItem> qw = ...;     // SQL #2
e.setItems(itemMapper.selectList(qw));
```

- 2 次 SQL（主表 + 子表），无 N+1 ✅

### 展开行查询子表 🔴 N+1

```java
// OtherInItemsSubTable.vue: onMounted()
const doc = await queryOtherInById({ id: props.docId });        // 1 次
// 然后逐物料查物料名称
const materials = await Promise.all(ids.map((id) =>
    queryMaterialById({ id }).catch(() => null)                   // N 次!
));
```

**问题：** 展开行显示子表明细时，每个物料都单独调一次 `queryMaterialById` API → N 个物料 = N 次 HTTP 请求。

**严重性：** 
- 1 行物料 = 1 次额外请求（可接受）
- 10 行物料 = 10 次额外请求（明显延迟）
- 100 行物料 = 100 次额外请求（卡死）

**注意：** 但实际上 `queryOtherInById` 返回的 `items` 中已包含 `materialId_dictText`（MyBatis-Plus 的 `@Dict` 注解翻译），子表组件其实**不需要再单独查物料名称**。`materialText(record)` 的 fallback 逻辑中 `record.materialId_dictText` 已经是可用的。

```vue
function materialText(record: any) {
    const m = materialMap.value[record.materialId];
    if (m) return m.code;
    return record.materialId_dictText || record.materialId || '-';  // ← 已有 dictText!
}
```

**结论：** `queryMaterialById` 的 N 次调用其实是**过度设计**——`materialId_dictText` 已经可用，只需写 `spec` 字段。降级为 P2。

## SQL 性能

### 索引分析

```sql
-- c_mes_other_stock_in
PRIMARY KEY (id),
UNIQUE INDEX uk_other_stock_in_code_del (code, del_flag)  ✅

-- c_mes_other_stock_in_item
PRIMARY KEY (id),
INDEX idx_item_in_id (in_id)  ✅

-- c_mes_other_stock_out (同上镜像)
-- c_mes_other_stock_out_item (同上镜像)
```

| 查询 | 索引使用 | 评估 |
|------|---------|:--:|
| 列表分页（`order by create_time desc`） | **无 `create_time` 索引** | 🔴 P1 |
| 按 code 查重 | `uk_other_stock_in_code_del` | ✅ |
| 按 id FOR UPDATE | `PRIMARY KEY` | ✅ |
| 子表按 in_id 查 | `idx_item_in_id` | ✅ |

**🔴 P1：`order by create_time desc` 无索引 → 10000 条数据时全表扫描排序。**

当前数据量（预计 < 1000 条/月）可接受，但未来积累后性能会退化。

修复：
```sql
ALTER TABLE c_mes_other_stock_in ADD INDEX idx_create_time (create_time);
ALTER TABLE c_mes_other_stock_out ADD INDEX idx_create_time (create_time);
```

## 事务持有时间

### audit() 事务

```java
@Transactional
public void audit(String id) {
    queryWithItems(id);                    // ~10ms (2 SQL)
    if (!"1".equals(e.getStatus())) throw; // 内存操作
    int rows = baseMapper.auditWithGuard(); // ~5ms (1 UPDATE)
    if (rows == 0) throw;
    for (item : items) {
        inventoryService.stockIn(...);      // ~20ms/item (FOR UPDATE + upsert + ledger)
    }
}
```

- 事务持有时间：10ms + 5ms + N×20ms（N=明细行数）
- N=10 → ~215ms，可接受 ✅
- N=1000 → ~20s，不可接受 🔴

**评估：** 单次入库单的明细行数通常 ≤ 20，事务持有时间在 500ms 以内，问题不大。审核操作频率低（每小时个位数），不是瓶颈。

## 并发吞吐量预估

- 核心瓶颈：`FOR UPDATE` 行锁在库存表的争用
- 单个事务 ∼200ms
- 理论 TPS（单物料单仓库）：5 QPS
- 实际吞吐（多物料多仓库并发表）：取决于库存表的分区策略

对其它出入库来说，业务场景是盘盈/盘亏/报废/领用——低频操作（日个位数），TPS 完全足够。

## 前端性能

- 列表用 `BasicTable` + `useListPage`（自带虚拟滚动 + 分页）✅
- Drawer 中明细用原生 `<a-table>` 无虚拟化 ⚠️ → 100 行明细时拖慢渲染 🟡 P2

## 结论

核心查询路径性能合理。1 个 P1（`create_time` 索引缺失）、1 个 P2（子表组件 N+1 查询 + 无虚拟滚动）。

**风险汇总：0 P0 / 1 P1 / 2 P2**
