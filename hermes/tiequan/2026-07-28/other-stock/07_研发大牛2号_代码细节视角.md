## 精度分析 🔴 P0

### `totalAmount` 和 `amount` 定义不一致

```sql
-- V9.8.1: total_amount DECIMAL(18,2)
ALTER TABLE c_mes_other_stock_in ADD COLUMN total_amount DECIMAL(18,2) DEFAULT 0.00;
-- V9.8.1: amount DECIMAL(18,2)
ALTER TABLE c_mes_other_stock_in_item ADD COLUMN amount DECIMAL(18,2) DEFAULT 0.00;
-- V9.8.0: qty DECIMAL(18,4)
-- V9.8.1: unit_cost DECIMAL(18,4)
```

- `qty DECIMAL(18,4)` ✅
- `unit_cost DECIMAL(18,4)` ✅
- `amount DECIMAL(18,2)` → 只有 2 位小数，`qty × unit_cost` 的 4+4=8 位精度丢失 ⚠️
- `total_amount DECIMAL(18,2)` → 多行合计舍入误差累积 🔴

**严重性分析：**
- 单行：`qty=1000.0001 × unitCost=1.0001 = 1000.1002` → `setScale(2)` → `1000.10`（丢失 0.0002）
- 100 行 × 每行丢失 ∼0.005 → 累计丢失 ∼0.50
- 对账时 `SUM(amount) ≠ totalAmount`（极少但可能发生）

**建议：** `amount` 和 `total_amount` 改为 `DECIMAL(18,4)` 消除截断误差，或在应用层计算时延迟舍入到 `totalAmount` 赋值后。

### audit 反审核不一致

```java
// StockInServiceImpl.audit():
MesOtherStockIn e = queryWithItems(id);  // 不加锁
if (e == null) throw...
if (!"1".equals(e.getStatus())) throw...
int rows = baseMapper.auditWithGuard(id, username, now);  // CAS 原子更新

// StockInServiceImpl.unaudit():
MesOtherStockIn e = queryWithItems(id);  // 不加锁（同上）
if (e == null) throw...
int rows = baseMapper.unauditWithGuard(id, username, now);
```

**问题：** `audit()` 在 CAS 更新**前**先调 `queryWithItems()` 检查状态，存在 **TOCTOU（Time-of-check-to-time-of-use）** 间隙：

1. `queryWithItems` 返回 status='1'（通过检查）
2. 另一个线程 CAS 更新为 '2'（审核成功）
3. 当前线程 CAS 更新失败 → 抛"审核失败"

此场景下异常消息"审核失败：入库单不存在或状态已变更"正确，但浪费了一次 `queryWithItems` 的 SQL 查询（查了明细但没用上）。 **非功能 bug，是冗余查询**。

### 🔴 严重问题：audit() 无 `FOR UPDATE`，read-write 间存在并发窗口

```java
// audit():
MesOtherStockIn e = queryWithItems(id);  // ← 普通 SELECT，无锁
// ... validate status ...
int rows = baseMapper.auditWithGuard(id, username, now);  // ← CAS
```

在 `queryWithItems` 和 `auditWithGuard` 之间，另一个事务可能已经 `auditWithGuard` 成功 → 当前事务 CAS 返回 0 → 抛"审核失败"。这个错误消息对用户友好，但**明细的 qty/unitCost/amount 使用的是旧快照**：

- 如果 CAS 在两次 `queryWithItems` 之后都失败 → 最终状态正确（回滚）
- 但如果在这期间明细被修改（`updateWithItems` 删+重建）→ `e.getItems()` 可能已经是旧数据 → `stockIn` 使用旧 qty

**实际风险评估：** CAS `auditWithGuard` 返回 0 后抛异常，整个方法 `@Transactional` 回滚，`stockIn` 不会执行。**数据不会出错，但存在一次冗余读取。** 降级为 P2（性能浪费），非数据风险。
