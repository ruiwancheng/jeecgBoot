## 金额计算链

### 明细行金额计算 🔴 P0（精度丢失）

```java
// validate() 方法 L172-173
BigDecimal cost = item.getUnitCost() != null ? item.getUnitCost() : BigDecimal.ZERO;
item.setAmount(item.getQty().multiply(cost).setScale(2, java.math.RoundingMode.HALF_UP));
```

**问题：`qty` 和 `unitCost` 相乘的中间结果被截断为 2 位小数，舍入误差无法审计。**

- `unitCost DECIMAL(18,4)` × `qty DECIMAL(18,4)` → 中间精度最高 8 位小数
- `.setScale(2)` 截断为 2 位小数 → 丢失 3-6 位精度
- 多行合计 `totalAmount` 时舍入误差累积
- 财务审计时逐行验证 `qty×unitCost≠amount` → 对账失败

**修复建议：**
```java
// 先做乘法（保留中间精度），再做舍入
BigDecimal product = qty.multiply(unitCost);
// 可选：保留全精度或统一舍入到 2 位
item.setAmount(product.setScale(2, RoundingMode.HALF_UP));
```
当前代码已做乘法再舍入，但 `unitCost` 为 null 时设为 `BigDecimal.ZERO` 是正确的。**实际风险窗口在 `setScale(2)` 截断 + 多行合计的累进误差。**

### 总金额合计 ✅

```java
totalAmount = totalAmount.add(item.getAmount());

```

- 在 validate() 中逐行累加，然后在 persist 前设到 entity ✅

### 🔴 但库存主表的 `upsertWithDelta` 只看数量，不看金额！

```java
// L37: stockIn
inventoryMapper.upsertWithDelta(id, materialId, warehouseId, before, qty, username, username);
// ^ 只有 qty，没有 unitCost/amount！

// L51: stockOut
```

**后果：**

- 任何依赖库存表金额字段的查询（如"库存金额总计"）结果为 0

**等级：🔴 P0** — 业财数据永久不一致，台账有金额但库存主表金额为 0。

## 成本单价来源 🔴 P1（移仓算价风险）

```java
// OtherInDrawer.vue L67: 批量添加物料
items.value.push({ materialId: m.id, qty: 1, unitCost: m.movingAvgCost ?? 0 });
```

**问题：** 批量添加物料时，`unitCost` 默认为物料的 `movingAvgCost`（移动加权平均成本），而非 null。用户可能：
1. 看到自动填入了成本单价 → 以为是系统计算的准确值 → 不手工修改
2. 但 `movingAvgCost` 是移动平均成本，不等于该批次的真实采购成本
3. 导致库存金额快照与实际不符

**与 `unitCost: 0` 默认值的叠合问题：** 前端默认 `unitCost: 0` → 如果用户不填 → 后端 `setScale(2)` 后 amount = 0 → 入库后库存金额未增长 → 与实物价值不符

**等级：🔴 P1** — 可能导致成本核算失真（出入库无应收应付，但会影响库存成本报表的移动加权平均基数）。

## 结论

发现 2 个 P0（库存主表金额未更新、台账 beginningAmount/endingAmount 固定为 0）和 1 个 P1（批量添加物料的 unitCost 默认为 movingAvgCost）。业财一致性是最大风险。

**风险汇总：2 P0 / 1 P1 / 0 P2**
