> 审计视角：极值、空值、非法参数、并发异常

## 非法参数攻击面

### API 参数注入

| 攻击向量 | 防御 | 状态 |
|---------|------|:--:|
| `PUT /edit` → body 含 `status='2'` 试图直接改状态 | `entity.setStatus(null)` 置空 + Service 校验 `if(!"1".equals(exist.getStatus()))` | ✅ |
| `PUT /edit` → body 含 `createBy='hacker'` 伪造创建人 | `entity.setCreateBy(null)` 置空 | ✅ |
| `PUT /edit` → body 含 `delFlag=1` 标记删除 | `entity.setDelFlag(null)` 置空 | ✅ |
| `PUT /audit?id=xxx` → 无权限 | `@RequiresPermissions("mes:otherStockIn:edit")` | ✅ |
| `POST /add` → body 含 `id='malicious'` 指定 ID | `IdType.ASSIGN_ID` 自动生成，body 中的 id 被忽略 | ✅ |
| `DELETE /delete?id=' OR '1'='1` → SQL 注入 | MyBatis `#{}` 参数化 | ✅ |
| `PUT /audit?id=not-exist` → 不存在的单据 | `queryWithItems` 返回 null → 抛"入库单不存在" | ✅ |
| `PUT /unaudit?id=xxx` → 审核中状态 | `WHERE status='2'` 守卫 → rows=0 → 抛异常 | ✅ |

### 并发异常测试（补充研发牛马3号）

| 场景 | 模拟方法 | 预期结果 | 状态 |
|------|---------|---------|:--:|
| 两线程同时审核 | 并行 `audit(id)` | 一个成功，一个抛"状态已变更" | ✅ |
| 审核+编辑并发 | `audit(id)` || `updateWithItems(id,{code:'X'})` | 编辑被 FOR UPDATE 锁等待，CAS 守卫判定 | ✅ |

## 未知/非法字段传递

### Controller 请求体直接绑定 Entity

```java
@PostMapping("/add")
public Result<String> add(@RequestBody MesOtherStockIn entity) { ... }
```

**攻击向量：** 前端传给后端的 JSON 可能包含未知字段（如 `items[].hackField`），Spring Boot 默认忽略未知字段 — 不抛异常。但如果 Entity 恰好有 `hackField` 字段，则会被赋值。

**实际风险：** `MesOtherStockInItem` 字段少而精，攻击面小。但如果是未来扩展加字段后，老的 API 调用会出问题。

等级：🟡 P2（低概率）

## 数据一致性边界

### validate 做合计但在 save/update 事务内

```java
// saveWithItems: validate(entity) 后 baseMapper.resurrect 或 super.save
// resurrect 和 save 之间：
//   validate 中 entity.setTotalAmount(totalAmount) — 在 saveItems 前
//   save 后 entity 的 totalAmount 已持久化 ✅
```

合计计算时机正确（在持久化之前）✅

### 但是：`unaudit` 中的 data race 🔴 P1

```java
// unaudit():
MesOtherStockIn e = queryWithItems(id);  // 读取明细 + 状态
// ... 检查单据存在 ...
int rows = baseMapper.unauditWithGuard(id, username, now);  // CAS
if (rows == 0) throw ...
// 使用 e.getItems() 做库存回冲
for (MesOtherStockInItem item : e.getItems()) {
    inventoryService.stockOut(item.getMaterialId(), ...);
}
```

**时序分析：**
1. `unaudit` 线程: `queryWithItems` → 读到明细（qty=10, unitCost=5.00）
2. 期间另一个线程 `updateWithItems` 成功修改了明细（qty=8, unitCost=6.00）
3. `unaudit` 线程: `unauditWithGuard` CAS 成功（status 仍为 '2'）
4. `unaudit` 线程: `stockOut(qty=10, unitCost=5.00)` — 使用旧明细！

**但：** `updateWithItems` 的守卫是 `if (!"1".equals(exist.getStatus()))` — 已审核单据无法编辑。所以步骤 2 的 `updateWithItems` 会失败 ← "仅草稿状态可操作"。**这个时序不可能发生。**

✅ 当前设计中，`audit`/`unaudit` 的明细读取是安全的——因为审核状态下的单据不能被编辑。（研发2号报告也确认了此点。）

但 **audit 场景**不同：

```java
// audit():
MesOtherStockIn e = queryWithItems(id);  // status='1' 草稿
// ... 检查 status='1' ...
int rows = baseMapper.auditWithGuard(id, ...);  // CAS '1'→'2'

// 此时另一个线程的 updateWithItems 可能已经在 audit 之前改了明细：
// updateWithItems: FOR UPDATE 锁 → 修改成功（草稿可编辑）
// audit: queryWithItems 之后 → CAS 发现状态还是 '1' → 成功
//       但使用的 e.getItems() 是 queryWithItems 时的旧快照（可能被 update 覆盖过）
```

**实际时序：**
```
T1: 线程 A — updateWithItems (FOR UPDATE → 改明细 → COMMIT)
T2: 线程 B — queryWithItems (走到 T1 前 → 拿到旧明细) → auditWithGuard (T1 COMMIT 后, CAS: '1'→'2' 成功) → stockIn(旧明细)
```

**后果：** 审核时的库存增加量 ≠ 最终保存的明细量。数据不一致。

**等级：🔴 P0** — audit 的 `queryWithItems` 和 `auditWithGuard` 之间可以被另一个事务的 `updateWithItems` 插入修改，导致审核生效的明细 ≠ 数据库中的最终明细。

**修复建议：** `audit` 方法中的 `queryWithItems` 应改为 `baseMapper.selectByIdForUpdate(id)` 加 FOR UPDATE 锁，然后再查明细。

同理，`unaudit` 也有同等问题（尽管已审核状态下 `updateWithItems` 被阻止，但如果存在超级管理员直接改数据库 → 极低风险，可不修）。

## 第三方依赖异常

| 依赖 | 失败模式 | stock 模块行为 |
|------|---------|---------------|
| `IMesInventoryService.stockIn(...)` | 抛 RuntimeException | 事务回滚，CAS 状态恢复 ✅ |
| `IMesInventoryService.stockOut(...)` | 抛"库存不足" | 事务回滚，CAS 状态恢复 ✅ |
| `getNextCode(MES_BIZ_CODE)` | HTTP 500 | catch(e) → 静默回退手工输入 ✅ |
| `queryWarehouseSelect` | HTTP 500 | 前端下拉为空，用户无法提交 ✅ |
| `queryMaterialById` (SubTable) | HTTP 500 | catch → items 为空，显示"暂无明细" ✅ |

## 结论

攻击面防御齐全（敏感字段置空、CAS 守卫、参数化 SQL）。发现 1 个 P0（audit 的 TOCTOU 导致审核生效明细≠DB 明细）、1 个 P1（unaudit 同等 TOCTOU，虽被 updateWithItems 守卫挡住但有理论风险）。

**风险汇总：1 P0 / 1 P1 / 1 P2**
