> 审计对象：MES 其它出入库模块
> 审计视角：超卖、重复提交、分布式锁、隔离级别、幂等

## 并发场景分析

### 场景 1：并发审核同一单据 ✅

```
线程A & 线程B 同时调用 audit(id)

线程A: auditWithGuard → WHERE id=x AND status='1' → 更新成功(rows=1)
线程B: auditWithGuard → WHERE id=x AND status='1' → 更新失败(rows=0) → 抛异常
```

CAS 原子守卫正确防止双重审核 ✅

### 场景 2：审核+反审核并发 ✅

```
线程A: audit(id) → auditWithGuard(status='1'→'2') 成功
线程B: unaudit(id) → unauditWithGuard(status='2'→'1') 成功
```

两个 CAS 互斥，只有一个会成功 ✅

### 场景 3：编辑+审核并发 ✅

```
线程A: updateWithItems    → FOR UPDATE 锁住行 → 修改明细
线程B: audit              → auditWithGuard → WHERE status='1' → 失败(已被A锁住)
```

`FOR UPDATE` 行锁 + `WHERE status='1'` 守卫双重保护 ✅

### 场景 4：并发新增同一单号 ✅

```
线程A: saveWithItems → selectCount(code) → 0 → insert → 成功
线程B: saveWithItems → selectCount(code) → 0 → insert → DuplicateKeyException → 抛异常
```

数据库唯一索引 `uk_other_stock_in_code_del` 兜底 ✅

### 场景 5：并发入库/出库导致库存不足 🔴 P0

```
初始库存: material M = 10

线程A: stockOut(qty=8) → FOR UPDATE 锁 M → before=10 ≥ 8 → 扣减成功 → after=2
线程B: stockOut(qty=5) → FOR UPDATE 等待 A 释放锁 → before=2 < 5 → 抛"库存不足"
```

`FOR UPDATE` 在 `MesInventoryServiceImpl.stockOut` 中正确使用 ✅

但是：这是 `IMesInventoryService` 的并发保护，**stock 模块只作为调用方**。stock 模块依赖 inventory 模块的 `FOR UPDATE` 来做并发保护——这是正确的分层设计。

### 场景 6：审核后库存被其他单据消耗 → 反审核时库存不足 🔴 P1

```
库存初始: material M = 0

1. 其它入库 #01: 审核 → stockIn(qty=10) → 库存 M = 10
2. 销售出库 #02: 审核 → stockOut(qty=8)  → 库存 M = 2
3. 其它入库 #01: 反审核 → stockOut(qty=10) → 库存不足! (2 < 10)
```

**此时反审核失败 → 单据锁死在"已审核"状态 → 无法回退！**

这是一个真实的业务流程死锁：
- 入库单已审核 → 库存增加了 10
- 库存 10 后来被销售出库消耗了 8 → 只剩下 2
- 现在要反审核入库单 → 需要回冲 10 个单位的库存 → 但库存只有 2 → `stockOut` 抛异常
- 反审核失败 → 入库单永远"已审核"状态

**等级：🔴 P1** — 业务流程死锁，单据无法回退。需要业务决策：
- 方案 A：反审核时忽略库存不足（允许库存变负，记录差异到 pending 表）
- 方案 B：反审核前先检查库存 → 库存不足时不抛异常而是标记为"待处理"
- 方案 C：禁止在库存不足时反审核（当前行为，但需要提示用户先补库存）

### 场景 7：批量操作的并发一致性

```js
// index.vue: batchAudit()
for (const r of selectedRows) { await auditOtherIn({ id: r.id }); }
```

**问题 1：非事务性。** 选了 5 条单据审核 → 前 3 条成功、第 4 条失败 → 前 3 条已审核无法回滚 → 用户不知道哪些成功了。

**问题 2：无并发加速。** 逐条串行 → N 条 = N×单个耗时。应该并发：`Promise.all(selectedRows.map(r => auditXxx({id: r.id})))`。

等级：🟡 P2（非资损，但用户体验差）

## 幂等性

### audit 幂等 ✅

```sql
UPDATE ... WHERE id=#{id} AND status='1'
```

- 第二次调用（status 已 ='2'）：返回 0 → 抛异常 ✅
- 不会重复增加库存 ✅

### unaudit 幂等 ✅

```sql
UPDATE ... WHERE id=#{id} AND status='2'
```

- 第二次调用（status 已 ='1'）：返回 0 → 抛异常 ✅

### saveWithItems（借尸还魂）幂等 ⚠️

```java
// saveWithItems: L53
MesOtherStockIn old = baseMapper.selectDeletedByCode(entity.getCode());
if (old != null) {
    // 复用旧 ID + 创建人/时间 → resurrect
    itemMapper.delete(delQw);  // 删旧明细
    entity.setId(old.getId());
    baseMapper.resurrect(entity);
} else {
    super.save(entity);  // DuplicateKeyException 兜底
}
```

**问题：`selectDeletedByCode` 和 `resurrect` 之间无锁。** 两个线程同时 save 同一单号：

1. 线程 A: `selectDeletedByCode(code)` → 找到软删除记录（id=旧ID）
2. 线程 B: `selectDeletedByCode(code)` → 找到同一软删除记录（id=旧ID）
3. 线程 A: 删旧明细 → `resurrect` 旧记录 → 成功
4. 线程 B: 删旧明细（已空）→ `resurrect` 旧记录 → 成功（无唯一冲突！因为线程 A 已经把记录复活了，del_flag=0）
5. 结果：两条**不同的明细集**关联到**同一个主表 ID** ❌

**但**：线程 B 的 `QueryWrapper.eq("code", entity.getCode())` 在 `saveWithItems` 开头会检测到：线程 A 复活后，线程 B 的 `selectCount(activeQw)` 会发现 code 已被占用 → 抛"入库单号已存在"。✅

**结论：** `selectCount` 前检查 + `DuplicateKeyException` 兜底 + 复活的唯一索引三保险——并发安全 ✅（但有时间窗口浪费）。

## 隔离级别

MySQL 默认 `REPEATABLE READ`：
- CAS 更新（WHERE + atomic UPDATE）在 RR 下正确 ✅
- FOR UPDATE 在当前快照下加行锁 ✅

## 分布式锁

未使用。单服务端部署场景不需要。

## 结论

CAS 原子守卫 + FOR UPDATE 行锁设计到位，核心并发路径安全。1 个 P1（反审核库存不足死锁）、1 个 P2（批量操作非事务性 / 无并发）。

**风险汇总：0 P0 / 1 P1 / 1 P2**
