## 一、总体评价

销售模块整体代码结构规范，CRUD 功能完整，主子表联动和参数校验到位，`update-begin/update-end` 标记完整。但存在 **8个P0级真实Bug**（含1个功能性Bug导致价格模块新增/编辑完全不可用），以及若干并发安全和性能隐患。业务流程方面，状态流转API和上下游联动属于Phase 2规划范围，不视为Bug。

## 二、共识P0级风险（按共识人数排序）

### 🔴 P0-1 | 价格API前端传参方式错误 — 新增/编辑功能完全不可用
**共识人数：4/10** | 分类：**真实Bug**

| 位置 | `jeecgboot-vue3/src/views/project/mes/sales/price/price.api.ts:19-20` |
|------|------|
| 发现者 | 研发大牛2号、测试牛马1号、测试牛马2号、产品大佬1号 |

**问题：** `addPrice` 和 `editPrice` 使用 `params`（URL查询参数）发送数据，而后端 `@RequestBody MesPrice` 期望JSON请求体。数据进入URL query string而非request body，后端收到的全部字段为null。

```typescript
// 错误 — 价格管理模块
export const addPrice = (params: Recordable) => defHttp.post({ url: Api.add, params });
export const editPrice = (params: Recordable) => defHttp.put({ url: Api.edit, params });

// 正确 — 参照其他三个模块(order/delivery/outbound)
export const addPrice = (data: Recordable) => defHttp.post({ url: Api.add, data });
export const editPrice = (data: Recordable) => defHttp.put({ url: Api.edit, data });
```

**修复：** 将 `params` 改为 `data`。

### 🔴 P0-2 | MesPrice status字段类型DDL与Entity不一致
**共识人数：7/10** | 分类：**真实Bug**

| 位置 | `MesPrice.java:61` vs `V2.0.0__mes_price_init.sql:18` |
|------|------|
| 发现者 | 产品大佬2号、产品大佬3号、研发大牛1号、研发大牛2号、测试牛马2号、测试牛马3号、测试牛马4号 |

**问题：** SQL DDL `status VARCHAR(20) DEFAULT '1'`，Java实体 `private Integer status;`。`checkPriceOverlap()` 中 `qw.eq("status", "1")` 用String查询。同模块其他实体（订单/发货/出库）的status全是`String`类型，只有价格模块不一致。

**修复：** 统一为 `String` 类型（与订单、发货单、出库单保持一致），同时修改Entity声明和相关QueryWrapper。

### 🔴 P0-3 | 发货单超量校验并发竞态（TOCTOU）
**共识人数：4/10** | 分类：**真实Bug**

| 位置 | `MesDeliveryNoteServiceImpl.checkDeliveryQty():130-162` |
|------|------|
| 发现者 | 产品大佬2号、产品大佬3号、研发大牛3号、测试牛马3号 |

**问题：** `checkDeliveryQty` 先查已有发货总量（SELECT），判断通过后再INSERT。两个并发请求读取相同的已发货数据，都判定未超量，同时写入。无数据库行锁、版本号或唯一约束保护。

```
Thread A: SELECT SUM(delivery_qty) → 80，80+15=95 ≤ 100 → PASS → INSERT 15
Thread B: SELECT SUM(delivery_qty) → 80，80+15=95 ≤ 100 → PASS → INSERT 15
最终累计发货 = 110 > 100（订单数量）→ 超发
```

**修复：** 方案A：`SELECT ... FOR UPDATE` 锁定订单行；方案B：Redis分布式锁（key: `salesOrderId + materialId`）。

---

### 🔴 P0-4 | 批量删除逐条循环 + this自调用违反规范
**共识人数：4/10** | 分类：**真实Bug**

| 位置 | `MesSalesOrderServiceImpl.removeByIds` / `MesDeliveryNoteServiceImpl.removeByIds` / `MesSalesOutboundServiceImpl.removeByIds` |
|------|------|
| 发现者 | 研发大牛2号、研发大牛3号、测试牛马3号、测试牛马4号 |

**问题：** `removeByIds` 循环调用 `this.removeWithItems()`，违反 `code-style.md` "禁止Service内部this.xxx()自调用"规范。N个ID产生3N条SQL在一个长事务中。

**修复：** 改用 `super.removeByIds(list)`，明细行用 `QueryWrapper.in("parent_id", ids)` 批量删除。

---

### 🔴 P0-5 | N+1查询 — 发货单校验嵌套查库
**共识人数：3/10** | 分类：**真实Bug**

| 位置 | `MesDeliveryNoteServiceImpl.checkDeliveryQty()` |
|------|------|
| 发现者 | 研发大牛1号、研发大牛2号、测试牛马3号 |

**问题：** 每个明细行校验时：(a)查sales_order_item（1次），(b)查同一订单所有发货单（1次），(c)对每张已有发货单查其明细行（N次）。5个明细行×10张已有发货单 = 约56次查询。

**修复：** 改为一条聚合SQL：
```sql
SELECT dni.material_id, SUM(dni.delivery_qty) as total_shipped
FROM c_mes_delivery_note_item dni
JOIN c_mes_delivery_note dn ON dni.delivery_id = dn.id
WHERE dn.sales_order_id = ? AND dn.del_flag = 0 AND dn.id != ?
GROUP BY dni.material_id
```

### 🔴 P0-6 | @Transactional缺少rollbackFor
**共识人数：3/10** | 分类：**真实Bug**

| 位置 | `MesPriceServiceImpl.save()`, `updateById()`, `removeById()`, `removeByIds()` |
|------|------|
| 发现者 | 研发大牛1号、研发大牛2号、测试牛马4号 |

**问题：** 四个方法的 `@Transactional` 未指定 `rollbackFor = Exception.class`。Spring默认只对RuntimeException回滚，与其他3个Service的实现不一致。

**修复：** 添加 `rollbackFor = Exception.class`。

### 🔴 P0-8 | 出库审核audit/cancel并发竞态
**共识人数：2/10** | 分类：**真实Bug**

| 位置 | `MesSalesOutboundServiceImpl.audit():69`, `cancel():72` |
|------|------|
| 发现者 | 研发大牛3号、测试牛马2号 |

**问题：** audit和cancel都是 select-then-update 模式，无锁保护。audit() 和 cancel() 并发执行时可能绕过状态约束。

```
audit() 读到 status="1" → 设为"3"
cancel() 读到 status="1" → 设为"0"
结果：已审核的出库单被取消（违反"已审核不可取消"规则）
```

**修复：** 使用带WHERE条件守卫的原子UPDATE：
```sql
UPDATE c_mes_sales_outbound SET status='3' WHERE id=? AND status='1'
```
检查affected rows，为0则状态已被其他请求修改。
