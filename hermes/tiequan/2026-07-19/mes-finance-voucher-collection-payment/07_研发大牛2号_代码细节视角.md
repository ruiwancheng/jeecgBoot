## 一、总体结论

| 维度 | 评级 | 摘要 |
|---|---|---|
| update-begin/end 标记 | ✅ 良好 | 32/32 后端 java 文件完整包裹；ServiceImpl 内嵌 P0-08 段也独立包裹 |
| 事务边界 | ⚠️ 基本正确但有盲区 | 凭证主子表、收款核销应收在同一事务内（OK）；但**凭证 deleteBatch 绕过 `removeWithItems`**，**收/付款单无 delete/edit 接口**，事务模型不完整 |
| BigDecimal 精度 | ⚠️ 后端规范 / 前端失守 | 后端全程 `compareTo/add/subtract`，无 `new BigDecimal(double)`、无 equals 比较；**前端用 `Number()` + `toFixed(2)` 字符串比较做借贷平衡，存在浮点误差风险** |
| 借贷平衡校验 | ⚠️ 双保险但前端可绕过 | 后端 save/update/audit 三处均 `compareTo` 校验（严谨）；前端 `drTotal !== crTotal` 是**字符串比较**（"0.10"+"0.20"=0.30000000000000004 → toFixed 后碰巧相等，但 0.1+0.2 类经典陷阱仍可能在合计 >2 位小数时漏判） |
| 空指针防护 | ⚠️ 大部分到位，存在具体漏洞 | `validate()` 中第 i 行 item 未判 null；`ar.getAmount()` 未判 null 直接 `subtract`；`queryWithItems` 主表 null 时下游 audit 有判空（OK） |
| SQL 注入 | ✅ 安全 | 手写 SQL 全部 `#{}` 预编译占位符；QueryWrapper 列名硬编码；无 `${}` 拼接 |
| N+1 | ✅ 无 | 明细一次性 selectList，科目树一次性 list() 后内存分组 |
| 数据字典 | ✅ 规范 | 实体 `@Dict` + 前端 dictCode/dictTable 一致（mes_voucher_status / mes_receivable_status / mes_payment_method 等） |
| Result 响应 | ⚠️ 统一但语义有瑕疵 | `Result.ok/error` 使用一致；但 `deleteBatch` 空参返回 `Result.ok("无需删除")` 语义含糊 |
| VO/实体映射 | ⚠️ 无 VO 层 | Controller 直接 `@RequestBody 实体` 接收 + 返回实体；`items`/`children` 用 `transient` 字段承载——简单场景可用，但**无 @Validated 参数校验、可批量赋值任意字段（含 createBy/delFlag/status）** |
| 字段校验 | ❌ 严重缺失 | 全模块 **0 处** `@NotNull/@NotBlank/@DecimalMin/@Pattern/@Validated/@Valid`；所有校验靠 Service 手写 if-throw |
| 异常处理 | ⚠️ 风格统一但有隐患 | 统一抛 `JeecgBootException`；但 `getUsername()` catch 所有异常吞掉返回 "system" |

## 二、逐模块问题清单（按严重度排序）

### 【P0-严重】

#### 1. 凭证 `deleteBatch` 绕过主子表事务，产生孤儿明细
- **位置**：`MesVoucherController.java:43` + `MesVoucherServiceImpl.java:59`
- **现象**：单条删除走 `removeWithItems`（先删 item 再删主表，@Transactional），**批量删除直接调 `service.removeByIds(idList)`**（MyBatis-Plus 默认实现，只删主表、不删 `c_mes_voucher_item`、也不做"非草稿禁止删除"状态校验）。
- **后果**：
  1. `c_mes_voucher_item` 残留孤儿数据（该表无 del_flag，是物理 delete vs 主表逻辑删——主表 del_flag=1、明细还在）；
  2. 已审核（status=2）凭证可被 deleteBatch 直接"删除"，绕过状态守卫。
- **建议**：Controller deleteBatch 改为循环调 `removeWithItems` 或在 Service 增加 `removeBatchWithItems(Collection<String>)` 并加 @Transactional。

#### 2. 收/付款单只有 add，无 edit/delete/作废，且收款核销无并发保护
- **位置**：`MesCollectionController.java`（仅 list/queryById/add/queryAll/exportXls）、`MesPaymentController.java` 同构
- **现象**：
  1. 收款单/付款单**没有作废接口**——若收款录错，应收单 `received_amount/unsettled_amount/status` 已被改写且**无任何反向冲正路径**，数据永久错乱；
  2. `MesCollectionServiceImpl.save` 中"读应收 → 比较 → 累加 → updateById"是**读改写（read-modify-write）竞态**：两个并发收款请求都读到 unsettled=100，各收 80，均通过校验，最终 received=160 > amount=100。无乐观锁（@Version）、无悲观锁（select for update）、无 DB 层 CHECK 约束兜底；
  3. 应收状态机 `newReceived>0 && newReceived<amount ? "2" : "3"`：当 `newReceived > amount`（并发超收场景）也会落入 "3"（已结清），掩盖超收。
- **建议**：
  - 增加作废/红冲接口，在同一事务中回滚应收金额；
  - 应收更新改用 `UPDATE c_mes_receivable SET received_amount = received_amount + #{amt} WHERE id=#{id} AND received_amount + #{amt} <= amount` 的原子 SQL 并检查影响行数（与 voucher 的 `auditWithGuard` 同款守卫模式）；
  - 状态判断改为 `newReceived.compareTo(ar.getAmount()) >= 0 ? "3" : (newReceived.signum()>0 ? "2" : "1")`。

#### 3. 全模块零 Bean Validation，Controller 直接裸收实体
- **位置**：所有 Controller 的 `@RequestBody XxxEntity entity`
- **现象**：无 `@Validated`、实体字段无 `@NotNull/@DecimalMin("0.01")/@Size`；校验全部下沉到 Service 手写。`MesReceivableController`/`MesPayableController` 连 add/edit 都没有（只能从来源单据生成），但 voucher/collection/payment/subject 的 add/edit 均裸收。
- **后果**：前端可构造 JSON 直接写入 `createBy`、`delFlag`、`totalDebit/totalCredit`（凭证合计字段本应由后端 calcTotal 覆盖——目前确实被覆盖了，OK）、`status`（收/付款单 status 被强制 set "1"，OK；但**凭证的 `sourceBillId`、`remark` 等未做长度限制**，DB 500 字截断或报错）。更严重的是**凭证编辑时 entity 可携带任意 id 字段**（虽有 id 判空，但无越权校验他人数据的逻辑——依赖 Shiro 权限码，无数据级权限）。
- **建议**：引入 `@Validated` + 实体注解，或至少建立 XxxVO 隔离可写字段。

### 【P1-高】

#### 4. 前端借贷平衡用浮点 + 字符串比较，可被绕过
- **位置**：`VoucherDrawer.vue:51-52, 73`
```js
const drTotal = computed(() => items.reduce((s, r) => s + (Number(r.debitAmount) || 0), 0).toFixed(2));
const crTotal = computed(() => items.reduce((s, r) => s + (Number(r.creditAmount) || 0), 0).toFixed(2));
if (drTotal.value !== crTotal.value) { message.error('借贷不平衡'); return; }
```
- **问题**：
  1. `Number()` 累加是 IEEE754 浮点，多行 0.1/0.07 类金额累加后再 toFixed(2) **可能**产生与分位四舍五入不一致的结果（边界场景：多行各 0.005 类型金额）；
  2. 提交时 `debitAmount: Number(r.debitAmount) || 0` 把金额以 number 序列化为 JSON——`0.1+0.2=0.30000000000000004` 会原样发给后端 BigDecimal 反序列化（Jackson 对 number → BigDecimal 是精确的十进制文本转换，风险较低但依赖 Jackson 配置）；
  3. 前端只拦不平衡，不拦"明细为空"、"同行为 0/0"——全靠后端兜底（后端拦了，OK，但用户体验差）。
- **建议**：前端以"分"为单位整数累加再比较，或引入 decimal.js / big.js；金额输入用 `:precision="2"` 的 a-input-number。

#### 5. `MesCollectionServiceImpl` / `MesPaymentServiceImpl` 对 `ar.getAmount()` 未判空
- **位置**：`MesCollectionServiceImpl.java:38-39`、`MesPaymentServiceImpl.java:37-38`
```java
ar.setUnsettledAmount(ar.getAmount().subtract(newReceived));
ar.setStatus(... newReceived.compareTo(ar.getAmount()) < 0 ...);
```
- **现象**：`c_mes_receivable.amount` DDL 为 `NOT NULL`，理论不空；但若历史脏数据/其他写入路径把 amount 写 null，直接 NPE（500 而非业务异常）。同理 `ar.getUnsettledAmount()` 为 null 时回退用 amount 是 OK 的，但 amount 本身没兜。
- **建议**：入口处 `if (ar.getAmount() == null) throw new JeecgBootException("应收单金额异常")`。

#### 6. `auditWithGuard` 手写 UPDATE 未带 del_flag 条件
- **位置**：`MesVoucherMapper.java:9`
```sql
UPDATE c_mes_voucher SET status='2', update_by=#{updateBy}, update_time=#{updateTime}
WHERE id=#{id} AND status='1'
```
- **现象**：逻辑删除（del_flag=1）的凭证仍满足 `status='1'`，该 SQL 会把**已删除凭证复活式地更新 update_by/update_time**（status 本来就是 '1'，值不变，但 update_time 被刷新）。主键 id 全局唯一、前端拿不到已删 id，实际可利用面小，但语义不严谨。
- **对比**：`resurrect` 系列手写 SQL（receivable/payable/subject Mapper）**正确**地处理了 del_flag（`SET ... del_flag=0 WHERE id=#{id} AND del_flag=1`）。
- **建议**：补 `AND del_flag = 0`。

#### 7. 凭证 `validate()` 中明细 item 未判 null
- **位置**：`MesVoucherServiceImpl.java:89-91`
```java
for (int i = 0; i < items.size(); i++) {
    MesVoucherItem item = items.get(i);
    if (!StringUtils.hasText(item.getSubjectId())) ...
```
- **现象**：前端传 `items: [null]` → `item.getSubjectId()` NPE，返回 500 而非业务提示。
- **建议**：`if (item == null) throw new JeecgBootException("第"+(i+1)+"行数据为空")`。

#### 8. 凭证号唯一性校验存在 TOCTOU 竞态
- **位置**：`MesVoucherServiceImpl.java:39-40, 51-52`
```java
QueryWrapper<MesVoucher> qw = new QueryWrapper<>(); qw.eq("voucher_no", ...);
if (baseMapper.selectCount(qw) > 0) throw ...;
super.save(entity);
```
- **现象**：先 count 后 insert，并发下同号凭证双双通过。DDL 有 `UNIQUE INDEX uk_voucher_no_del (voucher_no, del_flag)` 兜底——但代码**没有 catch DuplicateKeyException**（对比 `MesAccountSubjectServiceImpl:59` 有 catch 并翻译为业务异常），并发冲突时用户收到的是 500 + SQL 约束堆栈。
- **注意**：QueryWrapper 会自动追加 `del_flag=0`（@TableLogic 生效），所以查重语义正确。
- **建议**：捕获 DuplicateKeyException 转业务提示（同学科目实现）。

### 【P2-中】

#### 9. `getUsername()` 静默吞异常
- **位置**：`MesVoucherServiceImpl.java:112`、`MesAccountSubjectServiceImpl.java:100-102`
```java
try { LoginUser u = (LoginUser) SecurityUtils.getSubject().getPrincipal(); return u != null ? u.getUsername() : "system"; }
catch (Exception e) { return "system"; }
```
- **问题**：异常被吞且无日志，排障困难；定时任务/异步线程调用时审核人全部记为 "system"，审计追溯失真。建议 catch 后 `log.warn`。

#### 10. 凭证明细保存是逐条 insert
- **位置**：`MesVoucherServiceImpl.java:111`
```java
for (MesVoucherItem item : entity.getItems()) { item.setVoucherId(...); itemMapper.insert(item); }
```
- **现象**：N 行明细 N 次 JDBC roundtrip。凭证明细通常 <50 行，性能可接受，但建议改 `saveBatch` / `insertBatch`（ItemMapper 是 BaseMapper，可用 `Db.saveBatch` 或自定义 foreach insert）。注意这不是 N+1 查询问题（查询侧无 N+1），是写入放大。

#### 11. `deleteBatch` 空参返回 `Result.ok("无需删除")`
- **位置**：`MesVoucherController.java:43`、`MesAccountSubjectController.java:57-59`
- **现象**：传空 ids 返回 success=true，调用方无法区分"真的删了"还是"什么都没做"。语义建议改 `Result.error("ids不能为空")` 或保持 ok 但 message 明确。

#### 12. 前端所有 await 无 try/catch，依赖 defHttp 全局拦截
- **位置**：`VoucherDrawer.vue:77`、`voucher/index.vue:46-47`、`SubjectDrawer.vue:24`、`subject/index.vue:53`
- **现象**：所有 `await xxxApi(...)` 后紧跟 `message.success(...)`。JeecgBoot 的 defHttp 默认在响应 success=false 时 reject 并全局弹错——**依赖全局配置**。若某环境关闭了全局错误提示（`errorMessageMode='none'`），失败也会继续执行 `message.success('删除成功')`，产生假成功提示。建议关键操作（审核、删除）显式 try/catch 或检查返回值。

#### 13. 前端集合页按钮指向不存在的路由
- **位置**：`collection/index.vue:27`
```js
function handleAdd() { router.push('/project/mes/finance/collection/add'); }
```
- **现象**：全前端仓库 grep 不到 `collection/add` 路由/页面——**收款新增页面缺失**，按钮点击后 404 或白屏。付款 `payment/index.vue`、应收 `receivable/index.vue`、应付 `payable/index.vue` 三个 **index.vue 文件本身不存在（0 字节/找不到）**，只有 api/data 文件——前端页面不完整。
- **建议**：补收款/付款新增表单页（含金额 precision=2 校验、客户/供应商 JSearchSelect、应收/应付单联动查询未结金额），补 receivable/payable 列表页。

#### 14. `MesReceivableServiceImpl` / `MesPayableServiceImpl` 是空壳
- **位置**：两个 ServiceImpl 仅 `extends ServiceImpl` 无任何方法；但 Mapper 里有 `selectDeletedByCode` / `resurrect`（复活逻辑）——**没有任何 Service/Controller 调用它们**（grep 全模块仅 subject 用了自己的 resurrect）。应收/应付的"删后重建同 code 单据"场景会撞 `uk_rec_code_del` 唯一索引报 500。
- **建议**：要么补应收/应付的 save 复活逻辑（参照 subject），要么删除死代码 Mapper 方法。

#### 15. `MesAccountSubjectServiceImpl.removeById` 引用校验是空桩
- **位置**：`MesAccountSubjectServiceImpl.java:79-81`
```java
if (baseMapper.selectCount(qw) > 0) {} // 子科目已检查
// 注：凭证/应收/应付引用检查待 Phase2 后续补 ... 实现
```
- **现象**：已被凭证使用的科目可被直接软删（del_flag=1），历史凭证的 `@Dict(dictTable="c_mes_account_subject"...)` 翻译将显示空/原 ID。注释里已自认 TODO——**确认遗留**。
- **建议**：注入 MesVoucherItemMapper count subject_id 引用。

### 【P3-低 / 规范类】

16. **`MesCollection`/`MesPayment` 的 status 字典用 `yn`**（1收款/0作废），DDL 注释与字典语义匹配但不如专字典直观；`MesVoucher.sourceType` 用 `mes_voucher_source` 字典但 **DDL V9.0.0 未注册该字典**（只注册了 mes_subject_category / mes_balance_direction / mes_receivable_status / mes_payable_status / mes_voucher_status）——字典缺失会导致前端下拉空。**需补字典 SQL**。
17. **Controller 单文件多语句挤一行**（如 `queryById` 一行 150+ 字符），虽不影响功能，但降低 code review 效率，建议格式化。
18. **`queryAll` 用 `service.count()` + `service.list()` 两次查询**，且 `service.list()` 不带排序；5000 条阈值合理。
19. **`Page<>(pageNo, pageSize)` 未限制 pageSize 上限**，可传 pageSize=100000 全表扫描；JeecgBoot 全局通常有 PageInterceptor 限制，建议显式 `Math.min(pageSize, 500)`。
20. **应收/应付 Controller 无 add/edit/delete 接口**（设计如此——单据由销售出库/采购入库生成），但**没有提供来源单据的回溯查询接口**，前端 `receivable.data.ts` 列表只读。这是设计决策，记录备查。
21. **导出 exportXls 对 voucher/receivable 未做 QUERY_ALL_MAX 限制**（voucher 无限制，receivable/payable/subject 有）——不一致。

## 三、做得好的地方（值得沉淀为团队规范）

1. **借贷平衡三道防线**：save / update / audit 三处独立 `BigDecimal.compareTo` 校验，且审核用 DB 乐观守卫（`auditWithGuard` 条件更新 + 影响行数检查）——这是全模块最严谨的一段代码。
2. **BigDecimal 全程无反模式**：无 `new BigDecimal(double)`、无 `equals` 比金额、无 doubleValue 转换；累加用 `BigDecimal.ZERO` 起手。
3. **手写 SQL 全部 #{} 预编译**，`resurrect` 系列对逻辑删除 + 唯一索引（code, del_flag）的处理是教科书式写法。
4. **事务注解统一 `@Transactional(rollbackFor = Exception.class)`**，含 RuntimeException 之外的受检异常回滚。
5. **update-begin/end 标记 100% 覆盖**（32 个文件 grep 验证），含 author/date/for 三要素。
6. **数据字典前后端一致**：@Dict 与前端 dictCode/dictTable 一一对应（除 mes_voucher_source 漏注册）。
7. **科目树构建无 N+1**：一次 list() + 内存 groupingBy。
8. **queryAll/export 有 5000 条熔断**（部分接口）。
