## 0. 执行摘要

三模块整体**模块分层干净**（controller/service/mapper 切分到位，包结构 `org.jeecg.modules.mes.finance.{voucher,collection,payment}` 完全遵循 JeecgBoot 约定），且**凭证主子表设计符合标准**、`@Transactional` 边界清晰。

但存在 **3 个 P0 架构级阻断缺陷**，按优先级排序：

| # | 严重级别 | 问题 | 影响面 |
|---|---|---|---|
| 1 | **P0** | V9.1.0 / V9.1.1 SQL **不在 Flyway 扫描路径**（只放在 `project-mes/db/` 而未拷入 `project-mes/src/main/resources/flyway/sql/mysql/`） | 部署后 `c_mes_collection`、`c_mes_payment`、`mes_payment_method` 字典、`mes_voucher_source` 字典**不会被自动迁移**，线上启动即报"表不存在" |

另有 **2 个 P1、3 个 P2** 问题，详见正文。

## 1. 模块分层 / 接口契约 / 服务边界

### 1.1 分层结构（✅ 合规）

三模块均严格按 JeecgBoot 标准四层组织：

```
org.jeecg.modules.mes.finance.{voucher|collection|payment}
├── controller   MesXxxController  extends JeecgController<Entity, IService>
├── entity       MesXxx            @TableName("c_mes_xxx")
├── mapper       MesXxxMapper      extends BaseMapper<Entity>
├── service      IMesXxxService    extends IService<Entity>
└── service.impl MesXxxServiceImpl extends ServiceImpl<Mapper, Entity>
```

`MesVoucher` 额外有 `MesVoucherItem`（子表）+ `MesVoucherItemMapper`，属标准一对多。

### 1.2 接口契约（⚠️ 基本合规，但接口粒度失衡）

| 模块 | 自定义方法 | 评价 |
|---|---|---|
| voucher | `queryWithItems / saveWithItems / updateWithItems / removeWithItems / audit` | 主子表聚合契约清晰，`audit` 单独建模 |
| collection | 空接口 `IMesCollectionService extends IService<MesCollection> {}` | **过载** `ServiceImpl.save()`，把"应收联动"塞进 ORM 默认方法，**违反单一职责** |
| payment | 空接口（同 collection） | 同上 |

**P1-1：空接口 + 重载 `save()` 的反模式**

`MesCollectionServiceImpl.save(MesCollection)` 重写 MyBatis-Plus 默认方法，混入"应收金额核销"业务。问题：
- 接口签名没有任何提示（`IService.save` 是通用 ORM 签名，调用者不会意识到有副作用）
- 与 MyBatis-Plus 批量 `saveBatch()` 行为不一致（batch 不走重写的 save，会出现"批量导入不核销应收"陷阱）
- 与 `MesVoucherServiceImpl.saveWithItems()` 命名风格不统一

**建议**：抽出 `boolean saveWithSettlement(MesCollection)` 自定义方法，或拆解为 `save(entity)` + `settleReceivable(entity)` 两步。

### 1.3 服务边界（⚠️ 跨界调用需规范化）

- `MesCollectionServiceImpl` 依赖 `IMesReceivableService`（跨 collection → receivable 边界）
- `MesPaymentServiceImpl` 依赖 `IMesPayableService`（跨 payment → payable 边界）

**两个跨界调用本身合理**（收付款必须联动应收付），但调用方式采用**同库 Service 直调 + `@Transactional` 同事务**：

```java
@Transactional(rollbackFor = Exception.class)
public boolean save(MesCollection entity) {
    ...
    receivableService.updateById(ar);   // 同库同事务
    return super.save(entity);
}
```

**评价**：
- 在单体架构下是**可接受的最低成本方案**，事务一致性强（任何一步失败都回滚）
- **但未来如果应收应付要独立微服务，这里是硬伤**——没有事件机制，没有任何"先记录，后对账"的能力
- **建议至少引入 Spring `ApplicationEvent` 解耦**：`CollectionSavedEvent` → `ReceivableSettlementListener`，好处是 (a) 后续可平移到 MQ；(b) 凭证生成可挂同一事件而不污染 collection 模块

## 2. 凭证主子表设计（✅ 符合 JeecgBoot 标准）

`MesVoucher` + `MesVoucherItem` 是教科书式的一对多实现：

| 检查项 | 评价 |
|---|---|
| 主键 | 双方都用 `@TableId(type = IdType.ASSIGN_ID)` 雪花 ID ✅ |
| 外键字段 | `MesVoucherItem.voucherId` 关联主表 `id` ✅ |
| 主子表装载 | `MesVoucher` 持有 `transient List<MesVoucherItem> items` ✅ |
| 主子表保存 | `saveWithItems` / `updateWithItems` 同事务 ✅ |
| 子表覆盖更新 | `updateWithItems` 先 `delete by voucherId` 再 `insert`，符合 JeecgBoot 标准做法 ✅ |
| 行号 | `lineNo` 在 Service 校验时强制重新赋值，保证顺序 ✅ |
| 业务校验 | `validate()` 强制借贷平衡、明细非空、科目非空、单行金额非零 ✅ |
| 审核并发 | `auditWithGuard` 用 `UPDATE ... WHERE status='1'` 乐观状态守卫，避免并发重复审核 ✅ |

**P2-1：`voucher_item` 表缺 `del_flag`，与主表逻辑删除不一致**

`MesVoucher` 有 `@TableLogic delFlag`，`MesVoucherItem` **没有**。意味着：主表逻辑删除时，子表数据残留在库里（从 `removeWithItems` 看子表是物理 `delete`，与主表逻辑删除语义混乱）。建议要么主表也物理删（凭证审核前的草稿删除场景），要么子表也加 `del_flag`。

**P2-2：`updateWithItems` 先删后插，子表 ID 不稳定**

子表每次都是新雪花 ID，如果未来有"凭证明细引用"（如审计日志、明细级注释）将无法追溯。建议改造为"按 lineNo 比对差异更新"。

## 3. 收款/付款 ↔ 应收/应付联动（⚠️ 同事务硬编码）

**当前实现**（以 `MesCollectionServiceImpl.save` 为例）：

```java
@Transactional(rollbackFor = Exception.class)
public boolean save(MesCollection entity) {
    // 1. 校验收款单本身
    // 2. 查应收单
    MesReceivable ar = receivableService.getById(entity.getReceivableId());
    // 3. 校验未结金额
    if (entity.getAmount().compareTo(unsettled) > 0) throw ...;
    // 4. 内存里累加 + 重新计算状态
    ar.setReceivedAmount(newReceived);
    ar.setUnsettledAmount(ar.getAmount().subtract(newReceived));
    ar.setStatus(...);
    // 5. updateById 回写
    receivableService.updateById(ar);
    return super.save(entity);
}
```

### 3.1 联动方式评估

- **类型**：同事务硬编码（直接 Service 调用 + 同事务）
- **优点**：强一致、实现简单、可回滚
- **缺点**：
  1. **存在并发更新丢失**：两个用户同时对同一应收单收款，两个事务都读到 `receivedAmount=100`，都加 50，都写回 150，**实际收了 100 但只记了 50**（典型 lost update）
  2. 没有数据库行锁（`SELECT ... FOR UPDATE`）
  3. 没有乐观锁（`@Version` 或 `WHERE received_amount = 旧值`）
  4. `updateById` 全字段覆盖，进一步放大并发风险

### 3.2 建议（P1-2）

**最低成本修复**（保留同事务，仅消除并发漏洞）：

```java
// 在 MesReceivableMapper 加：
@Update("UPDATE c_mes_receivable SET received_amount = received_amount + #{amount}, " +
        "unsettled_amount = amount - (received_amount + #{amount}), " +
        "status = CASE WHEN amount - (received_amount + #{amount}) <= 0 THEN '3' ELSE '2' END, " +
        "update_by = #{user}, update_time = NOW() " +
        "WHERE id = #{id} AND del_flag = 0 " +
        "AND amount - (received_amount + #{amount}) >= 0")  // 金额守卫
int addReceivedAmount(@Param("id") String id, @Param("amount") BigDecimal amount, @Param("user") String user);
```

调用处检查 `rows == 0` 即抛"超出未结金额或并发更新"。一步到位消除 lost update，且把 `unsettledAmount` 和 `status` 推到 SQL 层原子计算。

**更彻底方案**：解耦为事件 + 异步核销 + 对账 Job，但这超出本期范围。

## 4. 凭证 vs 收付款是否应该打通（✅ 应该，且当前是 P0 缺失）

### 4.1 现状

| 维度 | 状态 |
|---|---|
| `MesVoucher.sourceType` 字典 | 已就位（手工=1、业务=2） |
| `MesVoucher.sourceBillId` 字段 | 已就位 |
| 凭证 `sourceType='2'`（业务自动生成）的写入路径 | **无任何代码写入** |
| 收款/付款保存时是否触发生成凭证 | **未触发** |
| 凭证与收付款的关联回查 | **无字段**（`MesCollection`/`MesPayment` 没有 `voucherId`） |
| 凭证字（收/付/转） | **未建模** |

**结论**：凭证模块和收付款模块**在数据模型上预留了集成接口，在代码上完全没接**。凭证管理目前只能手工录入。

### 4.2 应该打通的架构方案

**推荐方案：事件驱动 + 模板化凭证生成**

```
MesCollectionService.save()
   ↓ 同事务
save(collection)
   ↓ 同事务内
receivableService.updateById(ar)
   ↓ 事务提交前
applicationEventPublisher.publishEvent(CollectionSavedEvent)
   ↓ @TransactionalEventListener(AFTER_COMMIT)
VoucherAutoGenerateListener
   ↓ 调用
VoucherTemplateService.generateFrom(billType=COLLECTION, bill=collection)
   ↓ 根据模板（收：借银行存款/贷应收账款）
saveWithItems(voucher)
```

**模板示例**（应在 `c_mes_voucher_template` 表或字典配置）：

| 业务类型 | 借方科目 | 贷方科目 | 金额来源 |
|---|---|---|---|
| 收款-银行转账 | 1002 银行存款 | 1122 应收账款 | collection.amount |
| 收款-现金 | 1001 库存现金 | 1122 应收账款 | collection.amount |
| 付款-银行转账 | 2202 应付账款 | 1002 银行存款 | payment.amount |

**反向关联**：`c_mes_collection` / `c_mes_payment` 应增加 `voucher_id VARCHAR(32)`，凭证生成后回写，便于双向追溯、避免重复生成（幂等键）。

**自动生成凭证的状态机**：建议初始 `status='1'`（草稿），由财务人工审核，避免完全自动化绕过内控。

## 5. 数据库设计详评

### 5.1 字段类型与金额精度（✅ 合规）

| 检查项 | 评价 |
|---|---|
| 金额字段 | 全部 `DECIMAL(18,2)`，对应 Java `BigDecimal` ✅ |
| 主键 | `VARCHAR(32)` 雪花 ID ✅ |
| 状态/类型字段 | `VARCHAR(20)` + 字典 ✅ |
| 时间字段 | `DATETIME`（建议改 `DATETIME(3)` 或 `TIMESTAMP` 提高精度，可接受） |
| 审计字段 | `create_by/create_time/update_by/update_time` 齐 ✅ |
| 逻辑删除 | 主表 `del_flag INT DEFAULT 0` ✅（但 `c_mes_voucher_item` 缺失，见 §2） |

### 5.2 索引设计（⚠️ 基本合规，但有遗漏）

**已有索引（合理）**：
- `c_mes_collection`: `uk_col_code_del(code, del_flag)` 唯一、`idx_col_customer`、`idx_col_receivable`
- `c_mes_payment`: `uk_pmt_code_del`、`idx_pmt_supplier`、`idx_pmt_payable`
- `c_mes_voucher`: `uk_voucher_no_del`、`idx_voucher_date`
- `c_mes_voucher_item`: `idx_vi_voucher_id`

**缺失索引**（P1-3）：
- `c_mes_voucher_item.subject_id` 无索引 → 按科目查凭证明细（财务常用查询，如"查 1002 科目的所有分录"）会全表扫
- `c_mes_collection.collection_date`、`c_mes_payment.payment_date` 无索引 → 按日期区间对账/月结慢
- `c_mes_voucher.source_bill_id` 无索引 → 未来打通业务单据后反查慢
- `c_mes_receivable.status`、`c_mes_payable.status` 无索引 → "未结清应收"列表全表扫

**建议**：补一份 V9.1.2 SQL：

```sql
ALTER TABLE c_mes_voucher_item ADD INDEX idx_vi_subject (subject_id);
ALTER TABLE c_mes_voucher ADD INDEX idx_voucher_source (source_bill_id);
ALTER TABLE c_mes_collection ADD INDEX idx_col_date (collection_date);
ALTER TABLE c_mes_payment ADD INDEX idx_pmt_date (payment_date);
ALTER TABLE c_mes_receivable ADD INDEX idx_rec_status (status);
ALTER TABLE c_mes_payable ADD INDEX idx_pay_status (status);
```

### 5.3 主外键关系（⚠️ 弱约束，符合 JeecgBoot 惯例但需说明）

**所有外键均为应用层维护，无 DB 层 FOREIGN KEY 约束**。这是 JeecgBoot 一贯风格（便于分库分表、提升导入性能），本模块也遵循。

| 关系 | 类型 | 评价 |
|---|---|---|
| `c_mes_voucher_item.voucher_id` → `c_mes_voucher.id` | 应用层 | Service 层保证同事务 ✅ |
| `c_mes_voucher_item.subject_id` → `c_mes_account_subject.id` | 应用层 | **未校验！**（P1-4，见下） |
| `c_mes_collection.receivable_id` → `c_mes_receivable.id` | 应用层 | Service 校验存在性 ✅ |
| `c_mes_collection.customer_id` → `c_mes_customer.id` | 应用层 | **未校验**（P1-4） |
| `c_mes_payment.payable_id` → `c_mes_payable.id` | 应用层 | Service 校验存在性 ✅ |
| `c_mes_payment.supplier_id` → `c_mes_supplier.id` | 应用层 | **未校验**（P1-4） |

**P1-4：引用完整性校验不完整**

- `MesVoucherServiceImpl.validate()` 只校验 `subjectId` 非空，**不校验该科目是否真实存在、是否启用、是否叶子科目**
- `MesCollectionServiceImpl.save()` 校验了 `receivableId` 存在，但**没校验 `customerId` 是否存在**，且**没校验 `receivable.customerId == collection.customerId`**（可能出现收款挂错客户）
- `MesPaymentServiceImpl.save()` 同上（`supplierId` 与 `payable.supplierId` 一致性未校验）

**建议**：抽出 `ReferentialValidator`，所有外键校验集中处理；引用一致性校验（收款客户 == 应收客户）必须加。

### 5.4 唯一键设计（✅ 合规）

- `uk_col_code_del(code, del_flag)`：支持逻辑删除后复用同一单号 ✅
- `uk_voucher_no_del(voucher_no, del_flag)`：同上 ✅

注意：`del_flag` 目前只有 0/1 两种取值，**MySQL 唯一索引下 (code, 0) 仍唯一**，但若未来改用时间戳式 del_flag（JeecgBoot 高版本支持），需保证 SQL 兼容。

## 7. 权限设计（⚠️ 制单/审核未分离，P0）

### 7.1 现状

```
MesVoucherController:
  add    → @RequiresPermissions("mes:voucher:add")
  edit   → @RequiresPermissions("mes:voucher:edit")
  delete → @RequiresPermissions("mes:voucher:delete")
  audit  → @RequiresPermissions("mes:voucher:edit")    ← ❌ 错
```

`MesMenuRegistry.java` line 98：
```java
addPerms(list, "mes:voucher:", "mes_finance_voucher",
    new String[]{"list","add","edit","delete","deleteBatch","export"});
// 注意：没有 "audit" 权限码
```

### 7.2 问题（P0-3 之一）

1. **审核 = 编辑权限**：任何能"编辑凭证"的角色都能"审核凭证"，**制单/审核不相容职责未分离**，违反最基础的财务内控（SOX / 会计基础工作规范）
2. **没有审核人字段**：`MesVoucher` 没有 `auditBy` / `auditTime`，`auditWithGuard` 只把审核人写到 `update_by`，无法区分"制单人 vs 审核人"
3. **没有禁止自审**：`audit()` 不检查 `create_by != current_user`，制单人可以审核自己的凭证
4. **菜单注册缺权限码**：`MesMenuRegistry` 没注册 `mes:voucher:audit`，就算代码改了权限码也没有菜单数据可用

### 7.3 建议

- `MesVoucher` 增加 `auditBy VARCHAR(50)` / `auditTime DATETIME`
- `MesVoucherController.audit` 改 `@RequiresPermissions("mes:voucher:audit")`
- `MesMenuRegistry` 增加 `"audit"` 到 voucher 权限数组
- `audit()` 增加自审校验：`if (e.getCreateBy().equals(currentUser)) throw new JeecgBootException("制单人不能审核本人凭证")`
- 同步在 SQL V9.1.2 中给 `c_mes_voucher` 加列、给角色授权补 `mes:voucher:audit`

收/付款单**目前没有任何审核机制**（保存即生效），建议未来补 `status` 流转（草稿→审核→已收付）。

## 8. SQL 是否在 Flyway 扫描路径（❌ P0 阻断）

### 8.1 现状

- **Flyway 配置**：`spring.flyway.locations = classpath:flyway/sql/mysql`（`application-dev.yml` line 30）
- **应放位置**：`jeecg-boot-module/project-mes/src/main/resources/flyway/sql/mysql/`
- **该目录现状**：仅 `V3.9.3_0__mes_price_dict.sql` 1 个文件
- **V9.1.0 和 V9.1.1 实际位置**：`jeecg-boot-module/project-mes/db/`（**不在 classpath，Flyway 完全扫不到**）

进一步核查历史 SQL：`db/` 目录下从 V1.0.0 到 V9.1.1 共 34 个 SQL，**只有 V3.9.3_0 一个文件被拷贝到 flyway 扫描路径**。这说明项目历史上**有手动执行 SQL 的运维流程**，但本期新增的 V9.1.0/V9.1.1 **是否已手动在库中执行**无法从代码侧确认。

### 8.2 影响

如果新环境/新部署拉起：
- `c_mes_collection`、`c_mes_payment` 表不存在 → 收款/付款页面启动即 500

## 9. 命名规范（✅ 大体合规，2 处不一致）

| 项 | 评价 |
|---|---|
| 表名 `c_mes_xxx` | ✅ 项目前缀统一 |
| 实体 `MesXxx` | ✅ |
| 包路径 `modules.mes.finance.{module}` | ✅ |
| 权限码 `mes:{module}:{action}` | ✅ 全模块统一 |

| 字典码 `mes_xxx_yyy` | ✅ |

**不一致项**：

1. **`MesCollection.code` 字段在实体是 `code`，`MesVoucher` 用 `voucherNo`**——同为单号字段命名风格不一（receivable/payable 用 `code`）。建议统一为 `code`，或全部改 `xxxNo`。当前属可接受范围。
2. **`MesCollection.paymentMethod` 用于收款方式**：字段名 `payment_method` 同时承载收款方式和付款方式语义，建议未来拆分 `collection_method` / `payment_method`，或重命名为通用 `pay_method`。当前共用字典 `mes_payment_method`，属可接受范围。

## 10. 前端联动 / 完整性（❌ P0 阻断）

### 10.1 收付款新增页面缺失（P0-2）

`collection/index.vue` line 27：
```js
function handleAdd() { router.push('/project/mes/finance/collection/add'); }
```

`payment/index.vue` line 27：
```js
function handleAdd() { router.push('/project/mes/finance/payment/add'); }
```

但 `src/views/project/mes/finance/collection/` 和 `payment/` 下**只有 index.vue + api + data**，**没有 add.vue / AddForm.vue / Drawer 等任何形式的录入组件**。整个 `views/project/mes` 下也搜不到对应路由。

**后果**：用户点击"新增收款"或"新增付款"按钮，前端路由跳转到不存在的路径，Vue Router 落在 404 或菜单兜底，**收付款功能完全无法录入数据**。

**建议**：参考凭证模块的 `VoucherDrawer.vue` 模式，新增 `CollectionDrawer.vue` / `PaymentDrawer.vue`，列表页改用 `openDrawer` 而非 `router.push`。

### 10.2 凭证审核权限按钮

`voucher/index.vue` line 39：
```js
acts.push({ label: '审核', popConfirm: { title: '确认审核？', confirm: () => handleAudit(r) } });
```

按钮没有 `auth` 属性控制（JeecgBoot 通常 `<a-button auth="mes:voucher:audit">`），且**没有根据 `status` 显示已审核状态**。已审核的凭证行内"审核"按钮消失是因 `if (r.status == '1')`，这点 OK；但 `audit` 操作按钮文案、确认提示、权限控制都比较粗糙。

## 12. 总结

三模块代码风格高度统一、JeecgBoot 基础组件复用度高、主子表设计教科书化，**单点技术质量不差**。但架构层面存在 4 个关键断点：

1. **运维断点**：SQL 未入 Flyway 路径，部署即炸
2. **功能断点**：收付款无录入页面，UI 流程断裂
3. **数据断点**：业务单据与财务凭证不通，凭证模块沦为手工记账
4. **内控断点**：制单/审核权限未分离，凭证可以自审

建议按 P0 → P1 → P2 顺序在本迭代内依次闭环，预计修复工作量 1.5 人日（不含 P0-4 凭证打通的模板设计部分，该部分建议独立排 1 人日）。
