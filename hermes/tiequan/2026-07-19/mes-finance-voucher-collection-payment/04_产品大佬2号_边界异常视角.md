## 一、审计范围与方法

本次审计聚焦**边界条件、异常状态、空值/零值/负数、重复提交、状态流转、并发操作**六大风险面，逐行阅读以下核心实现：

- `MesVoucherServiceImpl`（凭证保存/更新/删除/审核）
- `MesCollectionServiceImpl`（收款保存 + 应收联动）
- `MesPaymentServiceImpl`（付款保存 + 应付联动）
- `MesVoucherController` / `MesCollectionController` / `MesPaymentController`
- 实体与 DDL：`MesVoucher` / `MesVoucherItem` / `MesCollection` / `MesPayment` / `MesReceivable` / `MesPayable`
- 上游联动：`MesSalesOutboundServiceImpl.audit/cancel`（自动生成应收）

## 二、总体结论

| 维度 | 评级 | 说明 |
|------|------|------|
| 借贷平衡校验 | ⚠️ 中风险 | 有校验但存在负数/单行双向漏洞 |
| 金额边界（0/负数/超额） | ❌ 高风险 | 收款/付款超额仅靠 Java 比较，无并发锁 |
| 状态机流转 | ❌ 高风险 | 凭证无反审核/作废；收付款无作废/删除 |
| 联动异常（应收不存在/已结清） | ⚠️ 中风险 | 存在性有校验，已结清状态未拦截 |
| 并发/重复提交 | ❌ 高风险 | 无乐观锁/悲观锁，唯一索引缺失 |
| 凭证明细完整性 | ⚠️ 中风险 | 空明细拦截，但单行双向、负数未拦截 |
| 删除/作废保护 | ❌ 高风险 | 凭证删除保护有但批量删除绕过；收付款无删除接口 |

**核心结论**：模块在“单线程、正常流程”下基本可用，但在**并发、重复提交、异常边界**场景下存在多处可导致**账实不符、超额核销、状态错乱**的缺陷。

## 三、逐项风险详查

### 3.1 借贷平衡校验

| 检查项 | 代码位置 | 现状 | 风险 |
|--------|----------|------|------|
| 借方合计 = 贷方合计 | `MesVoucherServiceImpl.validate()` L99 | `dr.compareTo(cr) != 0` 抛异常 | ✅ 基本有效 |
| 0 金额行 | L94 | `debit=0 && credit=0` 抛异常 | ✅ 有效 |
| 负数金额 | L92-96 | **未校验** | ❌ 允许负数，可构造借 -100 / 贷 100 的异常凭证 |
| 单行同时有借有贷 | L92-96 | **未校验** | ❌ 同一行 debit>0 且 credit>0 被允许，破坏会计惯例 |
| 审核时二次校验 | `audit()` L72-77 | 有 | ✅ 有效，但审核后不可改，意义有限 |

**风险场景**：
- 用户录入借方 -100、贷方 100，合计相等，系统通过，但出现负金额凭证。
- 同一行录入借 100、贷 100，合计相等，系统通过，但该科目同时虚增借贷。

---

### 3.2 金额边界：收款/付款超额

| 检查项 | 代码位置 | 现状 | 风险 |
|--------|----------|------|------|
| 收款金额 = 0 | `MesCollectionServiceImpl.save()` L27 | `<= 0` 抛异常 | ✅ 有效 |
| 收款金额 > 应收余额 | L36 | Java 比较 `> unsettled` | ⚠️ 有校验，但**并发下失效** |
| 付款金额 > 应付余额 | `MesPaymentServiceImpl.save()` L35 | 同上 | ⚠️ 同上 |
| 应收单不存在 | L34 | `ar == null` 抛异常 | ✅ 有效 |
| 应收单已结清（status=3） | L35-40 | **未校验状态**，仅看 `unsettledAmount` | ❌ 若 `unsettledAmount` 因脏数据为 0 以下或并发被改，可能通过 |

**关键代码**：
```java
BigDecimal unsettled = ar.getUnsettledAmount() != null ? ar.getUnsettledAmount() : ar.getAmount();
if (entity.getAmount().compareTo(unsettled) > 0) throw ...;
```

**风险场景**：
- 应收单 A 余额 1000，两个并发请求各收款 800。两者同时读到 `unsettled=1000`，均通过校验，最终 `receivedAmount=1600`，`unsettledAmount=-600`，**超额核销**。
- 应收单已结清（status=3）后，因 `unsettledAmount` 可能为 0，再次收款 0 会被拦截，但收款 0.01 若 `unsettledAmount` 为脏数据正数则可能通过。

---

### 3.3 状态机流转

| 单据 | 状态定义 | 当前流转 | 风险 |
|------|----------|----------|------|
| 凭证 | 1草稿 / 2已审核 / 3已过账 / 0已作废 | 仅支持 1→2（审核） | ❌ 无反审核、无作废、无过账 |
| 收款单 | 1已收款 / 0已作废 | 仅创建时置 1 | ❌ 无作废接口、无删除接口 |
| 付款单 | 1已付款 / 0已作废 | 仅创建时置 1 | ❌ 同上 |
| 应收单 | 1未结清 / 2部分结清 / 3已结清 | 收款时自动流转 | ⚠️ 无手工调整接口，红冲逻辑在出库单取消时直接置 3，不校验是否已有收款 |

**风险场景**：
- 凭证审核后发现错误，**无法反审核**，只能删除重录（但删除仅限草稿，已审核凭证删不掉）。
- 收款单录入错误，**无法作废或删除**，只能数据库手工改。
- 出库单取消时，应收单被直接置为“已结清”（`MesSalesOutboundServiceImpl.cancel()` L158-161），**不检查该应收单是否已有收款记录**。若已有收款，应收单状态被错误置 3，且收款单与应收单数据脱节。

### 3.4 联动异常：收款对应应收单不存在/已结清/已删除

| 场景 | 现状 | 风险 |
|------|------|------|
| 应收单不存在 | `ar == null` 抛异常 | ✅ 有效 |
| 应收单已逻辑删除 | `getById` 默认带 `@TableLogic`，查不到 | ✅ 有效 |
| 应收单已结清（status=3） | **不拦截**，仅看金额 | ⚠️ 金额边界可绕过，状态未校验 |
| 应收单被并发修改 | 无锁 | ❌ 见 3.5 |

---

### 3.5 并发操作

| 场景 | 保护机制 | 风险 |
|------|----------|------|
| 同一应收单同时被两笔收款核销 | **无** `SELECT ... FOR UPDATE`，无乐观锁 | ❌ 超额核销 |
| 同一应付单同时被两笔付款核销 | **无** | ❌ 同上 |
| 凭证号重复 | Java `selectCount` + 数据库 `uk_voucher_no_del` | ⚠️ 有唯一索引兜底，但 `selectCount` 与 `insert` 之间仍有并发窗口 |
| 收款单号重复 | **无唯一索引**，无 Java 校验 | ❌ 可重复提交相同单号 |
| 付款单号重复 | **无唯一索引**，无 Java 校验 | ❌ 同上 |
| 凭证审核并发 | `auditWithGuard`（`WHERE status='1'`） | ✅ 有效 |

**关键缺失**：
- `c_mes_collection` 和 `c_mes_payment` 表缺少 `code` 唯一索引（DDL 中仅 `uk_col_code_del` 和 `uk_pmt_code_del`，但 `del_flag` 默认 0，重复 `code` 在 `del_flag=0` 时仍可插入多条——等等，唯一索引是 `(code, del_flag)`，若 `del_flag` 固定 0，则 `code` 实际唯一。但逻辑删除后 `del_flag=1`，相同 `code` 可再次插入。这是 Jeecg 常见设计，但**业务上允许同号单复活**，可能导致混乱）。

### 3.6 凭证明细边界

| 检查项 | 现状 | 风险 |
|--------|------|------|
| 空明细 | `items == null || items.isEmpty()` 抛异常 | ✅ 有效 |
| 只有借方无贷方 | 合计不平衡被拦截 | ✅ 有效 |
| 明细行顺序 | `lineNo` 按插入顺序 1..N | ✅ 有效 |
| 单行借>0 且 贷>0 | **未拦截** | ❌ 会计上不允许 |
| 明细科目不存在/已停用 | **未校验** `subjectId` 有效性 | ❌ 可关联到不存在或停用科目 |
| 明细金额精度 | `BigDecimal`，但 DDL `DECIMAL(18,2)` | ⚠️ 若传入更多小数位，数据库截断或报错，Java 层未 `setScale` |

### 3.7 删除/作废保护

| 场景 | 现状 | 风险 |
|------|------|------|
| 已审核凭证能否删除 | `removeWithItems()` 检查 `status != '1'` 抛异常 | ✅ 有效 |
| 凭证批量删除 | `MesVoucherController.deleteBatch()` 调用 `service.removeByIds(idList)` | ❌ **绕过状态检查**，已审核凭证可被批量删除 |
| 收款单删除 | Controller 无 delete 接口 | ❌ 无法删除，但也无法作废 |
| 付款单删除 | 同上 | ❌ 同上 |
| 已核销收款能否作废 | 无作废功能 | ❌ 功能缺失 |

**关键代码**（`MesVoucherController.java` L43）：
```java
service.removeByIds(idList); // 直接调用 MyBatis-Plus 基类方法，无状态校验
```

## 四、高危漏洞清单（Top 5）

| # | 漏洞 | 影响 | 复现路径 |
|---|------|------|----------|
| 1 | **并发超额核销** | 应收/应付出现负余额，账实不符 | 同一应收单并发提交两笔收款，金额均 ≤ 余额但合计 > 余额 |
| 2 | **凭证批量删除绕过审核保护** | 已审核凭证被删除，审计追踪断裂 | 调用 `/mes/finance/voucher/deleteBatch?ids=已审核凭证ID` |
| 3 | **负数金额凭证** | 出现借 -100 / 贷 100 的异常凭证，破坏账簿 | 新增凭证，明细行借方填 -100，贷方填 100 |
| 4 | **单行双向金额** | 同一科目同时虚增借贷，试算平衡表失真 | 新增凭证，某一行同时填借 100 和贷 100 |
| 5 | **出库单取消时应收状态错乱** | 已有收款的应收单被强制置为“已结清” | 销售出库→生成应收→收款→取消出库单 |

## 五、修复建议

### P0（立即修复）

1. **收款/付款增加悲观锁或乐观锁**
   ```java
   // 方案 A：悲观锁
   MesReceivable ar = receivableService.getByIdForUpdate(entity.getReceivableId());
   // 方案 B：乐观锁（在 c_mes_receivable 加 version 字段）
   ```

2. **凭证批量删除增加状态校验**
   ```java
   // MesVoucherController.deleteBatch 改为调用 removeWithItems 循环
   for (String id : idList) service.removeWithItems(id);
   ```

3. **凭证明细增加负数与双向校验**
   ```java
   if (item.getDebitAmount().compareTo(BigDecimal.ZERO) < 0 ||
       item.getCreditAmount().compareTo(BigDecimal.ZERO) < 0)
       throw new JeecgBootException("第" + (i+1) + "行金额不能为负数");
   if (item.getDebitAmount().compareTo(BigDecimal.ZERO) > 0 &&
       item.getCreditAmount().compareTo(BigDecimal.ZERO) > 0)
       throw new JeecgBootException("第" + (i+1) + "行不能同时录入借贷金额");
   ```

### P1（本周修复）

4. **收付款单增加作废功能**
   - 新增 `status='0'` 作废接口，作废时回冲应收/应付的已收/已付金额。
   - 已作废单不允许重复作废。

5. **凭证增加反审核与作废**
   - 反审核：2→1，需校验是否已过账。
   - 作废：1→0，已审核凭证需先反审核。

6. **出库单取消时校验应收单状态**
   ```java
   if (ar.getReceivedAmount() != null && ar.getReceivedAmount().compareTo(BigDecimal.ZERO) > 0)
       throw new JeecgBootException("该应收单已有收款，禁止取消出库");
   ```

### P2（迭代优化）

7. **收付款单号增加业务唯一性校验**（或前端生成 UUID 单号）
8. **凭证明细科目存在性/启用状态校验**
9. **金额精度统一处理**：Java 层 `setScale(2, RoundingMode.HALF_UP)` 后再入库
