## 一、总体结论

财务模块的**状态机流转（审核/取消）普遍使用了带状态守卫的原子 UPDATE（auditWithGuard 模式），设计正确**；但**金额核算链路（收付款核销应收应付）存在严重的 SELECT-then-UPDATE 丢失更新竞态**，是整个模块最危险的并发缺陷。此外，凭证主子表保存、单号幂等、跨模块金额联动等方面均无锁保护，依赖默认事务隔离级别（REPEATABLE READ）裸奔。

**风险定级**：
- 🔴 **P0（必须立即修复）**：收款/付款核销应收应付的丢失更新竞态
- 🟠 **P1（应尽快修复）**：销售出库 cancel 联动应收的竞态与逻辑错误、收付款单号无服务端幂等、凭证号查重 TOCTOU
- 🟡 **P2（建议改进）**：凭证编辑/删除状态守卫非原子、事务隔离级别未显式声明、无分布式锁兜底

## 二、🔴 P0：收款/付款核销应收应付的 SELECT-then-UPDATE 丢失更新竞态

### 2.1 问题代码

**`MesCollectionServiceImpl.save`**（collection/service/impl/MesCollectionServiceImpl.java:24-45）：

```java
@Override @Transactional(rollbackFor = Exception.class)
public boolean save(MesCollection entity) {
    ...
    if (StringUtils.hasText(entity.getReceivableId())) {
        MesReceivable ar = receivableService.getById(entity.getReceivableId());  // ① 普通 SELECT，无锁
        ...
        BigDecimal unsettled = ar.getUnsettledAmount() != null ? ar.getUnsettledAmount() : ar.getAmount();
        if (entity.getAmount().compareTo(unsettled) > 0) throw ...;              // ② 基于快照校验
        BigDecimal newReceived = (ar.getReceivedAmount()...).add(entity.getAmount());
        ar.setReceivedAmount(newReceived);
        ar.setUnsettledAmount(ar.getAmount().subtract(newReceived));
        ar.setStatus(...);
        receivableService.updateById(ar);                                        // ③ 全字段覆盖 UPDATE
    }
    return super.save(entity);
}
```

**`MesPaymentServiceImpl.save`**（payment/service/impl/MesPaymentServiceImpl.java:24-44）结构与上完全对称（应收→应付，received→paid）。

### 2.2 竞态复现

两个并发收款请求同时核销同一张应收单（应收金额 1000，已收 0，未结 1000）：

| 时刻 | 事务 A（收款 600） | 事务 B（收款 600） |
|---|---|---|
| T1 | SELECT → received=0, unsettled=1000 | |
| T2 | 校验 600 ≤ 1000 ✔ | SELECT → received=0, unsettled=1000 |
| T3 | 计算 newReceived=600 | 校验 600 ≤ 1000 ✔ |
| T4 | UPDATE received=600, unsettled=400 | 计算 newReceived=600（**基于旧快照**） |
| T5 | COMMIT | UPDATE received=600, unsettled=400 |
| T6 | | COMMIT |

**结果**：实际收款 1200（已超额 200），但应收单上 received_amount=600、unsettled_amount=400，**账面少记 600，且状态可能错误地停留在"部分结清"**。两笔收款单都落库成功（`super.save` 在 update 之后），资金口径与账面口径永久不一致。

### 2.3 根因分析

1. **无行锁**：`receivableService.getById()` 是普通 SELECT（非 FOR UPDATE），两个事务读到同一快照。
2. **读-改-写非原子**：校验（`compareTo(unsettled) > 0`）和更新（`updateById`）分离，校验基于过期数据，超额校验形同虚设。
3. **MyBatis-Plus `updateById` 全字段覆盖**：`receivedAmount`/`unsettledAmount` 是用 Java 内存中的旧值算好后整体 SET，而非 SQL 端 `received_amount = received_amount + #{delta}` 增量更新，天然丢失并发增量。
4. **实体无乐观锁**：`MesReceivable`/`MesPayable` 实体**没有 `@Version` 字段**（已全仓搜索确认 finance 包下无 `@Version`、无 `selectByIdForUpdate`、无 `FOR UPDATE`），数据库表（V9.0.0 DDL）也没有 version 列。
5. **事务隔离级别未显式声明**：`@Transactional(rollbackFor = Exception.class)` 走 MySQL 默认 REPEATABLE READ——普通 SELECT 是一致性非锁定读，更加助长了快照过期问题。

### 2.4 修复建议（按优先级）

**方案 A（推荐，最小改动且最可靠）— 行锁 + 重读**：
在 `MesReceivableMapper`/`MesPayableMapper` 增加：

```java
@Select("SELECT * FROM c_mes_receivable WHERE id = #{id} AND del_flag = 0 FOR UPDATE")
MesReceivable selectByIdForUpdate(@Param("id") String id);
```

`MesCollectionServiceImpl.save` 中改为 `selectByIdForUpdate` 后再做校验与更新。注意：**行锁必须在事务内获取，且获取锁后看到的才是最新已提交值**（InnoDB 中 FOR UPDATE 是当前读，自动读最新版本）。

**方案 B — 条件更新（原子守卫 SQL）**：
将金额更新写成带守卫条件的原子 UPDATE：

```java
@Update("UPDATE c_mes_receivable SET received_amount = received_amount + #{delta}, " +
        "unsettled_amount = amount - (received_amount + #{delta}), " +
        "status = CASE WHEN received_amount + #{delta} >= amount THEN '3' ELSE '2' END, " +
        "settlement_date = IF(received_amount + #{delta} >= amount, NOW(), settlement_date), " +
        "update_time = NOW() " +
        "WHERE id = #{id} AND del_flag = 0 AND received_amount + #{delta} <= amount")
int applyCollection(@Param("id") String id, @Param("delta") BigDecimal delta);
```

`rows == 0` 即并发冲突或超额，抛异常回滚。**该方案无需长事务持锁，吞吐更高，是互联网业态的标准做法。**

**方案 C — 乐观锁**：表加 `version` 列 + 实体 `@Version`，冲突时重试（需配重试逻辑，否则用户体验差）。可作为方案 A/B 的补充防线。

> 同时建议：**收款/付款也应支持作废/红冲**（当前实体有 status='0' 作废定义但无对应接口），作废时同样需要以同样的原子方式回滚应收/应付金额。

## 三、🟠 P1：销售出库 cancel 联动应收的并发安全与逻辑错误

**`MesSalesOutboundServiceImpl.cancel`**（sales/service/impl/MesSalesOutboundServiceImpl.java:142-168）：

```java
public void cancel(String id) {
    MesSalesOutbound e = queryWithItems(id);
    if ("3".equals(e.getStatus())) {
        for (...) { inventoryService.stockIn(...); }          // ① 先恢复库存
        try {
            List<MesReceivable> ars = receivableService.list(arQw);
            for (MesReceivable ar : ars) {
                ar.setStatus("3");                             // ② 应收"作废"=置为已结清？
                receivableService.updateById(ar);              // ③ 普通 updateById，无锁无守卫
            }
        } catch (Exception ex) { /* 应收不存在则忽略 */ }       // ④ 吞异常！
    }
    int rows = baseMapper.cancelWithGuard(id, username, now);  // ⑤ 最后才改出库单状态
    if (rows == 0) throw ...;
}
```

**并发与一致性问题清单**：

1. **操作顺序倒置（P0-05 注释声称"先改状态再扣库存"，cancel 却反着来）**：先 `stockIn` 恢复库存、改应收，**最后**才执行 `cancelWithGuard`。若两个线程并发 cancel 同一单据：两个线程都在 T1 读到 status='3'，都执行库存回冲 → **库存被双倍回冲**；应收被重复 updateById。虽然 `cancelWithGuard` 最终只有一个成功，但失败方的事务会回滚——这一点事务能兜住。**真正的问题是**：`cancelWithGuard` 成功的一方与另一方在中间窗口期内的库存/应收写操作都依赖事务回滚兜底，一旦 `stockIn` 内部有自治事务或异常被吞（见第 3 点），就会出现"状态守卫失败但库存已回冲"的脏数据。
2. **应收"作废"语义错误**：把应收单状态置为 `'3'`（已结清）。但应收状态字典中 1=未结清 2=部分结清 3=已结清，**没有"作废"状态**。取消出库理应使应收失效，却标记为"已结清"——财务报表上将表现为"钱已收齐"，这是**业务口径造假**，且后续真实收款若再关联该应收（receivableId 仍可选中它），金额校验基于已被错误结清的数据。
3. **吞异常（`catch (Exception ex) {}`）**：应收更新失败被静默忽略，事务不回滚，库存已回冲、出库单已取消、应收却残留未结清状态——三处数据各说各话。
4. **应收更新无锁无守卫**：`receivableService.updateById(ar)` 与第二节的收款核销存在交叉竞态——cancel 正在"作废"应收的同时，另一线程正在对该应收做收款核销，两个基于旧快照的全字段 UPDATE 互相覆盖，金额与状态错乱。
5. **应收 unsettled_amount 未同步调整**：cancel 只改 status，没有把 `received_amount`/`unsettled_amount` 归零或冲销，账龄/未结报表仍然计入。

**修复建议**：
- 先执行 `cancelWithGuard` 原子改状态（失败即抛异常终止），再做库存回冲和应收冲销；
- 应收冲销用带守卫的原子 SQL（如 `WHERE source_bill_id = #{id} AND status != '0'`，并清零或保留金额但置独立"作废"状态——建议字典补充 `0=已作废`）；
- 严禁吞异常，让事务回滚兜底。

## 四、凭证模块并发安全审计

### 4.1 ✅ 凭证审核 `auditWithGuard` —— 设计正确

`MesVoucherMapper.auditWithGuard`：

```sql
UPDATE c_mes_voucher SET status='2', update_by=#{updateBy}, update_time=#{updateTime}
WHERE id=#{id} AND status='1'
```

- 单条原子 UPDATE，自带状态守卫（乐观并发控制），`rows==0` 即失败抛异常——**审核状态机是并发安全的，不会重复审核**。
- `audit()` 先 `queryWithItems` 读明细验借贷平衡，再原子改状态；即使校验期间状态被并发改变，最终 UPDATE 守卫也能拦截。校验与状态变更之间的 TOCTOU 窗口无害（校验失败方会因守卫 UPDATE 返回 0 而抛错）。

**轻微瑕疵**：`audit` 先按 `status='1'` 校验抛"只有草稿可审核"，再执行守卫 UPDATE 抛"凭证不存在或状态已变更"，两个异常文案对并发场景有冗余但无害。

### 4.2 🟠 凭证主子表保存的并发问题（`saveWithItems` / `updateWithItems`）

```java
QueryWrapper<MesVoucher> qw = new QueryWrapper<>(); qw.eq("voucher_no", entity.getVoucherNo());
if (baseMapper.selectCount(qw) > 0) throw new JeecgBootException("凭证号已存在");   // ① SELECT 查重
super.save(entity);                                                                  // ② INSERT
saveItems(entity);
```

1. **凭证号查重是 TOCTOU**：selectCount 与 insert 之间无锁。好在 DDL 有 `UNIQUE INDEX uk_voucher_no_del (voucher_no, del_flag)` 兜底，并发重复会抛 `DuplicateKeyException`——但代码**没有像销售出库那样捕获 DuplicateKeyException 转为友好提示**，用户会看到堆栈级 SQL 异常。属于健壮性缺陷而非数据正确性缺陷。
2. **`uk_voucher_no_del (voucher_no, del_flag)` 复合唯一索引与软删除语义存在隐患**：`del_flag` 逻辑删除后值非 0，删除两张同号凭证后 `del_flag` 各为其 ID 或 1（取决于 @TableLogic 配置），若为固定值 1，则**删除两张同号凭证后第三张同号凭证可以再插入**（历史脏数据残留时唯一性被绕过），且软删恢复场景可能撞唯一键。建议确认 @TableLogic 的删除值策略；财务凭证号建议永久唯一（不随 del_flag 释放）。
3. **`updateWithItems` 的"删明细-插明细"模式**：`itemMapper.delete(voucher_id)` + 逐条 `insert`，事务内安全；但编辑时 `exist` 状态校验（`!"1".equals(exist.getStatus())`）与 `updateById` 分离，存在 TOCTOU：编辑提交瞬间另一线程完成审核，则已审核凭证的明细被删插重建。建议 update 也采用守卫 SQL（`UPDATE ... WHERE id=#{id} AND status='1'`），或用 `auditWithGuard` 同款模式。
4. **`removeByIds`（Controller deleteBatch）绕过状态校验**：`MesVoucherController.deleteBatch` 直接调 `service.removeByIds(idList)`——这是 MyBatis-Plus 默认实现，**不走 `removeWithItems` 的状态校验，已审核凭证可被批量删除**！同时凭证明细也未级联删除，留下孤儿明细行。这是权限+并发双重缺陷。

### 4.3 凭证实体无乐观锁

`MesVoucher` 无 `@Version` 字段。草稿状态下两人同时编辑同一凭证，后提交者全量覆盖先提交者（含明细全删全插），无任何冲突提示。视使用强度定 P2。

## 五、收付款单号与幂等设计

1. **无服务端单号生成**：`MesCollectionServiceImpl.save`/`MesPaymentServiceImpl.save` 仅校验 `code` 非空，**单号完全由前端传入**，后端无生成、无服务端幂等键。前端双击/重试/网络重放会产生两条不同 code 的收款单，对同一应收重复核销——叠加第二节的竞态，资金安全雪上加霜。
2. **数据库唯一索引兜底**：`uk_col_code_del (code, del_flag)`、`uk_pmt_code_del (code, del_flag)` 能挡住**同 code** 的重复提交（前提前端重试时用同一单号），但 `save` 未捕获 `DuplicateKeyException`，用户看到的是 SQL 异常。
3. **建议**：服务端按规则生成单号（如 `SK-yyyyMMdd-序列`，用独立序列表或 Redis INCR 保证单调唯一），或要求前端提交幂等键（Idempotency-Key）+ 服务端去重表。这是核销场景防重复扣款的行业标准做法。

## 六、跨模块调用与分布式锁

1. **无任何分布式锁**：全仓搜索 `Redisson`/`RedisLock`/`DistributedLock`/`@Lock`/`ReentrantLock` 在 MES 模块均无匹配（仅菜单注册器有 JVM `synchronized`）。当前为单体应用 + 单库，行锁足以覆盖大部分场景；**但若未来拆分为多实例部署，现有代码没有任何横向保护**，第二节的竞态会被放大。
2. **跨模块调用链的事务边界**：收付款 → 应收应付是同事务内的本地调用（`@Autowired` 直接注入 Service），无 RPC，无分布式事务问题——这一点是安全的。销售出库 audit/cancel 链（出库单 → 库存 → 发货单 → 应收）同样在同一本地事务内，异常可整体回滚，**前提是中途不吞异常**（第三节第 3 点违反了该前提）。
3. **库存模块的对比**：`MesInventoryServiceImpl.stockOut` 使用 `selectForUpdate` 行锁 + `upsertWithDelta`（SQL 端 `current_qty + delta` 增量），是**全模块并发设计的正面样板**；`stockIn` 却是 `findByMaterialAndWarehouse` 普通查询后 upsert——upsert 本身是 SQL 端增量所以金额不错，但台账 `before` 值基于过期快照，台账流水会出现前后不衔接（P2）。财务模块应对标 stockOut 的写法。

---

## 七、事务隔离级别

- 所有写方法均为 `@Transactional(rollbackFor = Exception.class)`，**未显式声明 isolation**，使用 MySQL InnoDB 默认 REPEATABLE READ。
- REPEATABLE READ 下普通 SELECT 是一致性快照读，**这恰恰放大了 SELECT-then-UPDATE 的窗口**：事务开启后第一次快照读建立 read view，后续校验一直基于该快照，即使别的事务已提交新值也看不见。
- 修复不一定靠改隔离级别（READ COMMITTED 也救不了丢失更新），**正确姿势是当前读（FOR UPDATE）或原子守卫 UPDATE**（第二、三节方案）。显式声明 `isolation = Isolation.READ_COMMITTED` 可作为辅助措施减少快照滞留时间，但不能替代锁。

## 八、状态机安全汇总

| 单据 | 状态流转 | 并发保护 | 评级 |
|---|---|---|---|
| 凭证审核 | 1→2 | ✅ `auditWithGuard` 原子守卫 UPDATE | 安全 |
| 凭证编辑/删除 | 校验+非守卫 UPDATE | ❌ TOCTOU；批量删除完全绕过校验 | 🟠 P1 |
| 销售出库审核 | 1→3 | ✅ `auditWithGuard`，且先改状态后联动 | 安全（联动部分见第三节） |

| 收款/付款单 | 固定置 '1'，无作废接口 | ⚠️ 无状态机可言，无红冲能力 | 🟡 P2 |

## 十、结语

凭证审核的 `auditWithGuard` 证明团队是懂乐观并发控制的，库存 `stockOut` 的 FOR UPDATE + 增量 upsert 也是正确范式——**但同样的纪律没有贯彻到金额最敏感的收付款核销链路上**。收款/付款核销当前等同于"读快照、心算、盲写"，在双人同时收款、或收款与出库取消并发时，账面金额必然失真且无任何报警。建议按第九节清单 P0 → P1 → P2 顺序推进修复，并在修复后补充并发集成测试（双线程同应收核销断言金额守恒）。
