## 二、P0 资损风险（4 项）

### P0-1 并发收款/付款竞态超收
- **代码位置**：`MesCollectionServiceImpl.java:32-43`、`MesPaymentServiceImpl.java:31-42`
- **现状**：收/付款保存采用"先 `getById` 读应收 → 内存比较 → `updateById`"模式，无 `FOR UPDATE` 锁或乐观锁（销售出库模块有 `selectByIdForUpdate`，收付款模块没有）
- **影响**：两并发请求可同时通过超额校验 → `received_amount` 超累加，`unsettled_amount` 变负数 → **资损实锤**
- **修复**：参照销售出库，加 `selectByIdForUpdate` 行锁；或用 `UPDATE ... WHERE unsettled_amount >= #{amount}` 原子守护

### P0-2 收付款无作废/红冲机制
- **现状**：`status` 字段定义了"0已作废"但全系统无任何代码设置它；Controller 只暴露 add/list/export
- **影响**：录错金额无法冲正，已累加到应收/应付的金额永久无法回滚
- **修复**：补作废 API + 联动回滚应收/应付的 `received_amount`/`paid_amount`/`unsettled_amount`

### P0-3 凭证批量删除绕过状态校验
- **代码位置**：`MesVoucherController.java:43`
- **现状**：`deleteBatch` 直接调 `service.removeByIds`（不走 `removeWithItems` 的"非草稿禁止删除"校验）
- **影响**：已审核凭证可被批量删除，审计链断裂
- **修复**：`deleteBatch` 走 `removeWithItems` 或在 Controller 层校验每行状态

### P0-4 销售出库 cancel 红冲破坏应收数据
- **代码位置**：`MesSalesOutboundServiceImpl.java:142-168`
- **现状**：`cancel` 把应收单 `setStatus("3")` 但不校验是否已有收款、不回滚 `receivedAmount/unsettledAmount`
- **影响**：已部分收款的出库单被红冲后：库存退了、应收显示"已结清"、收款单里的钱还在 → **账实三方不一致**
- **修复**：cancel 前校验应收单 `receivedAmount > 0` 时禁止红冲；或联动冲销收款

## 三、P1 精度/一致性（3 项）

### P1-1 收款金额未 `setScale(2, HALF_UP)` 归一化
- **现状**：前端可传 100.005，Java 校验/累加用原始精度，落库 `DECIMAL(18,2)` 时 MySQL 舍入
- **影响**：多次部分收款后 Σcollection.amount ≠ receivable.received_amount，分分钱差
- **修复**：在 `MesCollectionServiceImpl.save` 入口对 amount 做 `setScale(2, HALF_UP)`

### P1-2 前端凭证合计用 JS Number 浮点累加
- **代码位置**：`VoucherDrawer.vue:51-52`
- **现状**：`drTotal/crTotal` 用 `reduce(Number).toFixed(2)`，浮点误差可致平衡误判
- **影响**：后端校验兜底，资损风险低但精度违规，可能误导用户
- **修复**：用 decimal.js 或后端校验结果回填

### P1-3 凭证与业务完全脱节
- **现状**：收款/付款不生成凭证，凭证纯手工录入，`source_bill_id` 字段闲置；无科目余额表，审核仅翻转状态，"已过账"状态无实现
- **影响**：财务账与业务账无核对机制，凭证可能成为"孤儿账"
- **修复**：① 短期：凭证补 `source_type`/`source_bill_id` 关联收款/付款单；② 长期：收款/付款审核时自动生成凭证

## 四、P2 合规/健壮性（4 项）

### P2-1 制单与审核同权限
- **现状**：`audit` 用 `mes:voucher:edit`，无职责分离，不校验审核人≠制单人
- **修复**：拆权限 `mes:voucher:audit`，审核人≠制单人校验

### P2-2 收款单/凭证新增未捕获 `DuplicateKeyException`
- **现状**：并发/重复单号抛 500 而非友好提示
- **修复**：参照销售出库 `try-catch DuplicateKeyException → JeecgBootException("单号已存在")`

### P2-3 允许不关联应收单的"游离收款"
- **现状**：`receivableId` 可空，资金无去向跟踪，无预收款机制
- **修复**：`receivableId` 必填，或补预收款机制（关联客户不关联单）

### P2-4 状态机边界检查
- **现状**：`0<new<amount→"2" 否则"3"` 边界正确（金额>0 已拦截零值）
- **评价**：✅ 已正确处理

## 七、总结

**P0=4 / P1=3 / P2=4（含 1 项 ✅）**

最致命的是 **P0-1 并发竞态超收** 和 **P0-2 收付款无作废**——前者会导致资损实锤，后者让任何录入错误都变成永久伤害。两者叠加，意味着这个收付款模块**不能上生产**。

凭证侧最严重的是 **P0-3 批量删除绕过校验**，审计链一旦断裂，财务合规直接失败。
