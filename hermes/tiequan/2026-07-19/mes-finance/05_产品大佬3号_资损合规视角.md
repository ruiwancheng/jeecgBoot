## 一、结论摘要

| 等级 | 数量 | 核心结论 |
|------|------|----------|
| P0 资损 | **2** | 应付单金额永远为 0；销售出库单价取 `get(0)` 同物料多行错价 |
| P1 合规/资损隐患 | **5** | 应收/应付无 source_bill_id 唯一约束可被恶意/异常重复生成；销售端税额全链路缺失；科目删除未校验凭证引用；单价 DECIMAL(18,2) 精度不够；账期/到期日硬编码 30 天 |
| P2 数据一致性 | **3** | 应收应付缺少结算 API 状态永远"未结清"；库存台账 bizId 用 code 不用 id；AR/AP 单号可因删除复活撞单号 |

**一句话结论：** 应付模块当前是**废的**（金额=0），应收模块存在**重复生成、错价、漏税**三大隐患，整个业财联动尚不具备投产条件。

## 二、P0 资损（必须立即修复）

### P0-01：采购入库自动生成应付单金额 = 0（直接资损）

**位置：** `MesPurchaseReceiptServiceImpl.java:125-138`

```java
String apCode = "AP-" + ... + e.getCode();
MesPayable ap = new MesPayable();
ap.setAmount(java.math.BigDecimal.ZERO); // MVP: 金额待采购价格模块完善后自动计算
ap.setPaidAmount(java.math.BigDecimal.ZERO);
ap.setUnsettledAmount(java.math.BigDecimal.ZERO);
...
payableService.save(ap);
```

**问题：**
- 采购订单行已经有 `unitPrice / quantity / amount / taxRate`，采购订单表已经有 `totalAmount / taxAmount / totalWithTax`（见 `MesPurchaseOrderServiceImpl.calcTotal`），**数据完全可用**，但应付单生成时**完全没取**。
- 结果：应付单 amount=0、unsettled=0、paid=0 —— 财务对账时永远显示"不欠供应商钱"，**任何一笔真实采购都形成资损**（钱照付、账上不显示）。
- 合规上等于伪造应付数据。

**修复建议：**
按 `receiptQuantity` 与 `purchaseOrderItem.unitPrice` 计算实际应付金额（含税），并按订单税率分离税额。建议取 `order.totalWithTax * (本次累计入库量 / 订单总量)` 或逐行 `receiptQty * unitPrice * (1+taxRate)` 累加。

### P0-02：销售出库取单价用 `get(0)`，同物料多行订单错价

**位置：** `MesSalesOutboundServiceImpl.java:222-231`

```java
if (StringUtils.hasText(e.getSalesOrderId())) {
    LambdaQueryWrapper<MesSalesOrderItem> oiQw = new LambdaQueryWrapper<>();
    oiQw.eq(MesSalesOrderItem::getOrderId, e.getSalesOrderId())
       .eq(MesSalesOrderItem::getMaterialId, item.getMaterialId());
    java.util.List<MesSalesOrderItem> orderItems = salesOrderItemMapper.selectList(oiQw);
    if (!orderItems.isEmpty() && orderItems.get(0).getUnitPrice() != null) {
        item.setUnitPrice(orderItems.get(0).getUnitPrice());
    }
}
```

**问题：**
- 同一销售订单中**允许同物料出现多行**（不同批次/规格/让利价），这里 `get(0)` 只取第一行的单价。
- 实际企业场景：销售订单同物料不同价极常见（首单优惠、阶梯价、搭赠）。出库单一旦命中非首行，应收金额就错。
- 错误金额会一路传染：`item.amount → totalAmount → receivable.amount / unsettledAmount`，**直接形成应收资损或客户纠纷**。

**修复建议：**
- 严格做法：出库单行必须显式指定 `salesOrderItemId`（不是仅 materialId），按行维度回源取价。
- 兜底：若同物料多行，抛异常要求前端选择行号，禁止默认取 `get(0)`。

## 三、P1 合规 / 资损隐患

### P1-01：应收/应付缺 `source_bill_id` 唯一约束，可被重复生成

**位置：** `V9.0.0__mes_finance_init.sql:50, 77`（唯一索引只覆盖 `code`），`MesSalesOutboundServiceImpl.audit:118-134`、`MesPurchaseReceiptServiceImpl.audit:124-139`

**问题：**
- 表结构只有 `uk_rec_code_del (code, del_flag)`，**没有 `(source_bill_id, del_flag)` 唯一约束**。
- 虽然 `auditWithGuard` 保护了 audit 不被二次触发，但**这只是应用层保护**：
  - DBA 手工修数据、后台脚本误调 `receivableService.save`、未来新增的"补单"接口都绕过保护。
  - 删除应收单后（del_flag=1），再次审核出库单会因 `code` 已被占用导致 audit 整体回滚（见 P1-05）。
- 没有任何代码路径校验 `source_bill_id` 是否已存在应收/应付。

**修复建议：**
```sql
ALTER TABLE c_mes_receivable ADD UNIQUE INDEX uk_rec_source (source_bill_id, del_flag);
ALTER TABLE c_mes_payable  ADD UNIQUE INDEX uk_pay_source (source_bill_id, del_flag);
```
并在 service 层加 `existsBySourceBillId` 预检查，捕获重复时明确报错而不是依赖唯一索引爆炸。

### P1-02：销售端税额全链路缺失，应收是否含税口径不明

**位置：** `MesSalesOrder` / `MesSalesOrderItem` 实体无 `taxRate/taxAmount/totalWithTax`；`MesSalesOutboundServiceImpl.calcTotal`；`MesReceivable.amount`

**问题：**
- 采购订单行有 `tax_rate (DECIMAL(5,2) DEFAULT 0.13)`，主表有 `tax_amount / total_with_tax` —— 采购端税务合规 OK。
- **销售端没有任何税率字段**：销售订单行只算 `quantity * unitPrice = amount`，主表 `totalAmount` 即"未含税总额"或"已含税总额"无从区分。
- 应收单 `amount = e.getTotalAmount()`，**财务无法知道这笔应收是含税还是不含税**。
- 中国企业开具增值税发票必须价税分离，应收与发票必须能核对，目前**完全无法核对**。

**修复建议：**
- 销售订单行/主表补齐 `taxRate / taxAmount / totalWithTax`（镜像采购订单）。
- 应收单按 `totalWithTax` 入账，并新增 `taxAmount` 字段。
- 出库单明细同步补齐 `taxRate`，取价时继承销售订单行税率。

### P1-03：会计科目删除未校验"是否被凭证/应收应付/凭证明细引用"

**位置：** `MesAccountSubjectServiceImpl.java:70-78`

```java
public boolean removeById(java.io.Serializable id) {
    LambdaQueryWrapper<MesAccountSubject> qw = new LambdaQueryWrapper<>();
    qw.eq(MesAccountSubject::getParentId, id);
    if (baseMapper.selectCount(qw) > 0) throw new JeecgBootException("该科目下存在子科目，无法删除");
    return super.removeById(id);
}
```

**问题：**
- 只校验子科目，**完全未校验** `c_mes_voucher_item.subject_id`。
- 删除已被凭证使用的科目 → 凭证明细 `subject_id` 指向不存在/已删除科目 → 财务报表/余额表必然错乱，年末审计直接翻车。
- 未来应收/应付单大概率也要挂"应收科目/应付科目"，同样要预校验。

**修复建议：**
```java
LambdaQueryWrapper<MesVoucherItem> viQw = new LambdaQueryWrapper<>();
viQw.eq(MesVoucherItem::getSubjectId, id);
if (voucherItemMapper.selectCount(viQw) > 0)
    throw new JeecgBootException("科目已被凭证引用，禁止删除，建议停用");
```
并且科目应优先走"停用"（status=0）而非物理/逻辑删除。

### P1-04：单价 DECIMAL(18,2) 精度不够，长尾物料失真

**位置：** `V3.0.0__mes_sales_order_init.sql:33`、`V6.0.1__mes_purchase_order_init.sql:37`、`V8.0.0__mes_sales_amount_fields.sql:18`

```sql
unit_price DECIMAL(18,2)   -- 全部模块
quantity   DECIMAL(18,4)
amount     DECIMAL(18,2)
```

**问题：**
- 化工/五金/大宗散料/电子料行业，**单价 0.0005、0.0125 元极常见**（电阻电容按厘/毫报价）。
- `DECIMAL(18,2)` 截断后 `0.0005 → 0.00`，`0.0125 → 0.01`（四舍五入），单价直接归零或错 25%。
- 数量 `quantity DECIMAL(18,4)` 精度是够的，但单价先死，金额 = qty × 单价 永远无法还原真实值。
- 业界通用做法：`unit_price DECIMAL(18,6)` 或 `(20,8)`，金额仍 `DECIMAL(18,2)`。

**修复建议：**
```sql
ALTER TABLE c_mes_sales_order_item    MODIFY unit_price DECIMAL(18,6);
ALTER TABLE c_mes_purchase_order_item MODIFY unit_price DECIMAL(18,6);
ALTER TABLE c_mes_sales_outbound_item MODIFY unit_price DECIMAL(18,6);
ALTER TABLE c_mes_delivery_note_item  MODIFY unit_price DECIMAL(18,6);
-- amount 仍 DECIMAL(18,2)，乘完后 setScale(2, HALF_UP)
```

### P1-05：账期 30 天 / 到期日硬编码，客户/供应商级信用配置未接入

**位置：** `MesSalesOutboundServiceImpl.java:130-131`、`MesPurchaseReceiptServiceImpl.java:135-136`

```java
ar.setCreditPeriod(30);
ar.setDueDate(new Date(now.getTime() + 30L * 86400000));
```

**问题：**
- 信用期是企业风控关键参数（KA 客户 60/90 天、小客户款到发货），硬编码 30 天 = **信用政策完全失效**。
- `now + 30*86400000` 不考虑节假日 / 账期起算日（货到 vs 票到 vs 月结），实际企业月结 30 天是从月底起算，**到期日计算错误会导致催收时点错误**。
- `c_mes_customer` / `c_mes_supplier` 主数据如果有 `credit_period` 字段（需确认），未被使用。

**修复建议：**
- 客户/供应商主数据加 `credit_period` / `settle_type`（货到/票到/月结）。
- 应收/应付生成时从主数据读，主数据缺失才 fallback 30 天。
- 到期日应按 settle_type 走不同算法。

## 四、P2 数据一致性 / 可追溯性

### P2-01：应收/应付无结算 API，状态机死锁

**位置：** `MesReceivableController.java` / `MesPayableController.java` 只有 `list/queryById/queryAll/exportXls`

**问题：**
- 没有 `receive / pay / settle` 接口，`received_amount / unsettled_amount / status / settlement_date` 永远停在初始值。
- 意味着应收应付模块**当前不可用于实战**，只能算"展列"。
- 短期看不是 Bug，但需在 PRD/路线图明确，**否则财务一旦用起来数据全错**。

---

### P2-02：库存台账 bizId 用业务单号 code，跨模块 join 不可靠

**位置：** `MesInventoryServiceImpl.stockIn / stockOut`；调用方 `MesSalesOutboundServiceImpl.audit:111` / `MesPurchaseReceiptServiceImpl.audit:118`

```java
inventoryService.stockOut(item.getMaterialId(), e.getWarehouseId(), item.getActualQty(), "销售出库", e.getCode());
```

**问题：**
- 传入的是 `e.getCode()`（业务编号字符串），不是 `e.getId()`。
- 业务编号有**复活机制**（删除后同 code 重建，见 `selectDeletedByCode` / `resurrect`），同一 code 可对应多个历史 id。
- 台账后续要反查"这条出库记录对应哪张出库单"时，必须用 code LIKE 匹配 + create_time 排序猜，**审计追溯性弱**。

**修复建议：** `IMesInventoryService.stockIn/Out` 增加 `bizId` 参数为业务主键 id，code 放在 `bizNo` 冗余字段。

---

### P2-03：AR/AP 单号规则 `AR-yyyyMMdd-出库单code` 不抗删除复活

**位置：** `MesSalesOutboundServiceImpl.java:120` / `MesPurchaseReceiptServiceImpl.java:125`

**问题：**
- 单号 = `AR-20260719-出库单code`，跨天重复审核同一出库单（先删除应收再重新审核）会产生 `AR-20260719-xxx` 与 `AR-20260720-xxx` 两条应收，都指向同一 `sourceBillId`。
- 唯一的保险是 `auditWithGuard` + 应收 code 唯一索引 —— 但跨天 code 不冲突。
- 根本解法见 P1-01：给 `source_bill_id` 加唯一约束。

## 五、跨模块数据一致性检查表

| 检查项 | 现状 | 风险 |
|--------|------|------|
| 出库单 `totalAmount` vs 应收单 `amount` | ✅ 一致（直接赋值） | 但上游 totalAmount 本身可能错（P0-02） |
| 应收 `amount` vs `received+unsettled` | ✅ 生成时一致 | 后续无结算 API 维持一致性（P2-01） |
| 采购订单 `totalWithTax` vs 应付单 `amount` | ❌ **完全无关，应付永远 0** | **P0-01** |
| 出库单 `actualQty` vs 库存台账 `outQty` | ✅ 一致（同事务） | — |
| 入库单 `receiptQuantity` vs 库存台账 `inQty` | ✅ 一致（同事务） | — |
| 出库单状态 vs 应收单存在性 | ⚠️ 出库单删除（软删）后应收不会级联删 | 应收成孤儿数据 |
| 入库单状态 vs 应付单存在性 | ⚠️ 同上 | 应付成孤儿数据 |
| 销售订单金额 vs 应收金额 | ⚠️ 订单 ≠ 出库，部分出库时仅按实际出库金额生成应收（合理），但销售订单已关闭后应收仍可新生成（缺校验） | 超订单应收风险 |

## 七、附：金额计算正确性代码片段对比

**正确示例（采购订单，已修复）：**
```java
// MesPurchaseOrderServiceImpl.calcTotal
for (MesPurchaseOrderItem item : entity.getItems()) {
    taxTotal = taxTotal.add(item.getAmount().multiply(rowTaxRate));
}
entity.setTotalAmount(total.setScale(2, RoundingMode.HALF_UP));
entity.setTaxAmount(taxTotal.setScale(2, RoundingMode.HALF_UP));
entity.setTotalWithTax(total.add(entity.getTaxAmount()).setScale(2, RoundingMode.HALF_UP));
```
✅ 逐行金额 × 行税率，支持混合税率；BigDecimal + HALF_UP，未用 double/float。

**错误示例（应付生成）：**
```java
// MesPurchaseReceiptServiceImpl.audit
ap.setAmount(java.math.BigDecimal.ZERO); // MVP: 金额待采购价格模块完善后自动计算
```
❌ 价格数据明明已经存在（采购订单 `unitPrice / totalWithTax`），却写死 0。

**精度风险示例：**
```java
// MesSalesOutboundServiceImpl.validate
item.setAmount(item.getActualQty().multiply(item.getUnitPrice()).setScale(2, RoundingMode.HALF_UP));
```
⚠️ `unitPrice` 来源字段是 `DECIMAL(18,2)`，单价已被截断，乘出来再 setScale(2) 是"精确的错值"。
