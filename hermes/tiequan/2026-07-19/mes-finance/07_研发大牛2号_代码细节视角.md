## 一、总体结论

| 维度 | 评级 | 说明 |
|------|------|------|
| update-begin/end 标记 | ✅ 优秀 | 15/15 个 Java 文件首行尾部均成对出现，嵌套块标记也成对 |
| BigDecimal 使用 | ✅ 良好 | 全部走 `BigDecimal.ZERO`、`new BigDecimal("0.13")`（字符串构造）、`setScale(2, HALF_UP)`，未发现 `new BigDecimal(double)` |
| SQL 注入 | ✅ 安全 | Mapper 注解 SQL 全部 `#{}` 占位符，未发现 `${}`；查询统一走 QueryGenerator |
| N+1 | ⚠️ 一般 | `queryTree()` 一次性 `list()` 后内存拼装（OK）；但 `save()` 父节点回写 / `removeById()` 子节点检查为单条 SQL，目前深度可控；多处 `selectCount + selectById` 串行调用 |
| 数据字典 | ⚠️ 一般 | 后端 `@Dict` 注解 + 前端 `dictCode` 配置齐全；但 `sourceType` 字段为裸字符串（"销售出库"/"采购入库"），未走字典，硬编码散落后端两处 |
| Result 响应 | ✅ 统一 | 所有 Controller 均返回 `Result<T>`，错误走 `Result.error` 或 `JeecgBootException` |
| VO / 实体映射 | 🔴 缺失 | **未定义任何 VO/DTO**，Controller 直接 `@RequestBody MesAccountSubject` 接收实体，等同于把表结构暴露给前端，存在批量赋值（mass assignment）风险 |
| 事务边界 | 🔴 高危 | `audit()` 内顺序为 "扣库存 → 改状态 → 生成应收/应付"，**改状态应在最前**；且 `MesReceivableServiceImpl` / `MesPayableServiceImpl` **完全没有事务方法**，多步写入（未来收款/付款核销）将无原子性保障 |
| 空指针 | ⚠️ 一般 | `parent.getIsLeaf() == 1` 自动拆箱 NPE；`e.getItems()` 若 `queryWithItems` 返回的 items 为 null 时 audit 直接 NPE |
| 字段校验 | 🔴 缺失 | 实体上 **0 个 `@NotNull / @DecimalMin / @Pattern`**，Controller 入口未 `@Validated`，所有校验靠手写 if，遗漏风险大 |
| 异常处理 | ⚠️ 一般 | `getUsername()` 用 try-catch 吞掉 Shiro 异常返回 "system"，掩盖权限上下文异常；Controller 未捕获 `JeecgBootException` 之外异常，依赖全局异常处理 |
| 前端 | ⚠️ 一般 | API 全部裸调 `defHttp`，删除/保存仅 success message，**无 error catch**；字典列仅设置 `dictCode` 但缺 `ellipsis`/`align`，金额列右对齐未配置；table key 用 `id` 无重复风险 |

## 二、P0 级问题（必须立即修复）

### P0-1 【资损风险】应收/应付金额计算事务时序错误
**位置**：
- `MesSalesOutboundServiceImpl.java:100-136`
- `MesPurchaseReceiptServiceImpl.java:112-140`

**问题**：
销售出库 audit 顺序：
```java
// 1. 先原子改状态 ✓ 正确
int rows = baseMapper.auditWithGuard(id, username, now);
// 2. 扣库存 —— OK，状态已改
for (...) inventoryService.stockOut(...);
// 3. 联动发货单
deliveryNoteMapper.updateStatus(...);
// 4. 生成应收 —— 此处若 save 失败，库存已扣但应收单未生成
receivableService.save(ar);
```
采购入库 audit 顺序（**反了**）：
```java
// 1. 先加库存（在改状态之前！）
for (...) inventoryService.stockIn(...);
// 2. 再改状态
int rows = baseMapper.auditWithGuard(id, username, now);
if (rows == 0) throw ...; // 此时库存已加，状态还是草稿，事务回滚 —— OK，但顺序仍不一致
// 3. 生成应付
payableService.save(ap);
```
**两个 audit 的"先扣库存还是先改状态"顺序完全相反**，违反团队一致性铁律。虽然都在同一 `@Transactional` 内可回滚，但：
- 采购入库在库存加完才发现状态已变更会白加一次（回滚补偿 OK，但库存流水日志已写）
- 销售出库"先改状态再扣库存再生成应收"，**若 `receivableService.save` 抛出非 RuntimeException 子类异常或下游 RPC 抖动**——目前 IService.save 是本地调用，OK；但未来的收款核销一旦跨服务，**没有 SAGA 或本地消息表兜底**

**修复建议**：
1. 统一为先改状态 → 再做联动（参考 P0-02 已落地注释 `先改状态再扣库存+联动发货单`）
2. `MesPurchaseReceiptServiceImpl.audit` 把库存循环移到 `auditWithGuard` 之后
3. 应收/应付生成增加防重复校验：`selectCount(source_bill_id = e.getId())` 不为 0 则跳过，避免重试产生重复单

### P0-2 【实体暴露】Controller 直接 @RequestBody 实体
**位置**：`MesAccountSubjectController.java:47, 50`

```java
@PostMapping("/add")
public Result<String> add(@RequestBody MesAccountSubject entity) { service.save(entity); ... }
```

**问题**：
- 前端可任意塞入 `id / createBy / createTime / delFlag / children`，在 `super.save(entity)` 路径上，若前端恶意传入 `id` 会触发 ASSIGN_ID 覆盖（虽 IdType.ASSIGN_ID 会重新生成，但 `createBy/createTime` 不会被 MyBatis-Plus 自动覆盖——取决于 MetaObjectHandler 配置，需复核）
- 当前 `MesAccountSubject` 含 `transient List<MesAccountSubject> children`，序列化时虽跳过，但反序列化若 Jackson 配置不严仍可能注入
- `MesReceivable` / `MesPayable` 暂未暴露 add/edit，**未来加上时必须建 VO**

**修复建议**：
```java
public class MesAccountSubjectVO {
    @NotBlank(message = "科目编码不能为空")
    @Size(max = 50) @Pattern(regexp = "^[0-9A-Za-z.-]+$")
    private String code;
    @NotBlank private String name;
    @NotBlank private String category;
    @Min(1) @Max(9) private Integer level;
    private String parentId;
    @Pattern(regexp = "^[12]$") private String balanceDirection;
    @Pattern(regexp = "^[01]$") private String status;
    @Size(max = 500) private String remark;
}
// Controller 用 BeanUtils.copyProperties(vo, entity) 显式字段拷贝
```

### P0-3 【校验缺失】零 JSR-303 注解
**位置**：3 个实体类全字段

**问题**：
```java
// MesReceivable.java:35
@Excel(name = "应收金额", width = 15) @Schema(description = "应收金额") private BigDecimal amount;
// ❌ 缺 @DecimalMin("0.00") @Digits(integer=17, fraction=2)
```

应收金额、已收金额、未结金额、应付金额、已付金额、未付金额 6 个金额字段全部无校验。当前 Controller 也未 `@Validated` 触发校验，等于两道防线都没建。`MesAccountSubjectServiceImpl#validate` 手写校验了 code/name/category，但 `balanceDirection`、`status`、`level` 完全未校验，可写入任意值（如 `balanceDirection="999"`）。

**修复建议**：
- 实体字段加 `@DecimalMin(value="0", inclusive=true)` / `@Digits(integer=17, fraction=2)` / `@Pattern` / `@Size(max=500)`
- Controller `@PostMapping` / `@PutMapping` 参数加 `@Validated @RequestBody`
- 状态字段后端枚举白名单校验（参考 `MesPurchaseReceiptServiceImpl#validateReceipt` 中 qcResult 的白名单做法）

### P0-4 【事务缺失】Receivable/Payable Service 零事务方法
**位置**：`MesReceivableServiceImpl.java`、`MesPayableServiceImpl.java`

**问题**：
```java
@Service
public class MesReceivableServiceImpl extends ServiceImpl<MesReceivableMapper, MesReceivable> implements IMesReceivableService {
}  // ← 空实现，没有任何事务方法
```

虽然 `audit` 中由上游 `MesSalesOutboundServiceImpl#audit` 的 `@Transactional` 传播覆盖（同一线程同一事务），但：
- 未来增加"收款核销"（receivable.receivedAmount += x, unsettledAmount -= x, 写流水表）时，若忘了加事务，**金额三段式更新将无原子性**
- 当前 `selectDeletedByCode + resurrect` 在 `MesAccountSubjectServiceImpl#save` 已有事务保护，但 Receivable/Payable Mapper 也定义了相同方法却**从未在 Service 中编排**，疑似半成品

**修复建议**：
- 在 `IMesReceivableService` 增加 `void receive(String id, BigDecimal amount)` 方法，ServiceImpl 用 `@Transactional(rollbackFor=Exception.class)` + 乐观锁（`update ... where id=#{id} and unsettled_amount >= #{amount}`）
- 同上对 IMesPayableService

## 三、P1 级问题（本迭代内修复）

### P1-1 【NPE】`parent.getIsLeaf() == 1` 自动拆箱
**位置**：`MesAccountSubjectServiceImpl.java:46`

```java
if (parent != null && parent.getIsLeaf() == 1) {  // ← isLeaf 为 Integer，DB 中可为 NULL
    parent.setIsLeaf(0); super.updateById(parent);
}
```
若老数据 `is_leaf` 为 NULL，`parent.getIsLeaf()` 返回 null，`null == 1` 触发 `NullPointerException`。

**修复**：`if (parent != null && Integer.valueOf(1).equals(parent.getIsLeaf()))`

### P1-2 【NPE】audit 中 `e.getItems()` 未判空
**位置**：`MesSalesOutboundServiceImpl.java:110`、`MesPurchaseReceiptServiceImpl.java:117`

```java
for (MesSalesOutboundItem item : e.getItems()) { ... }
```
`queryWithItems` 内部 `selectById` 后用 `LambdaQueryWrapper` 查 items；如果明细表数据被物理删除或 items 为 null，`for-each` 直接 NPE。

**修复**：循环前 `if (e.getItems() == null || e.getItems().isEmpty()) throw new JeecgBootException("出库单明细为空，禁止审核");`

### P1-3 【硬编码】sourceType 字符串散落各处
**位置**：
- `MesSalesOutboundServiceImpl.java:124` → `ar.setSourceType("销售出库")`
- `MesPurchaseReceiptServiceImpl.java:129` → `ap.setSourceType("采购入库")`

**问题**：
- 中文硬编码进 DB，前端展示时无法走字典翻译
- 后续新增"完工入库→应收"、"退货→应付红字"会继续散落

**修复**：建数据字典 `mes_finance_source_type`，后端用常量类 `FinanceSourceTypeEnum.SALES_OUTBOUND.getCode()`，实体字段加 `@Dict(dicCode="mes_finance_source_type")`。

### P1-4 【硬编码】账期/到期日魔法数字
**位置**：
- `MesSalesOutboundServiceImpl.java:130-131`
- `MesPurchaseReceiptServiceImpl.java:135-136`

```java
ar.setCreditPeriod(30);
ar.setDueDate(new Date(now.getTime() + 30L * 86400000));
```

**问题**：
- 30 天账期写死，应来自客户/供应商主数据的 `creditPeriod` 字段
- `86400000` 魔法数字，跨夏令时/时区会漂移
- `new Date(now.getTime() + 30L * 86400000)` 不严谨，应该用 `LocalDate.now().plusDays(30)`

**修复**：
```java
MesCustomer customer = customerMapper.selectById(e.getCustomerId());
int period = customer != null && customer.getCreditPeriod() != null ? customer.getCreditPeriod() : 30;
ar.setCreditPeriod(period);
ar.setDueDate(Date.from(LocalDate.now().plusDays(period).atStartOfDay(ZoneId.systemDefault()).toInstant()));
```

### P1-5 【SQL 兼容性】`selectDeletedByCode` 用 LIMIT 1
**位置**：3 个 Mapper

```java
@Select("SELECT * FROM c_mes_receivable WHERE code = #{code} AND del_flag = 1 LIMIT 1")
```

**问题**：`LIMIT 1` 是 MySQL 方言，未来切 PG / Oracle 会报错。JeecgBoot 主打 MySQL，但保留兼容性更佳。

**修复**：改 `List<MesReceivable> selectDeletedByCode(String code)` + Service 端 `list.size() > 0 ? list.get(0) : null`，或保留 LIMIT 但加注释说明仅支持 MySQL。

### P1-6 【重复调用】count + list 串行执行
**位置**：3 个 Controller 的 `queryAll` 和 `exportXls`

```java
if (service.count() > QUERY_ALL_MAX) throw new JeecgBootException("...");
return Result.ok(service.list());  // 又扫一遍全表
```

**问题**：先 count 再 list，2 次全表扫描；count 与 list 之间无锁，**理论上 count 通过但 list 时数据已超**。

**修复**：
```java
IPage<MesReceivable> page = service.page(new Page<>(1, QUERY_ALL_MAX + 1));
if (page.getRecords().size() > QUERY_ALL_MAX) throw new JeecgBootException("...");
return Result.ok(page.getRecords());
```
一次查询搞定，O(N) 减半。

### P1-7 【字典设计】status 用 "1" 字符串
**位置**：`MesReceivable#status`、`MesPayable#status`、`MesAccountSubject#status`

**问题**：
- 应收/应付状态用 `"1"` 表示"未结清"，字典 `mes_receivable_status` 维护语义；但 `MesAccountSubject#status` 用 `yn` 字典（"1"/"0"），**两个 status 字段语义完全不同却共用一个字段名**
- 已收/已付金额变化时，状态字段需联动更新（如 receivedAmount >= amount → status = "2"已结清），**目前代码中无此联动逻辑**

**修复**：
- 状态枚举类 `ReceivableStatusEnum { DRAFT("0"), UNSETTLED("1"), PARTIAL("2"), SETTLED("3") }`
- 在收款核销方法中维护状态机

### P1-8 【前端】金额列未右对齐 + 无精度处理
**位置**：`receivable.data.ts:6-8`、`payable.data.ts:6-8`

**问题**：
```ts
{ title: '应收金额', dataIndex: 'amount', width: 120 },
```
- 缺 `align: 'right'`，财务表格习惯右对齐
- 缺自定义 render 做千分位格式化 `1,234,567.89`
- 后端返回 `BigDecimal` 序列化为数字（如 `123.450000000`），前端展示保留多余尾零

**修复**：
```ts
{ 
  title: '应收金额', dataIndex: 'amount', width: 120, align: 'right',
  customRender: ({ text }) => text == null ? '-' : Number(text).toLocaleString('zh-CN', { minimumFractionDigits: 2, maximumFractionDigits: 2 })
}
```

### P1-9 【前端】删除/保存无错误兜底
**位置**：`subject/index.vue:53`、`SubjectDrawer.vue:22-27`

```ts
async function handleDelete(record: Recordable) { 
  await deleteSubject({ id: record.id }); 
  message.success('删除成功'); 
  reload(); 
}
```

**问题**：`deleteSubject` 失败时 throw 会被 `defHttp` 全局拦截，但 `message.success` 仍会执行（除非 defHttp 内部 reject——需复核）；删除失败后误提示"删除成功"是典型 UX bug。

**修复**：
```ts
async function handleDelete(record: Recordable) {
  try {
    await deleteSubject({ id: record.id });
    message.success('删除成功');
    reload();
  } catch (e) { /* defHttp 已 toast，无需重复 */ }
}
```

### P1-10 【字典复用】前端字典 key 散落
**位置**：`subject.data.ts`、`receivable.data.ts`、`payable.data.ts`

**问题**：`mes_subject_category / mes_balance_direction / mes_receivable_status / mes_payable_status / yn` 直接以字符串字面量出现 6+ 次，改字典 code 时漏改风险。

## 四、P2 级问题（关注即可）

### P2-1 【注释格式】update-begin 日期格式不一致
**位置**：所有 update 标记
```
//update-begin---author:ruiwancheng---date:2026-07-19---for: Phase2 Step3 ...
//update-end---author:ruiwancheng---date:2026-07-19---for: ...
```
✅ begin/end 成对，作者、日期、原因齐全，符合项目铁律。但部分早期标记（`MesSalesOutboundServiceImpl.java:1`）日期为 `2026-07-15`，跨多日的累积修改集中在一个文件，建议未来按"一次提交一对标记"原则。

### P2-2 【Swagger】@Tag 描述不统一
- `MesReceivableController` → `MES-应收账款`
- `MesPayableController` → `MES-应付账款`
- `MesAccountSubjectController` → `MES-会计科目`
建议统一前缀 `MES-业财-xxx`。

### P2-3 【导入】通配符 import
**位置**：3 个 Controller + SubjectServiceImpl
```java
import java.util.*;
import java.util.stream.Collectors;
```
实际只用了 `Arrays, List` 等少量类，建议显式导入便于静态分析。

### P2-4 【entity 设计】@EqualsAndHashCode(callSuper = false)
**位置**：3 个实体
实体没继承基类，`callSuper = false` 冗余但无害。建议未来提取 `BaseMesEntity` 抽象基类承载 `id/createBy/createTime/updateBy/updateTime/delFlag`，避免重复字段。

### P2-5 【并发】code 唯一约束依赖 DB
`checkCodeDuplicate` 先 selectCount 再 save 存在 TOCTOU 竞态，唯一约束兜底在 DB（依赖 `uk_code` 唯一索引），代码已 catch `DuplicateKeyException`，**可接受**，但建议在 `code` 字段 `@TableField` 上注释说明 DB 层有唯一索引。

### P2-6 【工具类】`getUsername()` 重复实现
**位置**：`MesAccountSubjectServiceImpl#getUsername`、`MesSalesOutboundServiceImpl#getUser`、`MesPurchaseReceiptServiceImpl#getCurrentUsername`
3 处几乎相同的方法，应提取到 `MesBaseService` 基类或 `SecurityUtils` 工具类。

### P2-7 【树形查询】queryTree 全量加载
`MesAccountSubjectServiceImpl#queryTree` 一次 `list()` 加载全表 + 内存分组，**当前科目数 < 1000 可接受**，超过 5000 需改递归 SQL 或懒加载。

### P2-8 【审计字段】Resurrect 未清空 createBy/createTime
**位置**：`MesAccountSubjectServiceImpl.java:54-56`
```java
entity.setId(old.getId()); entity.setCreateBy(old.getCreateBy()); entity.setCreateTime(old.getCreateTime());
```
✅ 保留了原创建人和创建时间，这是合理的。但 `MesReceivable` / `MesPayable` 的 Mapper 中也有 `resurrect`，**当前 Service 中并未编排调用**，是死代码——要么删除，要么补全 Service 端的"删后重建"逻辑。

### P2-9 【前端】rowKey 与 dataIndex 重复
3 个 `index.vue` 都用 `rowKey: 'id'`，列定义中无 `dataIndex: 'id'`，✅ 无重复 key 风险。但 `subject.data.ts` 中 `code` 设置了 `sorter: true`，会触发后端排序，但后端 `MesAccountSubjectController#queryPageList` 中固定 `qw.orderByAsc("code")`，前端 sorter 失效——**前后端排序语义冲突**。

### P2-10 【前端】缺少批量删除按钮
`MesAccountSubjectController#deleteBatch` 已暴露，但前端 `subject/index.vue` 未注册批量删除按钮（仅行内删除），权限 `mes:subject:deleteBatch` 实际无用武之地。

## 十、亮点（值得肯定的实践）

1. **update-begin/end 标记 100% 合规**，包含 author/date/for 三要素，团队铁律执行到位
2. **BigDecimal 全部走字符串构造或常量**，未发现 `new BigDecimal(0.13)` 这类精度陷阱
3. **audit 改状态用 `auditWithGuard` 原子 UPDATE**，利用影响行数判断并发冲突，避免 select-then-update 竞态
4. **删除前子节点检查**（`MesAccountSubjectServiceImpl#removeById`）防止误删父科目
5. **删除重建逻辑**（`selectDeletedByCode + resurrect`）保留审计字段，符合财务数据合规要求
6. **金额计算用 `setScale(2, HALF_UP)`** 在 `calcTotal` 中已落地
7. **数据字典使用规范**，@Dict 注解 + Excel 注解 dictCode/dictTable 双写
8. **QUERY_ALL_MAX = 5000 兜底**，防止 queryAll/export 拉爆内存
9. **重复编码捕获 `DuplicateKeyException`** 转业务异常，DB 唯一索引 + 应用层校验双保险
10. **Shiro `@RequiresPermissions` 全覆盖** Controller 方法，权限粒度到按钮级
