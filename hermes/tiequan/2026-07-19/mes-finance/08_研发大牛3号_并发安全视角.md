## 二、总体结论（TL;DR）

| 维度 | 评价 | 风险等级 |
|---|---|---|
| `auditWithGuard` 状态原子更新 | 实现正确，乐观锁思想 | ✅ 低 |
| 库存扣减（stockOut） | 行锁 + 原子 UPSERT，但 stockIn 无锁 | 🟡 中 |
| 库存入库（stockIn） | 无 `FOR UPDATE`，先查后写，并发丢失更新 | 🔴 **高** |
| 应收/应付 code 幂等 | 日期+单号有唯一索引，但无业务幂等查询 | 🟡 中 |
| 并发审核同一单据 | `auditWithGuard` 拦截，但无数据库唯一约束兜底 | 🟡 中 |
| 事务传播（生成应收失败回滚出库状态） | 同事务内，可回滚 | ✅ 低 |
| 跨模块分布式锁 | 完全缺失，库存/发货单/订单无统一锁 | 🔴 **高** |
| 库存扣减与应收生成原子性 | 同事务，但应收生成失败导致库存回滚，业务语义危险 | 🟡 中 |
| 死锁风险 | 多物料行锁顺序不一致，存在交叉死锁可能 | 🟡 中 |

## 三、分项审计

### 3.1 `auditWithGuard` 实现细节

#### 3.1.1 销售出库（MesSalesOutboundServiceImpl）

```java
// MesSalesOutboundMapper.java:20-21
@Update("UPDATE c_mes_sales_outbound SET status = '3', update_by = #{updateBy}, update_time = #{updateTime} WHERE id = #{id} AND status = '1'")
int auditWithGuard(@Param("id") String id, @Param("updateBy") String updateBy, @Param("updateTime") Date updateTime);
```

**Service 层调用顺序**（L100-136）：
1. `queryWithItems` 查出库单 + 明细
2. 内存判断 `status = '1'`
3. 先调 `auditWithGuard` 原子改状态（1→3）
4. 逐行 `inventoryService.stockOut(...)` 扣库存
5. 联动 `deliveryNoteMapper.updateStatus(...)` 改发货单状态（2→3）
6. 生成应收单 `receivableService.save(ar)`

**评价**：
- `auditWithGuard` 使用 `WHERE id = ? AND status = '1'` 是标准的乐观锁/CAS 模式，能防止并发审核同一单据时两个线程都通过内存校验后同时改状态。 ✅
- 但**步骤 3 和步骤 4 之间没有数据库唯一约束兜底**。如果两个线程同时进入 `audit()`，线程 A 的 `auditWithGuard` 成功，线程 B 的 `auditWithGuard` 返回 0 并抛异常，这是正确的。 ✅
- 真正的问题在**库存扣减与应收生成的耦合**：如果 `receivableService.save(ar)` 失败（如唯一索引冲突），整个事务回滚，包括已扣减的库存。这会导致"库存已扣但出库单状态回滚"的假象。实际上因为同事务，库存也会回滚，但**业务上库存扣减和应收生成是硬耦合**，应收生成失败会拖累库存操作。见 §3.6。

#### 3.1.2 采购入库（MesPurchaseReceiptServiceImpl）

```java
// MesPurchaseReceiptMapper.java:20-21
@Update("UPDATE c_mes_purchase_receipt SET status = '2', update_by = #{updateBy}, update_time = #{updateTime} WHERE id = #{id} AND status = '1'")
int auditWithGuard(@Param("id") String id, @Param("updateBy") String updateBy, @Param("updateTime") Date updateTime);
```

**Service 层调用顺序**（L112-140）：
1. `queryWithItems` 查入库单 + 明细
2. 内存判断 `status = '1'`
3. **先逐行 `inventoryService.stockIn(...)` 加库存**
4. 再调 `auditWithGuard` 原子改状态（1→2）
5. 生成应付单 `payableService.save(ap)`

**⚠️ 关键差异**：与销售出库相反，这里是**先加库存再改状态**。

**风险分析**：
- 线程 A 执行 `stockIn` 成功，但尚未执行 `auditWithGuard`。
- 线程 B 同时进入，也执行 `stockIn` 成功。
- 线程 A 执行 `auditWithGuard` 成功（状态 1→2）。
- 线程 B 执行 `auditWithGuard` 返回 0（状态已是 2），抛异常回滚。

**结果**：线程 B 的 `stockIn` 回滚，但线程 A 的 `stockIn` 已提交。库存只加了一次，看似正确。

**但存在另一种竞态**：
- 如果 `stockIn` 内部抛出异常（如库存不足，但入库不会不足），或者 `stockIn` 成功但 `auditWithGuard` 之前 JVM 崩溃，则库存已加但状态未改。由于 `stockIn` 也是 `@Transactional`，且与 `audit()` 在同一事务中，实际上会一起回滚。 ✅

**真正的问题**：`stockIn` 本身没有行锁，见 §3.2。

#### 3.1.3 生产领料/完工入库（对照）

```java
// ProductionPickingServiceImpl.java L120-126
for (...) { inventoryService.stockOut(...); }
int rows = baseMapper.auditWithGuard(id, username, now);
```

```java
// CompletionReceiptServiceImpl.java L120-126
for (...) { inventoryService.stockIn(...); }
int rows = baseMapper.auditWithGuard(id, username, now);
```

**模式**：生产领料先扣库存再改状态；完工入库先加库存再改状态。
**风险**：与采购入库相同，`stockIn` 无锁导致并发入库时可能超量/丢失更新。

### 3.2 库存扣减与入库的锁机制

#### 3.2.1 `stockOut`（销售出库/生产领料）

```java
// MesInventoryServiceImpl.java L45-58
@Transactional(rollbackFor = Exception.class)
public void stockOut(String materialId, String warehouseId, BigDecimal qty, String bizType, String bizId) {
    // 行锁查当前库存
    MesInventory inv = inventoryMapper.selectForUpdate(materialId, warehouseId);
    BigDecimal before = inv != null ? inv.getCurrentQty() : BigDecimal.ZERO;
    if (before.compareTo(qty) < 0) throw new JeecgBootException("库存不足");
    BigDecimal after = before.subtract(qty);
    String id = inv != null ? inv.getId() : UUID.randomUUID().toString().replace("-", "");
    inventoryMapper.upsertWithDelta(id, materialId, warehouseId, before, qty.negate(), username, username);
    writeLedger(...);
}
```

```java
// MesInventoryMapper.java L14-18
@Select("SELECT * FROM c_mes_inventory WHERE material_id = #{materialId} AND warehouse_id = #{warehouseId} FOR UPDATE")
MesInventory selectForUpdate(@Param("materialId") String materialId, @Param("warehouseId") String warehouseId);

@Update("INSERT INTO c_mes_inventory (id, material_id, warehouse_id, current_qty, ...) VALUES (#{id}, #{materialId}, #{warehouseId}, #{currentQty}, ...) ON DUPLICATE KEY UPDATE current_qty = current_qty + #{delta}, ...")
int upsertWithDelta(...);
```

**评价**：
- `SELECT ... FOR UPDATE` 对 `(material_id, warehouse_id)` 加行锁，防止并发扣减同一物料同一仓库。 ✅
- `upsertWithDelta` 使用 `ON DUPLICATE KEY UPDATE current_qty = current_qty + delta`，是原子操作。 ✅
- 但注意：如果 `inv == null`（新物料），`selectForUpdate` 不会锁任何行，两个并发线程都查到 `null`，都执行 INSERT，依赖 `uk_inv_material_wh` 唯一索引兜底，第二个线程会抛 `DuplicateKeyException`。由于 `stockOut` 在 `audit()` 事务内，会触发整个审核回滚。 ✅ 可接受。

#### 3.2.2 `stockIn`（采购入库/完工入库）

```java
// MesInventoryServiceImpl.java L27-41
@Transactional(rollbackFor = Exception.class)
public void stockIn(String materialId, String warehouseId, BigDecimal qty, String bizType, String bizId) {
    // 查或建库存快照
    MesInventory inv = findByMaterialAndWarehouse(materialId, warehouseId);  // ❌ 无 FOR UPDATE
    BigDecimal before = inv != null ? inv.getCurrentQty() : BigDecimal.ZERO;
    BigDecimal after = before.add(qty);
    String id = inv != null ? inv.getId() : UUID.randomUUID().toString().replace("-", "");
    inventoryMapper.upsertWithDelta(id, materialId, warehouseId, before, qty, username, username);
    writeLedger(...);
}
```

**🔴 严重问题**：
1. `findByMaterialAndWarehouse` 使用普通 `selectOne`，**没有 `FOR UPDATE`**。
2. 两个并发线程同时执行 `stockIn`：
   - 线程 A 查到 `current_qty = 100`，计算 `after = 150`。
   - 线程 B 查到 `current_qty = 100`，计算 `after = 150`。
   - 线程 A 执行 `upsertWithDelta`：`current_qty = 100 + 50 = 150`。
   - 线程 B 执行 `upsertWithDelta`：`current_qty = 150 + 50 = 200`。
   - 结果 `current_qty = 200`，但正确应为 `200`（100+50+50）。**这个例子看似正确，因为 `ON DUPLICATE KEY UPDATE` 是原子的**。

**等等，再仔细分析**：
- `upsertWithDelta` 的 SQL 是 `current_qty = current_qty + #{delta}`，**不依赖 Java 层查到的 `before`**。
- 所以即使两个线程都查到 `before = 100`，最终 `current_qty` 也是 `100 + 50 + 50 = 200`，结果正确。
- `writeLedger` 中的 `beginningQty` 和 `endingQty` 会不准确（两个线程都写 `beginning=100, ending=150`），但台账是流水，不影响库存余额。

**但仍有风险**：
- 如果 `inv == null`（新物料），两个线程都执行 INSERT，依赖唯一索引兜底，第二个抛异常回滚。 ✅
- `stockIn` 的 `before` 用于写台账，并发时台账的 `beginningQty`/`endingQty` 会错乱，但不影响库存余额正确性。

**结论**：`stockIn` 的库存余额在并发下**最终是正确的**（得益于 `ON DUPLICATE KEY UPDATE` 的原子性），但**台账流水会错乱**。不过，如果未来改为 `UPDATE current_qty = #{after}`（覆盖式），就会立即出现丢失更新。当前实现**侥幸安全**，但属于**脆弱设计**。

**建议**：`stockIn` 也应使用 `SELECT ... FOR UPDATE`，保持与 `stockOut` 一致的锁粒度，避免未来重构引入竞态。

### 3.3 应收/应付 code 生成规则与幂等性

#### 3.3.1 生成规则

```java
// MesSalesOutboundServiceImpl.java L120
String arCode = "AR-" + new SimpleDateFormat("yyyyMMdd").format(now) + "-" + e.getCode();
// 示例：AR-20260719-SO001

// MesPurchaseReceiptServiceImpl.java L125
String apCode = "AP-" + new SimpleDateFormat("yyyyMMdd").format(now) + "-" + e.getCode();
// 示例：AP-20260719-PO001
```

#### 3.3.2 幂等性分析

**数据库约束**：
```sql
-- V9.0.0__mes_finance_init.sql L50
UNIQUE INDEX uk_rec_code_del (code, del_flag),
-- L77
UNIQUE INDEX uk_pay_code_del (code, del_flag),
```

**评价**：
- `code` 有唯一索引，重复插入会抛 `DuplicateKeyException`。 ✅
- 但 code 包含**日期**（`yyyyMMdd`），如果出库单在 23:59:59 审核，应收单在 00:00:01 生成，日期不同，code 不同，不会冲突。但这会导致**同一出库单生成两个应收单**（跨天重试）。 🔴
- 更关键的是：**没有基于 `source_bill_id` 的唯一约束**。同一出库单 (`source_bill_id`) 可以生成多张应收单，只要 code 不同。 🔴
- `saveWithItems` 中有 `selectDeletedByCode` + `resurrect` 逻辑，但 `audit()` 中直接 `receivableService.save(ar)`，**没有先查是否已存在该来源的应收单**。 🔴

**幂等性结论**：**不幂等**。如果 `audit()` 被重试（如网络超时后用户重试），可能生成多张应收单。

**建议**：
1. 应收/应付表增加 `source_bill_id` 唯一索引：`UNIQUE INDEX uk_rec_source (source_bill_id, source_type)`。
2. 或在 `audit()` 中先查询 `source_bill_id = ?` 是否已存在，存在则跳过或复用。
3. code 生成规则去掉日期，或改为 `AR-单号`（不含日期），利用 `code` 唯一索引实现幂等。

### 3.4 并发审核同一单据：数据库唯一约束兜底

| 表 | 唯一索引 | 说明 |
|---|---|---|
| `c_mes_sales_outbound` | `uk_outbound_code_del (code, del_flag)` | code + 删除标记 |
| `c_mes_purchase_receipt` | `uk_receipt_code_del (code, del_flag)` | code + 删除标记 |
| `c_mes_receivable` | `uk_rec_code_del (code, del_flag)` | code + 删除标记 |
| `c_mes_payable` | `uk_pay_code_del (code, del_flag)` | code + 删除标记 |
| `c_mes_inventory` | `uk_inv_material_wh (material_id, warehouse_id)` | 物料+仓库 |

**分析**：
- 单据表有 `code` 唯一索引，防止重复创建相同 code 的单据。 ✅
- 但**并发审核**的场景是：两个线程同时审核**同一张已存在的单据**（相同 `id`），不是创建新单据。
- `auditWithGuard` 通过 `WHERE id = ? AND status = '1'` 防止并发审核，这是应用层乐观锁，**不是数据库唯一约束**。
- 数据库层面**没有防止并发审核的唯一约束**（也不应该有，因为审核是 UPDATE 不是 INSERT）。
- 真正的兜底是 `auditWithGuard` 的原子 UPDATE，这在 MySQL InnoDB 中行锁保证下是可靠的。 ✅

**结论**：`auditWithGuard` 足以防止并发审核，但**应收/应付生成缺少 `source_bill_id` 唯一索引**，导致重试可能产生重复财务单据。

### 3.5 事务传播：生成应收失败是否回滚出库状态

```java
// MesSalesOutboundServiceImpl.java L99-136
@Override @Transactional(rollbackFor = Exception.class)
public void audit(String id) {
    // 1. auditWithGuard 改状态
    int rows = baseMapper.auditWithGuard(id, username, now);
    if (rows == 0) throw new JeecgBootException("审核失败");
    // 2. 扣库存
    for (...) { inventoryService.stockOut(...); }
    // 3. 联动发货单
    deliveryNoteMapper.updateStatus(...);
    // 4. 生成应收
    receivableService.save(ar);  // 如果这里失败...
}
```

**分析**：
- `audit()` 标注 `@Transactional(rollbackFor = Exception.class)`。
- `receivableService.save(ar)` 使用默认传播 `REQUIRED`，加入当前事务。
- 如果 `save(ar)` 抛异常（如 `DuplicateKeyException`），整个事务回滚，包括：
  - `auditWithGuard` 的状态更新回滚（出库单回到草稿状态）。
  - `stockOut` 的库存扣减回滚。
  - `deliveryNoteMapper.updateStatus` 回滚。

**结论**：**会回滚**，出库状态、库存、发货单状态都会回滚。 ✅

**但业务语义危险**：
- 用户看到"审核失败：应收单已存在"，但出库单实际已回滚到草稿。
- 用户重新审核，又会生成相同的 `arCode`（因为日期相同、单号相同），再次冲突，**形成死循环**。 🔴
- 除非用户删除已存在的应收单，否则出库单永远无法审核。

### 3.6 库存扣减与应收生成的原子性

**现状**：同事务，原子性有保证。

**风险**：
1. **硬耦合**：应收生成失败 → 库存回滚。这导致库存操作被财务逻辑绑架。
2. **跨天重试**：如果审核在 23:59 发起，应收生成在 00:00 执行，日期变化导致 `arCode` 不同，不会冲突，但会生成两张应收单（如果第一次审核因其他原因失败）。 🔴
3. **无分布式锁**：如果系统部署多实例，没有 Redis/ZooKeeper 分布式锁防止同一单据并发审核。虽然 `auditWithGuard` 能兜底，但**库存扣减在 `auditWithGuard` 之前**（采购入库模式），可能导致库存先被扣/加，然后状态改不了。

**建议**：
- 将应收/应付生成改为**异步事件**或**事后补偿**，与库存操作解耦。
- 或至少在 `audit()` 中先检查 `source_bill_id` 是否已存在应收单，存在则跳过。

### 3.7 跨模块分布式锁缺失

**审计发现**：
- 全项目搜索 `distributed.?lock|redis.?lock|Redisson|lock4j|@Lock|synchronized|ReentrantLock`，仅发现：
  - `MesMenuRegistry.java` 有 `synchronized`（菜单初始化，与业务无关）。
  - `MesInventoryMapper.java` 有 `SELECT ... FOR UPDATE`。
  - `MesSalesOrderMapper.java` 有 `SELECT ... FOR UPDATE`（发货单并发超量校验）。

**缺失场景**：
1. **多实例部署**：JeecgBoot 支持 Spring Cloud 微服务模式，但 MES 模块没有分布式锁。
2. **库存扣减**：`stockOut` 依赖数据库行锁，在单实例下有效，但**多实例下如果库存表做分库分表，行锁可能失效**。
3. **发货单-出库单联动**：`deliveryNoteMapper.updateStatus` 是裸 UPDATE，没有锁。
4. **累计出库量校验**：`MesSalesOutboundServiceImpl.validate()` 中的 `checkDeliveryQty` 逻辑（L192-213）是**先查再校验**，并发下两个出库单同时校验通过，累计超量。

**🔴 高风险示例**：
- 发货单剩余可发数量 = 10。
- 线程 A 创建出库单，实出数量 = 6，校验通过（已发 0 + 6 <= 10）。
- 线程 B 同时创建出库单，实出数量 = 6，校验通过（已发 0 + 6 <= 10）。
- 两单都审核通过，累计发货 12 > 10，**超发**。

`MesDeliveryNoteServiceImpl.saveWithItems` 中有 `salesOrderMapper.selectByIdForUpdate`（L53-55），锁住了销售订单行，防止并发创建发货单超量。但**销售出库的累计校验没有类似的 `FOR UPDATE`**。 🔴

### 3.8 状态机安全

**销售出库状态机**：
```
1(草稿) --audit--> 3(已审核)
1(草稿) --cancel--> 0(已取消)
2(待审核) --cancel--> 0(已取消)   // cancelWithGuard 允许 1,2
```

**问题**：
- `auditWithGuard` 只允许 `1→3`，`cancelWithGuard` 允许 `1,2→0`。
- 但**没有 `1→2` 的提交操作**（销售出库没有 submit 方法），状态 2 是孤儿状态。
- `cancelWithGuard` 允许状态 2 取消，但没有任何入口能到状态 2。这不会导致错误，但说明状态机设计不完整。

**采购入库状态机**：
```
1(草稿) --audit--> 2(已入库)
```
- 没有 cancel 方法，没有状态 0。设计简单，但缺少取消能力。

**生产领料/完工入库**：
```
1(草稿) --audit--> 2(已审核)
```
- 同样没有 cancel。

**结论**：状态机本身安全（`auditWithGuard` 保证原子迁移），但**状态定义不完整**，部分状态无入口/无出口。

### 3.9 死锁风险

**场景**：销售出库单有多个明细，涉及多个物料。

```java
// MesSalesOutboundServiceImpl.java L110-112
for (MesSalesOutboundItem item : e.getItems()) {
    inventoryService.stockOut(item.getMaterialId(), e.getWarehouseId(), item.getActualQty(), ...);
}
```

- 线程 A 审核出库单 X，明细顺序：物料 M1 → M2。
- 线程 B 审核出库单 Y，明细顺序：物料 M2 → M1。
- 线程 A 锁 M1，线程 B 锁 M2。
- 线程 A 请求 M2，线程 B 请求 M1。
- **死锁**。 🔴

**当前缓解**：
- `stockOut` 的 `SELECT ... FOR UPDATE` 会持有行锁直到事务提交。
- 如果两个出库单有相同物料集合但顺序不同，必然死锁。

**建议**：
- 在 `audit()` 中对明细按 `materialId` 排序后再循环扣库存。
- 或一次性 `SELECT ... FOR UPDATE` 锁住所有涉及物料。
