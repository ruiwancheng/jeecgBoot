## 一、总体结论

| 维度 | 评级 | 说明 |
|------|------|------|
| 分页防护 | ✅ 良好 | 所有 `/list` 走 `Page<>(pageNo, pageSize)`，默认 pageSize=10，未发现裸 `list()` 列表接口 |
| queryAll / exportXls 上限 | ✅ 良好 | 全部 4 个 Controller（receivable/payable/subject/ledger）设置 `QUERY_ALL_MAX=5000`（出库/入库为 1000），超限抛异常，防 OOM 兜底到位 |
| @Dict 翻译 N+1 | ✅ 良好 | `DictAspect#translateAllDict` 按 dictCode 分组收集 value 后**一次性批量翻译**（`translateDictFromTableByKeys` 走 IN 查询 + Redis 缓存），**不是逐行 N+1** |
| 列表查询索引 | 🔴 高危 | **应收/应付表缺 `source_bill_id`、`status`、`create_time` 索引**；10 万/50 万数据量下，列表按 `create_time DESC` 排序 + 按 `source_bill_id` 反查均为**全表扫描+filesort** |
| 大批量主子表保存 | 🔴 高危 | `saveItems` 逐行 `itemMapper.insert()`，N 行明细 = N 次单条 INSERT；audit 中 `stockIn/stockOut` 每行 3 条 SQL（select + upsert + ledger insert），**无批量化** |
| 大批量删除 | ⚠️ 一般 | 出库单 `removeByIds` 循环内逐条 `checkStatus`（N 次 selectById），入库单已改 `selectBatchIds` 批量，**两个模块实现不一致** |
| 累计出库量校验 | 🔴 高危 | 出库 `validate` 中对**每个明细行**查一次"同发货单其他出库单"+再查一次累计明细，**行级 N+1**；入库 `validateReceipt` 同样按单查历史入库（单级，可接受） |
| 财务台账查询 | ⚠️ 一般 | 台账表有 `idx_ledger_date` 索引，排序走索引；但 `queryAll` 上限 5000 在 100 万+ 台账下永远触发，**该接口对台账实质不可用** |
| audit 批量插入 | ⚠️ 一般 | audit 一次只生成 1 张应收/应付（单条 save），无批量提交问题；但**缺 `source_bill_id` 防重复唯一约束**，重试/并发可产生重复财务单 |

**一句话结论**：JeecgController 基座的分页/导出上限/@Dict 批量翻译三板斧把"常见 N+1 与 OOM"基本都挡住了，**真正的性能地雷集中在两点——(1) 财务三表索引设计不足以支撑 10 万+ 数据量的列表查询，(2) 主子表明细的逐行 INSERT / 逐行库存扣减在百行级大单下 SQL 数爆炸**。

## 二、P0 级问题（本迭代必须修复）

### P0-1 【全表扫描】应收/应付列表排序与反查无索引支撑

**位置**：
- `MesReceivableController.java:35` → `qw.orderByDesc("create_time")`
- `MesPayableController.java:35` → `qw.orderByDesc("create_time")`
- `V9.0.0__mes_finance_init.sql:50-53, 77-80`

**现状 DDL**：
```sql
-- c_mes_receivable 只有这 3 个索引
UNIQUE INDEX uk_rec_code_del (code, del_flag),
INDEX idx_rec_customer (customer_id),
INDEX idx_rec_due_date (due_date)
-- ❌ 无 create_time 索引 → 列表 ORDER BY create_time DESC 全表扫 + filesort
-- ❌ 无 status 索引     → 前端常按"未结清"过滤，全表扫
-- ❌ 无 source_bill_id 索引 → P0-2 防重复校验和"按来源单查应收"全表扫
```

**影响量化**（10 万应收单）：
- 列表首页 `SELECT ... ORDER BY create_time DESC LIMIT 10`：MySQL 需扫全表 10 万行做 filesort，**单次 ~300-800ms**（SSD, innodb_buffer_pool 命中），数据到 50 万行退化为 2-4s
- 按 `customer_id` 过滤有索引（✅），但 `customer_id + create_time DESC` 组合场景仍需 filesort
- `source_bill_id` 目前无查询入口，但 **P0-2 修复防重复时必然加 `selectCount(source_bill_id=?)`**，届时每次审核都全表扫 10 万行

**修复建议**：
```sql
ALTER TABLE c_mes_receivable
  ADD INDEX idx_rec_ctime (create_time),
  ADD INDEX idx_rec_status_ctime (status, create_time),
  ADD INDEX idx_rec_source_bill (source_bill_id);
ALTER TABLE c_mes_payable
  ADD INDEX idx_pay_ctime (create_time),
  ADD INDEX idx_pay_status_ctime (status, create_time),
  ADD INDEX idx_pay_source_bill (source_bill_id);
```
参考 `V7.0.4__mes_sales_index_fix.sql` 的 `INFORMATION_SCHEMA.STATISTICS` 幂等写法（该文件是销售模块补索引的成熟模板，直接复用）。

### P0-2 【重复财务单 + 全表扫】应收/应付生成缺防重复机制

**位置**：
- `MesSalesOutboundServiceImpl.java:119-134`
- `MesPurchaseReceiptServiceImpl.java:124-138`

**问题**：audit 中 `receivableService.save(ar)` 前**无任何防重复校验**。虽然 `auditWithGuard` 原子 UPDATE 保证了"已审核单不能重复审核"，但以下场景仍会产生重复应收：
1. 审核事务在 `receivableService.save` 之后、commit 之前宕机 → 事务回滚 → 用户重试审核 → 正常，无重复（OK）
2. **出库单取消后重新审核**：`cancelWithGuard` 把状态从 3 改回可审状态？—— 看 `cancelWithGuard` 的 SQL `WHERE id=#{id} AND status IN ('1','2')`，已审核(3)的单不能取消，OK
3. **但 code 生成规则 `AR-yyyyMMdd-出库单code` 固定**：同一天同一出库单重试生成的 `arCode` 相同，依赖 `uk_rec_code_del` 唯一索引兜底 → 重试时抛 `DuplicateKeyException` → 事务回滚 → **用户看到"审核失败"但库存已扣**（虽然回滚，但用户体验差且日志误导）
4. 跨天重试（审核中途 JVM 崩溃，第二天恢复重审）：`arCode` 日期部分变化 → **生成第二张应收单**，资损

**性能维度评估**：防重复校验若简单加 `selectCount(source_bill_id = e.getId())`，在 P0-1 索引未补的情况下**每次审核全表扫 10 万行**，审核接口 P99 从 50ms 退化到 500ms+。所以 P0-1 与 P0-2 必须配套修。

**修复建议**：
```sql
-- 方案 A（推荐）：source_bill_id 加唯一索引（一单一应收），DB 层硬约束
ALTER TABLE c_mes_receivable ADD UNIQUE INDEX uk_rec_source_bill (source_bill_id);
ALTER TABLE c_mes_payable    ADD UNIQUE INDEX uk_pay_source_bill (source_bill_id);
```
```java
// 代码层 catch DuplicateKeyException 转为幂等成功（重复审核视为已处理）
try { receivableService.save(ar); }
catch (DuplicateKeyException dke) { log.warn("应收单已存在，幂等跳过: {}", arCode); }
```
这样无论同一天还是跨天重试，DB 层都只会有一张应收单，且**唯一索引查询 O(log N)**，不引入性能负担。

### P0-3 【行级 N+1】出库单累计出库量校验逐行 2 次 SQL

**位置**：`MesSalesOutboundServiceImpl.java:177-214`（validate 内层循环）

**问题**：
```java
for (int i = 0; i < items.size(); i++) {          // 明细行循环
    // 每行都执行：
    List<MesSalesOutbound> otherObs = baseMapper.selectList(obQw);   // ① 查同发货单其他出库单
    if (!otherObs.isEmpty()) {
        List<MesSalesOutboundItem> cumItems = itemMapper.selectList(cumQw); // ② 查累计明细
    }
}
```
**SQL 数 = 2 × 明细行数**。一张 100 行的大出库单，保存/编辑时**额外 200 次 SQL**，且这 200 次全部在同一个 `@Transactional` 长事务内执行，事务持锁时间被放大。50 万出库单 × 平均 20 行明细的场景下，`cumQw.in(outboundId, obIds)` 的 IN 列表也可能很长。

**修复建议**：把"按发货单聚合已出库量"改为**一条 GROUP BY 聚合 SQL**：
```java
// 一次性查出该发货单下所有其他出库单的按物料聚合出库量
@Select("SELECT i.material_id, SUM(i.actual_qty) AS cumQty " +
        "FROM c_mes_sales_outbound_item i " +
        "JOIN c_mes_sales_outbound o ON i.outbound_id = o.id " +
        "WHERE o.delivery_note_id = #{deliveryNoteId} AND o.id != #{excludeId} AND o.del_flag = 0 " +
        "GROUP BY i.material_id")
List<Map<String,Object>> sumByMaterial(@Param("deliveryNoteId") String dnId, @Param("excludeId") String excludeId);
```
内存里构建 `Map<materialId, cumQty>`，循环内 O(1) 查询。**SQL 数从 2N 降到 1**。

### P0-4 【批量保存退化】主子表明细逐行 INSERT，无批量提交

**位置**：
- `MesSalesOutboundServiceImpl.java:251` → `saveItems: for (...) itemMapper.insert(i)`
- `MesPurchaseReceiptServiceImpl.java:239-251` → 同上
- `MesInventoryServiceImpl.java:29-58` → audit 中每行 stockIn/stockOut = select + upsert + ledger insert 共 3 条 SQL

**问题量化**：
| 场景 | 明细行数 | SQL 数（保存） | SQL 数（审核） | 单事务总 SQL |
|------|---------|---------------|---------------|-------------|
| 小单 | 10 | 10 INSERT | 30 | ~50 |
| 中单 | 100 | 100 INSERT | 300 | ~410 |
| 大单（年终盘点级） | 1000 | 1000 INSERT | 3000 | ~4010 |

1000 行明细的大单，单事务 4000+ 条 SQL：
- 事务持续时间轻松超过 10s（按平均 3ms/SQL 计）
- InnoDB undo log 膨胀，长事务阻塞 purge
- `stockOut` 的 `selectForUpdate` 持有库存行锁，**高并发下其他出库单对同物料的审核全部排队**，雪崩风险

**修复建议**：
1. 明细 INSERT 改 MyBatis-Plus `saveBatch(list, 500)`（底层 JDBC batch，1000 行 → 2 个批次）：
```java
private void saveItems(MesSalesOutbound e) {
    e.getItems().forEach(i -> i.setOutboundId(e.getId()));
    ((ServiceImpl<MesSalesOutboundItemMapper, MesSalesOutboundItem>) itemService).saveBatch(e.getItems(), 500);
}
```
（需注入 `IMesSalesOutboundItemService`；或直接手写 `<insert>` foreach XML 批量）
2. 库存台账写入可保留逐行（业务审计要求每行一条台账），但库存快照的 upsert 可合并：**同一大单内同 material+warehouse 的行先内存聚合再一次 upsert**，把 N 次 select+upsert 降为 distinct(material,warehouse) 次
3. 给前端/接口加明细行数硬上限（如 500 行/单），超限要求拆单

## 三、P1 级问题（本迭代内修复）

### P1-1 【批量删除不一致】出库单 removeByIds 逐条 checkStatus

**位置**：`MesSalesOutboundServiceImpl.java:88-95`
```java
for (Object id : list) checkStatus((String) id);  // N 次 selectById
```
入库单 `MesPurchaseReceiptServiceImpl.java:148` 已用 `selectBatchIds` 一次批量查——**同一项目两种实现，出库单是落后的那个**。
100 个 ID 批量删除：出库单 101 次 SQL，入库单 3 次。
**修复**：出库单对齐入库单写法。

### P1-2 【count+list 双扫】queryAll / exportXls 前置 count 后仍全量 list

**位置**：4 个 Controller 共 8 处（receivable:44,50 / payable:44,50 / subject:66,72 / ledger:49,58）
```java
if (service.count() > QUERY_ALL_MAX) throw ...;   // 第 1 次全表扫（COUNT）
return Result.ok(service.list());                  // 第 2 次全表扫（SELECT *）
```
10 万行应收单：`COUNT(*)` 走聚簇索引估算较快（~50ms），但 `list()` 把 10 万行全部捞进 JVM 堆（约 200-400MB，视字段宽度），**exportXls 时 AutoPoi 再复制一份构建 XSSFWorkbook**，内存峰值翻倍。
**修复**（成员 5 号 P1-6 已提，性能视角附议）：用 `Page(1, MAX+1)` 一次查询替代 count+list；exportXls 超 5000 直接拒绝并引导走 `exportXlsForBigData`（基类 L144 已有现成的大数据导出演示方法，分批查询+IExcelExportServer 流式写出，当前项目**零调用**）。

### P1-3 【台账接口实质不可用】inventory_ledger 的 queryAll/exportXls 上限与数据量不匹配

**位置**：`MesInventoryLedgerController.java:32,49-51,58-60`

台账表按 100 万+/年 的速度增长，`QUERY_ALL_MAX=5000` 意味着：
- `queryAll`：系统上线 2 周后**永久抛异常**，该接口成为死接口
- `exportXls`：财务月底导出台账对账**必然失败**——而台账恰恰是财务最可能需要全量导出的表

**修复**：台账导出改走 `exportXlsForBigData`（分页流式），或强制带 `record_date` 区间参数（QueryGenerator 自动支持 `record_date_begin/end`），去掉裸 count 前置。

### P1-4 【subject 树查询】queryTree 全量 list() + 内存拼装

**位置**：`MesAccountSubjectServiceImpl.java:26` → `List<MesAccountSubject> all = list();`

1 万科目时：单条科目约 300 字节，1 万行 ≈ 3MB 堆内存，**单次查询 RT ~100-200ms，可接受**（成员 5 号 P2-7 同结论）。但每次打开科目树页面都全量查，无缓存。
**修复**：科目是低频变更数据，加 `@Cacheable("mes:subject:tree")` + save/update/remove 时 `@CacheEvict`；或 SQL 层加 `WHERE del_flag=0`（@TableLogic 已自动处理）+ `status=1` 过滤减少传输量。**1 万行量级不阻塞上线，标 P1 关注**。

### P1-5 【save 链路串行 SQL 偏多】科目 save 最多 5 次 SQL

**位置**：`MesAccountSubjectServiceImpl.java:40-60`
`validate`(0) + `checkCodeDuplicate`(1 selectCount) + `selectById(parent)`(1) + `updateById(parent)`(1) + `selectDeletedByCode`(1) + `resurrect/save`(1) = **最多 6 次 SQL/次保存**。
科目保存是低频操作（管理员手工维护），**单次 6 SQL 可接受**，不阻塞；但 `checkCodeDuplicate` 的 `selectCount(code=?)` 依赖 `uk_subject_code_del` 最左前缀 `code`，走索引 OK。**仅记录，无需立即改**。

| 表 | 现有索引 | 评估 | 缺口 |
|----|---------|------|------|
| `c_mes_account_subject` | uk(code,del_flag), idx(parent_id) | ✅ 1 万行够用；checkCodeDuplicate 走 uk 最左前缀 | 无紧急缺口 |

| `c_mes_payable` | uk(code,del_flag), idx(supplier_id), idx(due_date) | 🔴 同上 | P0-1 所列 3 个 |

| `c_mes_sales_outbound` | uk(code,del_flag), idx(delivery_note_id), idx(status), idx(create_time) | ✅ 良好（V7.0.4 补过） | customer_id 无索引（按客户查出库历史时全表扫，50 万行 ~2s） |
| `c_mes_sales_outbound_item` | idx(outbound_id), idx(material_id)（V7.0.4 补） | ✅ | 建议加 (outbound_id, material_id) 复合 |
| `c_mes_purchase_receipt` | uk(code,del_flag) | 🔴 **缺 create_time / supplier_id / purchase_order_id 索引** | 列表排序全表扫 |
| `c_mes_purchase_receipt_item` | idx(receipt_id) | ⚠️ 缺 material_id（累计入库校验按物料查时全表扫） | (receipt_id, material_id) 复合 |
| `c_mes_inventory` | uk(material_id, warehouse_id) | ✅ 完美匹配 stockIn/stockOut 查询 | 无 |
| `c_mes_inventory_ledger` | idx(material_id), idx(warehouse_id), idx(record_date) | ⚠️ 单字段索引；`ORDER BY record_date DESC, material_id ASC` 只能利用前一个 | 建议 (record_date, material_id) 复合；(material_id, record_date) 用于物料流水查询 |

**采购入库表索引缺口与应收/应付同级严重**，但本次审计范围以财务模块为主，入库表列入 P1 附带修复（审核联动点性能直接受它影响）。

## 五、N+1 / SQL 调用次数全景表

| 场景 | SQL 调用次数 | 评价 |
|------|-------------|------|
| 应收/应付/科目 列表分页 | 2（count + page） | ✅ 标准，@Dict 批量翻译不再额外查库（走 IN+缓存） |
| 应收/应付/科目 queryAll | 2（count + list）**但都是全表扫** | ⚠️ P1-2 |
| 科目 queryTree | 1 次全表 list | ⚠️ 1 万行可接受，P1-4 |
| 科目 save | 最多 6 次 | ⚠️ 低频可接受 |
| 出库单 queryWithItems | 2（主 + 明细） | ✅ 无 N+1 |
| 出库单 saveWithItems（含 validate） | 3 + 2N（N=明细行，累计校验）+ N（INSERT） | 🔴 P0-3 + P0-4 |
| 出库单 audit | 2（queryWithItems）+ 1（auditWithGuard）+ 3N（stockOut）+ 1（发货单状态）+ 1（应收 save） | 🔴 P0-4 |
| 入库单 audit | 2 + 3N（stockIn）+ 1（auditWithGuard）+ 1（应付 save） | 🔴 P0-4 |
| 出库单 removeByIds（批量删除） | N（checkStatus）+ 1（批量删明细）+ 1（批量删主表） | ⚠️ P1-1 |
| 入库单 removeByIds | 1（selectBatchIds）+ 1 + 1 | ✅ 已优化 |
| @Dict 客户/供应商表字典翻译 | 每 dictCode 1 次 IN 查询（`translateDictFromTableByKeys`）+ Redis 命中时 0 | ✅ 非 N+1 |
| JeecgController exportXls | 1（list）+ AutoPoi 内存构建 | ⚠️ ≤5000 行可控，P1-2 |

## 六、数据量场景响应时间预估

| 场景 | 1 万科目 | 10 万应收 | 50 万出库 | 瓶颈 |
|------|---------|----------|----------|------|
| 科目树 queryTree | ~150ms（全表扫+内存拼装） | — | — | 内存传输，可接受 |

## 九、亮点（值得肯定的实践）

1. **@Dict 批量翻译机制**：`DictAspect` 按 dictCode 聚合 value 后一次 IN 查询 + Redis 缓存，列表页字典翻译**不是 N+1**，这是 JeecgBoot 基座的红利
2. **QUERY_ALL_MAX 上限全覆盖**：4 个财务相关 Controller 的 queryAll/exportXls 均有硬上限，OOM 兜底意识到位
3. **auditWithGuard 原子 UPDATE**：一行 SQL 完成状态守卫，性能最优且防并发
4. **库存表 uk(material_id, warehouse_id) 唯一索引 + ON DUPLICATE KEY UPDATE upsert**：单次 SQL 完成"查或建+增量更新"，无先 select 后 insert 的往返
5. **入库单 removeByIds 用 selectBatchIds 批量查状态**：批量删除的正确示范
6. **出库单主表索引在 V7.0.4 已补齐**（delivery_note_id/status/create_time/item.material_id）：上一轮审计的修复落地到位，说明团队对索引问题响应快
7. **JeecgController 基类自带 exportXlsForBigData 流式导出**：虽然当前未启用，但基础设施已就位，改造仅差 Controller 层一行调用切换
