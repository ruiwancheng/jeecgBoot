## 二、详细发现

### F-01【P0】应付单 `amount=0`，业务上是空账

**位置**：`MesPurchaseReceiptServiceImpl.java:132-134`

```java
ap.setAmount(java.math.BigDecimal.ZERO); // MVP: 金额待采购价格模块完善后自动计算
ap.setPaidAmount(java.math.BigDecimal.ZERO);
ap.setUnsettledAmount(java.math.BigDecimal.ZERO);
```

**问题**：
- 采购入库审核时强制生成应付单，但**金额硬编码为 0**。
- 应付单存在的意义是"告诉财务要付多少钱"，金额为 0 等于告诉财务"不用付钱"。
- 虽然注释里写了 "MVP"，但代码已经 `@Transactional` 落库，没有任何后续补偿/重算机制。后续采购价格模块上线时，**所有历史应付单金额都是 0**，需要数据迁移。

**攻击/异常场景**：
1. 财务按月对账：应付总额 = 0，与采购订单总额完全对不上。
2. 如果未来有人写 `WHERE unsettled_amount > 0` 的催款报表，将查不到任何数据。
3. 入库单一旦审核就生成 AP，且 `MesPurchaseReceipt` 没有 cancel/反审核接口，**这张 0 元应付单永远无法被修正或删除**（关联 F-02/F-10）。

**修复建议**：
- audit 时若金额未知，**应跳过生成应付单**，或生成"待定价"状态（新增字典值）的应付单；
- 或在 `c_mes_purchase_order_item` 上取 `unit_price * receipt_quantity` 实时计算。

### F-02【P0】应收/应付状态机是死胡同：只有 `1=未结清` 一个状态能被写入

**位置**：`MesReceivableController` + `MesPayableController` + 两个 `ServiceImpl`

**事实**：
- 两个 Service **完全为空**，只有 `extends ServiceImpl`，**零业务方法**。
- 两个 Controller **只暴露只读接口**：`list / queryById / queryAll / exportXls`，**无 add/edit/delete/audit/receive/pay/writeoff 任何写操作**。
- 但 `V9.0.0__mes_finance_init.sql` 第 147-149 行、第 156-158 行定义了字典 `1=未结清 / 2=部分结清 / 3=已结清`。
- 整个工程**搜遍代码找不到任何一处写入 `status='2'` 或 `status='3'`** 的代码。

**问题**：
- 应收单生成后，**永远没有"收款"动作**，永远停在 `未结清`；
- `received_amount` / `paid_amount` / `settlement_date` 字段**从生到死都是初始值**；
- 字典里 `2/3` 是**死字典**，前端筛选"已结清"将永远查不到数据，用户会以为系统出 bug。

**这本质上是产品闭环缺失**：业财联动只完成了"业务→财务"的左半张图，"财务→核销→状态回流"完全缺失。

### F-03【P0】采购入库 audit 顺序颠倒 + 重复 audit 库存双倍

**位置**：`MesPurchaseReceiptServiceImpl.java:112-140`

```java
public void audit(String id) {
    MesPurchaseReceipt e = queryWithItems(id);
    if (e == null) throw ...;
    if (!"1".equals(e.getStatus())) throw ...;
    // ⚠️ 先逐行加库存
    for (MesPurchaseReceiptItem item : e.getItems()) {
        inventoryService.stockIn(...);
    }
    // ⚠️ 后改状态
    int rows = baseMapper.auditWithGuard(id, username, now);
    if (rows == 0) throw new JeecgBootException("审核失败：...");
    // ⚠️ 再生成应付单
    payableService.save(ap);
}
```

**对比销售出库 `MesSalesOutboundServiceImpl.java:99-136`** 是 **先 `auditWithGuard` 改状态 → 再 `stockOut`**，顺序正确。

**问题（按严重度递进）**：

1. **顺序颠倒**：`stockIn` 在 `auditWithGuard` 之前。两个并发请求同时进入：
   - 请求 A：`stockIn` 成功（库存 +100），`auditWithGuard` 成功（status 1→2）→ 提交。
   - 请求 B：`stockIn` 成功（库存又 +100），`auditWithGuard` 返回 0 → 抛 `JeecgBootException` → 事务回滚。
   - 结果：单看数据库最终是一致的（B 回滚），**但 `stockIn` 在 B 事务里执行的 `upsertWithDelta` 是否完全回滚取决于 `MesInventoryServiceImpl` 的事务传播**。
   - 实际：`@Transactional` 默认 `REQUIRED` 会加入调用方事务，所以 B 的 stockIn 会回滚。**这次运气好，但代码结构本身是反模式**。
   - 真正的地雷：如果未来有人给 `stockIn` 加 `REQUIRES_NEW` 或改成异步消息，双倍入库会立刻发生。销售出库那边已经吃过亏（注释 `P0-02/P1-01 先改状态再扣库存`），采购入库却又踩一遍。

2. **`e` 是 audit 之前的快照**：`queryWithItems(id)` 在 `auditWithGuard` 之前读取。audit 成功后，`e.getStatus()` 仍然是 `"1"`。后续如果 `payableService.save(ap)` 抛错回滚，整个流程能回滚，没问题；但如果未来在 audit 之后追加"通知/消息"逻辑（不受事务保护），会基于过期快照做判断。

3. **`payableService.save(ap)` 在 audit 之外还可能抛 `DuplicateKeyException`**：AP code 是 `AP-yyyyMMdd-{入库单号}`，**如果同一天对同一入库单重复 audit**——不会发生，因为 auditWithGuard 已拦下；但**如果跨天做"取消→重新审核"**（虽然 cancel 接口本身缺失，但假设 DBA 直接 UPDATE 状态回 1），会生成 **不同 code** 的两张 AP，且 `source_bill_id` 相同，**财务端出现重复应付**。详见 F-08。

4. **如果 `payableService.save(ap)` 抛错**（如 code 唯一冲突），整个 audit 回滚，**库存也被回滚**——从业务上看是合理的，但用户体验是"我点了审核，告诉我应付单重复，库存没加，状态没改"，报错信息却是"应付单号已存在"，**误导排查方向**。

**修复建议**：
- 顺序调整为：`auditWithGuard` → `stockIn`（多行）→ `payableService.save`；
- `payableService.save` 包 try-catch，若失败把异常转成业务提示，不要让用户看到 "Duplicate entry"。

### F-04【P1】会计科目删除/停用校验缺失

**位置**：`MesAccountSubjectServiceImpl.java:71-78`

```java
public boolean removeById(java.io.Serializable id) {
    // 检查是否有子科目
    LambdaQueryWrapper<MesAccountSubject> qw = new LambdaQueryWrapper<>();
    qw.eq(MesAccountSubject::getParentId, id);
    if (baseMapper.selectCount(qw) > 0) throw new JeecgBootException("该科目下存在子科目，无法删除");
    return super.removeById(id);
}
```

**问题**：
1. **未校验"是否被凭证引用"**：`c_mes_voucher_item.subject_id` 存在外键引用关系（虽然 SQL 没写 FK，但业务上是引用）。删除一个已被凭证使用的科目，凭证里就只剩一个失效的 `subject_id`，前端通过 `@Dict(dictTable="c_mes_account_subject")` 翻译时显示空白。
2. **未校验"是否被启用状态的子科目引用"**：只查了 `parent_id = id`，没考虑 `del_flag`（虽然 MyBatis-Plus `@TableLogic` 会自动加 `del_flag=0`），但**没考虑子科目本身是停用状态**——停用子科目也阻塞删除，用户体验不友好但可接受。
3. **停用 (`status='0'`) 完全无校验**：`updateById` 只校验了 code 重复，**用户可以把一个被 1000 张凭证引用的科目直接停用**，后续新凭证选择科目时通过 `@Dict` 仍能看到（除非前端过滤），无服务端拦截。
4. **父科目删除后，子科目的 `parentId` 成孤儿**：`removeById` 已有子科目校验保护了直接父科目，但**多级场景**：A→B→C，删除 B 时校验"B 下是否有 C"是通过 `parent_id=B.id` 查的，能拦住；删除 A 时校验"A 下是否有 B"，也能拦住。OK。但若 DBA 直接 UPDATE B.parent_id=NULL，A 的子树就断了——这是 DBA 层面，不在代码范围。
5. **`is_leaf` 维护是单向的**：`save` 时如果 parent 是叶子会置 0，但**删除子科目时不会把父科目重新置回叶子**。A 下原本只有 B 一个子科目，A.is_leaf=0；删除 B 后，A.is_leaf 仍为 0，但已实际无子，树形展示时会多出"展开"图标但点不开。

### F-05【P1】科目编码唯一性：TOCTOU 竞态 + 复活逻辑的隐藏坑

**位置**：`MesAccountSubjectServiceImpl.java:38-68`

```java
public boolean save(MesAccountSubject entity) {
    validate(entity);
    checkCodeDuplicate(entity.getCode(), null);   // ① 先 select count(*)
    ...
    MesAccountSubject old = baseMapper.selectDeletedByCode(entity.getCode());  // ② 再 select del_flag=1
    if (old != null) { ... resurrect ... }
    try { return super.save(entity); } catch (DuplicateKeyException e) { ... }  // ③ 最后 insert
}
```

**问题**：
1. **TOCTOU**：`checkCodeDuplicate` 和 `super.save` 之间没有锁。两个并发请求同时 add 同一个 code：
   - A: checkCodeDuplicate → 0，通过；
   - B: checkCodeDuplicate → 0，通过；
   - A: super.save → 成功；
   - B: super.save → 触发 `uk_subject_code_del` 唯一索引 → `DuplicateKeyException` → 转化为 "科目编码已存在"。
   - **结果 OK**，但依赖 DB 唯一索引兜底。**真正的坑在于**：
2. **`(code, del_flag)` 唯一索引的语义陷阱**：`UNIQUE INDEX uk_subject_code_del (code, del_flag)` 允许 `(code='1001', del_flag=0)` 一行 + `(code='1001', del_flag=1)` 一行，但**不允许多行 `del_flag=1`**。也就是说：同一 code **只能"复活"一次**，第二次删除后再 add 相同 code：
   - 第一次：insert (code='1001', del_flag=0) → delete → (del_flag=1)
   - add 同 code → `selectDeletedByCode` 命中 → `resurrect` (del_flag=0) ✓
   - 再次 delete → (del_flag=1)
   - 再次 add 同 code → `selectDeletedByCode` 命中 → `resurrect` → 但此时表里已有 (code='1001', del_flag=1) 的旧记录 + 即将 update 的这条也要变成 del_flag=0...等下，`resurrect` 是 `WHERE id=#{id} AND del_flag=1`，只 update 当前这一行。
   - **真实陷阱**：假设用户不用 add 而是直接 `INSERT`（如 SQL 工具），第二条 del_flag=1 同 code 记录会**违反唯一索引**。`uk_subject_code_del` 设计本身**限制了"一个 code 最多存在一条已删除历史"**，这与"逻辑删除"语义相悖——一旦数据被反复删除/复活，会出现无法预期的 `DuplicateKeyException`。
   - 业内更安全的做法是 `(code, del_flag, id)` 或干脆 `(code)` 唯一 + 删除时把 code 改为 `code#deleted#id`。

3. **`updateById` 时未处理"复活"分支**：`save` 里有 `selectDeletedByCode → resurrect` 路径，`updateById` 里只有 `checkCodeDuplicate`，**编辑场景下不会触发复活**。这本身是对的（编辑不该复活），但用户视角："我新增一个被删除过的 code 行，系统把它复活了，但 level/parentId 被老数据覆盖"——见 F-06。

4. **`resurrect` 不更新 `parentId`**：看 `MesAccountSubjectMapper.resurrect` 的 SQL：
   ```sql
   UPDATE c_mes_account_subject SET code=..., name=..., category=..., level=..., parent_id=#{parentId}, ...
   ```
   `parent_id` 是更新的，OK。但**没有更新 `is_leaf`**：`is_leaf=#{isLeaf}` 实际是更新的，OK。但**老父科目的 `is_leaf` 标志没维护**：如果复活的科目 parentId 变了，老父科目该被改回 leaf=1，新父科目该被改成 leaf=0，都没做。

### F-06【P1】金额字段裸奔：null / 负数 / 超大数 / 精度全部无校验

**位置**：`MesReceivable` / `MesPayable` 实体 + 对应 Controller

**事实**：
- 实体字段 `BigDecimal amount / receivedAmount / unsettledAmount` **零校验注解**（无 `@NotNull`、`@DecimalMin`、`@Digits`）。
- Controller **直接 `service.save(entity)`**（虽然当前 Controller 没暴露 add/edit，但 `JeecgController` 基类有默认 `add` 方法吗？看代码里没继承，但 base class `JeecgController` 默认是有 `add/edit` 的——需要确认。
- 看 `MesReceivableController`：只重写了 `list/queryById/queryAll/exportXls`，**没屏蔽基类的 add/edit/delete**！意味着 **`POST /mes/finance/receivable/add` 仍然可以调用**（虽然 `@RequiresPermissions` 没加，但是否会被 Shiro 默认拦截取决于全局配置）。这是一个**潜在的越权写入点**。

**验证基类默认行为**：`JeecgController` 通常自带 `add/edit/delete` 端点，未在子类中显式禁用即暴露。这意味着：
1. 任何登录用户**可能可以**手工 POST 创建应收单，金额任意填（负数、0、999999999999.99）。
2. 数据库 `DECIMAL(18,2)` 对超过 16 位整数部分的值会报 `Out of range`，触发 500，**没有优雅的业务提示**。
3. `received_amount` 可以是**负数**（等于退款），`unsettled_amount` 可以是**负数**，**没有任何 DB CHECK 约束**。

**攻击/异常场景**：
- 直接 POST `/mes/finance/receivable/add` body `{"code":"HACK-001","customerId":"x","amount":-99999}` → 落库成功（假设权限放行）。
- 即使权限拦截，`MesSalesOutboundServiceImpl.audit` 中 `ar.setAmount(e.getTotalAmount())` 也没校验 `totalAmount` 的精度——`calcTotal` 用了 `setScale(2, HALF_UP)` 所以是 2 位小数，OK；但 `totalAmount` 累加时如果某个 `item.amount` 是 `null` 会被跳过（F-07 详述）。

### F-07【P1】销售出库→应收：`totalAmount=0/null` 静默跳过 + `item.amount` 累加丢失

**位置**：`MesSalesOutboundServiceImpl.java:119-134` + `240-246`

```java
// audit 中
if (e.getTotalAmount() != null && e.getTotalAmount().compareTo(java.math.BigDecimal.ZERO) > 0) {
    // 生成应收
}
// 否则静默跳过
```

```java
// calcTotal 中
for (MesSalesOutboundItem item : entity.getItems()) {
    if (item.getAmount() != null) total = total.add(item.getAmount());
}
```

**问题**：
1. **`item.amount` 是 `null` 时静默跳过**：`validate` 里 `item.setAmount(item.getActualQty().multiply(item.getUnitPrice()).setScale(2, ...))` 总是有值，但 `unitPrice` 兜底是 `BigDecimal.ZERO`（line 232）。也就是 **订单行找不到单价时，amount=0**，最终 `totalAmount=0`，audit 时**不生成应收单**。
   - 业务场景：销售订单录入了但忘记填单价 → 出库审核通过 → **没有应收单** → 财务不知道要收钱 → 货已发出。
   - 这是**收入性 bug**，比 F-01 的 0 元应付更危险（应付 0 至少还提示"不付钱"，应收缺失意味着"以为没这笔收入"）。
2. **`unitPrice` 找不到时静默置 0**：`if (item.getUnitPrice() == null) item.setUnitPrice(BigDecimal.ZERO);` 没有警告、没有日志。
3. **`creditPeriod` 硬编码 30**：`ar.setCreditPeriod(30); ar.setDueDate(now + 30 天)`，**客户档案上的账期完全被忽略**。`c_mes_customer` 表大概率有 `credit_period` 字段（未审计），即便没有，硬编码 30 也是产品灵活性的硬伤。
4. **`dueDate` 计算**用 `now.getTime() + 30L * 86400000`：**没考虑跨月/跨年/夏令时**（中国无夏令时，但 `86400000ms` 强假设每天 24h，遇到 UTC 偏移边界会出错；更严重的，`due_date` 是 `DATETIME` 类型，但实体 `Date dueDate` 用 `yyyy-MM-dd` 序列化——`@JsonFormat(pattern="yyyy-MM-dd")` 会丢失时分秒，展示给用户的到期日可能比实际少 8 小时，跨时区部署时会差一天）。

---

### F-08【P1】AR/AP code 基于日期，跨天操作产生重复

**位置**：`MesSalesOutboundServiceImpl.java:120`、`MesPurchaseReceiptServiceImpl.java:125`

```java
String arCode = "AR-" + new java.text.SimpleDateFormat("yyyyMMdd").format(now) + "-" + e.getCode();
String apCode = "AP-" + new java.text.SimpleDateFormat("yyyyMMdd").format(now) + "-" + e.getCode();
```

**问题**：
1. **同一来源单跨天重新审核会生成不同 code**：
   - 7-19 audit → AR-20260719-SO001
   - 假设引入 cancel 后，7-20 再 audit → AR-20260720-SO001
   - 财务端同一笔销售出库看到**两张应收单**，对账炸锅。
2. **`SimpleDateFormat` 是线程不安全的**：每次 `new` 一个，正确。但代码风格上不推荐，建议 `DateTimeFormatter`。
3. **没有时区指定**：`new SimpleDateFormat("yyyyMMdd")` 使用默认时区。若服务器跨时区部署（容器 UTC + 应用 CST），同一时刻生成的 code 可能差一天。
4. **`(source_bill_id, source_type)` 没有唯一索引**：数据库层无法兜底"同一来源单只能生成一张应收/应付"，完全靠 code 唯一约束。code 又含日期，**实际上失去了去重能力**。

**修复建议**：
- code 改为 `AR-{source_bill_no}` 或 `AR-{来源单号}`（不含日期）；
- DB 加 `UNIQUE INDEX (source_bill_id, source_type, del_flag)`；
- 或在 audit 前先 `selectCount(source_bill_id=...)`，命中则跳过生成（幂等）。

## 三、交叉场景压力测试（脑暴推演）

### 场景 A：财务月结高峰期，10 个用户同时审核 10 张采购入库单

- 每张入库单 audit 都触发 `stockIn` + `payableService.save`；
- `stockIn` 内部 `upsertWithDelta` 是 `INSERT ... ON DUPLICATE KEY UPDATE current_qty = current_qty + delta`，**SQL 层原子**，并发安全 ✓；
- 但 `MesInventory` 表的 `material_id + warehouse_id` **是否有唯一索引**？看 `MesInventoryMapper.upsertWithDelta` 依赖 `ON DUPLICATE KEY`，**前提是 `(material_id, warehouse_id)` 有 UNIQUE 索引**——未在审计范围内确认，如果没有唯一索引，会插入多行，库存爆炸。

### 场景 B：同一张销售出库单，用户连续点击"审核"按钮 3 次

- 第 1 次：`auditWithGuard` 返回 1，扣库存、生成 AR、提交；
- 第 2 次：`auditWithGuard` 返回 0，抛 "审核失败：出库单不存在或状态已变更" ✓；
- 第 3 次：同上 ✓。
- **正常**，销售出库这里有防护。**但前端没有任何防重**：按钮没 loading、没 disable，用户会看到两次同样的错误提示，体验差。

### 场景 C：编辑一张已生成应收的出库单（虽然代码上 checkStatus 拦截了）

- `MesSalesOutboundServiceImpl.updateWithItems` line 73 `checkStatus(entity.getId())` 只允许 `status='1'` 编辑；
- 但**前端如果绕过**直接 PUT，依然能被拦住 ✓；
- 然而 `audit` 之后 `status='3'`，发现明细错了想改 → 无法修改、无法 cancel 后改（cancel 后 status='0'，依然非 '1'），**只能删库**。业务上是死胡同。

### 场景 D：科目编码 "1001" 反复删除/新增 5 次

- 每次 `save` 都走 `selectDeletedByCode → resurrect`；
- `resurrect` 是 UPDATE，不插入新行，**所以 `(code, del_flag)` 唯一索引不会冲突** ✓；
- 但 `create_by/create_time` 会继承最早的创建人，**审计追踪混乱**；
- `is_leaf` 在 `save` 里被强制设为 1，**如果它原来有子科目**（删除前是父科目），复活后 is_leaf=1，但 `c_mes_account_subject` 表里仍有 `parent_id=它` 的子科目，**数据不一致**——子科目成了"无叶之父"。

### 场景 E：出库单 totalAmount = 0.001（3 位小数）

- `calcTotal` 用 `setScale(2, HALF_UP)` → 0.00；
- audit 时 `compareTo(ZERO) > 0` 为 false，**不生成应收**；
- 但 `actualQty * unitPrice = 0.001` 这个原始值已丢失，业务上 0.001 元等于 0，可接受；
- 但如果 `totalAmount = 0.005`，`HALF_UP` 进位为 0.01，会生成 0.01 元的应收——**财务会为 1 分钱挂账**，月末对账繁琐。

### 场景 F：科目查询 `queryAll` 接口的并发上限保护

- `MesAccountSubjectController.queryAll`：`if (service.count() > 5000) throw`，**先 count 再 list**，两次 SQL。如果 count=4999 通过，并发瞬间另一请求插入 100 条，list 返回 5099 条，**保护失效**——属于软限制，可接受。
