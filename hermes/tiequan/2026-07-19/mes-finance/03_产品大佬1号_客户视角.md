## 二、风险点清单（按文件分组，按严重度分级）

**分级标准**：
- **P0** —— 阻断客户核心财务业务，或导致客户做出错误财务决策，必须修复才能交付。
- **P1** —— 严重影响客户使用体验或流程完整性，客户会立即投诉/要求补齐。
- **P2** —— 体验/习惯性问题，客户会吐槽但不阻断使用。

### 2.1 `MesPurchaseReceiptServiceImpl.java`（audit hook 生成应付单）

#### 🔴 P0-1 应付单自动生成时金额恒为 0，客户会基于错误数据做付款决策
- **位置**：第 132-134 行 `ap.setAmount(java.math.BigDecimal.ZERO); // MVP: 金额待采购价格模块完善后自动计算`
- **风险描述**：采购入库审核后自动生成的应付单，`amount` / `paidAmount` / `unsettledAmount` 三个金额字段全部硬编码为 `BigDecimal.ZERO`。
- **业务影响（客户视角）**：
  - 财务应付专员打开"应付账款"列表，看到的全是 **应付金额 ¥0.00** 的单据——这会被理解为"这批货不用付钱"，或直接认为系统坏了。
  - 客户无法基于该系统回答最基本的问题："我到底欠供应商多少钱？"
  - 若客户真的基于这份数据付款/对账，将造成**直接的资金差错**；即便不付款，财务也会立刻判定该模块不可用并弃用。
  - 注释中"MVP 待完善"对客户不可见，客户只会看到一个金额全为 0 的应付台账。
- **修复建议**：
  1. 审核时应从采购订单明细/收货明细聚合含税金额写入 `amount` 和 `unsettledAmount`（应收侧已经这么做了：`ar.setAmount(e.getTotalAmount())`，应付侧应对齐）。
  2. 若短期内价格模块确实无法对接，则**不要自动生成应付单**，或生成后状态置为"待补价"并在前端醒目标红提示"金额未确认"，而不是静默写 0。

### 2.2 `receivable/index.vue` + `receivable.data.ts` + `receivable.api.ts` + `MesReceivableController.java`

#### 🔴 P0-2 应收账款无任何"收款登记/核销"操作，财务核心业务闭环断裂
- **位置**：`receivable/index.vue` 整个表格只有一个"导出"按钮；`receivable.api.ts` 只有 `list / queryById / exportXls`；`MesReceivableController` 没有 add/edit/delete 之外更没有任何收款接口；菜单注册（`MesMenuRegistry.java:86`）仅授权 `list, export`。
- **风险描述**：应收单由销售出库审核自动生成后，客户**只能查看和导出**。没有"收款登记"、"部分收款"、"核销"、"调整"任何入口；`receivedAmount`、`unsettledAmount`、`status`（未结清/部分结清/已结清）、`settlementDate` 这些字段在数据库里设计好了，但**没有任何前后端代码会更新它们**——它们永远是初始值（已收=0、未结=全额、状态=未结清）。
- **业务影响（客户视角）**：
  - 客户收到客户回款后，**无法在系统中登记**——这本该是应收账款模块存在的唯一理由。
  - "已收金额/未结金额/部分结清/已结清"这套状态机是死代码，列表上永远显示"未结清"，账期到期后也没有"已逾期"状态，财务无法跟踪回款。
  - 一个月后客户看到的应收列表和第一天一模一样（全部未结清、全额未收），模块失去存在价值，客户会要求退货或自研。
- **修复建议**：
  1. 必须补"收款登记"操作：列表行内按钮「收款」，弹出表单录入本次收款金额、收款日期、收款方式、备注；后端新增 `POST /mes/finance/receivable/receive` 接口，累加 `received_amount`、重算 `unsettled_amount`、按结果流转 `status`（1→2→3），全部收款完成后写 `settlement_date`。
  2. 每次收款应留有收款流水记录（子表），而不是只更新主表金额——否则客户无法回答"这笔钱是哪几次收的"。
  3. 菜单注册处补齐 `mes:receivable:receive` 权限码。

#### 🔴 P0-3 列表缺少"客户"列，应收台账看不到欠款方
- **位置**：`receivable.data.ts` 的 `columns`：应收单号、来源单据号、应收金额、已收金额、未结金额、到期日、状态、来源类型——**没有客户名称列**；搜索表单也没有客户筛选。
- **风险描述**：`MesReceivable` 实体本身有 `customerId` 且配了 `@Dict(dictTable = "c_mes_customer", ...)` 翻译，后端返回是带客户名的，但前端列配置没有展示。
- **业务影响（客户视角）**：应收台账第一要务是"**谁欠我钱**"。客户打开列表，看到一堆 AR-20260719-XXX 单号和金额，却不知道是哪家的账，必须逐条点详情或凭单号记忆——这在有两家以上客户时就完全不可用。
- **修复建议**：columns 中在"应收单号"后增加 `{ title: '客户', dataIndex: 'customerId_dictText', width: 160 }`（JeecgBoot 字典翻译字段惯例），并在搜索表单加客户下拉（JDictSelectTag 或 JSearchSelect 绑 c_mes_customer）。

#### 🟡 P1-1 无逾期/账龄视角，"到期日"列形同虚设
- **位置**：`receivable.data.ts` 有"到期日"列，但无逾期天数、无账龄分组、无"已逾期"红色标识、无按到期日筛选。
- **业务影响**：财务催收依赖账龄表（30/60/90 天）。当前客户只能肉眼逐条对比到期日和今天日期。
- **修复建议**：列表增加"逾期天数"计算列（今天 - dueDate，负数不显示），逾期行标红；搜索表单加"到期日范围" RangePicker；中期提供账龄分析汇总视图（按客户分组，0-30/31-60/61-90/90+ 分桶）。

### 2.3 `payable/index.vue` + `payable.data.ts` + `payable.api.ts` + `MesPayableController.java`

#### 🔴 P0-4 应付账款无"付款登记"操作，且列表无"供应商"列
- **位置**：与应收侧完全对称——只有一个"导出"按钮；菜单仅授权 `list, export`；columns 无供应商列（实体 `supplierId` 同样配了 @Dict 翻译但未展示）。
- **业务影响（客户视角）**：
  - 与 P0-2 对称的断裂：客户付钱给供应商后无法登记，`paid_amount`/`unsettled_amount`/`status` 同样是死字段。
  - 叠加 P0-1（金额恒为 0），应付模块目前对客户是**双重不可用**：既不知道欠多少（金额=0），也无处记录付了多少。
  - 不知道欠"谁"——无供应商列，与 P0-3 同性质。
- **修复建议**：与应收对称为供应商列 + 「付款」行内按钮 + `POST /mes/finance/payable/pay` 接口 + 付款流水子表 + 权限码 `mes:payable:pay`。**但前提是先修 P0-1，否则付款登记基于 0 金额单据毫无意义。**

### 2.4 `MesSalesOutboundServiceImpl.java`（audit hook 生成应收单）

#### 🟡 P1-2 应收单账期硬编码 30 天，无视客户主数据上的账期约定
- **位置**：第 130-131 行 `ar.setCreditPeriod(30); ar.setDueDate(new Date(now.getTime() + 30L * 86400000));`
- **业务影响（客户视角）**：真实企业里不同客户账期不同（月结 30/60/90、货到付款）。系统对所有客户一刀切 30 天，到期日全错，财务的催收计划会被误导。客户会问："我在客户档案里维护的账期为什么没用？"——如果客户主数据根本没有账期字段，那就是主数据缺字段的更大问题。
- **修复建议**：从 `c_mes_customer`（或销售订单）读取该客户约定账期；无约定时才回落到系统参数默认值（且默认值应可配置，而非硬编码 30）。

#### 🟡 P1-3 出库单取消/红冲时，已生成的应收单无联动处理
- **位置**：`cancel()` 方法（第 138-144 行）只改出库单状态，**不触碰已生成的应收单**。
- **业务影响（客户视角）**：出库单审错了取消掉，应收台账里那笔 AR 还在，且金额照旧——财务账实不符。虽然当前 cancel 有守卫（已审核不能取消），但只要存在任何反审核/红冲路径（或未来开放），应收就会变成孤儿数据。审计/对账时客户会发现"系统里的应收和实际发货对不上"。
- **修复建议**：明确业务规则——若允许反审核，则同步作废/红冲对应应收单（状态置废或生成红字单）；若不允许反审核，需在 UI 和文档中明示客户"审核即生成应收，不可逆"。

#### 🟢 P2-1 "防重复"注释名不副实，依赖唯一索引兜底但无友好提示
- **位置**：第 118 行注释 `// 4. 自动生成应收单（防重复）`，实际代码没有先查询是否已存在该来源单的应收，仅依赖 `uk_rec_code_del (code, del_flag)` 唯一索引——而 code 规则 `AR-yyyyMMdd-出库单号` 同日同单号重审会撞唯一键。虽然当前 auditWithGuard 保证一次审核，但若未来有重审/补偿机制，撞键抛 DuplicateKeyException 对客户是裸异常。
- **修复建议**：生成前先按 `source_bill_id` 查询已存在则跳过（真正的防重复）；或在注释/异常信息中给出客户能看懂的话术。

### 2.5 `MesAccountSubjectController.java` + `MesAccountSubjectServiceImpl.java`（会计科目后端）

#### 🔴 P0-5 科目可随意物理删除，无"是否已被凭证/业务引用"检查
- **位置**：`MesAccountSubjectServiceImpl.removeById()` 第 72-78 行只检查"是否有子科目"，**不检查该科目是否已被凭证明细（c_mes_voucher_item.subject_id）引用**，也不检查是否被业务单据作为默认科目引用。且前端 index.vue 行内直接有"删除"按钮，popConfirm 仅一句"确认删除？"。
- **业务影响（客户视角）**：财务铁律是"已发生业务的科目不能删，只能停用"。客户会计删了一个已被凭证引用的科目后，历史凭证上的科目变成悬空外键，账簿查不了、报表错乱——这是**会计数据完整性事故**。实体里明明设计了 `status`（启用/停用）字段，正确做法就是禁用物理删除、引导停用。
- **修复建议**：
  1. 删除前校验 `c_mes_voucher_item` 是否存在该 subject_id 的引用，存在则拒绝并提示"该科目已被凭证引用，请使用停用"。
  2. 更稳妥：对被引用科目前端直接隐藏删除按钮，只留"停用"。

#### 🟡 P1-4 新增科目时 parentId 不可选，树形结构实际建不起来
- **位置**：`subject.data.ts` 的 `formSchema` 字段：code/name/category/level/balanceDirection/status/remark——**没有 parentId 字段**！后端实体有 parentId、有 tree 接口、SQL 有 parent_id 索引，但前端抽屉表单根本不让客户选上级科目。
- **业务影响（客户视角）**：会计科目的行业惯例是树形（如 1001 库存现金 → 100101 人民币户）。当前客户只能通过手填"级别"数字来自我安慰，**所有科目实际都是平级根节点**；"树形视图"按钮（index.vue 里 `loadTree` 实际只是 `reload()`，见 P2-2）也永远只能看到一层平铺。对客户来说"树形科目"是虚假宣传。
- **修复建议**：formSchema 增加 `parentId` 字段，用 TreeSelect 组件（数据来自 `/tree` 接口）；选择父级后自动带出 level=父级+1、category 继承父级。

#### 🟡 P1-5 科目级别 level 由客户手填，无校验无自动推导
- **位置**：`subject.data.ts` formSchema 中 level 是 `InputNumber` 默认值 1；后端 `validate()` 不校验 level 与 parentId 的一致性。
- **业务影响**：客户不知道"级别"该填几，填错后树形展示错乱；会计习惯的编码规则（4-2-2，如 1001→100101）系统完全不感知、不辅助。
- **修复建议**：level 由 parentId 自动推导（父级+1），前端只读展示；编码层面建议增加"子级编码必须以父级编码开头"的弱校验或至少前端提示。

#### 🟢 P2-2 "树形视图"按钮名不副实，点击只是刷新列表
- **位置**：`subject/index.vue` 中 `function loadTree() { reload(); }`——按钮文案"树形视图"，实际行为是重新加载平铺分页列表。`subject.api.ts` 里 `querySubjectTree()` 定义了但**页面没有任何地方调用**。
- **业务影响**：客户点"树形视图"期待看到层级树，结果只是列表闪了一下——认为功能坏了。
- **修复建议**：接入 `/tree` 接口，将 BasicTable 切换为树形表格（`isTreeTable` + children 字段），或移除该按钮。

#### 🟢 P2-3 新增科目默认值风险：isLeaf 固定写死、父级复活场景边界
- **位置**：`SubjectDrawer.vue` 中 `setFieldsValue(data.record || { status: '1', level: 1, isLeaf: 1 })`；`MesAccountSubjectServiceImpl.save()` 第 50 行无条件 `entity.setIsLeaf(1)`。若客户以某科目为父新增子级后，再把该父级下的子科目全部删除，父级 isLeaf 不会回到 1（无回写逻辑）。
- **业务影响**：树形展示时"已无子级的科目仍显示可展开"，小问题但会计会困惑。
- **修复建议**：删除子科目后检查父级剩余子级数，为 0 则回写 isLeaf=1。

#### 🟢 P2-4 删除已删科目后"复活"机制对客户不可见，可能吓到客户
- **位置**：`MesAccountSubjectServiceImpl.save()` 第 52-58 行：新增科目时若发现同 code 的已删除记录，会**静默复活旧记录**（保留原 createBy/createTime）。
- **业务影响**：客户删了"1001 现金"，再新建"1001 银行存款"（同名 code 不同 name），系统会把旧"现金"科目复活改成"银行存款"——旧凭证如果引用了这个 id，科目名就**在历史凭证上被改名了**，这对会计是不可接受的（历史凭证的科目名称应当固化）。当前虽然凭证模块未上线暂无实害，但凭证上线即爆雷。
- **修复建议**：复活机制仅允许在"同名同性质"场景使用，或取消复活改为提示"该编码曾使用，已归档"；至少在凭证引用存在时禁止复活改语义。

### 2.6 `V9.0.0__mes_finance_init.sql` + `MesMenuRegistry.java`

#### 🟡 P1-6 菜单注册了"凭证管理"，但凭证模块前后端均未实现——客户点进去是 404/空页
- **位置**：`MesMenuRegistry.java` 第 91-92 行注册了"凭证管理"叶子菜单（路由 `/project/mes/finance/voucher`，组件 `project/mes/finance/voucher/index`，权限 `mes:voucher:*`）；SQL 建了 `c_mes_voucher` / `c_mes_voucher_item` 表和 `mes_voucher_status` 字典——但**没有任何 voucher 的 Java 代码，也没有前端 voucher 目录**。
- **业务影响（客户视角）**：客户在菜单里看到"凭证管理"，点进去前端路由找不到组件（404 或白屏）。凭证是财务模块的心脏，客户看到菜单却用不了，会直接判定"这是个半成品"。
- **修复建议**：二者择一——① 本次交付隐藏凭证菜单（注释掉注册代码），避免给客户错误预期；② 补齐凭证管理最小闭环（手工凭证 CRUD + 借贷平衡校验）。**强烈建议 ①**，因为凭证模块涉及过账、审核、作废完整状态机，仓促上线风险更大。

#### 🟢 P2-5 字典"应收状态/应付状态"只有三个终态，无"已逾期"
- **位置**：SQL 字典 `mes_receivable_status` / `mes_payable_status` 仅：未结清(1)/部分结清(2)/已结清(3)。
- **业务影响**：见 P1-1，逾期是财务催收的核心状态，字典层就缺。
- **修复建议**：可不加字典值，逾期作为**派生状态**（dueDate < today 且未结清）在前端计算展示即可，避免双写不一致。

#### 🟢 P2-6 应收/应付单号的可读性尚可，但与来源单号拼接偏长
- **位置**：`AR-yyyyMMdd-出库单号`、`AP-yyyyMMdd-入库单号`。客户财务习惯的应收单号多为独立流水（如 AR20260719001）。当前拼接方式的好处是可溯源，坏处是单号长且随出库单号长度波动。
- **修复建议**：可保留，属习惯问题；但列表上建议把"来源单据号"做成可点击跳转到出库单详情（当前只是纯文本，客户想看出库单得自己记住单号去销售模块搜）。

## 四、给客户的一句话总结与修复优先级建议

**一句话总结**：当前版本把"业财联动生成单据"这一步做完了，但财务真正的日常工作——**收款、付款、对账、查欠谁钱、看哪些逾期**——一样都没有，且应付单金额是错的（恒为 0）。**不建议以当前状态交付给任何真实客户试用财务模块。**

**修复优先级（建议按此顺序排期）**：
1. **第一波（阻断级）**：P0-1 应付金额计算、P0-3/P0-4 客户/供应商列、P0-2/P0-4 收款/付款登记闭环（含流水子表）、P0-5 科目删除保护。
2. **第二波（体验级）**：P1-6 隐藏或实现凭证菜单、P1-4/P1-5 科目树可维护、P1-2 账期取自客户主数据、P1-7 手工补录入口、P1-1 逾期标识。
3. **第三波（打磨级）**：全部 P2 文案/格式/交互项。
