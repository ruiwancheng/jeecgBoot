## 逐项详查

### 1. 应收单 `amount` 是否 = 出库单 `totalAmount`，且 `totalAmount` = Σ(明细数量×单价)

**结论：一致（代码逻辑上成立，且有非零守卫）。**

证据链：

- **行金额计算**：`MesSalesOutboundServiceImpl.java:233`
  ```java
  item.setAmount(item.getActualQty().multiply(item.getUnitPrice()).setScale(2, RoundingMode.HALF_UP));
  ```
  明细 `amount = actualQty × unitPrice`，两位小数 `HALF_UP`。

- **合计计算**：`MesSalesOutboundServiceImpl.java:240-246` `calcTotal()`
  ```java
  for (MesSalesOutboundItem item : entity.getItems()) { total = total.add(item.getAmount()); }
  entity.setTotalAmount(total.setScale(2, HALF_UP));
  ```
  `totalAmount = Σ item.amount`，与明细同源，无独立计算路径，不存在"明细一套、合计一套"的漂移。

- **调用时机**：`saveWithItems` 在 `super.save` 前（L62）、`updateWithItems` 在 `updateById` 前（L77）均调用 `calcTotal`，主表落库前金额已固化。

- **应收生成**：`MesSalesOutboundServiceImpl.java:119-133`（audit 内）
  ```java
  if (e.getTotalAmount() != null && e.getTotalAmount().compareTo(BigDecimal.ZERO) > 0) {
      ar.setAmount(e.getTotalAmount());
      ar.setUnsettledAmount(e.getTotalAmount());
      receivableService.save(ar);
  }
  ```
  `ar.amount = e.totalAmount`，且三者（amount / unsettledAmount / totalAmount）同源同值。

- **遗留风险（非阻断）**：
  - `audit()` 在 L101 `queryWithItems(id)` 重新查库，但 `totalAmount` 取的是**主表字段**，而非重新 Σ 明细。若 save/update 与 audit 之间有人直接 SQL 改了明细（绕过 Service），`totalAmount` 不会重算。此为"信任已持久化合计"的设计，非缺陷，但属于对账盲区。
  - `e.getTotalAmount() == 0` 时**静默跳过**应收生成（L119 的 `> 0` 守卫），无日志、无告警。若因取价失败导致全单 0 元出库，应收将"无声消失"。

### 2. 应付单 `amount` 是否 = 入库单总额

**结论：否。`amount` 被硬编码为 `BigDecimal.ZERO`，资损实锤，与前序审计标记一致。**

硬编码位置（精确行号）：**`MesPurchaseReceiptServiceImpl.java:132`**

```java
// L124-138 audit() 内
String apCode = "AP-" + new SimpleDateFormat("yyyyMMdd").format(now) + "-" + e.getCode();
MesPayable ap = new MesPayable();
...
ap.setAmount(java.math.BigDecimal.ZERO);        // ← L132 硬编码 0
ap.setPaidAmount(java.math.BigDecimal.ZERO);
ap.setUnsettledAmount(java.math.BigDecimal.ZERO);
```

代码注释自证：`// MVP: 金额待采购价格模块完善后自动计算`。

**影响**：
- 所有采购入库审核后生成的应付单 `amount = 0`、`unsettled = 0`。
- 财务侧应付账龄、供应商对账、付款计划全部失真。
- 因 `unsettledAmount = 0`，任何按"未付余额"驱动的付款审批流都不会触发，属于**实质性资金流失控**。

**根因**（为何算不出来）：入库明细 `MesPurchaseReceiptItem` **根本没有 `unitPrice` / `amount` 字段**（见实体 L22-45，仅 `orderQuantity` / `receiptQuantity` / `qcResult`），DDL `V6.0.2__mes_purchase_receipt_init.sql` L27-41 同样无金额列。要算入库总额必须回查 `c_mes_purchase_order_item.unitPrice` 按 `materialId` 匹配——这正是第 3 项 `items.get(0)` 同款隐患在采购侧的镜像。

### 3. 销售出库取单价是否用 `items.get(0)`，多行同物料时是否错价

**结论：是，两处均用 `get(0)` 取首行，多行同物料不同价时必然错价。**

**位置一（销售出库）**：`MesSalesOutboundServiceImpl.java:226-228`
```java
LambdaQueryWrapper<MesSalesOrderItem> oiQw = new LambdaQueryWrapper<>();
oiQw.eq(MesSalesOrderItem::getOrderId, e.getSalesOrderId())
   .eq(MesSalesOrderItem::getMaterialId, item.getMaterialId());
java.util.List<MesSalesOrderItem> orderItems = salesOrderItemMapper.selectList(oiQw);
if (!orderItems.isEmpty() && orderItems.get(0).getUnitPrice() != null) {
    item.setUnitPrice(orderItems.get(0).getUnitPrice());   // ← L227-228 get(0)
}
```

**位置二（发货单，同病）**：`MesDeliveryNoteServiceImpl.java:172-175`
```java
java.util.List<MesSalesOrderItem> ol = salesOrderItemMapper.selectList(piQw);
if (!ol.isEmpty() && ol.get(0).getUnitPrice() != null) {
    item.setUnitPrice(ol.get(0).getUnitPrice());           // ← get(0)
}
```

**错价场景**：
- 销售订单允许同一 `materialId` 出现多行（`MesSalesOrderItem` 表无 `(order_id, material_id)` 唯一约束，见 `V3.0.0` 系 DDL）。
- 若业务上"同物料分批给价"（如第 1 行 100 元、第 2 行促销 80 元），`selectList` 按主键/插入序返回，`get(0)` 永远拿到**最早插入的那行价**。
- 出库/发货明细并不关联到具体的 `salesOrderItemId`（实体里只有 `materialId`，无 `orderItemId` 外键），因此**无法精确定位应取哪一行的价**——这是数据模型层面的缺陷，不是简单改 `get(0)` 能根治的。

**次生问题**：`if (unitPrice == null || unitPrice.compareTo(ZERO) == 0)` 才回查订单价。意味着前端传了 `unitPrice = 0.01`（恶意或脏数据），后端**不会**用订单价覆盖，直接信任前端。结合 `checkDeliveryQty` 只管数量不管价，存在**低价高录**的舞弊空间。

### 4. 税率/含税/不含税金额在哪些环节被忽略

**结论：税务字段只在采购订单内部闭环，跨模块全部断链；销售侧全链路无税概念。**

| 环节 | 税额处理 | 证据 | 风险 |
|------|----------|------|------|
| **采购订单** `calcTotal` | ✅ 逐行算税：`taxTotal += amount × taxRate`，默认税率 0.13 | `MesPurchaseOrderServiceImpl.java:142-155`；默认税率 L134 `item.setTaxRate(new BigDecimal("0.13"))` | 唯一闭环 |
| **采购入库 → 应付** | 🔴 **完全忽略**。入库明细无税率/单价字段；应付 `amount=0` 硬编码，更谈不上区分不含税/税额/含税 | `MesPurchaseReceiptItem` 无字段；`MesPurchaseReceiptServiceImpl.java:132` | 应付即无本也无税 |
| **销售订单** | 🟠 实体只有 `totalAmount`，无 `taxAmount` / `totalWithTax` / `taxRate` 字段 | `MesSalesOrder.java:55`；`MesSalesOrderItem.java` 无 `taxRate` | 销售侧税务空白 |
| **发货单 / 销售出库** | 🔴 无税字段，`unitPrice`/`amount` 未注明含税或不含税 | `V8.0.0__mes_sales_amount_fields.sql` 仅加 `total_amount`/`unit_price`/`amount` | 价税不明 |
| **应收单** | 🔴 无 `taxAmount` / `taxRate` / `withTaxAmount` 字段，`amount` 性质未定义 | `MesReceivable.java`；`V9.0.0` L31-53 | 应收开不了票 |

**关键断点**：采购订单的 `totalWithTax`（含税总额）算得再准，也**没有传递**到入库单，更到不了应付单。应付生成时既没引用 `purchaseOrder.totalWithTax`，也没按入库比例分摊，直接置 0。销售侧则连字段都没有，后续要加"销项税"必须动表结构。

### 5. 出库单审核后取消/删除，应收单是否联动（红冲机制）

**结论：零联动，无红冲，无反向应收。全代码库检索不到任何红冲/反审核逻辑。**

证据：

- **全库无红冲关键字**：`grep -ri "红冲\|red.*flush\|reversal\|reverse\|unaudit\|antiAudit" src/main/java/org/jeecg/modules/mes` → **0 命中**。
- **取消出库 `cancel()`**：`MesSalesOutboundServiceImpl.java:138-144`
  ```java
  public void cancel(String id) {
      int rows = baseMapper.cancelWithGuard(id, username, now);  // 仅改状态
      if (rows == 0) throw ...;
  }
  ```
  只 `UPDATE status`，**没有**：回补库存、回写发货单状态、删除/红冲应收单。
- **删除出库 `removeWithItems` / `removeByIds`**：L84、L87-95。`checkStatus` 要求"非草稿禁止删除"，所以**已审核单删不掉**——但 `cancel()` 把状态改成 `0`（已取消）后，应收单已成事实，无人清理。
- **应收侧无清理入口**：`MesReceivableServiceImpl` 是空 `ServiceImpl`（L11-12），`MesReceivableController` 只有 `list/queryById/queryAll/exportXls`（L32-52），**没有 delete/cancel/audit 任何写操作**，连手工删除应收的 API 都不存在。
- **库存同样不联动**：`cancel()` 不调用 `inventoryService.stockIn` 回补，已扣的库存永久沉没。

**资损/账实不符后果链**：
```
出库审核(扣库存+生应收) → 取消出库(仅改状态)
   ⇒ 库存少了、应收还在、实物没出 → 三处全错，且无单据可追
```

### 6. 库存台账与应收/应付生成是否在同一事务

**结论：在同一事务内（`@Transactional` 包住），但缺乏对账保障与失败告警，属于"同事务的脆弱联动"。**

证据：

- **销售出库审核**：`MesSalesOutboundServiceImpl.java:99-136`，方法级 `@Transactional(rollbackFor = Exception.class)`（L99）。内部顺序：
  1. L107 `auditWithGuard` 原子改状态
  2. L110-112 `inventoryService.stockOut(...)`（`MesInventoryServiceImpl.stockOut` 也带 `@Transactional`，L44，按 Spring 默认 `REQUIRED` 传播，**加入外层事务**）
  3. L115 更新发货单状态
  4. L119-133 `receivableService.save(ar)`（`MesReceivableServiceImpl` 无显式 `@Transactional`，但 `ServiceImpl.save` 走 `SqlSessionTemplate`，参与外层事务）

  → 任一环节抛异常整体回滚，**原子性 OK**。

- **采购入库审核**：`MesPurchaseReceiptServiceImpl.java:110-140`，同样 `@Transactional`（L111），先 `stockIn` 再 `payableService.save(ap)`，同事务。

**但存在三个"同事务也救不了"的问题**：

1. **无对账补偿**：事务只保证"同时成功/同时失败"，不保证"金额算对"。应付 `amount=0` 是在事务内被正确持久化的错误数据。
2. **`totalAmount=0` 静默跳过**（销售侧 L119）：出库审核成功、库存扣了、应收**故意不生**，事务照样提交。这不是异常路径，是设计路径，无日志。
3. **台账与应收无勾稽字段**：`MesInventoryLedger` 只记数量（`beginningQty/inQty/outQty/endingQty`，`MesInventoryServiceImpl.java:66-78`），不记金额；应收只记金额不记数量。两张表**没有可 JOIN 的勾稽键**（应收 `sourceBillNo` 是出库 `code`，台账 `bizId` 也是 `code`，能对上，但无金额-数量交叉校验逻辑），事后对账只能靠人工 SQL。

### 7. 数据库 CHECK 约束 / NOT NULL 是否覆盖关键金额字段

**结论：覆盖严重不足。关键金额字段大面积可空、无 CHECK、无非负约束，裸奔。**

逐表核对（`V9.0.0__mes_finance_init.sql` + `V8.0.0__mes_sales_amount_fields.sql` + `V5.0.0` + `V6.0.2`）：

| 表 | 字段 | 约束 | 缺口 |
|----|------|------|------|
| `c_mes_receivable` | `amount` | `DECIMAL(18,2) NOT NULL` (V9 L38) | ✅ NOT NULL，但**无 CHECK(amount>=0)** |
| `c_mes_receivable` | `received_amount` | `DEFAULT 0`，**可空** (L39) | 🟠 可空 |
| `c_mes_receivable` | `unsettled_amount` | **无任何约束，可空** (L40) | 🔴 可空 |
| `c_mes_payable` | `amount` | `NOT NULL` (L65) | ✅ NOT NULL，无 CHECK |
| `c_mes_payable` | `paid_amount` / `unsettled_amount` | `DEFAULT 0` / **可空** (L66-67) | 🔴 `unsettled` 可空 |
| `c_mes_sales_outbound` | `total_amount` | `DEFAULT NULL` (V8 L10) | 🔴 **可空** |
| `c_mes_sales_outbound_item` | `unit_price` / `amount` | `DEFAULT NULL` (V8 L18,26) | 🔴 **可空** |
| `c_mes_sales_outbound_item` | `actual_qty` | 无约束 (V5 L26) | 🔴 可空、无 `>0` CHECK |
| `c_mes_purchase_receipt_item` | `receipt_quantity` | 无约束 (V6.0.2 L33) | 🔴 可空 |
| `c_mes_voucher` | `total_debit` / `total_credit` | 无约束，可空 (V9 L92-93) | 🔴 借贷平衡无 CHECK |

**全库 CHECK 约束数量**：`grep -ri "CHECK" db/` → **0 个**（搜索命中均为 NOT NULL / UNIQUE，无一处 `CHECK (...)`）。

**含义**：
- 金额/数量是否非负，**100% 依赖 Java 层 `validate()`**。任何绕过 Service 的写入（直接 SQL、Mapper 自写 SQL、后续新写的 Controller、数据修复脚本）都能塞进负数金额、负数量、NULL 合计。
- `c_mes_receivable.unsettled_amount` 可空 + Java 里 `setUnsettledAmount(totalAmount)`（L129），若将来有代码路径忘了 set，DB 层不会拦截，对账时 NULL 参与比较直接漏行。
- 凭证明细 `debit_amount`/`credit_amount` 可空且无 `debit+credit` 平衡约束，凭证主表 `total_debit`/`total_credit` 也无相等 CHECK——借贷失衡在 DB 层完全无感。

## 修复建议（按优先级）

| 优先级 | 问题 | 建议 |
|--------|------|------|
| **P0-1** | 应付 `amount=0` 硬编码（`MesPurchaseReceiptServiceImpl.java:132`） | 入库审核时按 `materialId` 回查采购订单行 `unitPrice`，`Σ(receiptQty × unitPrice)` 赋值；同步决定是否用 `totalWithTax` 含税口径 |
| **P0-2** | 取消出库不红冲应收、不回补库存 | `cancel()` 增加：①`stockIn` 回补；②按 `sourceBillId` 查应收，生成红字应收（负金额）或置状态为作废；③回写发货单状态 |
| **P0-3** | 税务字段全链路缺失 | 销售订单/发货/出库/应收补齐 `taxRate/taxAmount/withTaxAmount`；应付生成引用采购订单 `taxAmount` 口径 |
| **P1-1** | 取价 `get(0)` 错价 | 出库/发货明细加 `orderItemId` 外键精确定位订单行；或至少按 `(materialId, unitPrice)` 匹配并告警多行 |
| **P1-2** | DB 无 CHECK | `ALTER TABLE ... ADD CHECK (amount >= 0)`、`unsettled_amount NOT NULL`、`actual_qty > 0`、凭证 `total_debit = total_credit` |
| **P1-3** | `totalAmount=0` 静默跳过应收 | 加 `log.warn` + 业务告警表，或对 0 元出库强制人工确认 |
| **P2** | 台账无金额 | `MesInventoryLedger` 增加 `unitPrice`/`amount`，建立数量-金额勾稽 |
