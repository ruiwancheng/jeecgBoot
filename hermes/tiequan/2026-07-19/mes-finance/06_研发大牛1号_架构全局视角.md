> **审计对象**：MES 财务模块（会计科目 `subject` / 应收账款 `receivable` / 应付账款 `payable`）

## 一、总体结论（TL;DR）

| 维度 | 结论 | 评级 |
|------|------|------|
| 标准三层架构 | ✅ 严格遵循 `Controller→Service→Mapper`，包路径与 JeecgBoot 约定一致 | 🟢 优 |
| JeecgBoot 基础组件复用 | ✅ `JeecgController`/`QueryGenerator`/`Result`/`@Dict`/AutoPoi 全部正确复用 | 🟢 优 |
| 命名规范 | ✅ 表名 `c_mes_*`、权限码 `mes:xxx:*`、组件名 `MesXxx` 一致 | 🟢 优 |
| 业财联动耦合方式 | ⚠️ **硬编码直连**：上游 `audit()` 内 `@Autowired` 财务 Service 并直接 `save()`，无事件/消息解耦 | 🟡 中 |
| 数据库设计 | ⚠️ 主键/唯一索引/逻辑删除规范，但**外键缺席、索引偏少、金额精度 18,2 够用但无分库分表预留字段** | 🟡 中 |
| 接口契约 | ⚠️ 应收/应付是**只读 API**（无 add/edit/delete/audit），前端只暴露查询+导出，符合"凭证由业务产生"设计，但缺结清/核销接口 | 🟡 中 |
| **凭证管理** | 🔴 **菜单已注册、权限码已分配、SQL 已建表，但后端 0 个 Java 文件、前端 0 个文件** —— 典型架构债务 | 🔴 高 |
| 应收金额来源 | 🔴 采购入库 hook 中 `ap.setAmount(BigDecimal.ZERO)` —— **应付单生成时金额恒为 0**，业务上等同于"记账失败" | 🔴 高 |

**整体评价**：财务模块的**代码骨架是教科书级的 JeecgBoot 标准实现**（三层清晰、组件复用规范、命名统一），但**业财联动的耦合方式是典型的"意大利面条式直调"**，且凭证模块处于"菜单已开、后端未建"的半拉子状态，应收/应付金额计算链路不完整，**距离"可投产的业财一体化"还差关键三步**。

## 四、业财联动耦合方式 — 🟡 中等风险（重点）

### 4.1 当前实现：硬编码直调

**采购入库 → 应付**（`MesPurchaseReceiptServiceImpl.audit()` 行 41-43, 124-139）：
```java
@Autowired private IMesPayableService payableService;   // 硬依赖
...
// audit() 末尾：
MesPayable ap = new MesPayable();
ap.setCode("AP-" + yyyyMMdd + "-" + e.getCode());
ap.setSupplierId(e.getSupplierId());
ap.setSourceType("采购入库");
ap.setAmount(BigDecimal.ZERO);        // 🔴 金额恒为 0！
ap.setPaidAmount(BigDecimal.ZERO);
ap.setUnsettledAmount(BigDecimal.ZERO);
payableService.save(ap);               // 同事务直接落库
```

**销售出库 → 应收**（`MesSalesOutboundServiceImpl.audit()` 行 46-48, 117-135）：结构相同，区别是 `ar.setAmount(e.getTotalAmount())` 有真实金额。

### 4.2 问题诊断

| 问题 | 严重度 | 说明 |
|---|---|---|
| **硬编码跨模块 `@Autowired`** | 🟡 中 | `purchase.receipt` 直接依赖 `finance.payable`，`sales.outbound` 直接依赖 `finance.receivable`。财务模块若重构/拆库/改接口，上游必须同步改代码重编译 |
| **无事件/消息解耦** | 🟡 中 | 全 project-mes 模块搜不到 `ApplicationEventPublisher`/`@EventListener`/`RocketMQ`/`Kafka`/`Rabbit` —— 一个事件机制都没有。审核动作和财务动作被绑死在同一个本地事务里 |
| **同事务强一致** | 🟡 中 | `payableService.save(ap)` 在 `@Transactional audit()` 内。若财务表慢/锁/失败，**采购入库审核会整体回滚** —— 业务可用性受财务拖累 |
| **金额计算时机错误** | 🔴 高 | 采购入库审核时，**入库金额还没算出来**（代码注释自承"MVP: 金额待采购价格模块完善后自动计算"），就把 `amount=0` 的应付单落库了。这等同于**财务端记了一笔 0 元应付款**，后续要么人工改、要么留脏数据 |
| **无防重机制** | 🟡 中 | 销售出库 hook 有 `if (totalAmount > 0)` 防御，但**没有"同一 sourceBillId 是否已生成过应收"的校验**。若 audit 接口被重试/幂等失效，会重复生成应收单（虽有 `uk_rec_code_del` 唯一索引兜底会抛 DuplicateKey，但错误体验差） |
| **审核/反审核缺反向联动** | 🟡 中 | 只有"审核生成应收/应付"，没有"取消审核红冲应收/应付"的对应逻辑（`cancel()` 方法里没动财务表） |

### 4.3 改进建议（事件驱动解耦）

**推荐方案：Spring 领域事件（`ApplicationEventPublisher`）+ 事务同步监听**

```java
// 1. 定义事件（放在 mes-api 或 common 包）
public class PurchaseReceiptAuditedEvent {
    private final String receiptId;
    private final String receiptCode;
    private final String supplierId;
    // ...
}

// 2. 上游改为发布事件（不再 @Autowired 财务 Service）
@Service
public class MesPurchaseReceiptServiceImpl {
    @Autowired private ApplicationEventPublisher eventPublisher;

    @Transactional
    public void audit(String id) {
        // ... 原有审核逻辑 ...
        eventPublisher.publishEvent(new PurchaseReceiptAuditedEvent(...));
    }
}

// 3. 财务模块监听
@Component
public class PayableEventListener {
    @Autowired private IMesPayableService payableService;

    @TransactionalEventListener(phase = AFTER_COMMIT)   // 主事务提交后再生成应付
    public void on(PurchaseReceiptAuditedEvent e) {
        // 生成应付，失败不影响入库审核
    }
}
```

**收益**：
- 上游只依赖事件对象（POJO），不依赖财务 Service 接口 → 模块可独立部署/拆分
- `AFTER_COMMIT` 保证审核先落库，财务失败不会拖垮审核
- 未来若要发 MQ（RocketMQ/Kafka），只需改 Listener，上游零改动

**配套措施**：
1. `c_mes_receivable` / `c_mes_payable` 增加 `source_bill_id + source_type` 唯一约束 → 数据库层防重
2. 金额计算应在审核前由 `purchase.receipt` 自己完成（调用采购价格模块），而非留给财务钩子

## 五、数据库设计审计 — 🟡 中等

### 5.1 已做到位的

- ✅ 主键统一 `VARCHAR(32)` + 雪花 ID
- ✅ 唯一索引 `(code, del_flag)` 支持逻辑删除后复用编码
- ✅ 审计字段 `create_by/create_time/update_by/update_time` 全齐
- ✅ `del_flag` 逻辑删除统一
- ✅ 金额字段 `DECIMAL(18,2)`（无 float/double 陷阱）
- ✅ 字典表 `mes_subject_category` / `mes_balance_direction` / `mes_receivable_status` / `mes_payable_status` / `mes_voucher_status` 全部预置

### 5.2 问题清单

| 问题 | 位置 | 严重度 | 建议 |
|---|---|---|---|
| **无外键约束** | 全部 5 张表 | 🟡 中 | `c_mes_receivable.customer_id → c_mes_customer.id`、`c_mes_voucher_item.subject_id → c_mes_account_subject.id` 等均无 FK。JeecgBoot 习惯不加 FK（便于水平扩展），但**至少应在应用层校验引用完整性**（当前 `MesReceivableServiceImpl` 是空类，无任何校验） |
| **`source_bill_id` 无索引** | receivable / payable | 🟡 中 | 按来源单据反查财务单（"这笔出库生成应收了吗"）是高频操作，建议加 `INDEX idx_source_bill (source_type, source_bill_id)` |
| **`source_bill_id` 无唯一约束** | receivable / payable | 🟡 中 | 应加 `UNIQUE (source_type, source_bill_id, del_flag)` 防止一笔业务生成多张财务单 |
| **无分库分表预留** | 全部 | 🟢 低 | 无 `tenant_id` / `shard_key` 字段。当前单体 MES 可接受，但**若未来 SaaS 化或多工厂部署，应收/应付表数据量会爆**（财务单只增不减），建议至少预留 `tenant_id` |
| **`c_mes_voucher_item` 无 `del_flag`** | voucher_item | 🟡 中 | 主表有 del_flag，明细表没有 —— 删除凭证时若只软删主表，明细变孤儿数据 |
| **`due_date` 用 DATETIME 而非 DATE** | receivable / payable | 🟢 低 | 到期日语义上是"日期"而非"时间戳"，DATETIME 会引入时区/比较歧义 |
| **索引未覆盖高频查询** | receivable / payable | 🟡 中 | "某客户的未结清应收" 需要 `(customer_id, status)` 复合索引；"到期提醒" 需要 `(status, due_date)` 复合索引。当前只有单列索引 |

### 5.3 SQL 部署位置问题 🔴

`V9.0.0__mes_finance_init.sql` 位于 `project-mes/db/`，**但 JeecgBoot 的 Flyway 扫描路径是** `jeecg-module-system/jeecg-system-start/src/main/resources/flyway/sql/mysql/`。

**结果**：这份 SQL **不会被 Flyway 自动执行**，需要手工导入或额外配置 `spring.flyway.locations`。这是部署链路的一个暗坑 —— 建议要么移到 flyway 目录，要么在 `application-*.yml` 显式追加 location。

**设计评价**：
- ✅ 符合"财务单据由业务动作（审核）触发，不允许手工增删改"的内控原则
- 🔴 但**缺"收款/付款核销"接口**——实际业务中，财务必须能登记"实收/实付"来冲销应收应付。当前 `receivedAmount/paidAmount/unsettledAmount/settlementDate` 字段都建了，却没有任何 API 能更新它们，**这是一个断头路设计**——应收应付生成后永远无法结清

### 6.3 接口契约缺陷

1. **`MesReceivableServiceImpl` / `MesPayableServiceImpl` 是空类**（只有 `extends ServiceImpl`，0 行业务代码）—— 所有"核销/结清/反审核红冲"业务都无处安放
2. **`MesReceivable` / `MesPayable` 实体字段验证缺失** —— 应收单 `amount` 是 `NOT NULL`，但 Service 层没有 `@NotNull` / `@DecimalMin` 校验注解，若直接调底层 save 可写入 null 触发 DB 异常
3. **`code` 生成规则硬编码在 Controller 之外**：`"AP-" + yyyyMMdd + "-" + e.getCode()` 这种规则应该走 JeecgBoot 的**编码规则生成器**（`sys_fill_rule` 或 `@Rule` 注解），而非手写字符串拼接。日期前缀意味着跨天重试会生成不同 code，幂等性差

## 九、其他架构级观察

### 9.1 代码复用机会

三个 Mapper 都有完全相同的 `selectDeletedByCode` + `resurrect` 模板（逻辑删除复活）。建议：
- 抽取 `BaseResurrectMapper<T>` 接口，定义默认方法
- 或在 `MesAccountSubjectServiceImpl.save()` 中使用的复活逻辑提取成 `AbstractResurrectService<T>` 基类

三个 Controller 都重复了 `QUERY_ALL_MAX = 5000` 常量。建议下沉到 `JeecgController` 或 `MesBaseController`。

### 9.2 命名规范 — 全部合规

| 检查项 | 结果 |
