## 逐项分析

### 一、产品视角

#### ✅ 正向流程：拖宽 → 刷新 → 宽度保持

**代码路径**：

```
拖动完成 → @resizeColumn → handleResizeColumn(w, col)
  → findItem.width = w（内存）
  → setColumns(columns)（更新视图）
  → saveTableColumnWidths(cacheKey, columns)（写入 localStorage）

刷新 → watchEffect → init()
  → columnCache?.columnWidths 分支（useColumnsCache.ts:107）
  → 遍历 table.getColumns()，按 key||dataIndex 匹配
  → col.width = cachedWidth → table.setColumns(columns)
```

**结论**：路径完整，正向流程可行。 ✓

#### ✅ P0 场景：仅拖过列宽，从未打开列配置面板点保存（checkedList 为空）

**关键代码**：`useColumnsCache.ts:107-118`

```typescript
// 宽度恢复独立于 checkedList 门控
if (columnCache?.columnWidths) {
  await nextTick();
  const columns = table.getColumns();
  for (const col of columns) {
    if (col.flag) continue;
    const key = col.key || col.dataIndex;
    if (key && columnCache.columnWidths[key] != null) {
      col.width = columnCache.columnWidths[key];
    }
  }
  table.setColumns(columns);
}
```

`handleResizeColumn` → `saveTableColumnWidths` 写入 `{ columnWidths: { "colA": 200 } }` 到 localStorage，此时缓存无 `checkedList`。刷新后 `init()` 的 `checkedList` 门控为 false → 跳过显隐/排序恢复，但 `columnWidths` 分支独立执行 → 宽度恢复成功。

**注意**：`saveTableColumnWidths()` 用了 read-modify-write 模式（`$ls.get(cacheKey) || {}` → 追加 `columnWidths` → `$ls.set`），不会覆盖可能已存在的 `checkedList/sortedList`。即使以后用户又点了保存配置、或缓存同时有 `checkedList` 和 `columnWidths`，两者共存不冲突。

**结论**：该场景已正确处理。 ✓

#### ⚠️ 重置行为：列宽恢复默认

**重置流程**：`ColumnSetting.vue:329-351`

```typescript
function reset() {
  setColumns(table.getCacheColumns());  // 1) 恢复到原始列定义(含默认width)
  setTimeout(() => {
    // ... 2) 重置 checkbox/排序状态 ...
    resetSetting();                      // 3) $ls.remove(cacheKey) 清除全部缓存
  }, 100);
}
```

| 步骤 | 行为 | 宽度影响 |
|------|------|:--:|
| `setColumns(table.getCacheColumns())` | 用原始 cacheColumns 重建列 | 宽度恢复为列定义默认值 ✓ |
| `resetSetting()` → `$ls.remove` | 删除整个 localStorage key | 清除列宽缓存 ✓ |
| 刷新后 | 无缓存 → 使用列定义默认 width | ✓ |

**P2 提醒**：重置只删缓存，不重置 `columnsRef` 中已变更的 width 属性。但 `getCacheColumns()` 返回的原始定义不含用户拖宽，`setColumns(table.getCacheColumns())` 已覆盖 `columnsRef`。刷新后无缓存 → 原始宽度。行为正确。唯一的不完美是：如果在重置→刷新之间 watchEffect 再次触发 init()，因 `isInit=true` 跳过，不会二次读缓存覆盖。✓

**结论**：宽度重置行为正确。 ✓

#### ✅ 多路由隔离

**缓存 key 计算公式**：`columnCache:` + `route.path.replace(///\\/g, '_')` + 可选 `:tableSetting.cacheKey` 后缀

不同路由 path 生成不同 key → 各自独立。同一路由下多表格通过 `tableSetting.cacheKey` 区分。与现有显隐缓存机制完全一致。

**结论**：路由隔离正确。 ✓

### 二、研发视角

#### ✅ computeColumnCacheKey 与内部 cacheKey 一致性

| 位置 | 计算逻辑 |
|------|---------|
| `computeColumnCacheKey()`（行 12-18） | `routePath.replace(/[\/\\]/g, '_')` + `:suffix` → `'columnCache:' + key` |
| `useColumnsCache` 内部 computed（行 61-70） | `route.path.replace(/[\/\\]/g, '_')` + `:table.getBindValues.value.tableSetting?.cacheKey` → `'columnCache:' + key` |

- 相同的 `replace` 正则 `/[/\\]/g`
- 相同的 `columnCache:` 前缀
- BasicTable.vue 调用方式：`computeColumnCacheKey(route.path, unref(getProps).tableSetting?.cacheKey)` — `route.path` 与内部 `route.path` 是同一对象。`unref(getProps).tableSetting` 与 `table.getBindValues.value.tableSetting` 等价（getBindValues 展开自 getProps）。→ 两者产生完全相同的 key。

**结论**：key 一致性有保障。 ✓

#### ✅ saveTableColumnWidths 与 saveSetting 写入竞争

**两种写入模式**：

| 函数 | 模式 | 数据源 |
|------|------|--------|
| `saveTableColumnWidths` | read-modify-write（读缓存→只更新 `columnWidths`→写回） | `columns` 参数（BasicTable 的 `getColumns()`） |
| `saveSetting` | 全量覆盖（构建完整对象→写回） | `opt.plainOptions.value`（ColumnSetting 组件内） |

**关键分析**：
1. JS 单线程 → 不存在并发竞态
2. `saveTableColumnWidths` 的 read-modify-write **保留了** `checkedList/sortedList/fixedColumns` 等字段，不会覆盖为 `undefined`
3. `saveSetting` 的全量写入也**包含了** `columnWidths: getColumnWidths()`，不会把宽度写丢
4. 两者数据源不同（`getColumns()` vs `opt.plainOptions`），可能短暂不同步，但用户点保存前，ColumnSetting 的 `watch([getColumnsRef])` 会触发 `init()` 重新同步 `plainOptions`，所以 `saveSetting` 调用时的 `plainOptions` 已反映最新状态。

**结论**：写入竞争风险低，不会导致数据丢失。 ✓

#### ✅ 列身份标识一致性

**统一使用 `column.key || column.dataIndex` 作为缓存键**：

| 位置 | 标识 | 代码行 |
|------|------|--------|
| `saveTableColumnWidths` | `col.key \|\| col.dataIndex` | useColumnsCache.ts:32 |
| `getColumnWidths` | `column.key \|\| column.dataIndex` | useColumnsCache.ts:160 |
| `init()` 宽度恢复 | `col.key \|\| col.dataIndex` | useColumnsCache.ts:112 |
| `getFixedColumns` | `column.key \|\| column.dataIndex` | useColumnsCache.ts:145 |
| `setColumnFixed` | `fc.key` 匹配 `column.key \|\| column.dataIndex` | useColumnsCache.ts:127 |
| `handleResizeColumn` 列匹配 | `item['dataIndex']` 优先 → `item['flag']` fallback | BasicTable.vue:425-428 |

`handleResizeColumn` 的列匹配用 `dataIndex/flag`（与宽度缓存的 `key||dataIndex` 不同），但：
- 当 `key === dataIndex` 或 `!key && dataIndex` 时，两者一致
- 当 `key !== dataIndex` 时，匹配的列对象的 `key` 字段就是正确的标识，`saveTableColumnWidths` 用它存宽度。恢复时也用 `key` 查找，匹配正确
- `flag` fallback 只用于 INDEX/ACTION 等特殊列（不会被保存——`col.flag` 跳过）

**结论**：标识一致性问题在本次改动中已规避——flag 列被跳过；`key||dataIndex` 三处一致。 ✓

#### ⚠️ localStorage.set() 无异常保护

**代码路径**：`saveTableColumnWidths()` → `$ls.set()` → `WebStorage.set()` → `this.storage.setItem(...)`

`storageCache.ts:63-71`：
```typescript
set(key: string, value: any, expire: number | null = timeout) {
  const stringData = JSON.stringify({...});
  const stringifyValue = this.hasEncrypt ? this.encryption.encryptByAES(stringData) : stringData;
  this.storage.setItem(this.getKey(key), stringifyValue);  // ← 无 try/catch
}
```

**风险场景**：
- 浏览器隐私模式 + localStorage 禁用 → `SecurityError`
- localStorage 配额满（5-10MB）→ `QuotaExceededError`
- Safari ITP 限制 → `QuotaExceededError`

**影响**：异常会从 `handleResizeColumn` 抛出，传播到 Ant Design Vue 内部的 resize handler。由于 `@resizeColumn` 是表格内部事件链的一部分，异常可能导致列宽拖动视觉效果异常（列宽已变但后续清理逻辑中断）。`saveSetting()` 同样受影响（点保存抛错）。

**评级**：P2。原因：
1. `saveSetting()` 同样无异常处理（**非本次引入**，是已有模式）
2. 触发概率低（localStorage 通常 5-10MB，列宽数据 ~500B/页面）
3. `get()` 有 try/catch（line 82-92），读取失败返回默认值不崩溃

**修复建议（可选）**：在 `saveTableColumnWidths` 内部加 try/catch + `console.warn`，静默降级不打断拖动流程。`saveSetting` 的建议同理但本次不要求。

#### ✅ 内存泄漏 / localStorage 增长

- 每个缓存条目 `columnWidths` 约 N × 20 字节（N=列数，30 列 ≈ 600 字节）
- 100 个不同路由页面全部可拖动 = ~60KB
- `createLocalStorage` 使用 `DEFAULT_CACHE_TIME = 60*60*24*7`（7 天过期），`get()` 时自动检查并 `remove()` 过期条目

**结论**：无无限增长风险。 ✓

| 缓存内容 | `columnWidths` 字段 | 行为 |
|----------|:--:|------|

| 空缓存 | 不存在 | `|| {}` → 跳过 |

#### ✅ TC5：表尾合计列宽同步（issues/7101）

`handleResizeColumn` 中已有逻辑（BasicTable.vue:422-435）：
```
const columns = getColumns();
const findItem = columns.find(...);
if (findItem) { findItem.width = w; setColumns(columns); }  // ← 同步到 columnsRef
col.width = w;  // ← 同步到事件传入的 col 对象（防呆）
saveTableColumnWidths(cacheKey, columns);                    // ← 新增持久化
```

`saveTableColumnWidths` 在 `setColumns` 之后调用，传入的 `columns` 已含更新后的宽度。表尾合计列宽同步逻辑不受影响——`setColumns` 会触发 `columnsRef` 变化 → `getViewColumns` 重新计算 → 合计行列宽从 columns 读取 → 正确。

**结论**：issues/7101 逻辑保持完整。 ✓
