## 结论

本次改动整体质量良好：update 标记齐全、权限注解复用合理、JMaterialSelect 改动向后兼容、税额计算在既有事务内无新增并发风险，未发现 P0/P1 级问题。主要风险集中在**前端税额展示口径与后端落库口径不一致**（差 0.01 元级）、**税率可清空导致保存后税额"凭空出现"**、**后端缺税率范围校验**三处，均为 P2，建议修复后放行。

## Findings

| 级别 | 位置 | 问题 | 影响 | 建议 |
|------|------|------|------|------|
| P2 | OrderDrawer.vue `#taxAmount` / `totalTax`（约 26-28、77-79 行） | 前端税额按 `数量×单价×税率` 连乘后 `toFixed(2)`，未先对金额四舍五入；后端是先 `amount=qty×price`（HALF_UP 保留2位）再乘税率。且 JS `toFixed` 是浮点近似舍入（如 `1.005.toFixed(2)="1.00"`），与后端 HALF_UP 不同 | 抽屉里看到的税额/合计与保存后展开子表显示的税额可能差 ¥0.01，业务对账时对不上、误以为系统算错 | 前端复刻后端口径：先金额四舍五入 2 位（`Math.round(x*100)/100` 或引入 decimal 库）再乘税率；最稳妥是保存后以后端返回值刷新展示 |
| P2 | OrderDrawer.vue `#taxRate` InputNumber（约 25 行）+ MesSalesOrderServiceImpl.java L177 | 税率输入框可清空 → `taxRate=null`：前端按 0 显示税额、合计不含该行；后端 null 时默认回填 0.13 并计算税额 | 用户清空税率以为"不含税"，保存后税额"凭空出现"，数据与用户预期相反 | 前端 `updateItem` 对 null 归一为 0.13，或输入框失焦自动回填默认值；前后端默认规则需明示给用户（如 placeholder"默认13%"） |
| P2 | MesSalesOrderServiceImpl.java validateOrder（L177-179） | 后端未校验税率取值范围。前端 `max=1` 仅是界面约束，直接调接口可传 `taxRate=50`（税额=金额×50），传 ≥1000 还会触发 DECIMAL(5,2) 溢出报 SQL 错误 | 脏数据落库或接口报错，财务数据失真 | validateOrder 中增加 `taxRate < 0 或 > 1` 时抛"第N行税率需在0~1之间" |
| P2 | OrderItemsSubTable.vue onMounted catch 块（约 62-65 行） | 任何异常（含无 `mes:material:list` 权限、网络失败）都被静默吞掉，`items=[]` 后显示"该订单暂无物料明细" | 把"查询失败"误导成"没有明细"，业务人员可能据此做错误判断 | catch 时展示"明细加载失败，请重试"类提示，与"真的无明细"区分开 |
| P3 | OrderItemsSubTable.vue onMounted + OrderDrawer.vue enrichItems | N+1 请求：每展开一行 = 1 次订单查询 + N 次物料逐条查询（`Promise.all(ids.map(queryMaterialById))`），编辑抽屉打开时同样 N 次，无批量接口、无缓存 | 明细行多时（几十种物料）展开/打开抽屉明显卡顿，且给后端带来瞬时并发请求 | 增加物料批量查询接口（ids in 查询一次返回），或前端做会话级物料缓存 |
| P3 | OrderDrawer.vue 合计行 `totalQty`（约 77 行） | 合计数量把不同单位的数量直接相加（件 + 公斤 + 米混在一起） | 合计数量无业务意义，可能误导 | 去掉数量合计，或按单位分组显示 |
| P3 | MesSalesOrderServiceImpl.java calcTotal（L184-190） | 订单头只汇总金额，不冗余税额合计；而采购订单头有 `tax_amount` 字段，销售侧口径不齐 | 后续应收/发票环节需要价税合计时只能逐行重算，存在口径漂移风险 | 评估是否在订单头补 `taxAmount` 汇总字段，与采购侧对齐 |
| P3 | OrderItemsSubTable.vue / OrderDrawer.vue 使用 `unit_dictText` | 规格/单位依赖 DictAspect 对 `queryById` 返回值的字典翻译；翻译不生效时该列显示 "-" | 仅展示降级，不影响数据 | 上线前在页面实际验证一次"单位"列是否正常显示中文 |

## 合规核查（通过项）

- **update 标记**：Java 新增税额计算块已正确包裹 `update-begin/update-end`（author/date/for 齐全）；实体类字段标记为 2026-07-20 既有提交，本次未动。Vue 文件按规范无需标记。✅
- **权限注解**：子表复用 `queryById`（`mes:salesOrder:list`），与列表权限一致，无越权放大；物料查询要求 `mes:material:list`（见 P2 第4条的表现问题）。✅
- **向后兼容**：JMaterialSelect change 负载新增 `record` 字段，全部 9 处消费方（销售/采购/制造各抽屉）均使用 `v?.value ?? v` 取值，不受影响；`handleClear` 不带 `record`，`onMaterialChange` 已做 `m?.spec || ''` 兜底。✅
- **数据库**：`tax_rate DECIMAL(5,2) DEFAULT 0.13`、`tax_amount DECIMAL(18,2)` 已在 V9.4.0 幂等脚本中存在，前后端字段名对齐；税率小数制（0.13）与发票/采购发票模块口径一致。✅
- **并发安全**：税额计算发生在既有 `@Transactional` 的 validateOrder 内，纯行内计算无共享状态；取号（getNextCode）、状态流转（带状态守卫的 UPDATE）为既有机制，本次未削弱。✅
