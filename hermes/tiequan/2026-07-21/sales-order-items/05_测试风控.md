# 铁拳团审计 · 销售订单明细子表 — 05 测试风控

- **审计对象**：commit `da8181b`（OrderItemsSubTable.vue 新增、index.vue、OrderDrawer.vue、JMaterialSelect.vue、MesSalesOrderServiceImpl.java 税额计算）
- **审计视角**：测试风控 —— 功能测试点遗漏、异常输入（负数/零/超长/非法税率）、老订单无税额数据的回归兼容性
- **审计方式**：只读审查 diff + 相关后端校验/建表 SQL，未修改任何被审文件

## 结论

本次改动的主体逻辑（后端强制重算金额/税额、前端只读展示）方向正确，但**测试盲区集中在三处**：① 后端对税率完全没有范围校验，直接调接口可传入负数或超 100% 的税率产生荒谬税额；② 前端清空税率框时按 0 算合计、后端却按默认 13% 入账，出现"提交前看到的税额 ≠ 入库税额"；③ 老订单（tax_rate 为 NULL）一旦打开编辑再保存会被静默回填 13% 税额，属于回归测试必须覆盖的数据兼容性场景。建议补齐下表 P0/P1 测试点后再放行。

## Findings

| 级别 | 位置 | 问题 | 影响 | 建议 |
|------|------|------|------|------|
| P0 | MesSalesOrderServiceImpl.java validateOrder（税额计算块） | 税率无任何后端范围校验：仅判 null 兜底 0.13，负数（-0.5）、超 100%（如 5、99）均可通过直接 API 调用写入；前端 InputNumber min=0/max=1 可被绕过 | 税额可为负或远超金额，财务数据失真；且 tax_rate 字段是 DECIMAL(5,2)，传 999.99 不报错、传 0.135 会被数据库截断/报错行为不一致 | 后端增加 `taxRate < 0 或 > 1 抛异常` 校验；测试点：API 直传 taxRate=-0.1 / 1.5 / 0.135 / 超大值，断言拒绝或明确舍入行为 |
| P0 | OrderDrawer.vue 税率 InputNumber + 后端默认值 | 清空税率输入框时 @change 回传 null：前端合计行 `totalTax` 按 `(i.taxRate \|\| 0)` 算显示税额为 0，但后端 null → 默认 0.13 入账 | 用户看到的合计税额与保存后实际税额不一致（显示 0 元，入库 13%），对账类投诉高发点 | 二选一：前端清空时回填 0.13 保持与后端一致，或后端拒绝 null 强制前端必输；测试点：清空税率→合计显示→保存→重开抽屉比对税额 |
| P0 | OrderDrawer.vue enrichItems / updateWithItems | 老订单（本次上线前创建，tax_rate/tax_amount 为 NULL）打开编辑即被兜底 `taxRate ?? 0.13`，更新接口是整单删行重插，保存后老订单被静默回填 13% 税额 | 历史数据在用户无感知的情况下被改写；若业务上老订单本不应有税额，属于数据污染 | 回归测试必测：用无税额的老订单做"编辑→不改任何字段→保存→查库"，确认 tax_rate/tax_amount 变化是否符合预期；产品需明确老数据回填策略（或跑一次数据订正脚本） |
| P1 | OrderDrawer.vue 税额/金额列 + 合计行 vs 后端计算 | 前端用 JS 浮点 `(qty*price).toFixed(2)` 展示，后端用 BigDecimal HALF_UP：`(1*3.845).toFixed(2)`="3.84"，后端 3.845→3.85；且前端税额是先全乘再 round、后端是先 round 金额再乘税率 | 边界单价下行显示金额/税额与入库值差 0.01；合计税额（各行未 round 浮点累加再 toFixed）也可能 ≠ 各行显示税额之和，用户自行加总对不上 | 测试点：单价 3.845/2.675、数量 3 位小数、多行税额尾差场景，断言"行税额之和 = 合计税额 = 重开订单后后端值"；建议前端展示以后端口径模拟（先 round 金额再乘税率） |
| P1 | OrderDrawer.vue removeLine + handleBatchAddMaterials | rowKey=lineNo 但删除中间行后 lineNo 不重排，批量添加物料用 `items.length+1` 起算，会产生重复 lineNo（如删第 2 行后剩 2 行，批量添加首行 lineNo=3 与已有第 3 行重复） | Vue 列表 key 重复，行渲染错乱/编辑串行；入库虽被后端重排 lineNo 掩盖，但抽屉内操作体验受损 | 测试点：3 行→删中间行→批量添加 2 个物料→逐行改数量，观察是否串行；建议 addLine/批量添加用 `Math.max(...lineNo)+1` |
| P1 | OrderItemsSubTable.vue onMounted | 查询失败（queryOrderById 或物料批量查异常）时 catch 后置 `items=[]`，页面显示"该订单暂无物料明细" | 加载失败被伪装成"无数据"，测试/用户无法区分"真没明细"和"接口挂了"，排障误导 | 测试点：mock 接口 500/超时，断言有错误提示而非"暂无明细"；建议 catch 中 message.error 提示 |
| P2 | OrderItemsSubTable.vue 税率/税额展示 | 老订单展开时税率/税额显示 '-'，新订单显示具体值，同一列表两种形态；税率展示 `(taxRate*100).toFixed(0)` 对 0.065 类两位小数以整百分比取整（6.5%→"7%"） | 展示口径不统一，验收用例若只测新订单会漏掉老数据 '-' 分支；百分比取整可能误显示 | 测试点：展开老订单确认 '-' 展示不报错不空白；若 DB 允许两位小数税率，展示改 `toFixed(1)` 或保留原值 |
| P2 | OrderItemsSubTable.vue / OrderDrawer.vue enrichItems | 规格/单位按物料 ID 逐条 `queryMaterialById`（N+1），物料被删除时 map 缺失 → 显示 '-'/'- ' 但物料列仍回退 `materialId_dictText` | 单行订单无感，明细 50+ 行且展开多订单时接口风暴；物料被删后展示降级路径需有测试覆盖 | 测试点：明细引用已删除物料的订单展开/编辑不白屏；性能场景可后续改批量接口，本次记录即可 |
| P2 | 订单总额口径 | calcTotal 只累加 amount，税额不进 totalAmount，也无"价税合计"字段 | 测试若按"总额=金额+税额"的常识断言会失败；业务对账时总额口径易被误解 | 测试用例中显式固化预期：totalAmount=不含税金额合计；建议产品确认是否需要价税合计列（转产品风控跟踪） |
| P3 | 数量/单价超长输入 | 后端校验数量>0、单价≥0，但无上限；amount DECIMAL 精度下单价 99999999.99 × 数量 99999999 可能超 DECIMAL(18,2) 入库报错，错误为数据库层 500 而非业务提示 | 极端输入下报错不友好 | 测试点：超大数量×超大单价保存，断言报错信息可读；建议后端加合理上限校验（优先级低） |

## 建议的最小回归测试清单（上线前必过）

1. 新增订单：默认税率 13% 带出，改税率 0/0.06/1，税额=金额×税率四舍五入 2 位，合计=各行之和。
2. 异常输入：税率清空（null）、API 直传负税率/超 1 税率/三位小数税率 → 明确拒绝或口径一致。
3. 尾差：单价 3.845、数量 0.015 等边界值，前端显示 = 后端入库值。
4. 老订单兼容：无税额老订单展开显示 '-'；编辑不改动直接保存后税额回填行为符合产品预期。
5. 行操作：删中间行 + 批量添加物料后逐行编辑不串行。
6. 接口异常：展开子表时详情接口 500，有错误提示而非"暂无明细"。
