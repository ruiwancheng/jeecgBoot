# 产品风控审计报告 — 销售订单物料明细子表

> **审计视角：** 产品风控 — 业务流程完整性、用户操作便利、边界场景（空明细/多物料/大数量）
> **审计对象：** commit da8181b（6 文件：OrderItemsSubTable 新增 + Drawer 税率/合计增强 + JMaterialSelect 回传 + 后端税额计算）
> **日期：** 2026-07-21

---

## 结论

整体改动方向正确——展开行查看明细、税率可编辑、底部合计行、物料选择自动带出规格/单位，补上了销售订单在财税对账和快速浏览场景的关键缺口。但存在 **1 个 P0 财务精度风险**（前端合计"先浮点累加再四舍五入"与后端"逐行 BigDecimal 取整再汇总"两条路径不一致，多行订单可差 1-2 分钱），以及 **4 个 P1 业务体验缺陷**，建议修复 P0 后再上线。

---

## Findings

| 级别 | 位置 | 问题 | 影响 | 建议 |
|:---:|---|------|------|------|
| **P0** | `OrderDrawer.vue` L.56-58 合计行 `totalAmount` / `totalTax` computed | **前端合计浮点累加路径与后端逐行 BigDecimal 取整路径不一致**。前端 `reduce(...).toFixed(2)` 先对原始浮点值累加再一次性四舍五入；后端 `amount.setScale(2, HALF_UP)` 逐行先取整再汇总。业务验证：3 行均 q=1/p=0.33/r=0.13 时，前端税额合计显示 0.13，后端存储 0.04×3=0.12，差 1 分钱。用户保存前看到合计 ¥0.13，保存后刷新看到 ¥0.12 → 财务对账困惑，严重时引发客户质疑系统可靠性 | 合计行改为**逐行先取整再求和**：`items.value.reduce((s, i) => s + Math.round((i.quantity \|\| 0) * (i.unitPrice \|\| 0) * 100), 0) / 100` 确保每行金额与后端 setScale(2) 一致后再累加，实现"所见即所存" |
| **P1** | `OrderDrawer.vue` L.25 `taxRate` InputNumber `:min="0" :max="1" :step="0.01"` | **税率无业务约束**。可手动输入 0~100% 任意两位小数（如 14%、25%），操作员大批量录单时可能误触输入无效税率 → 税额全错，后续开票环节才发现 | 改为 `a-select` 下拉限定 0%、3%、6%、9%、13% 五档常用税率，同时保留"自定义"选项允许手动输入（范围 0-0.3 即可覆盖所有现实场景） |
| **P1** | `OrderDrawer.vue` L.113 `enrichItems()` 异步调用 | **编辑打开抽屉时明细行无加载反馈**。`enrichItems` 逐个查物料 API（`Promise.all(ids.map(...))`），物料多（20+ 行）或网络慢时 Drawer 已打开但明细表格区域空白，用户不知道是"加载中"还是"数据丢失"，可能关掉重开 → 重复 API 调用 | 明细表格外包裹 `<a-spin :spinning="itemsLoading">`，`enrichItems` 执行前设 `itemsLoading=true`，完成后设 `false`；超 5 秒未完成展示"正在加载物料信息…"文案 + 部分结果 |
| **P1** | `OrderDrawer.vue` L.112 `removeLine()` | **删除最后一行无反馈**。`if (items.value.length > 1)` 不满足时静默跳过，按钮点击无任何反应。用户连点多次以为系统卡死 | `else` 分支加 `message.warning('至少保留一行明细')` |
| **P1** | `OrderDrawer.vue` L.30 `taxAmount` 模板 `(q*p*r).toFixed(2)` | **单行税额/金额前端预览与后端存储计算路径不同**。前端 `(q*p).toFixed(2)` 是 JS 浮点乘法后取整，后端 `quantity.multiply(unitPrice).setScale(2, HALF_UP)` 是 BigDecimal 运算。同一根因，但影响面小于合计行（单行差 1 分钱 vs 合计差数分钱）。用户在抽屉看到的单行金额 ¥123.46，保存后可能变为 ¥123.45 | 与 P0 一并修复：前端使用逐行精确取整逻辑，确保预览值 = 存储值 |
| **P2** | `OrderItemsSubTable.vue` L.48-65 `onMounted` | **每次展开行都重新发起 N+1 查询**。`queryOrderById` + `Promise.all(ids.map(id => queryMaterialById))`，无缓存。用户快速浏览多行时产生大量并发请求；展开→收起→再展开同一行，数据完全重复请求 | 加简单内存缓存 `Map<orderId, {items, materialMap}>`，同订单不重复请求；或父组件 list 接口直接返回 items 摘要，子表仅做格式化展示 |
| **P2** | `OrderDrawer.vue` L.133 `handleBatchAddMaterials()` | **批量添加物料不检测重复**。操作员可能误选已在明细中的物料 → 订单出现两行相同物料，审核时才被驳回，返工成本高 | 添加前 `items.value.find(i => i.materialId === m.id)` 检查，已有则 `message.warning('物料已存在于明细中')` 跳过 |
| **P2** | `OrderItemsSubTable.vue` L.4 `:pagination="false"` | **大量明细行无分页无滚动限制**。年度框架合同可达 50-200 行，展开后页面极长，用户需大量滚动，且后续订单列表项被推到屏幕外 | 加 `:scroll="{ y: 350 }"` 固定表头 + 纵向滚动；或明细超过 15 行时自动开启前端分页 |
| **P2** | `OrderItemsSubTable.vue` L.40-44 `materialText()` | **已删除物料的明细展示不友好**。物料被删后 `materialMap[record.materialId]` 为 undefined，回退到 `materialId_dictText`（也可能为空）或直接展示 UUID → 用户看到一串乱码般 ID，无法判断是"物料已删除"还是"系统取数失败" | 区分两种情况：`catch` 到网络错误展示"加载失败⚠"并提供重试；物料返回 null 展示"物料已删除 (ID: xxx)" |
| **P2** | `OrderItemsSubTable.vue` L.20 `taxAmount` 列模板 | **税额/金额列无格式化**。`record.taxAmount` 和 `record.amount` 直接展示原始数值，缺少千分位分隔符和货币符号，与合计行的 `¥` 前缀不一致 | 统一格式化：`¥{{ Number(record.amount).toLocaleString('zh-CN', { minimumFractionDigits: 2 }) }}` |
| **P3** | `OrderDrawer.vue` L.60-66 `itemColumns` | **列宽总计约 800px**，抽屉宽度如果较小（如 720px），操作列可能被挤出可视区或产生横向滚动条 | 物料列使用 `ellipsis: true` + tooltip 替代固定宽 180px；或操作列固定 `fixed: 'right'` |

## 审计维度覆盖

| 维度 | 结论 | 关键问题 |
|------|:--:|------|
| 业务流程完整性 | ⚠️ 有缺口 | P0 合计精度、P1 税率无约束 → 财税对账不可靠 |
| 用户操作便利 | ⚠️ 有改进 | P1 加载无反馈、删除无提示、P2 无去重 → 操作困惑 |
| 边界场景 — 空明细 | ✅ 已覆盖 | 展开行展示"暂无物料明细"；抽屉至少保留 1 行 |
| 边界场景 — 多物料 | ⚠️ 部分覆盖 | P2 无分页、无缓存 → 大量明细体验退化 |
| 边界场景 — 大数量/高精度 | ❌ 有风险 | P0 浮点精度 → 财务数据不可信 |
| 数据一致性（前后端） | ❌ 有风险 | P0/P1 浮点 vs BigDecimal → 所见非所存 |
| 向后兼容 | ✅ 无问题 | JMaterialSelect change 仅新增 record 字段，旧调用方无影响 |

## 补充说明

### 做得好的地方

1. ✅ **税率默认 13% 四处统一**：`addLine` / `handleBatchAddMaterials` / `enrichItems` / 后端 `saveOrder` 均设 `0.13`，不会遗漏
2. ✅ **JMaterialSelect 向后兼容**：change 新增 `record` 字段但保留 `{ value, label }`，其他使用方无需修改
3. ✅ **子表空状态提示**："该订单暂无物料明细"，用户知道是正常状态非故障
4. ✅ **后端强制重算金额**：`amount` 和 `taxAmount` 由 Service 统一 BigDecimal 计算，防止前端篡改（安全设计正确）
5. ✅ **物料选择自动带出规格/单位**：`onMaterialChange` 同步 set spec 和 unitText，操作流顺畅
6. ✅ **编辑回显补齐**：`enrichItems` 按物料 ID 批量补齐历史订单的规格/单位，老数据也能看到完整信息

### 未覆盖的边界（建议后续迭代，非本次阻塞）

- 订单明细行 >100 行时抽屉表格性能退化（考虑虚拟滚动）
- 客户自定义税率需求（跨境贸易 0% 出口退税 vs 国内 13%），税率值可能需从客户主数据继承
- 含税价/不含税价切换：金额列为不含税金额，部分行业用户习惯看含税价
- 税率变更历史追溯：若未来税率调整（如 13%→11%），历史订单明细税率应保持原值
