# 08_研发大牛3号_并发安全视角

**审计对象：** MES 编码规则模块（codeRule）+ 10 单据取号接线
**视角：** 并发取号、重复提交、分布式部署、幂等
**执行说明：** 降级模式（总调度单体会审），非独立 Agent

## 结论
取号核心逻辑存在教科书级的 `synchronized + @Transactional` 窗口期缺陷（与产品2号共识 P1）。单体部署+业务表唯一约束使其暂不致命，但该写法必须修。

## Findings

| 级别 | 位置 | 问题 | 影响 | 建议 |
|---|---|---|---|---|
| **P1** | MesCodeRuleServiceImpl.nextCode | 时序：代理开启事务 → 进入 synchronized 方法 → 方法退出（**锁已释放**）→ 代理提交事务。线程 B 可在"A 释放锁"与"A 提交"之间进入，getOne 读到旧流水号 → **两人拿到同一编码** | 业务表 code 唯一约束兜底：重复方保存报"编码已存在"，需重新打开弹窗。不会写坏数据，但高并发开单时偶发失败 | 推荐原子累加：`UPDATE c_mes_code_rule SET current_seq = current_seq + 1 WHERE rule_code=?` 后 SELECT；或 SELECT ... FOR UPDATE 行锁。synchronized 对集群部署无效，一并去除 |
| P2 | 前端取号时机 | 10 个页面均为"打开弹窗取号"，无保存重试联动：若因并发取到重号导致保存报错，用户需手动关闭重开 | 偶发操作中断 | 保存报"编码已存在"时自动重新取号重填 |
| P3 | 前端重复提交 | Drawer 提交均有 confirmLoading 防连点 | 通过 | — |
| P3 | 规则 CRUD 幂等 | add 重复提交依赖 (rule_code, del_flag) 唯一索引兜底，报 500 原文 | 报错文案不友好但不丢数据 | 低优先 |

**验证记录：** 2026-07-21 实测 10 规则连续取号（0001→0003）序列正确无重复，单线程行为正确；并发窗口为主播代码走查发现，未做压测复现。
