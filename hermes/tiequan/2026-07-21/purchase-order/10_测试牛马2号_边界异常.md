# 铁拳团审计报告 — 采购订单模块（测试牛马2号 · 边界异常视角）

> 审计范围：`project-mes/.../mes/purchase/order/`（Entity×2 / Mapper×2 / ServiceImpl / Controller）、前端 `views/project/mes/purchase/order/`（index.vue / OrderDrawer.vue / order.api.ts / order.data.ts）、`V6.0.1__mes_purchase_order_init.sql`
> 视角：极值/空值/非法参数、超长输入、并发冲突、未授权访问。只查不改。

## 结论

模块边界防护意识整体较好（编号长度校验、强制草稿状态、审核用 guarded UPDATE 防并发、编号唯一性"先查后插 + 捕获重复键"双保险），但仍存在两个可稳定复现的数据一致性问题：一是并发新增同编号时的"复活竞态"会把订单行挂到他人订单上，二是"编辑改编号为已删除订单编号后再删除"必然触发唯一索引冲突报 500。此外数值字段（数量/单价/税率/金额）普遍缺上限与范围校验、客户端可注入 delFlag/createBy 等敏感字段、前端自动编号因缺少 import 完全失效，需按 P1/P2 尽快修复。

## Findings

| 级别 | 位置 | 问题 | 影响 | 建议 |
|------|------|------|------|------|
| P1 | `MesPurchaseOrderServiceImpl.saveWithItems()` + `MesPurchaseOrderMapper.resurrect` | **并发复活竞态**：`resurrect` 的 UPDATE 带 `del_flag=1` 条件但返回值是 void 未检查。两个请求同时新增同一编号（且存在已删记录）时，都查到同一个 old，先提交者复活成功，后到者 UPDATE 0 行却不报错，继续执行 `saveItems`，把订单行插到别人的订单（同一 orderId）下 | 并发下同编号新增会产生：A 订单下混入 B 的订单行、金额合计错乱，且无任何报错，业务上极难排查 | `resurrect` 返回 int，检查影响行数，0 行时抛"订单编号已存在"或重走 insert 分支 |
| P1 | `updateWithItems()` + SQL `uk_po_code_del (code, del_flag)` | **改编号后删除必失败**：编辑时查重只查活跃记录（逻辑删除自动过滤），可把订单编号改成某个已删除订单的编号 Y（此时库中存在 Y/已删 + Y/活跃两行，不违反唯一索引）；之后再删除该订单时逻辑删除把 del_flag 置 1，与已存在的 (Y,1) 冲突，报 DuplicateKeyException 500 | 用户按"改编号 → 删除"操作即触发数据库异常，订单删不掉且报错为底层 SQL 错误，体验差且脏数据残留 | 唯一索引改为 `uk(code, del_flag, id)` 或改用"删除时 del_flag 置为 id/时间戳"的方案；或编辑时查重包含已删记录 |
| P2 | `validateOrder()` | **数量/单价/金额无上限**：仅校验 quantity>0、unitPrice≥0。quantity 为 DECIMAL(18,4)、unitPrice/amount 为 DECIMAL(18,2)，极大值（如 quantity=999999999999、unitPrice=9999999999999.99）相乘后 amount 超出 DECIMAL(18,2)，insert 时数据库报 Out of range 500；total 累加同样可溢出 | 恶意或误输入极大数值直接打爆接口（500），且错误信息为底层 SQL 异常 | 增加业务上限校验（如 quantity≤99999999、unitPrice≤999999999999、单笔 amount≤DECIMAL(18,2) 上限），超限抛业务异常 |
| P2 | `validateOrder()` 税率分支 | **税率无范围校验**：taxRate 仅判 null 补默认值，可传负数（-1 → 负税额）或 9999（税率 999900%）；且 DECIMAL(5,2) 上限 999.99，传更大值入库溢出 | 可造出负税额/天文税额订单，财务数据失真；极端值报 500 | 校验 `0 ≤ taxRate ≤ 1`（或业务允许区间），非法值抛业务异常 |
| P2 | `validateOrder()` 金额计算 | **单价精度未收敛**：后端直接用原始 unitPrice 计算 amount 并原样 insert，而 unit_price 列为 DECIMAL(18,2)。传 1.234 时 amount 按 1.234 算、库存 1.23（静默四舍五入），导致 amount ≠ 数量 × 存库单价 | 订单行金额与单价对不上，下游对账/报表出现分分钱差 | insert 前对 unitPrice 做 `setScale(2, HALF_UP)`，用收敛后的单价计算 amount |
| P2 | `updateWithItems()` / `removeWithItems()` 与 `audit()` | **状态机 TOCTOU**：编辑/删除是"先 selectById 查状态、再执行写"，审核用 guarded UPDATE。时序：编辑方查到 status='1' → 审核方提交把状态改为 '3' → 编辑方继续 updateById 成功，已审核订单被改/被删 | 并发下"非草稿禁止编辑/删除"的约束可被绕过，审核流于形式 | 编辑/删除同样改为带状态条件的 guarded SQL（`UPDATE ... WHERE id=? AND status='1'`，检查影响行数），或加乐观锁 |
| P2 | `MesPurchaseOrderController.add/edit` + Entity | **客户端可注入敏感字段**：`@RequestBody` 直接绑定整个实体，`delFlag`、`createBy`、`createTime` 均未屏蔽。MyBatis-Plus insert/updateById 会写入非空字段：编辑时传 `delFlag:1` 订单立刻"消失"（且污染唯一索引），传 `createBy` 可伪造创建人 | 越权篡改审计字段、可隐藏订单（等同无痕迹删除），绕过状态机删除限制 | 服务端强制 `entity.setDelFlag(null)`、`setCreateBy(null)`、`setCreateTime(null)`，或使用专用 DTO 白名单字段 |
| P2 | `OrderDrawer.vue:64` | **自动编号完全失效（缺少 import）**：使用了 `getNextCode` 和 `MES_BIZ_CODE` 但未 import（兄弟模块 purchase/receipt、finance 等均有 `import { getNextCode } ...`，项目未配置 auto-import 插件，已核实）。打开"新增订单"抽屉必抛 ReferenceError，被 try/catch 静默吞掉 | 每次新增订单编号框为空，用户只能手输，编号规则形同虚设；且 catch 静默无日志，问题长期隐蔽 | 补上两行 import（参照 `purchase/receipt/ReceiptDrawer.vue:36`）；catch 里至少 console.warn |
| P2 | `MesPurchaseOrderController.queryPageList` | **pageSize 无上限**：pageNo/pageSize 直接进 `new Page<>()`，pageSize=1000000 时全表捞取；负数/0 也未防御 | 大 pageSize 可致慢查询、内存飙升，构成简易 DoS | 服务端 clamp：`pageSize = Math.min(Math.max(pageSize,1), 500)`，pageNo<1 时置 1 |
| P2 | Entity `paymentTerms`/`remark` + SQL | **超长输入后端无校验**：前端 maxlength 50/500 仅是 UI 限制，API 直调传超长字符串，VARCHAR(50)/VARCHAR(500) 在严格模式下报 Data truncation 500，非严格模式静默截断 | 绕过前端即可打爆接口或造成数据静默截断 | 后端 validateOrder 补长度校验（与 code 的 50 字符校验同款写法） |
| P3 | `MesPurchaseOrderController` + `index.vue` | **未授权访问细节**：后端各端点均有 @RequiresPermissions（好），但 ① 前端"新增/编辑/删除/导出"按钮无 v-auth 控制，无权限用户可见可点、点了才 403；② `audit` 复用 `mes:purchaseOrder:edit` 权限码，无法做到"可编辑不可审核"的权责分离；③ edit 传不存在的 id 时 checkStatus 放行、updateById 静默 0 行，仍返回"编辑成功" | 越权操作体验差、审核权限无法独立授予、误导性成功提示掩盖失败 | 按钮加 auth 指令；审核拆独立权限码 `mes:purchaseOrder:audit`；edit/delete 检查影响行数，0 行返回"订单不存在或已变更" |
| P3 | `MesPurchaseOrderController.deleteBatch` + `removeByIds` | **批量删除无数量上限且强转未校验**：ids 逗号串长度不限，可构造上万 id 的巨大 IN；`(Collection<String>)` 未经检查的强转，传入非 String 集合时 ClassCastException | 超长请求拖慢库；异常输入返回 500 | 限制单次批量数量（如 ≤200）；强转前校验元素类型 |
| P3 | `MesPurchaseOrderController.exportXls` | **导出超限判定与实际导出不一致**：count 用空 QueryWrapper 统计全表，而 `super.exportXls` 按 entity 条件导出。全表 >1000 但筛选后只有 10 条时也被拒绝导出 | 误伤正常的按条件导出 | count 使用与导出一致的 QueryWrapper（QueryGenerator 生成） |
| P3 | `OrderDrawer.vue` 金额列 | **前端金额用 JS number 浮点计算**：`((record.quantity \|\| 0) * (record.unitPrice \|\| 0)).toFixed(2)`，0.1×3 类浮点误差、超 2^53 精度丢失；仅展示，后端有强制重算兜底 | 展示金额与提交后回显可能差 1 分，引起用户疑惑 | 展示层用 decimal 库或乘 100 取整；或提交后以后端返回值为准 |
| P3 | `OrderDrawer.vue` addLine/removeLine | **行号 rowKey 可重复**：删除中间行后再 addLine，`lineNo = length+1` 可能与现存行重复（如 3 行删第 2 行再添加 → 两个 lineNo=3），a-table rowKey 重复告警；后端 saveItems 会重排行号兜底 | 前端控制台告警、Vue 渲染 key 冲突潜在错乱 | addLine 用 `Math.max(...lineNos)+1` 或改用临时 uuid 作 rowKey |

## 复现要点（供验证）

1. **P1 复活竞态**：先建订单 PO-001 并删除；用两个并发请求同时 POST `/mes/purchase/order/add`（code=PO-001，items 不同）→ 两者都返回成功，queryById 可见订单行混合。
2. **P1 改编号后删除**：建 PO-A 删除；建 PO-B，编辑把编号改为 PO-A（成功）；再删除该订单 → 500 DuplicateKeyException。
3. **P2 敏感字段注入**：PUT `/edit` 时 body 附带 `"delFlag":1` → 订单从列表消失。
4. **P2 自动编号失效**：打开新增抽屉，浏览器控制台无报错（被吞），编号框为空；对照 ReceiptDrawer 行为即可确认。
