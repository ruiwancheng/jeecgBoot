# 铁拳团审计 · 采购订单模块 · 07 研发大牛2号（代码细节）

- 审计日期：2026-07-21
- 审计视角：入参校验、SQL注入、空值、精度、硬编码、前后端VO对齐、update-begin/end标记
- 审计范围：后端 `jeecg-boot/jeecg-boot-module/project-mes/src/main/java/org/jeecg/modules/mes/purchase/order/`（Entity×2 / Mapper×2 / ServiceImpl / Controller / Service接口）、前端 `jeecgboot-vue3/src/views/project/mes/purchase/order/`（index.vue / OrderDrawer.vue / order.api.ts / order.data.ts）、SQL `project-mes/db/V6.0.1__mes_purchase_order_init.sql`

## 结论

模块整体工程质量在 MES 各模块中属中上：SQL 全部参数化无注入风险、逻辑删除唯一索引冲突用"复活"机制闭环、金额后端强制重算、批量删除有状态守卫、update-begin/end 标记齐全。但存在 1 个已失效的功能（前端自动取号因缺少 import 被 try/catch 静默吞掉）、1 个资损风险（税率无范围校验可为负）、以及审核链路前后端断层（后端有 /audit，前端完全没接）三类必须修的问题。

## Findings

| 级别 | 位置 | 问题 | 影响 | 建议 |
|------|------|------|------|------|
| P1 | 前端 OrderDrawer.vue:57-60 | `getNextCode(MES_BIZ_CODE.PURCHASE_ORDER)` 被调用但**两个标识符都未 import**（对照销售订单 OrderDrawer.vue:54-55 有正确 import）。运行期抛 ReferenceError，恰好被外层 `try{...}catch{}` 静默吞掉 | 新增采购订单时"自动获取编码"功能**永远失效**且无任何提示，用户只能手输编号，失去编码规则防重价值 | 补上两行 import：`getNextCode` from `/@/views/project/mes/basic/codeRule/codeRule.api`、`MES_BIZ_CODE` from `/@/views/project/mes/basic/codeRule/bizCodeMap`；同时建议 catch 里至少 console.warn |
| P1 | ServiceImpl validateOrder() | 税率 `taxRate` 无任何范围校验，客户端可传负数或 >1 的值；负数税额会使含税总额 < 不含税金额 | **资损风险**：可构造负数税额订单，后续入库/对账金额全部失真 | 增加校验 `taxRate >= 0 && taxRate <= 1`（或业务上限 0.13） |
| P2 | Mapper auditWithGuard + SQL 字典 | `audit` 一步把状态 '1' 直接置 '3'，而字典定义了 '2'(待确认) 状态，状态机 1→3 跳级，'2' 成为**不可达状态** | 字典与实际状态流不一致，报表按状态统计时"待确认"永远是 0，业务人员会困惑 | 明确状态机：要么 1→2→3 两步走，要么删掉字典里的 '2' |
| P2 | Controller /audit + 前端 index.vue / order.api.ts | 审核链路前后端断层：后端有 `/audit` 接口，但前端 order.api.ts 没有对应函数、index.vue 操作列只有编辑/删除（对照销售订单已有 auditOrder+批量审核按钮）；且 /audit 复用 `mes:purchaseOrder:edit` 权限码，无独立 `mes:purchaseOrder:audit` 权限 | 审核能力上线即悬空，只能在 Swagger 里调；审核与编辑同权限，无法做职责分离 | 前端补审核按钮+API（草稿状态才显示）；权限码拆分为独立的 audit 权限并注册菜单 |
| P2 | ServiceImpl saveWithItems() resurrect 分支 | 并发竞态：两个请求同 code 新增，同时查到已删除行→都走 resurrect→第二个 resurrect 影响 0 行但**未检查返回值**→双方继续 saveItems | 极端并发下同一订单 id 被插入两套订单行，数据错乱 | resurrect 改返回 int，影响 0 行时抛"订单编号已存在"重试 |
| P2 | ServiceImpl validateOrder / OrderDrawer.vue | **行级税率前后端断层**：后端 calcTotal 已支持逐行税率（多税率混单），但前端订单行编辑器没有税率列，新增行 taxRate 永远为 null → 落库固定默认 0.13 | 功能做了一半：非 13% 税率的物料无法录入，只能通过 API 绕过界面 | 前端订单行加税率列（InputNumber precision 2, 0~1）；或确认本期只支持 13% 则后端注释说明 |
| P2 | ServiceImpl calcTotal() | 精度口径：`unit_price` 字段是 DECIMAL(18,2)，但金额计算用的是客户端原始 BigDecimal 单价，未先 `setScale(2)` 归一；`quantity` 前端无 precision 限制而 DB 是 4 位 | 前端绕过 precision=2 传 3 位小数单价时，算出的 amount 与"入库单价×入库数量"对不上，差几分钱 | amount 计算前对 unitPrice/quantity 按库表精度归一 |
| P2 | ServiceImpl validateOrder() | 供应商/物料只校验非空，**不校验存在性**（无 FK、无 exists 查询） | 可传入已删除/不存在的 supplierId、materialId，列表字典翻译显示空白，后续入库环节才爆雷 | 保存时校验 supplierId、materialId 在对应主表中存在且未删除 |
| P3 | ServiceImpl updateWithItems / removeWithItems / checkStatus | 对不存在的订单（selectById 返回 null）静默放行，updateById 影响 0 行仍返回"编辑成功" | 误导性成功提示，并发删除场景难排查 | exist==null 时抛"订单不存在" |

## 合规性检查（通过项）

- **SQL注入**：Mapper 三处自定义 SQL 全部 `#{}` 参数化；列表查询走 Jeecg QueryGenerator 标准链路；未发现 `${}` 拼接。**无注入风险**。
- **update-begin/end 标记**：后端 5 个 Java 文件全部有标记且成对闭合；ServiceImpl 内嵌套的两处增量修复块标记完整。前端按规则不要求标记。**符合规范**。
- **空值处理**：validateOrder 对 code/supplierId/items/quantity/unitPrice 均有非空校验，数量>0、单价≥0；calcTotal 在 validateOrder 之后调用无 NPE 路径；getCurrentUsername 有兜底。
- **逻辑删除唯一索引**：`uk_po_code_del (code, del_flag)` 配合 selectDeletedByCode + resurrect 复活机制，避免了同一 code 两条已删记录的唯一冲突，闭环成立（但见 P2 并发竞态）。
- **前后端 VO 对齐**：主表字段（code/supplierId/purchaseType/orderDate/deliveryDate/paymentTerms/remark）前后端命名一致；items 结构对齐；金额字段全部由后端重算，前端提交值不影响结果。
- **权限注解**：Controller 各端点均有 @RequiresPermissions；deleteBatch 走自定义 removeByIds 带状态守卫，无自调用问题。
