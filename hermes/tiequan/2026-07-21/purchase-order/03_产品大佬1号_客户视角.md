# 产品大佬1号审计报告 — 采购订单模块（客户真实视角）

> **审计视角：** 客户真实 — 正向业务流程完整性、操作习惯贴合度、字段命名与布局是否符合业务人员直觉
> **审计对象：** 采购订单模块全栈（Entity×2 / Mapper×2 / ServiceImpl / Controller + 前端4文件 + SQL 迁移脚本）
> **日期：** 2026-07-21

---

## 结论

采购订单模块的数据模型（主子表+税率+含税合计）和后端校验（金额重算+状态机守卫）设计扎实，与销售订单模块保持了架构一致性。但 **前端存在 2 个 P0 阻断性缺陷**（缺少 `getNextCode`/`MES_BIZ_CODE` 导入 → 新增订单打开即报错；列表页无审核按钮 → 订单永远困在"草稿"状态），以及 **状态字典定义了 6 种状态但代码仅覆盖 2 种**（草稿↔已确认），导致业务人员看到的筛选选项与实际可达流程严重脱节。修复 P0 前，采购订单模块对业务人员实际不可用。

## 补充说明

### 做得好的地方

1. ✅ **主子表模型清晰**：`totalAmount`（不含税）+ `taxAmount`（税额）+ `totalWithTax`（含税总额）三字段覆盖完整财税维度，比大多数采购系统只存一个金额更专业
2. ✅ **后端状态机守卫正确**：`auditWithGuard` 用 `UPDATE ... WHERE status='1'` 原子 CAS 操作防并发；非草稿状态禁止编辑/删除
3. ✅ **"借尸还魂"模式**：订单编号唯一约束 + 软删除复活，避免编号冲突
4. ✅ **批量删除已优化**：`removeByIds` 批量 SQL（非循环自调用），已修复了 Service 自调用反模式
5. ✅ **供应商选择用 JSearchSelect**：`dict: 'c_mes_supplier,name,id'` 合写格式正确
6. ✅ **金额后端强制重算**：`amount = quantity × unitPrice`，防止前端篡改

### 架构一致性标注

- `status` 字段为 `String`（`'1'`/`'3'`），与 `c_mes_supplier`/`c_mes_customer` 等模块用 `Integer` 不一致 → **同模块内一致（采购订单 Item 无 status），可接受**，但建议在项目规范中明确统一类型
- `purchaseType` 为 String 字典字段，与 `mes_purchase_type` dict 一致 → ✅ 模式正确
