# 铁拳团审计 · 采购订单模块 · 研发大牛1号（架构全局）

> 审计视角：事务边界、服务分层、N+1/全表扫描、JeecgBoot 规范合规、跨模块耦合
> 审计范围：后端 purchase/order 全部（Entity×2/Mapper×2/Service/ServiceImpl/Controller）、前端 purchase/order 全部（index.vue/OrderDrawer.vue/order.api.ts/order.data.ts）、SQL V6.0.1
> 审计日期：2026-07-21

## 结论

事务边界与金额服务端重算等基本功扎实（auditWithGuard 原子守卫更新是亮点），但**状态机架构断裂**：字典定义 6 个状态而代码只实现 1→3 一条路径，且前端没有审核入口，导致"订单→审核→入库"主业务流程在页面上走不通；另有新增自动取号因漏 import 静默失效、收货模块直连对方 Mapper 跨聚合耦合两处结构性问题。

## Findings

| 级别 | 位置 | 问题 | 影响 | 建议 |
|------|------|------|------|------|
| P0 | 前端 index.vue / order.api.ts（对照 Controller L96 `/audit`） | 前端无"审核"按钮、无 audit API 封装，后端 `/audit` 接口无任何调用方 | 订单永远无法离开草稿态，而采购入库校验要求订单状态为 3/4（ReceiptServiceImpl L181），**主业务流程在 UI 层整体断通**，只能靠 Swagger/Postman 绕过页面操作 | index.vue 操作列按 `record.status==='1'` 增加"审核"按钮，order.api.ts 补 `auditOrder` 封装；审核后禁用编辑/删除 |
| P0 | ServiceImpl.audit + SQL 字典 mes_purchase_order_status + Receipt 模块 | 状态机断裂：字典定义 6 状态（草稿/待确认/已确认/部分到货/已到货/已关闭），代码仅实现 1→3；状态 2（待确认）无任何入口，4/5 需收货回写但 MesPurchaseReceiptServiceImpl 只读订单、从不回写状态（已全文核实），6（已关闭）无入口；无反审核 | 状态机名存实亡，"部分到货/已到货"永远不可达，后续基于状态的报表、预警全部失真 | 画出状态机图并补齐流转：①收货审核时按累计入库量回写 4/5（带状态守卫的原子 UPDATE，参照 auditWithGuard）；②明确是否需要 1→2→3 两段确认，不需要则裁剪字典 |
| P1 | OrderDrawer.vue L64 | `getNextCode`、`MES_BIZ_CODE` 未 import（对照兄弟模块 sales/order/OrderDrawer.vue L54-55 有正确导入）；运行时在 try 块内抛 ReferenceError 被 `catch(e){/* fallback */}` 静默吞掉 | 新增订单自动取号功能**静默失效**，用户只能手输编号，无任何报错提示，问题长期隐身 | 补两行 import；全局排查同类"try/catch 吞错 + 未导入"模式 |
| P1 | MesPurchaseReceiptServiceImpl L36-37/L120-122/L178-187（跨模块耦合） | 收货模块直接 `@Autowired` 采购订单的 **Mapper**（读订单、读订单行、取单价），绕过 IMesPurchaseOrderService 服务层 | 跨聚合直连对方持久层：订单侧后续加状态守卫、字段重构、缓存时，收货侧全部旁路无感知；两个聚合的边界形同虚设 | 在 IMesPurchaseOrderService 暴露 `getOrderWithItems(id)`、`checkReceivable(id)` 等接口，收货模块只依赖服务接口 |
| P2 | ServiceImpl.updateWithItems（checkStatus L145-150） | `checkStatus` 对不存在的订单 `exist==null` 静默放行；随后 updateById 影响 0 行 → 删旧行 0 行 → **saveItems 向不存在的 orderId 插入孤儿订单行** | 异常/并发/重放调用下产生无主的订单行脏数据，且无任何报错 | `exist==null` 时抛"订单不存在"；removeWithItems 同理补存在性校验 |
| P2 | ServiceImpl.saveWithItems L63 + Mapper.resurrect | 软删复活 `resurrect` 未检查 UPDATE 影响行数：并发下同编码两个请求可同时查到同一已删行，先者复活成功，后者 WHERE del_flag=1 匹配 0 行**静默丢失全部字段更新**，且双方都会插入订单行 | 并发下同编码订单数据错乱、订单行重复 | resurrect 返回 int，影响 0 行时抛"编号并发冲突请重试"（DuplicateKeyException 式的显式失败） |

| P2 | ServiceImpl.saveItems L157-161 | 订单行逐行 `itemMapper.insert` 循环，无批量插入 | N 行订单 = N 次数据库往返，大订单保存延迟线性放大 | 改 MyBatis-Plus `saveBatch` 或 foreach 批量 insert |
| P3 | Controller.deleteBatch → ServiceImpl.removeByIds | 覆写框架方法 `removeByIds` 隐式改变其语义（加状态守卫+级联删行），未在 IMesPurchaseOrderService 接口声明，且含 `(Collection<String>)` 未受检强转；父类 JeecgController 或其他框架调用方会得到意外行为 | 语义陷阱：后来者调用"框架标准方法"时触发业务级联删除 | 显式定义 `removeBatchWithItems(List<String>)` 业务方法并在接口声明，Controller 改调该方法 |

| P3 | OrderDrawer.vue 订单行列定义 | 无"税率"录入列，后端虽支持多税率逐行计税（calcTotal），但 UI 恒走默认 0.13 | 前后端能力口径不一致，多税率特性对用户不可见 | 订单行增加税率 InputNumber 列（precision 2，默认 0.13） |

## 做得好的地方（值得沉淀为团队模式）

- **事务边界完整**：saveWithItems/updateWithItems/removeWithItems/removeByIds/audit 全部 `@Transactional(rollbackFor = Exception.class)`，主子表同生共死。
- **auditWithGuard 原子状态守卫**（`UPDATE ... WHERE id=? AND status='1'` 判影响行数）是教科书级的防并发状态流转写法，建议推广到所有状态机。
- **金额服务端强制重算**（validateOrder 逐行 amount + calcTotal 逐行税率），不信任前端传值，含默认税率与多税率混合支持。
- **编号唯一性双保险**：业务预检 + uk(code,del_flag) 唯一索引 + DuplicateKeyException 兜底转业务异常。
- **软删复活（resurrect）机制**避免了 (code, del_flag) 唯一索引的经典冲突坑，createBy/createTime 保留、updateBy 刷新，审计字段处理正确。
- 权限注解齐全（list/add/edit/delete/deleteBatch/export 全覆盖）、菜单由 MesMenuRegistry Java Runner 注册（L66-67 与 SQL 注释一致）、update-begin/end 标记合规、列表查询走 QueryGenerator 标准模式、queryAll/export 有 1000 条上限守卫。
