# 采购订单模块审计报告 — 测试牛马3号（性能压测视角）

审计范围：后端 `project-mes/.../mes/purchase/order/`（Entity×2 / Mapper×2 / ServiceImpl / Controller）、前端 `views/project/mes/purchase/order/`（index.vue / OrderDrawer.vue / order.api.ts / order.data.ts）、SQL `V6.0.1__mes_purchase_order_init.sql`。
关注维度：接口响应、分页/索引、N+1、大事务、数据量增长适应性。

## 结论

模块整体为低频业务单据场景（采购订单量级通常在万级/年），当前实现在小规模数据下响应良好：列表走分页、唯一校验走索引、审核用单行带状态守卫的 UPDATE。但存在三类随数据量增长会放大的隐患：**列表默认排序字段 create_time 无索引 + 编号模糊查询无法走索引**（主表做全表排序/扫描）、**订单行保存为逐行 INSERT 的 N+1 写入**、**字典/表字典翻译与 count-then-list 的双倍扫描**。建议优先补索引、订单行改批量插入。

## Findings

| 级别 | 位置 | 问题 | 影响 | 建议 |
|------|------|------|------|------|
| P1 | `MesPurchaseOrderController.queryPageList` + SQL `c_mes_purchase_order` | 列表固定 `ORDER BY create_time DESC`，但主表只有 `uk_po_code_del(code, del_flag)`，**create_time 无索引** | 数据量上万后每次翻页都触发全表扫描+filesort；列表是模块最高频接口，响应随数据量线性恶化 | 增加索引 `idx_create_time (create_time)` 或复合索引 `(del_flag, create_time)` |
| P1 | `MesPurchaseOrderServiceImpl.saveItems`（saveWithItems / updateWithItems 共用） | 订单行**逐行 `itemMapper.insert(item)`**，N 行 = N 次数据库往返 | 100 行订单保存耗时约为批量插入的 10 倍以上；且 edit 是"全删 + 全插"，行数多事务变大、锁持有时间拉长 | 改用批量插入（`INSERT ... VALUES (...),(...)` 或 MyBatis-Plus `saveBatch`/JdbcBatch），一个订单一次往返 |
| P2 | `QueryGenerator.initQueryWrapper` + 前端 `order.data.ts` 搜索项 `code` | 订单编号搜索默认生成 `LIKE '%xx%'` 模糊匹配，**前导通配符无法使用 uk_po_code_del 索引** | 数据增长后按编号搜索退化为全表扫描 | 编号搜索改前缀匹配（`LIKE 'xx%'`）或对 code 建独立普通索引并接受前缀匹配；至少在前端引导精确/前缀输入 |
| P2 | `Controller.queryPageList` | `pageSize` 由前端传入且**无上限保护** | 恶意/误传 `pageSize=100000` 时单次查询拉全表进内存，接口被放大攻击或 OOM | 服务端钳制 pageSize 上限（如 ≤200），与 QUERY_ALL_MAX 保持一致策略 |
| P2 | `Controller.queryAll` / `exportXls` | 先 `count()` 再 `list()` / 再全量导出，**两次扫描**；且 exportXls 的 count 用空 QueryWrapper 统计全表、与用户实际过滤条件不一致 | 导出/查全部接口双倍 IO；表超过 1000 条后，即使用户只过滤出 5 条也被整体拒绝（阈值按全表算） | count 与查询用同一条件构造器；导出直接限制返回行数（SQL LIMIT）代替先 count |
| P2 | SQL `c_mes_purchase_order` | **status、supplier_id 无索引**，而二者是列表页高频过滤条件（前端搜索区直接暴露供应商、状态） | 按状态/供应商筛选在数据增长后走全表扫描；status 低基数单独建索引收益有限 | 建复合索引 `(status, create_time)` 或 `(supplier_id, create_time)` 兼顾过滤+排序 |
| P3 | `MesPurchaseOrder` / `MesPurchaseOrderItem` 的 `@Dict` 注解（supplierId、purchaseType、status、materialId） | 列表每页每条记录都要做字典/表字典翻译，supplierId 走 `dictTable=c_mes_supplier` | Jeecg 有 Redis 缓存兜底，但每页仍是 pageSize×字段数 次翻译调用，供应商表变化还会引发缓存一致性问题 | 接受现状（有缓存），或在列表 SQL 直接 JOIN 供应商表取 name，减少逐条翻译开销 |
| P3 | `ServiceImpl.updateWithItems` | 编辑采用"整单删除订单行 + 逐行重新插入"模式，整个流程（查状态→查重→更新主表→删行→N 次插行）在**一个事务**内完成 | 行数大时事务长、undo 日志大；`idx_item_po_id` 索引频繁删插导致页分裂/碎片化 | 配合 P1 的批量插入改造；行数特别大时可考虑差量更新（按 id 更新/新增/删除） |
| P3 | `Controller.deleteBatch` | ids 为逗号字符串无数量上限，解析后 `IN (...)` 一次删除 | 极端情况下 IN 列表过长、单事务删除行数过多 | 限制单次批量删除条数（如 ≤500） |
| P3 | `MesPurchaseOrderItemMapper` / SQL `c_mes_purchase_order_item` | 明细表仅 `idx_item_po_id(order_id)`，查询带 `ORDER BY line_no` 需排序；`material_id` 无索引 | 单订单行数少，影响可忽略；未来若做"按物料查采购订单行"类统计则全表扫 | 可建 `(order_id, line_no)` 复合索引；material_id 索引视后续统计需求再加 |
| P3 | `OrderDrawer.vue` 订单行表格 `:pagination="false"` | 订单行无分页无虚拟滚动，全部渲染 | 用户手工加几百行时页面卡顿（业务上罕见） | 行数超过阈值（如 100 行）时提示或启用虚拟滚动 |
| P3 | `MesPurchaseOrderMapper.resurrect` | 复活更新为全字段 UPDATE | 单行操作，开销小，无实际影响 | 无需处理 |
| 正面项 | `auditWithGuard`、`selectDeletedByCode`、`uk_po_code_del` | 审核用带状态守卫的单行 UPDATE（无先查后改），已删记录查询走唯一索引，编号查重走索引 | 高并发下审核无额外往返，写路径索引覆盖良好 | 保持 |

## 数据量增长适应性小结

- **1 万级**：现状基本无感，仅列表排序偶尔 filesort。
- **10 万级**：列表排序（P1-索引）、编号模糊搜索（P2-LIKE）明显变慢，须先落地两条索引改造。
- **大订单行（>100 行/单）**：保存/编辑接口耗时被逐行 INSERT 主导，须落地批量插入。
- 导出/查全部的 1000 条硬上限在增长后会成为业务阻塞点（按全表而非过滤结果计数），建议同步修正。
