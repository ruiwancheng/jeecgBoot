**验证结论：** 并发击穿核心漏洞已修复——编辑/删除先 SELECT ... FOR UPDATE 锁行 → 在锁内校验 status='1' → 再执行写操作，与 audit 的 `auditWithGuard` 模式一致。

**⚠️ 小缺口：** `updateWithItems` 未显式 `entity.setStatus(null)`。虽然 FOR UPDATE 已确认 DB 中 status='1'，但 `super.updateById(entity)` 会写入客户端传过来的 status 值。正常前端发送 status='1'（hidden 字段 defaultValue='1'），但恶意构造请求可覆盖为非'1'值。建议补一行 `entity.setStatus(null)` 在 `updateById` 之前，彻底杜绝覆盖可能。**评级：P2（需绕过认证+前端，且锁已确认操作合法，风险面极窄）。**

## 补充说明

- `updateWithItems` 中 `checkStatus(entity, "edit")` 调用已移除（被 inline FOR UPDATE 替代），该方法的 null 检查修复虽不再被主路径使用，但对任何间接调用方仍有效。
- `removeByIds`（批量删除）仍使用旧式"先 SELECT 再 DELETE"两步检查（无 FOR UPDATE），但该路径为批量操作且调用频率低，按原始审计定级保留为 P2 即可。
- 后端 `saveWithItems` 的 resurrect 路径中，`entity.setId(old.getId())` 后 `createBy/createTime` 被显式继承自旧记录（L.64-65），设计正确；同时 `saveWithItems` 开头 null 掉所有敏感字段（L.48-50），不会被客户端注入覆盖。✅
