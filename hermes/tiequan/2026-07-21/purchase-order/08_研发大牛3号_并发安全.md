# 铁拳团审计报告 — 采购订单模块

**视角：** 研发大牛3号（并发安全：超收、重复提交、check-then-act 非原子、单号并发、状态机并发、幂等）
**审计日期：** 2026-07-21
**审计范围：** 后端 `purchase/order/` 全部（Entity×2 / Mapper×2 / ServiceImpl / Controller）、前端 `views/project/mes/purchase/order/`（index.vue / OrderDrawer.vue / order.api.ts / order.data.ts）、SQL `V6.0.1__mes_purchase_order_init.sql`

## 结论

审核操作（audit）本身已用"带状态条件的原子 UPDATE"做了并发防护，值得肯定；但**编辑、删除路径仍是"先查状态再写库"的两步操作，与并发审核存在竞态窗口——已审核的订单可能被并发编辑静默改回草稿并整体替换明细、或被并发删除**。另外采购入库的超收校验（在入库模块中）是典型的"先汇总再比较再写入"非原子流程，两张入库单并发提交可双双通过校验造成超收。

## Findings

| 级别 | 位置 | 问题 | 影响 | 建议 |
|------|------|------|------|------|
| P0 | `MesPurchaseOrderServiceImpl.updateWithItems()` + `checkStatus()` | 状态机并发击穿：先 `selectById` 查状态（check），再 `updateById` 全字段写回（act），两步非原子；且编辑时强制 `entity.setStatus("1")`。与 `audit()` 并发时：编辑读到草稿→审核把状态改为已确认→编辑的 updateById 无状态条件，把状态**写回草稿**并删光旧明细、插入新明细 | 已审核订单被静默回退为草稿，明细与金额被整体替换，审核流于形式，下游入库/财务基于被篡改的订单继续流转 | 参照已有的 `auditWithGuard` 做法，编辑改用带条件 UPDATE：`UPDATE ... SET ... WHERE id=#{id} AND status='1'`，影响行数为 0 则抛"状态已变更"；编辑 SQL 中不得回写 status 字段 |
| P0 | `purchase/receipt/service/impl/MesPurchaseReceiptServiceImpl.java`（超收校验段，约 182-220 行）+ `V6.0.1` 订单行表结构 | 超收防护为 check-then-act：先 SELECT 汇总历史入库量 → 内存比较 → INSERT 入库行，全程无锁。同一订单两张入库单并发提交时，双方读到相同的历史累计量，双双通过校验 → 累计入库超过采购数量。订单行表（`c_mes_purchase_order_item`）没有"累计入库量"字段，数据库层面无法做原子守卫 | 超收：实际入库金额/数量超过合同订单，库存与应付账款虚增，且事后难以追责 | 在订单行加 `received_qty` 字段，入库时用原子语句扣减额度：`UPDATE c_mes_purchase_order_item SET received_qty = received_qty + #{qty} WHERE order_id=#{oid} AND material_id=#{mid} AND received_qty + #{qty} <= quantity`，影响行数 0 即拒绝；或对同一订单的入库加行锁（SELECT 订单 FOR UPDATE）串行化 |
| P1 | `MesPurchaseOrderServiceImpl.removeWithItems()` / `removeByIds()` | 删除同样是"先查状态再删"的非原子流程：与 `audit()` 并发时，删除方读到草稿状态后，审核先把订单置为已确认，删除方仍继续删明细、删主表 | 已审核（业务已生效、可能已有入库）的订单被删除，业务单据链断裂 | 删除改为带条件 DELETE/UPDATE：`... WHERE id=#{id} AND status='1'`，影响行数 0 抛异常；批量删除逐条用条件删除或先 `SELECT ... FOR UPDATE` 锁定再校验 |
| P1 | `MesPurchaseOrderServiceImpl.saveWithItems()` + `MesPurchaseOrderMapper.resurrect()` | 并发"复活"竞态：两个请求同时提交相同编号，都查到无生效订单、都找到同一条已删除记录，双双执行 resurrect。`resurrect` 的 WHERE 含 `del_flag=1`，后到者影响 0 行，但方法返回 void **未检查影响行数**，随后 `saveItems` 照常插入明细 | 同一订单被插入两套明细行（数量金额翻倍），且无任何报错，属于静默数据错误 | `resurrect` 改为返回 int 并校验影响行数，0 行时抛"订单编号已存在"由事务回滚 |
| P2 | `MesPurchaseOrderServiceImpl.updateWithItems()`；Entity `MesPurchaseOrder` | 无乐观锁：实体没有 `@Version` 字段，两个用户同时打开同一草稿订单编辑，后提交者静默覆盖先提交者的全部修改（last-writer-wins） | 多人协作时一方修改丢失且无任何提示 | 主表加 `version` 列 + MyBatis-Plus `@Version` 乐观锁；或在编辑时校验 `update_time` 与打开时一致 |
| P3 | `MesCodeRuleServiceImpl.nextCode()`（被 OrderDrawer 调用） | 单号并发本身安全（FOR UPDATE 行锁 + 事务内递增，集群可用，做得规范）；但取号发生在**打开新增抽屉时**，用户取消不保存则号码被烧掉，产生断号 | 单号不连续，对审计/对账造成困扰（不丢数据） | 可接受现状（业务上断号常见）；若要消除，改为保存提交时取号，或在编码规则中支持"预占-确认"两阶段 |
| P3 | `MesPurchaseOrderController.add` + `OrderDrawer.vue handleSubmit` | 重复提交/幂等：后端无幂等键，前端仅靠 `confirmLoading` 防连点、无显式 submitting 标志。幸而 `code` 唯一索引 + `DuplicateKeyException` 捕获兜底，重试/双击不会产生重复单，只会报"订单编号已存在" | 网络重试场景下用户看到误导性报错（以为是编号冲突，实际首单已保存成功），可能放弃或重复录入 | 前端 handleSubmit 加 `if (submitting) return` 显式守卫；后端可接受"编号即幂等键"现状，但报错文案建议提示"该单可能已保存，请刷新列表确认" |
| P3 | `MesPurchaseOrderServiceImpl.updateWithItems()` 编号查重段 | 编辑时的编号查重也是 check-then-act（`selectCount` 后 `updateById`），并发改同号时依赖唯一索引兜底，但 `updateById` 抛出的 `DuplicateKeyException` **未像新增路径那样捕获**转换 | 极小概率下用户收到 500 系统错误而非"订单编号已存在"友好提示 | 编辑路径同样 try/catch `DuplicateKeyException` 转换为业务异常 |
| 正面 | `MesPurchaseOrderMapper.auditWithGuard()` + `MesCodeRuleServiceImpl.nextCode()` | 审核用 `UPDATE ... WHERE status='1'` 原子守卫、取号用事务内 FOR UPDATE 行锁，均为教科书式的正确并发写法 | — | 将这两种模式推广到编辑/删除/超收校验路径 |
