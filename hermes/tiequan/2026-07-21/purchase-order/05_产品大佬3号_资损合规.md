# 铁拳团审计报告 — 采购订单模块（产品大佬3号：资损合规）

- 审计日期：2026-07-21
- 审计视角：金额精度与计算正确性（qty×price=amount/税额）、库存增减正确性、应付对账逻辑、退货退款路径
- 审计范围：后端 `jeecg-boot/jeecg-boot-module/project-mes/.../mes/purchase/order/` 全部、前端 `jeecgboot-vue3/src/views/project/mes/purchase/order/` 全部、SQL `V6.0.1__mes_purchase_order_init.sql`；为验证库存/应付链路，延伸只读了 `purchase/receipt` 与 `finance/payable` 的相关代码。

## 结论

主表金额计算链路基本扎实（服务端强制重算 qty×price、BigDecimal、审核带状态守卫、累计入库超量校验），但资损风险集中在三处：①应付生成口径错误——税率硬编码 13%、金额取不含税、取价按物料名模糊匹配，订单-入库-应付三单必然对不上；②编辑与审核存在并发缺口，已确认订单可被竞态改回草稿并改价改量；③全模块没有任何退货/红冲/退款路径，库存与应付只增不减，错单无法追回。

## Findings

| 级别 | 位置 | 问题 | 影响 | 建议 |
|------|------|------|------|------|
| P1 | receipt/service/impl/MesPurchaseReceiptServiceImpl.java#audit（约 L140-150，业财联动生成应付） | 应付税额 `totalAmount × 0.13` 硬编码，完全忽略订单行 taxRate；且应付 amount/unsettledAmount 取的是**不含税**金额，与采购订单"含税总额 total_with_tax"口径不一致 | 多税率订单（6%/9%/0%）应付税额必错；按不含税挂账导致少付供应商或付款审批金额口径混乱，订单-入库-应付三方对账永久存在差额 | 应付金额应按订单行 qty×price 逐行取行 taxRate 计算税额，并明确 amount 为含税口径（= 订单 total_with_tax 的入库比例部分） |
| P1 | 同上 audit 取价逻辑（约 L122-128） | 入库行取价按 `orderId + materialId` 查订单行后 `get(0)`，同一物料在同一订单出现多行（不同单价）时取价结果取决于数据库返回顺序，且无 ORDER BY | 入库金额、应付金额随机性错误，直接资损且无法复现排查 | 收货行应绑定 order_item_id 按行取价；至少应按 line_no 排序并禁止同物料多行 |
| P1 | order/service/impl/MesPurchaseOrderServiceImpl.java#updateWithItems | 状态校验是"先 selectById 再 updateById"的 check-then-act，UPDATE 语句无 `status='1'` 守卫（审核有 auditWithGuard，编辑没有）；且编辑强制 `setStatus("1")` | 审核与编辑并发时，已确认订单可被改回草稿并改价改量；而已生成的入库单/应付按旧金额入账，形成账实差 | updateById 改为带 `WHERE id=? AND status='1'` 的守卫 UPDATE，影响行数为 0 时报错 |
| P1 | 整个 purchase 模块（order/receipt/apply/ledger）+ 状态字典 | 无退货单、无红冲、无退款路径：入库审核后库存与应付只增不减；订单字典有"已关闭(6)"但无任何入口，已确认订单不能改、不能删、不能取消 | 错单、质量退货、供应商违约等场景无法处理，库存虚增、应付虚增，资损无法追回，只能靠 DBA 改库 | 增加采购退货单（审核时红冲库存+红冲应付），订单增加"关闭/取消"操作及反向状态机 |
| P2 | 前端 OrderDrawer.vue 订单行表格 | 行内只有 物料/数量/单价/金额，**没有税率输入列**；后端虽支持行级 taxRate，但 UI 提交时永远走默认 0.13 | 非 13% 税率物料的税额、含税总额全部错误，进项税与供应商发票对不上 | 行内增加税率列（下拉：13%/9%/6%/0%），并随提交传给后端 |
| P2 | receipt audit（约 L114-155） | 入库审核后不回写采购订单状态，字典中的"部分到货(4)/已到货(5)"永不可达（全模块 grep 无订单状态推进代码） | 订单执行进度失真，业务无法按状态区分"未到货/部分到货/已完成"，对账与催货失去依据 | 审核后按累计入库量回写订单状态 4/5 |
| P2 | receipt validateReceipt（约 L186-189） | `Collectors.toMap(materialId, quantity, (a,b)->a)` 合并同物料多行时只保留首行数量，超量校验基准小于订单实际采购总量 | 同物料多行的订单，合法入库被误拒（"累计入库量超过采购数量"），或不同行口径混乱 | 按物料对 quantity 求和（`BigDecimal::add`）作为校验基准 |
| P2 | receipt audit 生成应付（约 L148-149） | creditPeriod 固定 30、dueDate 固定 now+30 天，忽略订单 paymentTerms（付款条款）字段 | 账期与合同约定不符，导致提前付款占用资金或逾期产生违约金 | 解析 paymentTerms 或新增信用期字段计算到期日 |
| P2 | finance 全模块（延伸发现） | 无"订单-入库单-发票"三单匹配/对账机制：应付由入库单自动生成，但没有任何功能把应付与采购订单总额、采购发票核对 | 供应商多开票、重复开票无法被系统拦截，付款环节是资损最后一道门却没有闸 | 增加三单匹配校验，付款前强制核对 |
| P3 | order ServiceImpl#calcTotal（约 L157-172） | 税额在行级不舍入、订单级一次 HALF_UP，行税额不落库（item 无 tax_amount 字段） | 与按行开票的增值税发票逐行税额可能差 0.01×行数，产生对账尾差 | 行级税额 setScale(2) 后汇总，并在订单行表增加 tax_amount 列 |
| P3 | V6.0.1 SQL `c_mes_purchase_order_item.unit_price DECIMAL(18,2)` | 单价仅 2 位小数 | MES 常见低价大宗物料（如 ¥0.0035/个）无法精确录入，qty×price 金额系统性失真 | unit_price 改 DECIMAL(18,4)，与 quantity 精度对齐 |
| P3 | OrderDrawer.vue 金额列模板 | 前端用 JS number 浮点 `(quantity \* unitPrice).toFixed(2)` 展示金额 | 浮点误差导致页面显示与后端 BigDecimal HALF_UP 结果偶发差 0.01，用户误解为"系统算错" | 展示后端返回的 amount，或使用 decimal.js 计算 |
| P3 | OrderDrawer.vue L64 | `getNextCode`、`MES_BIZ_CODE` 未 import（其他模块如 sales/order 均有导入），ReferenceError 被外层 try/catch 静默吞掉 | 订单自动编号功能静默失效，用户只能手工输编号，易错且问题难以察觉 | 补充 `import { getNextCode } ... / MES_BIZ_CODE` 导入 |
| P3 | order Controller#audit | 审核接口复用 `mes:purchaseOrder:edit` 权限码，无独立审核权限 | 制单人与审核人无法职责分离，同一人可制单+审核+改价，内控缺失 | 新增 `mes:purchaseOrder:audit` 权限点并单独授权 |

## 做得好的地方（供其他模块参考）

- 服务端强制重算行金额（不信任前端传值），BigDecimal + HALF_UP，数量>0、单价≥0 校验齐全。
- 审核采用 `auditWithGuard`（UPDATE ... WHERE status='1'）防并发重复审核，是正确姿势——应尽快推广到编辑/删除。
- 入库累计超量校验（历史+本次 ≤ 采购量）思路正确，堵住了重复入库超收的主要口子。
- 新增/编辑强制 status='1'，防止 API 绕过状态机直接构造"已确认"订单。
