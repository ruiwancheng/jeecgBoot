# 铁拳团审计报告 — 采购订单模块（产品大佬2号：边界异常视角）

- 审计日期：2026-07-21
- 审计范围：`project-mes` 采购订单后端（Entity×2/Mapper×2/ServiceImpl/Controller）、前端 `views/project/mes/purchase/order/`（4 个文件）、SQL `V6.0.1__mes_purchase_order_init.sql`
- 审计视角：并发操作、逆向操作（取消已审核订单/退货）、临界值（零数量/超大数量）、上下游联动（订单变更不同步收货）

## 结论

状态机"有去无回"：订单一旦审核即永久锁死（无取消/关闭入口），且前端根本没有审核按钮导致收货流程走不通；同时"先查状态再改"的非原子检查与原子审核存在竞态窗口，编辑/删除可把已审核订单静默改回草稿。临界值方面数量/金额无上限校验，超大值直接打爆数据库字段。整体阻断级问题 1 个、高优先级并发/逆向问题 3 个，建议优先修复。

## Findings

| 级别 | 位置 | 问题 | 影响 | 建议 |
|------|------|------|------|------|
| P0 | 前端 `index.vue` getActions + `order.api.ts` | 前端只有"编辑/删除"两个操作，无审核按钮、api.ts 也未封装 `/audit` 接口；后端 `/audit` 成为孤儿接口 | 用户在页面上**永远无法审核订单**；而收货单校验要求订单状态=已确认（3)/部分到货（4)，意味着整个"下单→收货"主流程在界面上走不通，业务完全阻断 | 列表行操作按状态追加"审核"按钮（草稿显示），api.ts 补 `auditOrder` 封装；同时按状态隐藏"编辑/删除"（后端已拦截，但前端不应给可达的死按钮） |
| P1 | `MesPurchaseOrderServiceImpl.updateWithItems` / `removeWithItems` / `removeByIds` | 状态检查是"先 selectById 读状态、再 update/delete"的非原子操作；而 `auditWithGuard` 是原子 UPDATE。竞态时序：编辑事务读到草稿→审核事务提交（置已确认）→编辑事务提交 `updateById` 且**强制写回 status='1'** | 已审核订单被静默改回草稿且明细被整体替换；同理已审核订单可被并发删除。审核结果被撤销，下游收货校验随之失效，账实对不上且无日志可追 | 编辑/删除改用带状态守卫的原子 SQL（`UPDATE ... WHERE id=? AND status='1'`，影响 0 行即报"状态已变更"）；实体增加 `@Version` 乐观锁 |
| P1 | `MesPurchaseOrderServiceImpl`（全类）+ Controller | 无任何逆向操作：无取消审核、无关闭、无作废接口；`audit` 直接 1→3 跳过"待确认（2)"，字典里的"已关闭（6)"永不可达 | 订单误审核后**永久锁死**：不能改、不能删、不能关。业务上"供应商不做了/下错单"是常态，唯一出路是找运维改数据库，风险极高 | 增加 `unaudit`（已确认→草稿，需校验无关联收货单）与 `close`（草稿/已确认→已关闭）接口，均用原子状态守卫 SQL，并配独立权限码 |
| P1 | `MesPurchaseReceiptServiceImpl`（联动方）+ `MesPurchaseOrderMapper` | 收货审核后**不回写订单状态**：全模块只有订单自己的 `audit` 写状态，收货模块仅 `selectById` 读订单。字典中"部分到货（4)/已到货（5)"无任何代码可达 | 订单列表永远停留在"已确认"，采购员无法从订单维度看"收了多少、还差多少"；收货的累计超量校验靠扫收货单历史拼凑，订单侧无已收数量冗余，后续对账/报表无数据源 | 收货审核事务内按订单聚合已收量，原子回写订单状态（3→4→5）及已收数量字段；订单表增加 received_quantity 冗余列 |
| P2 | `MesPurchaseOrderServiceImpl.saveWithItems` 的 resurrect 分支 | 并发恢复回收站同编号订单：两事务都 `selectDeletedByCode` 命中同一行→都执行 `resurrect`，但 `resurrect` 返回 void **不校验影响行数**，第二个 UPDATE 命中 0 行仍继续 `saveItems` | 同一订单 ID 下明细行被插入两份（数量翻倍），且无任何报错，数据静默错误 | `resurrect` 改为返回 int 并校验=1，否则抛"订单编号已存在"；或直接用 `INSERT ... ON DUPLICATE KEY` 语义收口 |
| P2 | `MesPurchaseOrderServiceImpl.validateOrder` / `calcTotal` | 数量、单价无上限校验：`quantity` DECIMAL(18,4) × `unitPrice` DECIMAL(18,2) 的乘积超过 DECIMAL(18,2)（如 1 亿条 × 万元单价）时，插入明细/主表金额直接触发 MySQL 数据截断异常 | 用户录入超大数量后保存报一串英文 SQL 错误，业务人员完全看不懂；含税总额同理溢出 | 增加上限校验（如数量≤9999万、单行金额≤14 位整数），超限给出中文业务提示；前端 InputNumber 同步加 max |
| P2 | `MesPurchaseOrderServiceImpl.updateWithItems` | 同一草稿订单多人同时编辑：无版本号/乐观锁，编号唯一检查也 `ne id` 通过，后提交者整体覆盖先提交者（明细先全删再插） | 两人各改一行，后保存的人把先保存的人的修改无声吞掉（lost update），采购数量错误直接进入收货环节 | 实体加 `@Version` 乐观锁字段，冲突时提示"订单已被他人修改，请刷新" |
| P3 | `MesPurchaseOrderController.audit` | 审核沿用 `mes:purchaseOrder:edit` 权限码，无独立 `mes:purchaseOrder:audit` 权限 | 审核是资金承诺类关键动作，有编辑权的人即可审核，职责不分离；后续若加取消审核也面临同样问题 | 审核/取消审核配独立权限码并在菜单注册 |
| P3 | `MesPurchaseOrderServiceImpl.validateOrder` | `taxRate` 无范围校验（可传负数、100、999），且前端表单无税率字段用户无法修正；税率 DECIMAL(5,2) 存 0.13 实际是"小数"语义未文档化 | API 调用方可构造税额>金额的畸形订单；收货审核生成应付时又硬编码 0.13（见 receipt audit），两处税率口径不一致导致应付税额≠订单税额 | taxRate 校验 0≤rate≤1；应付生成改从订单行取实际税率 |
| P3 | `MesPurchaseOrderItem.quantity` DECIMAL(18,4) + 后端 amount 计算 | 后端用**未截断的原始 BigDecimal** 计算行金额，但数量入库时被四舍五入到 4 位小数 | 用户传 5 位以上小数数量时，出现 数量(库存口径)×单价 ≠ 金额(财务口径) 的分毫级差异，对账对不上 | 保存前先把 quantity setScale(4) 再算金额，保证两个口径同源 |
| P3 | `OrderDrawer.vue` 金额列 + addLine/handleSubmit | ①前端金额用 JS 浮点 `(q*p).toFixed(2)` 显示（浮点误差，仅显示层，后端重算兜底）；②订单行数无上限，可提交数千行逐行 insert | ①显示金额偶发与保存后差 1 分，引发客诉；②超大明细单拖慢事务、撑爆导出 | ①显示金额改为与后端一致的 decimal 计算或保存后回显；②限制单订单行数（如≤200 行） |
| P3 | `MesPurchaseOrderServiceImpl.validateOrder` | 允许单价=0（`compareTo(ZERO) < 0` 仅拦负数），整张 0 元订单可审核 | 赠品/样品场景或许是特性，但 0 元订单走完全套审核-收货-应付流程，应付生成 0 元单据污染财务数据 | 业务确认是否允许 0 单价；若允许，收货生成应付时跳过 0 金额单据 |

## 附：已验证的正面项（不属于问题）

- 订单编号唯一性有数据库唯一索引 `uk_po_code_del` + `DuplicateKeyException` 友好提示，新增并发有兜底。
- `auditWithGuard` 本身是原子 UPDATE 状态守卫，重复点击审核/并发审核不会重复生效。
- 数量=0、负单价、空明细、交货日期早于订单日期等临界值后端均有中文业务提示拦截。
- `queryAll`/导出接口有 1000 条上限保护，批量删除有空参数保护。
