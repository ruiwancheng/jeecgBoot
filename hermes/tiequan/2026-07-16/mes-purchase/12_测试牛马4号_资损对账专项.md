## 一、审计目标与范围

本次审计以**资金损失防控与账实一致性**为核心，聚焦采购管理模块中金额、数量、库存、状态四个关键维度的对账正确性。重点检查：

1. **金额/数量一致性**：主表合计与明细行汇总是否一致；
2. **入库累计与订单数量对账**：累计入库量是否不超过采购订单数量；
3. **库存台账与入库记录对账**：入库动作是否正确反映到库存台账；
4. **税额与含税金额计算**：增值税价税分离、四舍五入、多税率混排是否合规；
5. **删除/反审核后的数据一致性**：单据删除或状态回退后，关联数据是否仍可追溯、一致。

被审计对象：采购申请、采购订单、采购入库、库存台账四个模块的后端 Service/Entity、数据库脚本、前端 Drawer/列表。

风险等级定义：

| 等级 | 标识 | 判定标准 |
|------|------|----------|
| 致命 | 🔴 P0 | 可直接造成财务损失、库存账实不符、合规审计失败，或存在可被触发的线上资损事故 |
| 高危 | 🟠 P1 | 在异常路径或操作不规范下可能产生资损或合规风险，但短期内可临时规避 |
| 中危 | 🟡 P2 | 影响数据质量、审计效率、可维护性，长期可能演变为资损问题 |
| 低危 | 🟢 P3 | 优化建议、技术债务 |

## 二、总体结论

| 对账维度 | 当前状态 | 主要风险 | 风险等级 |
|---|---|---|---|
| 金额/数量一致性 | 订单后端强制重算，但申请金额被强制归零 | 申请金额永远为 0，预算控制失效；订单字段可写存在未来被绕过风险 | 🔴 P0 / 🟠 P1 |
| 入库累计与订单数量对账 | 已做累计校验，但物料存在性校验缺失 | 非订单物料可入库；并发下可能超量 | 🔴 P0 / 🟠 P1 |
| 库存台账与入库记录对账 | **完全未联动** | 入库不更新库存，账实严重不符 | 🔴 P0 |
| 税额与含税金额计算 | 后端重算但汇总后四舍五入，税率无范围校验 | 发票对账可能差 1 分；异常税率可导致税额暴涨 | 🔴 P0 |
| 删除/反审核后一致性 | 仅草稿可删除；入库编辑强置草稿 | 删除未校验下游单据；编辑后状态与已发生库存不一致 | 🟠 P1 |

**结论**：当前 MES 采购模块在资损对账维度存在多处致命风险，尤其是**库存台账与入库脱节、申请金额归零、入库物料一致性缺失、税额精度与税率校验不足**。建议在模块上线前必须完成 P0 级修复，否则无法通过财务审计与资金风控验收。

## 三、分项对账审计

### 3.1 金额/数量一致性

#### 3.1.1 采购申请

| 检查项 | 结果 | 说明 |
|---|---|---|
| 申请主表金额字段 | `totalAmount` | `MesPurchaseApplyServiceImpl.calcTotal` 中直接设为 `BigDecimal.ZERO` |
| 明细行金额字段 | 无 | `MesPurchaseApplyItem` 无单价/金额字段 |
| 前端是否提交金额 | 否 | 明细行仅物料、数量、单位、用途 |
| 后端是否校验/重算 | 仅强制归零 | 无论主表或明细是否有金额，均写 0 |

**风险：🔴 P0 - APPLY-AMT-001**
- **问题**：`MesPurchaseApplyServiceImpl.calcTotal` 将 `totalAmount` 强制置为 `0`。
- **资损影响**：采购申请的金额永远是 0，财务无法基于申请金额做预算控制、审批额度校验、资金计划。预算超支风险完全不可见，可能导致无预算采购、资金失控。
- **对账影响**：申请模块与订单模块之间无金额传承，无法核对「订单金额 ≤ 申请金额/预算」。
- **修复建议**：在申请行增加 `estimatedUnitPrice`（预估单价）字段；`calcTotal` 按 `Σ(quantity × estimatedUnitPrice)` 计算并写入 `totalAmount`；前端同步展示。

#### 3.1.2 采购订单

`MesPurchaseOrderServiceImpl.validateOrder` 和 `calcTotal` 逻辑：

```java
// 第 137 行：不含税金额 = 数量 × 单价，强制重算
item.setAmount(item.getQuantity().multiply(item.getUnitPrice()).setScale(2, RoundingMode.HALF_UP));
```

```java
// 第 141-154 行：汇总税额与含税总额
private void calcTotal(MesPurchaseOrder entity) {
    BigDecimal total = BigDecimal.ZERO;
    BigDecimal taxTotal = BigDecimal.ZERO;
    for (MesPurchaseOrderItem item : entity.getItems()) {
        if (item.getAmount() != null) total = total.add(item.getAmount());
        BigDecimal rowTaxRate = item.getTaxRate() != null ? item.getTaxRate() : new BigDecimal("0.13");
        if (item.getAmount() != null) {
            taxTotal = taxTotal.add(item.getAmount().multiply(rowTaxRate));
        }
    }
    entity.setTotalAmount(total.setScale(2, RoundingMode.HALF_UP));
    entity.setTaxAmount(taxTotal.setScale(2, RoundingMode.HALF_UP));
    entity.setTotalWithTax(total.add(entity.getTaxAmount()).setScale(2, RoundingMode.HALF_UP));
}
```

| 检查项 | 结果 | 说明 |
|---|---|---|
| 明细行金额是否后端重算 | ✅ 是 | `amount = quantity × unitPrice`，保留 2 位 |
| 主表合计是否后端重算 | ✅ 是 | `totalAmount = Σamount` |
| 税额是否按行计算 | ⚠️ 部分 | 按行 `amount × taxRate`，但汇总后再统一四舍五入 |
| 前端是否可篡改金额 | ⚠️ 可传入 | 实体字段可写，若 `calcTotal` 被绕过则存在风险 |
| 单价是否可负数 | ✅ 否 | 校验 `unitPrice >= 0` |
| 单价是否可为 0 | ⚠️ 是 | 校验 `unitPrice < 0` 拦截，但 0 可通过 |

**风险：🟠 P1 - ORDER-AMT-001**
- **问题**：`unitPrice` 允许为 0，业务上可能出现免费采购，但系统未做任何标记或审批控制。
- **资损影响**：免费采购可能绕过供应商付款审批，导致应付账款缺失、审计无法解释。
- **修复建议**：若业务允许 0 单价，增加「免费采购」标识并配置额外审批流；若不允许，改为 `> 0` 校验。

**风险：🟠 P1 - ORDER-AMT-002**
- **问题**：`totalAmount`、`taxAmount`、`totalWithTax` 等字段可被前端传入，虽然后端会重算，但字段本身可写。
- **资损影响**：若未来 `calcTotal` 被绕过或出现异常，错误金额可能直接落库。
- **修复建议**：在 `validateOrder` 或 `calcTotal` 开头强制重置金额字段为 `null`/`zero`，或改用只读 DTO 接收前端数据。

**风险：🔴 P0 - ORDER-AMT-003**
- **问题**：`taxRate` 未做范围校验，可传入任意值（如 13、-0.1、1.5）。
- **资损影响**：
  - 传入 `13`（误把 13% 传成 13）→ 税额 = 不含税金额 × 13，含税总额暴涨 13 倍；
  - 传入负数 → 税额为负，财务账异常；
  - 传入 0 → 可合理规避税额，但需明确业务规则。
- **修复建议**：在 `validateOrder` 中校验 `0 ≤ taxRate ≤ 1`（或限定为字典枚举值）；建议统一使用小数形式（0.13）。

### 3.2 入库累计与订单数量对账

`MesPurchaseReceiptServiceImpl.validateReceipt` 逻辑：

```java
// 第 133-138 行：按物料 ID 聚合订单数量
LambdaQueryWrapper<MesPurchaseOrderItem> oqw = new LambdaQueryWrapper<>();
oqw.eq(MesPurchaseOrderItem::getOrderId, order.getId());
List<MesPurchaseOrderItem> orderItems = purchaseOrderItemMapper.selectList(oqw);
Map<String, BigDecimal> orderQtyMap = orderItems.stream()
        .collect(Collectors.toMap(MesPurchaseOrderItem::getMaterialId, MesPurchaseOrderItem::getQuantity, (a, b) -> a));

// 第 139-154 行：累计历史入库量

LambdaQueryWrapper<MesPurchaseReceipt> rqw = new LambdaQueryWrapper<>();
rqw.eq(MesPurchaseReceipt::getPurchaseOrderId, entity.getPurchaseOrderId());
if (StringUtils.hasText(entity.getId())) {
    rqw.ne(MesPurchaseReceipt::getId, entity.getId()); // 编辑时排除自身

    LambdaQueryWrapper<MesPurchaseReceiptItem> hiqw = new LambdaQueryWrapper<>();

    }
}

// 第 164-172 行：逐行校验
BigDecimal orderQty = orderQtyMap.get(item.getMaterialId());
if (orderQty != null) {
    BigDecimal historyQty = historyQtyMap.getOrDefault(item.getMaterialId(), BigDecimal.ZERO);
    BigDecimal totalAfter = historyQty.add(item.getReceiptQuantity());
    if (totalAfter.compareTo(orderQty) > 0) {
        throw new JeecgBootException("第" + (i+1) + "行累计入库量(" + totalAfter + ")超过采购数量(" + orderQty

    }

```

| 检查项 | 结果 | 说明 |
|---|---|---|
| 是否校验订单存在 | ✅ 是 | 不存在抛异常 |
| 是否校验订单状态可入库 | ✅ 是 | 仅 `status=3`（已确认）或 `4`（部分到货） |
| 是否累计历史入库量 | ✅ 是 | 已修复 P0-004 |
| 编辑时是否排除自身 | ✅ 是 | `rqw.ne(id, ...)` |
| 是否校验入库物料在订单行中 | ❌ 否 | 若 `orderQtyMap.get(materialId)` 为 null，校验跳过 |
| 是否校验供应商一致 | ❌ 否 | `supplierId` 可手工输入，未与订单校验 |
| 是否防并发超量 | ❌ 否 | 无锁/乐观锁，两个并发入库可能同时通过 |
| 是否回写订单已入库数量 | ❌ 否 | 订单行无 `arrivedQty` 字段，状态不会自动更新 |
| 是否支持多单位换算 | ❌ 否 | 订单行/入库行均无 `unit` 一致性校验 |

**风险：🔴 P0 - RECEIPT-QTY-001**
- **问题**：入库物料若不在订单明细中，超量校验直接跳过。
- **资损影响**：用户可入库未采购的物料，造成库存虚增、应付账款异常、供应商对账困难。
- **修复建议**：校验 `item.getMaterialId()` 必须存在于 `orderQtyMap.keySet()` 中，否则报错；`orderQuantity` 应由后端从订单行反写，禁止前端写入。

**风险：🔴 P0 - RECEIPT-QTY-002**
- **问题**：累计入库校验未考虑并发。
- **资损影响**：两个并发入库单同时读取历史量，都判断通过并保存，总入库量可能超过订单数量，导致多付货款、库存虚增。
- **修复建议**：对采购订单行加数据库行锁或乐观锁；或使用 `INSERT ... ON DUPLICATE KEY UPDATE` 预占数量。

**风险：🟠 P1 - RECEIPT-QTY-003**
- **问题**：`supplierId` 可手工输入，未与采购订单供应商一致性校验。
- **资损影响**：用户可选择与订单不同的供应商，导致财务对账、供应商往来账、发票校验全部错误。
- **修复建议**：选择采购订单后自动带出供应商并禁用编辑；后端保存时强制校验 `receipt.supplierId == order.supplierId`。

**风险：🟠 P1 - RECEIPT-QTY-004**
- **问题**：订单行缺少 `arrivedQty`（已入库数量）字段，状态不会自动更新。
- **资损影响**：财务人员无法判断订单是否已执行完毕，可能出现重复采购或漏付款。
- **修复建议**：在订单行增加 `arrivedQty` 字段，入库时原子更新并回写订单状态（部分到货/已到货）。

### 3.4 税额与含税金额计算

#### 3.4.1 当前计算逻辑

```java
// 第 141-154 行
private void calcTotal(MesPurchaseOrder entity) {
    BigDecimal total = BigDecimal.ZERO;
    BigDecimal taxTotal = BigDecimal.ZERO;
    for (MesPurchaseOrderItem item : entity.getItems()) {
        if (item.getAmount() != null) total = total.add(item.getAmount());
        BigDecimal rowTaxRate = item.getTaxRate() != null ? item.getTaxRate() : new BigDecimal("0.13");
        if (item.getAmount() != null) {
            taxTotal = taxTotal.add(item.getAmount().multiply(rowTaxRate));
        }
    }
    entity.setTotalAmount(total.setScale(2, RoundingMode.HALF_UP));
    entity.setTaxAmount(taxTotal.setScale(2, RoundingMode.HALF_UP));
    entity.setTotalWithTax(total.add(entity.getTaxAmount()).setScale(2, RoundingMode.HALF_UP));
}
```

| 检查项 | 结果 | 说明 |
|---|---|---|
| 行级不含税金额 | ✅ 后端重算 | `amount = quantity × unitPrice`，保留 2 位 |
| 行级税额 | ❌ 不落库 | 仅计算到订单头，未在行上保存 |
| 税额计算方式 | ⚠️ 汇总后四舍五入 | 先汇总所有行税额，再统一 `setScale(2)` |
| 多税率混排 | ⚠️ 未区分 | 行税率不同，汇总后统一四舍五入 |
| 税率范围校验 | ❌ 无 | 可传入任意值 |
| 含税总额校验 | ✅ 自动 | `totalWithTax = totalAmount + taxAmount` |
| 与发票对账 | ⚠️ 可能差 1 分 | 汇总后四舍五入与发票按行四舍五入可能不一致 |

**风险：🔴 P0 - TAX-001**
- **问题**：税额未按税法要求「价税分离」逐行四舍五入，而是汇总后统一四舍五入；且税率未校验范围。
- **资损影响**：按中国增值税要求，通常应**逐行计算税额并四舍五入后再汇总**，否则合计税额可能与发票税额差 1 分钱，导致对账差异。更严重的是 `taxRate` 未校验范围，传入异常值可导致税额暴涨或负数。
- **修复建议**：
  1. 逐行计算税额并 `setScale(2)` 后再汇总；
  2. 校验 `taxRate` 范围（建议 `0 ≤ taxRate ≤ 1`）；
  3. 在订单行增加 `taxAmount`、`totalAmount`（行含税金额）字段，便于按行对账；
  4. 提供「价税合计 = 不含税 + 税」的校验。

**示例说明**：

假设订单有两行：
- 行 A：amount = 100.00，taxRate = 0.13
- 行 B：amount = 100.00，taxRate = 0.13

- 当前逻辑：`(100×0.13 + 100×0.13) = 26.00` → 26.00（正确）
- 若行 A：amount = 100.33，taxRate = 0.13
- 当前逻辑：`(100.33×0.13 + 100.33×0.13) = 26.0858` → 26.09
- 按行四舍五入：`(100.33×0.13 = 13.0429 → 13.04) × 2 = 26.08`
- **对账差异：1 分钱**

### 3.5 删除/反审核后的数据一致性

| 检查项 | 采购申请 | 采购订单 | 采购入库 | 库存台账 |

| 复活是否复用旧 ID | ✅ 是 | ✅ 是 | ✅ 是 | — |

**风险：🟠 P1 - DEL-001**
- **问题**：删除采购订单/申请时，未检查是否已生成下游单据（如订单已生成入库单、申请已生成订单）。
- **资损影响**：已收货订单被删除后，财务已付款但无订单记录，审计无法闭环；已转订单的申请被删除，预算执行与订单来源无法追溯。
- **修复建议**：删除前查询下游关联表，存在则禁止删除并提示关联单据号。

**风险：🟠 P1 - DEL-002**
- **问题**：所有状态字段可被前端任意传入，无状态机；订单/申请编辑接口未强制重置为草稿。
- **资损影响**：用户可能将已确认订单改回草稿，绕过已审批金额，重新编辑后产生与原订单不一致的财务数据；入库单编辑后强制变草稿，但库存已增加，状态与库存不一致。
- **修复建议**：定义每个模块的合法状态流转图；所有状态变更通过专门接口；Service 层统一校验；编辑接口强制 `status = "1"`（草稿）。

**风险：🟠 P1 - DEL-003**
- **问题**：复活已删除记录（`resurrect`）复用旧 ID。
- **资损影响**：已删除的单据复活后，旧审批记录、操作日志可能指向新数据，导致审计轨迹混乱。
- **修复建议**：复活时重新生成 ID 或废弃复活逻辑；保留原删除记录。

## 四、跨模块对账闭环缺陷

### 4.1 申请 → 订单：无引用关系，预算控制缺失

- 采购订单没有记录来源申请行，无法校验「已转订单数量 ≤ 申请数量」。
- 同一张申请可多次转订单，预算超支风险极高。
- **风险等级：🔴 P0**
- **修复建议**：订单行增加 `sourceApplyId` / `sourceApplyItemId`，保存时回写申请行的 `orderedQty`；超过申请数量时拒绝。

### 4.2 订单 → 入库：超量与供应商一致性校验缺失

- 入库单已校验订单状态和累计数量，但并发和物料存在性校验缺失。
- 供应商不一致会导致应付账款归属错误，财务对账困难。
- **风险等级：🔴 P0**
- **修复建议**：订单行增加 `arrivedQty` 字段并原子更新；入库时校验供应商一致性；使用数据库锁或乐观锁控制并发。

### 4.3 入库 → 库存：完全脱节，账实不符

- 入库单保存后库存不更新，库存台账无记录。
- 这会导致：存货账实不符、成本核算错误、盘点差异无法解释。
- **风险等级：🔴 P0**
- **修复建议**：入库审核后，在事务中更新 `c_mes_inventory` 并写入 `c_mes_inventory_ledger`。

## 七、审计结论

从资损对账专项视角看，当前 JeecgBoot MES 采购管理模块存在以下关键问题：

1. **🔴 申请金额归零**：采购申请金额永远为 0，预算控制完全失效，无法与订单金额进行对账。
2. **🔴 税额计算精度与税率校验不足**：汇总后四舍五入可能导致与发票对账差 1 分钱；税率未校验范围，异常税率可导致税额暴涨或负数。
3. **🔴 入库超量与物料一致性校验不完整**：入库物料若不在订单行中，超量校验会跳过；并发场景下也可能出现超量入库，导致多付货款、库存虚增。
4. **🔴 供应商一致性未校验**：入库单供应商可手工选择，与采购订单供应商不一致，导致应付账款归属错误。
5. **🔴 入库与库存完全脱节**：入库单保存后库存不更新、台账无记录，账实不符风险极高，直接影响财务核算和审计。
6. **🟠 删除/反审核后一致性不足**：删除未校验下游单据，状态字段可被任意篡改，复活复用旧 ID 可能导致审计轨迹混乱。
7. **🟠 跨模块引用缺失**：申请、订单、入库、库存之间没有形成闭环，无法做到预算控制、执行跟踪、账实一致。

建议优先修复 P0 级问题，尤其是**申请金额计算、税率校验、税额计算精度、入库物料存在性、供应商一致性、库存联动、订单已入库数量原子控制**。否则模块上线后将面临真实的财务损失、库存账实不符和合规审计失败风险。
