## 二、总体风险定级

| 风险领域 | 当前等级 | 说明 |
|----------|----------|------|
| 事务一致性 | ⚠️ 中 | 写操作均开启 `@Transactional`，但默认隔离级别下存在竞态 |
| 数据竞态 / 状态机并发 | 🔴 高 | 状态判断为"读-校验-写"模式，无悲观锁或乐观锁，存在 TOCTOU |
| 库存累计/扣减原子性 | 🔴 高 | 当前无库存更新实现，且已有销售出库未联动扣减库存，超卖风险被掩盖 |
| 幂等设计 | 🟡 中 | 编码唯一约束 + 软删除复活存在竞态；无请求级幂等令牌 |
| 分布式锁 | 🔴 高 | 业务代码未使用 Redisson/JLock，集群部署下 JVM 级同步无效 |
| 数据库锁 / 乐观锁 | 🔴 高 | 未使用 `@Version`、`FOR UPDATE`、唯一索引复合条件等 |
| 读写一致性与幻读 | 🟡 中 | MySQL 默认 RR 可防止部分幻读，但业务校验逻辑未加锁 |

## 三、逐项审计发现

### 3.1 采购申请模块（MesPurchaseApplyServiceImpl）

#### 3.1.1 保存/更新：重复单号校验存在 TOCTOU 竞态

```java
QueryWrapper<MesPurchaseApply> activeQw = new QueryWrapper<>();
activeQw.eq("code", entity.getCode());
if (baseMapper.selectCount(activeQw) > 0) throw new JeecgBootException("申请单号已存在");
try { super.save(entity); } catch (DuplicateKeyException e) { ... }
```

- **问题：** 先 `selectCount` 后 `insert` 不是原子操作。在并发下两个请求同时通过校验，会同时进入 `save`。
- **缓解：** 已存在唯一索引 `uk_apply_code_del(code, del_flag)`，可能触发 `DuplicateKeyException` 兜底。
- **风险：** 但数据库表结构是 `(code, del_flag)` 联合唯一。当 `del_flag=0` 时，重复 code 仍会被唯一索引拦截；但软删除复活路径 `selectDeletedByCode` + `resurrect` 在并发时可能多条线程同时找到 `del_flag=1` 的旧记录并同时更新，存在覆盖写和明细行重复插入。
- **建议：** 单号生成统一收口为带锁/原子的编码生成器；保存方法对 code 加分布式锁；或利用唯一索引直接插入后捕获异常，避免先查后插。

#### 3.1.2 批量删除：先读后删，状态校验非原子

```java
List<MesPurchaseApply> existing = baseMapper.selectBatchIds(...);
for (...) if (!"1".equals(e.getStatus())) throw ...;
```

- **问题：** 在 `selectBatchIds` 之后、`removeByIds` 之前，其他事务可能修改状态。
- **建议：** 使用数据库状态条件删除（如 `UPDATE ... WHERE status='1' AND id IN (...)`），返回影响行数判断。

#### 3.1.3 状态机保护：无锁、无版本号

- 申请状态为 `1=草稿/2=已提交/3=已通过/4=已驳回`。当前只做了"非草稿禁止编辑/删除"。
- 无 Flowable 工作流，但即使是简单状态机，并发提交/审批也可能出现状态覆盖。
- 建议：状态转换使用数据库条件更新，如 `UPDATE ... SET status='2' WHERE status='1'`。

### 3.2 采购订单模块（MesPurchaseOrderServiceImpl）

与采购申请几乎完全相同的模式，重复风险同样存在：

#### 3.2.1 重复订单号竞态

- 同 3.1.1，唯一索引 `uk_po_code_del(code, del_flag)` 仅在未删除记录上有效，软删除复活路径存在并发覆盖。

#### 3.2.2 金额重算在并发下是否安全？

```java
private void calcTotal(MesPurchaseOrder entity) {
    BigDecimal total = BigDecimal.ZERO;
    ...
    entity.setTotalAmount(total.setScale(2, RoundingMode.HALF_UP));
}
```

- 计算在本地 JVM 完成，无并发问题。但如果其他事务同时修改订单行，读取到的行数据可能不是最新（RR 快照读）。

#### 3.2.3 订单状态未与入库单联动

- 设计文档要求订单状态从 `已确认(3) → 部分到货(4) → 已到货(5)` 自动流转。
- 当前代码中订单状态字段存在，但没有任何服务方法更新订单的 `arrived_qty` 或 `status`。
- 入库单 `MesPurchaseReceiptServiceImpl.validateReceipt` 中只校验订单当前状态是否允许入库，但**不更新订单状态**。
- 风险：多个入库单并发对一个订单收货时，订单状态仍为"已确认"，无法自动触发关闭或阻止超量。

---

### 3.3 采购入库/收货模块（MesPurchaseReceiptServiceImpl）

#### 3.3.1 历史累计入库量校验存在严重竞态

```java
// 1. 查本订单所有历史入库单
List<MesPurchaseReceipt> existingReceipts = baseMapper.selectList(rqw);
// 2. 查这些入库单的历史入库行
List<MesPurchaseReceiptItem> historyItems = itemMapper.selectList(hiqw);
// 3. 内存累加 historyQty
// 4. 校验 historyQty + currentQty <= orderQty
```

- **问题：** 两次查询 + 内存累加 不是原子的。在并发下：
  - 事务 A 和 B 同时读取到相同历史入库量，都认为剩余可入数量足够；
  - 两者同时提交，导致实际累计入库量超过采购数量。
- **风险：** 这是典型的**丢失更新**（Lost Update）场景，在不加锁的情况下必然可复现。
- **严重程度：** 🔴 高
- **建议方案：**
  1. 在订单行表增加 `arrived_qty` 已到货数量，入库时使用 SQL 原子更新：`UPDATE c_mes_purchase_order_item SET arrived_qty = arrived_qty + ? WHERE id=? AND arrived_qty + ? <= quantity`；影响行数为 0 则抛异常。
  2. 或者在 `validateReceipt` 之前对订单 ID 加 Redisson 分布式锁（`JLock`/`RedissonLockClient`），串行化同一订单的入库。
  3. 或者使用 `SELECT ... FOR UPDATE` 对订单行加锁，但需注意事务范围，并保证所有状态读取也走锁。

#### 3.3.2 入库状态机未实现"审核后入库"

- 设计文档要求入库单 `草稿 → 已审核`，审核后触发库存更新。
- 当前代码中，入库保存即认为入库完成，没有独立的"审核/确认"动作。
- 风险：草稿状态的入库单已经参与历史累计量计算（所有记录都参与），但逻辑上草稿不应影响库存。更危险的是，如果将来实现"撤销审核"，库存回退需要可靠。

#### 3.3.3 缺少库存更新代码

- 当前 `MesPurchaseReceiptServiceImpl` 未调用任何库存服务。
- 库存表 `c_mes_inventory` 和台账 `c_mes_inventory_ledger` 仅由数据库脚本创建，后端未实现更新逻辑。
- 这导致即使入库完成，也不会扣减/增加库存。对于并发安全审计而言，该模块的**库存原子操作目前不存在**，属于功能缺失同时引发安全风险。

---

### 3.4 库存台账模块（MesInventoryLedgerServiceImpl）

- 当前 `MesInventoryLedgerServiceImpl` 仅继承 `ServiceImpl`，无任何业务方法。
- 未实现：
  - 按 `warehouse_id + material_id` 更新库存快照 `c_mes_inventory`；
  - 写入库存台账 `c_mes_inventory_ledger`；
  - 库存扣减/累计时的并发控制（`INSERT ... ON DUPLICATE KEY UPDATE`、`UPDATE ... WHERE current_qty >= ?`、`FOR UPDATE`、分布式锁等）。
- 从表结构看，库存快照已有 `uk_inv_material_wh`，适合用 `INSERT ... ON DUPLICATE KEY UPDATE current_qty = current_qty + ?` 实现原子累计。
- 但缺少 `version` 或 `update_time` 等字段配合乐观锁，后续应补充 `@Version` 字段并启用 MP 乐观锁拦截器（**已全局启用**，见 3.6）。

---

### 3.5 销售出库模块（MesSalesOutboundServiceImpl）

- 销售出库与销售发货单做数量校验，但同样**未扣减库存**。
- 当前代码 `audit` 只改状态，没有任何库存联动。
- 从设计文档看，计划"销售出库审核后扣减库存台账"，但未实现。
- 并发风险：如果库存扣减未来实现，将面对和采购入库同样的"先读后写"问题，需要提前设计。

---

### 3.6 框架级并发控制机制

#### 3.6.1 MyBatis-Plus 乐观锁已全局启用，但业务表未使用

- `MybatisPlusSaasConfig` 中注入了 `OptimisticLockerInnerInterceptor`。
- 但采购申请、采购订单、采购入库、库存快照等实体类均未声明 `@Version` 字段。
- 这导致全局乐观锁配置形同虚设，无法防止更新丢失。
- **建议：** 在需要并发控制的主表/库存表增加 `version` 字段并加 `@Version` 注解；状态转换使用条件更新 + 乐观锁组合。

#### 3.6.2 分布式锁 starter 存在但未被采购模块引入和使用

- `jeecg-boot-starter-lock`（Redisson）已在父 pom 定义，但仅在 `jeecg-cloud-test-more` 模块中引入，作为测试 Demo 使用。
- `project-mes` 模块的 `pom.xml` 未引入该 starter，且业务代码中未使用 `RedissonLockClient` 或 `@JLock`。
- 如果未来部署为多实例（Spring Cloud 模式），当前的所有"先读后写"校验都会失效。
- **建议：** 在 `project-mes` 引入 `jeecg-boot-starter-lock` 或至少基于 `RedisTemplate` 实现可重入分布式锁；在入库单保存、库存更新等关键路径加锁。

#### 3.6.3 事务注解使用现状

- 所有写方法都使用了 `@Transactional(rollbackFor = Exception.class)`，默认 Spring 事务隔离级别为 `DEFAULT`（继承数据库默认，MySQL InnoDB 为 `REPEATABLE READ`）。
- 默认 RR 下，快照读能防止不可重复读，但业务代码中 `selectCount` 均为快照读，不加锁，不能阻止并发写入。
- 如果要让查询具备排他性，需要显式使用 `SELECT ... FOR UPDATE` 或 `@Transactional` + 锁注解。

#### 3.6.4 数据库唯一索引存在但不够

- 采购申请、订单、入库单都有 `(code, del_flag)` 联合唯一索引，可阻止重复 code 创建。
- 但状态条件、累计数量、库存余额等关键约束无法通过唯一索引表达，需要应用层/存储层加锁。

## 四、关键风险场景复现（攻击面）

### 场景 1：并发入库超量（Confirmed）

**前提：** 采购订单 A 物料 M 采购数量 100，当前已入库 0。  
**并发请求：** 两个用户同时提交入库单，各入 80。  
**结果：** 两事务同时读取历史入库量 0，校验 `0 + 80 <= 100` 通过，均保存成功。最终实际入库 160 > 100。

### 场景 2：重复采购订单号（Confirmed）

**前提：** 单号生成逻辑在前端或后端未加锁。  
**并发请求：** 两个用户同时提交相同 `code` 的订单。  
**结果：** 同时命中软删除复活路径，覆盖同一旧记录，明细行被重复插入或被其中一个请求覆盖。

### 场景 3：库存扣减未来超卖（Predicted）

**前提：** 当前无库存扣减，但销售出库审核后若实现 `current_qty -= actualQty` 为"查-算-写"模式。  
**并发请求：** 库存 100，两个出库单各出 80。  
**结果：** 两事务都读取到 100，都扣减成功，库存变为 -60。

## 五、修复建议与优先级

### 5.1 P0（必须立即修复）

1. **采购入库累计量原子化**
   - 在 `c_mes_purchase_order_item` 增加 `arrived_qty` 字段。
   - 入库保存时，使用 SQL 原子更新：`UPDATE c_mes_purchase_order_item SET arrived_qty = arrived_qty + ? WHERE id = ? AND arrived_qty + ? <= quantity`。
   - 校验失败返回"累计入库量超过采购数量"。
2. **采购入库联动库存**
   - 在 `MesPurchaseReceiptServiceImpl` 增加库存服务注入，保存/审核后原子更新 `c_mes_inventory` 和 `c_mes_inventory_ledger`。
   - 使用 `INSERT ... ON DUPLICATE KEY UPDATE current_qty = current_qty + ?` 或 `UPDATE ... WHERE` 条件更新。
3. **销售出库联动库存扣减**
   - 同采购入库，实现出库审核后原子扣减库存，并防止负库存。
4. **为关键实体增加乐观锁字段**
   - 采购订单、采购入库、库存快照增加 `version` 字段并加 `@Version` 注解；状态转换使用 `UPDATE ... SET status=next, version=version+1 WHERE status=cur AND version=old`。

### 5.2 P1（尽快修复）

5. **单号重复竞态**
   - 保存前对 `code` 加分布式锁（Redisson key 如 `mes:purchase:order:lock:code:{code}`），锁超时 5-10 秒。
   - 或者使用数据库唯一索引 + 直接插入捕获异常，避免先查后插。
6. **批量删除状态条件原子化**
   - 使用 `UPDATE ... SET del_flag=1 WHERE status='1' AND id IN (...)` 并返回影响行数；未影响行数说明有非草稿状态。
7. **状态机转换使用数据库条件更新**
   - 例如提交/审批/驳回全部改为 `UPDATE ... SET status=next WHERE status=cur AND id=?`；影响行数为 0 则抛"状态已变更"。

### 5.3 P2（架构完善）

8. **引入 `jeecg-boot-starter-lock` 到 `project-mes` 模块**
   - 统一封装 `MesLockService`，提供 `lockByOrderId`、`lockByInventoryKey` 等语义化锁。
   - 关键路径：入库单创建、库存更新、订单状态转换、销售出库审核。
9. **请求级幂等**
   - 对保存/审核类接口增加 `idempotent_key` 或 `client_token` 参数，结合 Redis `SET NX` 做 5-15 分钟幂等窗口，防止网络重试导致重复提交。
10. **库存更新使用 MySQL 原子操作而非 Java 计算**
    - 禁止在 Java 中先 `select` 库存再 `set` 新值；所有库存变化通过数据库表达式完成。

## 六、最佳实践建议（可纳入研发规范）

| 实践 | 说明 |
|------|------|
| 状态机写操作必须带条件 | 任何状态变更使用 `WHERE status=current` |
| 资源累计/扣减必须原子 | 使用 `UPDATE ... SET qty = qty + delta` 或 `ON DUPLICATE KEY UPDATE` |
| 关键业务锁必须分布式 | 多实例下用 Redisson；单实例用数据库锁或乐观锁兜底 |
| 乐观锁全局启用 | 实体表增加 `@Version` 字段 |
| 单号/编码生成加锁 | 集中式编码生成服务，避免重复 |
| 接口幂等 | 增/改/审核类接口支持幂等键 |

---

## 七、结论

当前 MES 采购管理模块在并发安全方面存在**结构性缺陷**：

- 核心写链路采用"先读后写"模式，缺少悲观锁、乐观锁和分布式锁；
- 入库累计量校验、库存更新等关键业务逻辑存在可复现的竞态条件；
- 库存台账/库存快照目前仅停留在表结构，没有业务实现，导致采购入库和销售出库无法真正影响库存；
- 框架级虽然启用了乐观锁拦截器，但业务实体未使用 `@Version`；分布式锁 starter 存在但未被采购模块引入。

建议按 P0 → P1 → P2 优先级分批修复，优先保证**入库不超量**和**库存原子更新**，并尽快在 `project-mes` 中引入分布式锁能力，为后续微服务部署打好基础。
