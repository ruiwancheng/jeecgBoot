## 一、架构分层与模块边界

### 1.1 分层结构

| 分层 | 实现 | 评价 |
|------|------|------|
| 表现层（前端） | Vue3 + Vite + Ant Design Vue | 符合 JeecgBoot Vue3 技术栈；统一使用 `useListPage` / `BasicTable` / `BasicDrawer` 标准模式 |
| 接入层（Controller） | `org.jeecg.modules.mes.purchase.*.controller` | 均继承 `JeecgController`，统一返回 `Result<T>`；使用 `@RequiresPermissions` 权限注解 |
| 业务层（Service） | `IService` + `ServiceImpl` | 使用 MyBatis-Plus 标准 Service 模式；核心逻辑集中在 ServiceImpl |
| 数据层（Mapper/Entity） | `BaseMapper` + `@TableName` Entity | 无 XML，SQL 全部在 Mapper 接口或 Service 中 |
| 基础数据层 | `c_mes_supplier` / `c_mes_material` / `c_mes_warehouse` | 位于 `mes/basic` 基础模块，通过 ID 引用耦合 |

### 1.2 模块边界

- `project-mes` 作为独立 Maven 子模块，已注册在 `jeecg-boot-module/pom.xml` 中，边界清晰。
- 采购模块内部按子域划分 `apply` / `order` / `receipt` / `ledger` 四个包，子模块间通过 Service 直接调用（如 `receipt` 注入 `purchaseOrderMapper`），属于**同进程紧耦合**，但仍在单体架构预期范围内。
- 库存台账（`ledger`）物理路径位于 `purchase/ledger`，但菜单挂在“仓储管理”下，存在**领域归属与目录结构不一致**的架构负债。

## 二、接口契约与 API 规范

### 2.1 接口契约一致性问题

| 问题 | 风险等级 | 说明 |
|------|----------|------|
| 全模块使用同一套 CRUD 模式，但缺少 `queryById` 的 REST 资源路径规范 | P2 | 建议统一为 `/mes/purchase/{domain}/{id}` 或 `/queryById`，当前 `/queryById` 与 `list` 并列，不是最佳实践但可接受 |
| 入库状态字段不一致 | **P0** | 后端 `MesPurchaseReceipt.status` 使用字典 `mes_purchase_receipt_status`，但前端 `receipt.data.ts` 中 status 默认字典仍写死为 `yn`（`dictCode: 'yn'`）。前后端契约不一致会导致状态回显/默认值错误 |
| 导出接口 `exportXls` 使用 `GET` + `ModelAndView`，符合 JeecgBoot 传统模式 | 无风险 | 已复用 `JeecgController.exportXls` |
| 批量删除 `deleteBatch` 使用 `/deleteBatch` 路径，方法为 `DELETE` 且参数为逗号分隔字符串 | P2 | 语义上宜用 `/batch` 或 `POST /deleteBatch`，当前实现可工作但不够 RESTful |

### 2.2 Swagger/OpenAPI 注解

- 全部 Controller 使用 `@Tag` 和 `@Operation`，符合规范。
- 接口实体使用 `@Schema` 描述字段，Excel 使用 `@Excel` 注解，符合 JeecgBoot 的代码生成/导出标准。

## 三、服务边界与耦合

### 3.1 跨子模块直接调用

- `MesPurchaseReceiptServiceImpl` 直接注入 `MesPurchaseOrderMapper` / `MesPurchaseOrderItemMapper`，在**单体应用**内可接受，但存在以下问题：
  1. 跨子模块调用绕过了 `IMesPurchaseOrderService`，破坏了 Service 接口边界。
  2. 采购订单与入库之间的业务规则校验（状态、数量）被硬编码在 Receipt Service 中，订单模块自身无法复用该逻辑。
  3. 未来拆分为独立微服务时，该耦合会转化为 Feign 网络调用，改造成本高。

**修复建议（P1）**：在 `order` 子模块定义一个内部可暴露的 `IPurchaseOrderBizService`（或把状态/数量查询能力抽到 `order` 的 Service 接口），`receipt` 通过 Service 接口而非 Mapper 访问。

### 3.2 库存台账与入库动作脱节

- `c_mes_inventory_ledger` 和 `c_mes_inventory` 是两张独立表，但代码中没有：
  - 入库后自动生成台账记录的机制。
  - 库存快照（`c_mes_inventory`）的更新逻辑。
  - 事务一致性保证（库存快照与台账必须同步）。

**风险**：库存台账模块只是“台账查询”，没有“入库驱动台账/库存变更”的闭环，属于**架构能力缺失**。

**修复建议（P0）**：
1. 在 `MesPurchaseReceiptServiceImpl` 中增加“入库确认”动作（或独立 `InventoryService`），在事务内同步：
   - 更新/新增 `c_mes_inventory` 当前库存。
   - 写入 `c_mes_inventory_ledger` 本期入库记录。
   - 更新采购订单到货状态（`1→2→3→4→5`）。
2. 提供幂等键（bizId + bizType）防止重复记账。

## 四、代码复用与重复模式

### 4.1 重复代码严重

- `MesPurchaseApplyServiceImpl`、`MesPurchaseOrderServiceImpl`、`MesPurchaseReceiptServiceImpl` 三个 Service 中以下代码几乎完全相同：
  - `saveWithItems` / `updateWithItems` / `removeWithItems` 的框架结构
  - `calcTotal` 相关金额汇总（虽然申请是空实现）
  - 编码唯一性校验（`selectDeletedByCode` + `resurrect`）
  - 明细行保存与删除
  - `getCurrentUsername` 工具方法
  - 批量删除 `removeByIds` 模板

- 三个 Controller 的 `queryPageList` / `queryById` / `add` / `edit` / `delete` / `deleteBatch` / `queryAll` / `exportXls` 结构完全一致。

### 4.2 复用建议（P1）

- 抽象一个 `AbstractHeadTailService<Head, Tail>` 或 `JeecgHeadTailServiceImpl`，把“主表+明细表”的通用增删改查、编码唯一校验、批量删除、状态校验模板化。
- 子类仅实现 `validateHead`、`validateTail`、`calculateTotal` 等钩子。
- 这能显著降低后续维护成本，并减少因复制粘贴导致的 bug（如申请/订单/入库三个模块的 `removeByIds` 已分别实现，但逻辑几乎相同）。

## 五、命名规范

### 5.1 总体合规

| 项目 | 状态 | 说明 |
|------|------|------|
| Java 包名 | 合规 | `org.jeecg.modules.mes.purchase.{domain}.{layer}` |
| 类名 | 合规 | `MesPurchaseApply` / `MesPurchaseApplyController` 等 |
| 表名 | 基本合规 | 统一 `c_mes_` 前缀；但 `c_mes_inventory_ledger` 与 `c_mes_inventory` 命名不够对称 |
| 字段名 | 基本合规 | 使用下划线命名（如 `purchase_order_id`），Entity 中使用驼峰（`purchaseOrderId`） |
| 权限码 | 不一致 | 订单使用 `mes:purchaseOrder:list`，申请使用 `mes:purchaseApply:list`，混合使用驼峰与驼峰+小写；建议统一为 `mes:purchase:{apply/order/receipt}:{action}` 或 `mes:purchase_apply:{action}` |

### 5.2 命名问题（P2）

- `c_mes_inventory` 表注释为“库存快照”，但表名仅 `inventory`，建议改为 `c_mes_inventory_snapshot` 或 `c_mes_inventory_balance`，以区别于台账表。
- `c_mes_inventory_ledger` 的 `biz_type` 字段注释为“业务类型”，但值域包含“采购入库/销售出库/生产领料/完工入库”，说明未来会跨模块写数据，命名上应更通用，字段本身没问题。

## 六、主外键与数据库设计

### 6.1 外键约束缺失（P1）

所有子表（`apply_item`、`order_item`、`receipt_item`、`inventory_ledger`）均只有普通索引，**没有显式外键约束**（FOREIGN KEY）。在 JeecgBoot 中常见做法是逻辑外键，但采购业务链较长：

- 采购申请 → 采购订单（无关联字段，业务上脱节）
- 采购订单 → 采购入库行（`purchase_order_id` 逻辑关联）
- 采购入库 → 库存台账（无关联）
- 采购入库行 → 采购订单行（无 `order_item_id` 关联，仅通过 material_id 匹配）

### 6.2 数据完整性风险

| 问题 | 等级 | 说明 |
|------|------|------|
| 采购申请与订单无关联 | P1 | 无法追踪“哪些申请已转订单”；无法做申请-订单数量核销 |
| 采购入库行缺少 `order_item_id` | P1 | 当前通过 `material_id` 汇总，但若订单同一物料有多行，无法精确匹配 |
| 库存台账没有与入库单外键 | P2 | `biz_id` 是通用字段，但缺少索引 `idx_ledger_biz_id`；大数据量下按业务单号查询会慢 |
| 删除主表后明细行残留 | 已修复 | 通过 `removeWithItems` 和 `removeByIds` 手动删除，但依赖应用层，数据库层无级联 |

### 6.3 建议修复

1. 采购订单表增加 `apply_id` 或独立“申请转订单”中间表，建立申请→订单业务链路。
2. 采购入库行增加 `order_item_id`（可为空，允许无订单入库）。
3. 库存台账增加 `idx_ledger_biz_id` 索引，并补充 `biz_id` + `biz_type` 联合索引。
4. 若业务需要强一致性，建议对关键表加显式外键（权衡性能与数据完整性）。

## 七、状态机与业务闭环

### 7.1 状态机不完整

| 单据 | 状态 | 问题 |
|------|------|------|
| 采购申请 | 草稿→已提交→已通过→已驳回 | 缺少“已转订单”终态，无法关闭已完全转订单的申请 |
| 采购订单 | 草稿→待确认→已确认→部分到货→已到货→已关闭 | 状态机较完整，但代码中没有任何地方更新订单到货状态 |
| 采购入库 | 草稿→已入库 | 入库状态只有两级；入库动作发生后不会反向更新订单状态 |

### 7.2 业务闭环缺失（P0）

当前三个单据是“并行的录入单据”，而不是“拉通的业务流程”：
- 申请可以独立存在。
- 订单可以独立存在。
- 入库可以关联订单，但关联后订单状态不会自动变化。
- 库存不会自动变化。

这意味着“采购管理”模块只是实现了单据 CRUD，没有实现真正的采购-入库-库存业务闭环。需要在架构层设计一个 `PurchaseBizFlowService` 或事件驱动机制来串联状态流转。

## 八、权限与菜单

### 8.1 菜单注册

- 前端路由 `mes.ts` 已定义采购管理子菜单，且后端 `MesMenuRegistry` 也注册了菜单和权限码，二者一致。
- 但 `MesMenuRegistry` 只负责定义，**数据库初始化还需要 Flyway 或 SQL 执行**。V6.0.* 脚本的注释说“菜单和权限码由 MesMenuRegistry Java Runner 注册”，未在审计范围内看到具体 Runner 实现，需确认是否有启动类调用 `MesMenuRegistry.getMenus()` 写入数据库。

### 8.2 权限码一致性

- 后端 Controller 权限：`mes:purchaseApply:list`、`mes:purchaseOrder:list`、`mes:purchaseReceipt:list`
- 前端没有显式在 Vue 中写权限码，依赖后端菜单返回，风险可控。

## 九、前端架构

### 9.1 组件复用

- 三个 Drawer（`ApplyDrawer.vue`、`OrderDrawer.vue`、`ReceiptDrawer.vue`）结构高度相似，但均为独立文件，重复代码较多。
- 行内编辑表格使用 `a-table` + `slots` 实现，未复用 `JVxeTable` 或 `BasicTable` 的编辑能力，维护成本较高。

### 9.2 建议（P2）

- 抽象一个通用的 `HeadTailDrawer` 组件，通过 `props` 传入表单 schema、行 columns、API 即可生成三个页面。
- 或采用 `JVxeTable` 进行行内编辑，更符合 JeecgBoot 低代码组件生态。

### 9.3 数据字典不一致

- 入库状态后端字典：`mes_purchase_receipt_status`
- 前端 `receipt.data.ts` 中 status 默认字典：`yn`
- 这是 **P0 级** 前后端契约不一致，会导致新增入库时默认状态错误、编辑回显异常。

## 十、风险与修复建议汇总

### P0 风险（必须立即修复）

| 编号 | 问题 | 影响 | 修复建议 |
|------|------|------|----------|
| P0-001 | 采购入库模块状态前后端不一致：后端用 `mes_purchase_receipt_status`，前端用 `yn` | 新增/编辑入库单状态回显与默认值错误 | 前端 `receipt.data.ts` 中 `status` 字段的 `dictCode` 改为 `mes_purchase_receipt_status`，并确保 `defaultValue` 为 `'1'` |
| P0-002 | 采购入库与库存台账无闭环：入库后未更新库存快照和台账 | 库存台账数据永远为空或滞后，业务不可用 | 在入库保存/确认时，事务内调用 `InventoryService` 更新 `c_mes_inventory` 并写入 `c_mes_inventory_ledger` |
| P0-003 | 采购订单状态机未触发：入库后订单状态不会从“已确认”→“部分到货”→“已到货” | 订单状态永远是草稿或已确认，无法反映履约进度 | 在入库确认时，根据累计入库量更新订单状态 |

### P1 风险（高优先级修复）

| 编号 | 问题 | 影响 | 修复建议 |
|------|------|------|----------|
| P1-001 | 跨子模块直接注入 Mapper（receipt 注入 order Mapper） | 破坏服务边界，未来微服务拆分成本高 | 定义 `IMesPurchaseOrderBizService` 或 `IPurchaseOrderQueryService` 暴露订单状态/数量查询能力，receipt 通过 Service 调用 |
| P1-002 | 三个 Service/Controller 重复代码严重 | 维护成本高，复制粘贴容易引入 bug | 抽象 `AbstractHeadTailService` 和通用 Drawer/Index 模板 |
| P1-003 | 外键约束缺失，主表删除依赖应用层 | 数据库层无法保证引用完整性，极端情况出现孤儿数据 | 关键子表增加显式外键或至少增加触发器/定时检查任务；或依赖代码中 `removeWithItems` 但必须补充集成测试 |
| P1-004 | 采购申请→采购订单→采购入库无业务关联字段 | 无法做申请转订单、订单履约跟踪 | 订单表增加 `apply_id`，入库行增加 `order_item_id` |
| P1-005 | 库存台账缺少 `biz_id` 索引 | 未来按业务单号查询慢 | 增加 `idx_ledger_biz_id` 及 `(biz_type, biz_id)` 联合索引 |

### P2 风险（建议改进）

| 编号 | 问题 | 影响 | 修复建议 |
|------|------|------|----------|
| P2-001 | 库存台账物理路径在 `purchase/ledger`，但菜单属于“仓储管理” | 领域归属混乱，新开发者难以定位 | 将 `ledger` 目录迁移到 `views/project/mes/warehouse/ledger` |
| P2-002 | 权限码命名风格不一致 | 可读性差 | 统一为 `mes:purchase:order:list` 或 `mes:purchase_order:list` 等单一风格 |
| P2-003 | REST 路径不够规范（如 `deleteBatch` 使用 `DELETE` + 逗号字符串） | 不是严重问题，但可改进 | 批量删除改为 `POST /batch-delete` 或 `DELETE /{ids}` |
| P2-004 | 前端行内编辑未复用 `JVxeTable` | 维护成本高 | 逐步统一为 `JVxeTable` 或通用 Drawer 组件 |
| P2-005 | `c_mes_inventory` 表名/注释不够清晰 | 易与台账混淆 | 建议改为 `c_mes_inventory_balance` 或 `c_mes_inventory_stock` |

## 十二、结论

JeecgBoot MES 采购管理模块在**分层结构、Controller/Service/Mapper 划分、命名规范、权限注解、Swagger 文档**等方面基本符合 JeecgBoot 架构规范。但存在以下核心架构问题：

1. **业务闭环未打通**：采购申请、订单、入库、库存台账是四张独立单据，没有状态机联动和库存更新机制。
2. **前后端契约不一致**：入库状态字典前端使用 `yn`，后端使用 `mes_purchase_receipt_status`，属于 P0 级缺陷。
3. **服务边界与代码复用**：跨子模块直接注入 Mapper、Service/Controller/Drawer 复制粘贴严重，未来维护成本高。
4. **数据库设计**：外键约束缺失、关键业务索引不足、缺少申请-订单-入库的关联字段。
