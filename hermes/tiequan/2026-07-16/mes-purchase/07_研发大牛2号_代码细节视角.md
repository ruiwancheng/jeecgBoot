## 3. 问题清单

### 3.1 高风险问题

#### H01 批量删除存在未覆盖删除校验状态越权的隐藏路径（中高风险）

- **位置**：`MesPurchaseApplyController.java:76`、`MesPurchaseOrderController.java:76`、`MesPurchaseReceiptController.java:76`
- **代码**：

```java
@DeleteMapping("/deleteBatch")
public Result<String> deleteBatch(@RequestParam String ids) {
    ...
    service.removeByIds(idList); // 调用的是 Service 的批量删除
    return Result.ok("批量删除成功");
}
```

- **问题**：Controller 的 `deleteBatch` 调用的是 `ServiceImpl.removeByIds(Collection<?>)`，但各 Service 接口未显式声明 `removeByIds` 覆盖；实际会调用 `MesPurchaseApplyServiceImpl.removeByIds` 等重载方法（虽然源码存在同名方法），但**接口与实现之间签名不一致**，`IService` 默认签名是 `boolean removeByIds(Collection<? extends Serializable> list)`，实现为 `boolean removeByIds(java.util.Collection<?> list)`，类型擦除后虽然可编译，但属于**方法重载而非重写**，存在未来版本 MyBatis-Plus 升级时行为变更或绕过状态校验的风险。
- **建议**：在 `IMesPurchaseApplyService` 等接口中显式声明 `boolean removeByIds(Collection<String> list)`，并标注 `@Override`，确保实现类真正重写。
- **风险等级**：高（状态越权 + 未来兼容性）

#### H02 前端抽屉组件缺少行级校验，可提交非法数据（中高风险）

- **位置**：`ApplyDrawer.vue`、`OrderDrawer.vue`、`ReceiptDrawer.vue`
- **问题**：
  - 所有 `itemColumns` 使用 `<a-table>` + slots 渲染行内编辑组件，但**未对行数据做任何校验**，例如物料 ID 为空、数量为 0 或负数、单价未填等情况可直接提交到后端；
  - `OrderDrawer.vue` 的金额列在前端计算，但**仅展示不写入**，导致金额字段未提交（依赖后端计算，虽然后端已重算，但用户填写体验与计算不一致）；
  - `ReceiptDrawer.vue` 的 `purchaseOrderId` 使用普通 `Input` 组件，既无字典下拉，也未按采购订单状态过滤，容易输入不存在或不可入库的订单号。
- **建议**：
  - 在 `handleSubmit` 中对 `items` 做非空、数量大于 0、物料已选等校验；
  - 将 `purchaseOrderId` 改为 `JSearchSelect` 或带查询条件的输入，至少校验订单存在性；
  - 金额列建议统一提交 `quantity`、`unitPrice`，展示列仅作为参考。
- **风险等级**：高（用户体验 + 数据质量）

### 3.2 中风险问题

#### M01 `@Transactional` 中抛出非受检异常，但存在方法内吞异常导致事务不生效

- **位置**：`MesPurchaseApplyServiceImpl.java:64`、`MesPurchaseOrderServiceImpl.java:65`、`MesPurchaseReceiptServiceImpl.java:70`
- **代码**：

```java
try { super.save(entity); } catch (DuplicateKeyException e) { throw new JeecgBootException("申请单号已存在"); }
```

- **问题**：仅捕获 `DuplicateKeyException`，其他 MyBatis / SQL 异常仍会抛出让事务回滚，符合要求；但 `JeecgBootException` 是 `RuntimeException`，`@Transactional(rollbackFor = Exception.class)` 能捕获。**问题在于**：`saveWithItems` 中先 `save(entity)`，再 `saveItems(entity)`，如果 `saveItems` 抛异常，主表记录已写入，事务会整体回滚，设计正确。但如果 `baseMapper.resurrect(entity)` 失败（如 `del_flag=1` 记录已被物理删除），后续 `saveItems` 会插入到旧 ID 但主表无数据，导致脏数据。
- **建议**：`resurrect` 后检查返回影响行数，0 行时抛异常，避免向无效主表 ID 插入明细。
- **风险等级**：中

#### M02 死灰复燃（resurrect）逻辑缺少乐观锁与影响行数检查

- **位置**：`MesPurchaseApplyMapper.java:13`、`MesPurchaseOrderMapper.java:13`、`MesPurchaseReceiptMapper.java:13`
- **代码**：

```java
@Update("UPDATE c_mes_purchase_apply SET ... del_flag=0 WHERE id=#{id} AND del_flag=1")
void resurrect(MesPurchaseApply entity);
```

- **问题**：`resurrect` 方法返回 `void`，即使更新行数为 0（例如 ID 对应的记录已物理删除或已被其他线程恢复），调用方也无感知，后续仍会基于该 ID 插入明细行，导致**明细行主表 ID 指向不存在的记录**。
- **建议**：返回 `int` 并在 Service 中判断 `> 0`。
- **风险等级**：中

#### M03 `removeByIds` 的强制类型转换在集合类型非 `String` 时运行期失败

- **位置**：`MesPurchaseApplyServiceImpl.java:102`、`MesPurchaseOrderServiceImpl.java:103`、`MesPurchaseReceiptServiceImpl.java:108`
- **代码**：

```java
List<MesPurchaseApply> existing = baseMapper.selectBatchIds((Collection<String>) (Collection<?>) list);
```

- **问题**：`removeByIds` 的形参是 `Collection<?>`， Controller 传入的是 `List<String>`，此处二次强制转换存在双重 unchecked cast，虽然当前可运行，但**任何非 String 的集合都会导致 ClassCastException**。如果未来 `deleteBatch` 被改为按 code 批量删除，此处将直接崩溃。
- **建议**：将接口与实现参数统一为 `Collection<String>`，并在 Controller 中显式转 `List<String>` 后传入。
- **风险等级**：中

#### M04 查询接口未做数据权限过滤（机构/租户）

- **位置**：所有 `queryPageList` / `queryAll` / `queryById` 方法
- **问题**：JeecgBoot 通常使用 `@PermissionData` 或 `QueryGenerator` 的 `SysUserSQL` 注入数据权限。当前 `QueryGenerator.initQueryWrapper` 未显式注入 `数据权限规则`，如果该模块未来部署在多租户或多机构环境下，可能产生横向越权。
- **建议**：确认是否需要启用 `org.jeecg.common.aspect.annotation.PermissionData` 或在 QueryWrapper 中追加 `sys_org_code` 等条件。如果当前业务场景为单租户可忽略，但需在代码注释中说明。
- **风险等级**：中（视部署环境而定）

#### M05 入库超量校验未考虑单位换算

- **位置**：`MesPurchaseReceiptServiceImpl.java:164-171`
- **代码**：

```java
BigDecimal orderQty = orderQtyMap.get(item.getMaterialId());
if (orderQty != null) {
    BigDecimal historyQty = historyQtyMap.getOrDefault(item.getMaterialId(), BigDecimal.ZERO);
    BigDecimal totalAfter = historyQty.add(item.getReceiptQuantity());
    if (totalAfter.compareTo(orderQty) > 0) { ... }
}
```

- **问题**：超量校验仅按 `materialId` 累加，**未考虑采购单位与入库单位是否一致**；如果订单单位是“箱”，入库单位是“个”，则 `totalAfter` 比较会失准。另外，如果订单行被拆分为多个入库单行，同一 `materialId` 在单次请求中多次出现，历史累加会正确，但本次请求内自身多次出现的数量不会累加（每个 `item` 单独与 orderQty + historyQty 比较），存在**同一请求内自身超量**的漏洞。
- **建议**：在循环前构建本次请求内同一 `materialId` 的累计数量，校验 `history + 本次累计 <= orderQty`。
- **风险等级**：中

### 3.3 低风险 / 建议项

#### L01 `update-begin/end` 标记存在但覆盖范围过大，缺少中间版本标注

- **位置**：所有 Java / Vue 文件
- **问题**：每个文件顶部到尾部都只有一对 `//update-begin...//update-end`，虽然成对闭合，但内部包含多个功能点（P0 修复、初始生成）。当后续继续修改时，无法快速定位本次改动边界。JeecgBoot 推荐的做法是为每一轮改动增加独立 `update-begin/end` 块。
- **建议**：在后续修复中，新增 `update-begin/end` 块包裹改动函数，而不是复用最初的大块。
- **风险等级**：低

#### L02 代码中多次出现 `catch (Exception e) { return "system"; }` 的静默吞异常

- **位置**：`MesPurchaseApplyServiceImpl.java:160-165`、`MesPurchaseOrderServiceImpl.java:179-184`、`MesPurchaseReceiptServiceImpl.java:213-218`
- **问题**：`getCurrentUsername()` 在无法获取登录用户时返回 `system`，这种吞异常在审计字段上 acceptable，但缺少日志，排查时无法追踪为何无法获取用户。
- **建议**：至少记录 `log.warn` 输出异常信息，便于排查 Shiro 上下文缺失问题。
- **风险等级**：低

#### L03 计算总价时未对 `entity.getItems()` 重新做 NPE 判断

- **位置**：`MesPurchaseApplyServiceImpl.java:134-136`、`MesPurchaseOrderServiceImpl.java:141-154`
- **问题**：`calcTotal` 在 `validateApply` 之后调用，此时 `items` 理论上非空，但 `calcTotal` 方法本身未做防御，存在独立被调用时 NPE 的隐患。
- **建议**：`calcTotal` 开头增加 `if (entity.getItems() == null) return;`。
- **风险等级**：低

#### L04 前端搜索表单缺少字典组件与数据列 `_dictText` 不一致

- **位置**：`receipt.data.ts:16-18`、`ledger.data.ts:15-18`
- **问题**：
  - `receipt.data.ts` 中 `purchaseOrderId` 和 `warehouseId` 搜索条件使用普通 `Input`，但列表中显示 `warehouseId_dictText`，搜索无法按真实字典过滤；
  - `ledger.data.ts` 中 `materialId`、`warehouseId` 搜索条件使用普通 `Input`，列表显示 `_dictText`，用户需输入 ID 而非名称，体验差。
- **建议**：搜索条件改为 `JSearchSelect` 或 `JDictSelectTag`，或者支持模糊匹配名称。
- **风险等级**：低

#### L05 库存台账为只读列表，但提供了导出权限，未提供查看权限细分

- **位置**：`MesInventoryLedgerController.java`
- **问题**：台账只读，无新增/编辑/删除，但 `exportXls` 与 `list` 共用 `mes:inventoryLedger:export` / `mes:inventoryLedger:list`。 JeecgBoot 常见做法为敏感库存数据增加 `view` 权限，但当前未拆分。
- **建议**：如安全要求严格，可拆分 `list` 与 `export` 的权限粒度，增加 `mes:inventoryLedger:view`。
- **风险等级**：低（建议）

## 4. 各维度详细检查结论

### 4.1 update-begin/end 标记

| 文件 | 标记成对 | 覆盖范围 | 评价 |
|------|----------|----------|------|
| 所有 Java 文件 | 是 | 文件级 | 闭合正确，但粒度偏大 |
| 所有 Vue / TS 文件 | 无 | - | 前端未使用 update 标记，需后续统一 |

**结论**：后端标记存在且成对，但缺少细粒度版本标识；前端未使用标记，建议后续统一风格。

### 4.2 空指针与防御式编码

| 位置 | 风险 | 说明 |
|------|------|------|
| `queryWithItems` 各实现 | 低 | 均判断 `if (order != null)`，良好 |
| `validateApply/validateOrder/validateReceipt` | 低 | 对 `items`、主键、日期、数量均做了非空判断 |
| `calcTotal` | 中 | 依赖前置校验，自身未做 NPE 防御（见 M03/L03） |
| `getCurrentUsername` | 低 | 捕获异常并返回默认值，但吞异常（见 L02） |
| `deleteBatch` 的 `ids` 拆分 | 低 | 已过滤空字符串 |

### 4.3 异常处理与事务

| 位置 | 事务配置 | 评价 |
|------|----------|------|
| `saveWithItems` / `updateWithItems` / `removeWithItems` / `removeByIds` | `@Transactional(rollbackFor = Exception.class)` | 完整，包含非受检异常 |
| `DuplicateKeyException` 转换 | 已处理 | 转换后仍为 `RuntimeException`，回滚生效 |
| 前端抽屉 `try { queryById } catch (e) {}` | 吞异常 | 不会导致事务问题，但影响用户体验（见前端审计） |

**潜在问题**：`saveWithItems` 中 `resurrect` 失败后仍继续 `saveItems`（见 M01/M02）。

### 4.4 SQL 注入风险

| 位置 | 风险 | 说明 |
|------|------|------|
| `QueryGenerator.initQueryWrapper` | 低 | 使用 MyBatis-Plus 条件构造器，参数化查询 |
| `@Select` / `@Update` 注解 | 低 | 全部使用 `#{...}` 占位符，无 `${...}` 拼接 |
| 排序字段 `orderByDesc("create_time")` | 无 | 硬编码字段名，无用户输入 |
| 导出 Excel 的表头 | 无 | 使用实体字段反射 |

**结论**：当前代码未发现 SQL 注入风险。

### 4.5 SQL / XML 正确性

- 采购模块未使用独立的 `Mapper.xml` 文件，所有 SQL 通过 MyBatis-Plus 自动生成或注解实现。
- 注解 SQL：`selectDeletedByCode`、`resurrect` 语法正确，字段名使用下划线风格（与数据库表名一致）。
- 但 `resurrect` 的 `UPDATE` 字段列表写死，未来新增字段后容易遗漏，建议使用 `<script>` 动态 SQL 或 MyBatis-Plus 的 `update` 方法恢复逻辑删除。

### 4.6 N+1 查询与批量操作

| 位置 | 现状 | 评价 |
|------|------|------|
| `queryWithItems` | 主表 1 次 + 明细 1 次 | 共 2 条 SQL，非 N+1，良好 |
| `saveWithItems` / `updateWithItems` | 逐行 `insert` 明细 | 在批量保存大量行时效率低，但业务上单据行数通常 < 50，可接受 |
| `removeByIds` 批量删除 | 批量 `selectBatchIds` + 批量 `delete` 明细 + 批量 `delete` 主表 | 已改为批量 SQL，避免循环自调用（P0 修复） |
| 入库历史累计查询 | 多次查询 | 先查历史入库单，再查历史入库行，再 Map 合并，属于合理范围 |

### 4.7 数据字典使用

| 位置 | 字典用法 | 一致性 |
|------|----------|--------|
| 实体字段 `@Dict(dicCode = "...")` | 正确 | 后端返回 `_dictText` 给前端 |
| 前端 `columns` 使用 `status_dictText` | 正确 | 与后端一致 |
| 前端 `formSchema` 使用 `JDictSelectTag` | 正确 | 申请 / 订单状态、采购类型 |
| 前端 `JSearchSelect` 物料/供应商/仓库 | 正确 | 字典格式 `dict="c_mes_material,name,id"` |
| 入库单的 `purchaseOrderId` 搜索/表单 | 错误 | 使用普通 `Input`，应改为订单搜索选择（见 L04） |

### 4.8 Result 响应规范

| 接口 | 响应 | 评价 |
|------|------|------|
| `list` | `Result.ok(service.page(...))` | 规范 |
| `queryById` | `entity != null ? Result.ok : Result.error` | 规范 |
| `add/edit/delete` | `Result.ok("...")` | 规范 |
| `deleteBatch` | `Result.ok("无需删除")` | 当 ids 为空时返回 200，建议区分是否真正操作 |
| `queryAll` / `exportXls` | 超出阈值抛 `JeecgBootException` | 合理，防刷 |

### 4.9 VO 与实体映射

- 当前模块未引入独立的 VO 类，Controller 直接返回实体对象。
- 实体中使用 `private transient List<...> items` 承载子表，序列化到 JSON 时通过 getter 输出，无持久化风险。
- 但 `transient` 在 Java 序列化中会被忽略，如果该实体被放入 HttpSession 或缓存，子表会丢失；建议明确使用 DTO/VO 或添加 `@TableField(exist = false)` 替代/补充 `transient`。

| H02 | 前端行级无校验 | 在 `handleSubmit` 中校验 `items` 必填/数量/物料；优化 `purchaseOrderId` 输入组件 | P0 |

| M03 | `removeByIds` 双重 unchecked cast | 统一参数类型为 `Collection<String>` | P1 |
| M04 | 数据权限未注入 | 评估是否需要 `@PermissionData` 或 `SysUserSQL` 过滤 | P1 |
| M05 | 入库超量校验未考虑同请求内累计与单位 | 修复同请求内累计逻辑；明确单位换算规则 | P1 |
| L01 | update 标记粒度 | 后续修复使用独立 update 块 | P2 |
| L02 | `getCurrentUsername` 吞异常 | 增加 `log.warn` | P2 |

## 6. 审计结论

本次代码细节视角审计对 JeecgBoot MES 采购管理模块的后端 Java 代码与前端 TypeScript/Vue 代码进行了逐行检查。整体来看，模块符合 JeecgBoot 脚手架风格，核心逻辑正确，事务、SQL 注入、基础字典、响应规范等方面无重大缺陷。

**主要风险集中在**：
1. 批量删除的状态校验接口契约不严谨（H01）；
2. 前端行内编辑缺少校验，存在提交非法单据的可能（H02）；
3. 死灰复燃（逻辑删除恢复）与批量删除的边界情况处理不足（M01/M02/M03）；
4. 入库累计校验在单位与同请求累计维度存在缺陷（M05）。

建议开发团队按优先级表进行修复，并在修复后由测试团队补充边界场景用例（如批量删除非草稿、恢复已物理删除单据、同订单多次入库累计超量、前端空行提交等）。
