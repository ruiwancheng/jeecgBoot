## 1. 审计范围与边界异常视角定义

本次审计聚焦于采购管理模块在**极端、边缘、异常、并发、逆向操作**场景下的鲁棒性，重点检查：

- 空值、零值、负数、超大值等边界数据；
- 重复提交、重复保存、重复删除；
- 状态流转越界（如已审批单据被改回草稿、已入库单据被删除）；
- 并发操作导致的数据一致性问题；
- 上下游单据联动缺失导致的边界异常；
- 权限/数据越界（如看到他人单据、删除非草稿数据）；
- 系统异常后的数据残留/回滚一致性。

被审计代码与文件：

| 模块 | 后端文件 | 前端文件 | 数据库脚本 |

| 等级 | 标识 | 判定标准 |
|------|------|----------|
| 致命 | 🔴 P0 | 造成数据错乱、资损、库存不准、流程不可恢复，或存在明显可被触发的线上事故 |

## 2. 边界异常专项发现（按模块列出）

### 2.1 采购申请模块边界异常

#### 2.1.1 `MesPurchaseApply.java` / `MesPurchaseApplyItem.java`

| 风险编号 | 等级 | 风险点 | 边界异常说明 | 修复建议 |
|----------|------|--------|--------------|----------|
| APPLY-B01 | 🔴 P0 | `totalAmount` 被后端 `calcTotal` 强制置为 `0`，且数据库字段允许任意精度 | 当用户手工通过 API 提交 `totalAmount=999999.99` 时，后端会丢弃并写入 `0`，但数据库字段本身没有限制；若未来版本恢复计算逻辑，历史数据可能不一致。 | 在数据库层对金额字段增加 `DEFAULT 0` 且非空；后端在 calcTotal 中正确计算，或明确标记为占位字段。 |
| APPLY-B02 | 🟠 P1 | `status` 字段无数据库约束，可写入任意字符串 | 直接调用 API 传入 `status='99'` 或 `status=''` 均能被保存，导致字典回显失败、状态机混乱。 | 数据库增加 `CHECK` 约束或后端白名单校验；`status` 默认值仅允许字典中定义的枚举值。 |
| APPLY-B03 | 🟠 P1 | `applyDate` / `requiredDate` 允许为 `null` | 虽然前端可填，但后端 `validateApply` 只校验了顺序，未校验空值；需求日期为空时无法判断紧急程度。 | 后端校验关键日期非空；或数据库增加 `NOT NULL` 约束并给出默认业务日期。 |
| APPLY-B04 | 🟡 P2 | `remark` 长度前端限制 500，但后端未校验 | 绕过前端直接调用 API 可写入超长备注，导致导出 Excel 异常或数据库存储截断。 | 后端统一对 `remark` 做长度校验，与数据库 `VARCHAR(500)` 对齐。 |
| APPLY-B05 | 🟡 P2 | 申请行 `unit` 无字典约束，可写入任意值 | 边界情况下，用户可写入空字符串、SQL 保留字、特殊字符，影响下游统计。 | 建议与物料主档单位联动，或至少限制长度与字符集。 |

#### 2.1.2 `MesPurchaseApplyServiceImpl.java`

| 风险编号 | 等级 | 风险点 | 边界异常说明 | 修复建议 |
|----------|------|--------|--------------|----------|
| APPLY-B06 | 🔴 P0 | `saveWithItems` 的 `resurrect` 逻辑会复活已删除记录，但主键 ID 被复用 | 已删除记录复活后，关联历史操作日志、数据权限、审批流记录可能指向新单据，造成审计混乱。更严重的是，若原删除单据的明细行已关联下游，复活后旧数据被覆盖。 | 复活逻辑应彻底清理旧明细行，并重新生成 ID；或废弃复活模式，改用唯一索引 + 禁止重复单号。 |
| APPLY-B07 | 🟠 P1 | 单号重复校验在 `saveWithItems` 中基于当前未删除记录，但未考虑并发 | 两个并发请求同时提交同号单据，可能都通过 `selectCount` 校验并同时 `insert`，导致唯一索引冲突异常抛给用户，体验差。 | 依赖数据库唯一索引捕获冲突，这是已有的兜底，但应把 `DuplicateKeyException` 的处理范围扩大到所有 `save` 路径；并提示友好信息。 |
| APPLY-B08 | 🟠 P1 | `updateWithItems` 中 `checkStatus` 后 `entity.getStatus()` 仍可能被前端传入覆盖 | 校验通过的是数据库状态，但后续用前端传入的 `entity` 做 `updateById`，如果前端把 `status` 从 `1` 改成 `3`，可直接绕过状态校验。 | 编辑接口应忽略传入的 `status` 字段，或在 update 时重新设置 `status = '1'`。 |
| APPLY-B09 | 🟠 P1 | `removeByIds` 批量删除未处理「部分 ID 不存在」的情况 | 传入 `[存在的ID, 不存在的ID]` 时，已存在的会被删除，但调用方可能误以为全部成功；且未删除的 ID 没有提示。 | 返回被删除的实际数量/ID 列表，或校验所有 ID 存在后再执行删除。 |
| APPLY-B10 | 🟡 P2 | `validateApply` 对 `items` 数量仅校验 `> 0`，未限制最大行数 | 极端情况下，用户可一次性提交 10000 行，导致内存和数据库压力。 | 增加最大行数限制（如 200 行），或分页保存。 |
| APPLY-B11 | 🟡 P2 | `saveItems` 采用逐行 `insert` | 大数据量保存时效率低，且任意一行失败时事务回滚，但前端无法知道哪一行失败。 | 批量 insert 或在一行失败时返回具体行号信息。 |

#### 2.1.3 `apply/index.vue` / `ApplyDrawer.vue` / `apply.data.ts`

| 风险编号 | 等级 | 风险点 | 边界异常说明 | 修复建议 |
|----------|------|--------|--------------|----------|
| APPLY-B12 | 🟠 P1 | 抽屉内 `items` 使用 `lineNo` 作为行唯一 key，删除行后 key 重复 | 删除中间行后再次添加，可能出现两个 `lineNo` 相同的行，导致表格渲染异常或数据覆盖。 | 使用唯一临时 ID 作为 `rowKey`，显示行号时独立计算。 |

### 2.2 采购订单模块边界异常

#### 2.2.1 `MesPurchaseOrder.java` / `MesPurchaseOrderItem.java`

| 风险编号 | 等级 | 风险点 | 边界异常说明 | 修复建议 |
|----------|------|--------|--------------|----------|
| ORDER-B01 | 🔴 P0 | `totalAmount`、`taxAmount`、`totalWithTax` 由后端计算，但实体字段可写，且未忽略前端传入 | 恶意或异常请求可直接传入这些字段，后端 `calcTotal` 会覆盖；但如果计算逻辑被绕过，可能导致数据库保存错误金额。 | 在 `validateOrder` 或 `calcTotal` 前强制重置金额字段，避免使用前端值。 |
| ORDER-B02 | 🔴 P0 | `taxRate` 默认 0.13，但允许传入任意值 | 用户传入 `taxRate=999` 或负数时，`taxAmount` 会变得极大或反向扣减，导致含税总额异常。 | 后端校验 `taxRate` 在合理范围（如 `0 ≤ taxRate ≤ 1` 或具体字典值）。 |
| ORDER-B03 | 🟠 P1 | 订单行 `quantity` 校验 `> 0`，但 `unitPrice` 校验 `>= 0` | 单价为 0 的订单在业务上意味着免费采购，应允许但需明确；如果业务不允许，应改为 `> 0`。 | 明确业务规则：若不允许 0 单价，则校验 `> 0`；若允许，则在列表中明确标识。 |
| ORDER-B04 | 🟠 P1 | 订单状态 `status` 无白名单校验 | 与申请模块类似，可写入任意状态值，导致状态机失效。 | 统一状态枚举校验，编辑时强制保持草稿状态。 |
| ORDER-B05 | 🟡 P2 | `deliveryDate` 和 `orderDate` 均为 `Date` 类型，但数据库为 `DATETIME`，时间部分可能不一致 | 前端传 `yyyy-MM-dd`，后端可能带 `00:00:00`，在跨时区或夏令时场景下比较可能出错。 | 统一在比较时去除时间部分，或数据库改为 `DATE` 类型。 |

#### 2.2.2 `MesPurchaseOrderServiceImpl.java`

| 风险编号 | 等级 | 风险点 | 边界异常说明 | 修复建议 |
|----------|------|--------|--------------|----------|
| ORDER-B06 | 🔴 P0 | 税额计算 `item.getAmount().multiply(rowTaxRate)` 未对 `taxRate` 做边界校验 | 当 `taxRate=1` 时，税额等于不含税金额，含税总额为两倍；当 `taxRate=0` 时，无税；但 `taxRate` 传入 `null` 时 fallback 为 0.13，可能不符合业务。 | 校验 `taxRate` 范围；`null` 时应报错或明确使用默认税率；默认税率建议从配置读取。 |

| ORDER-B08 | 🟠 P1 | 订单删除未校验是否存在下游入库单 | 当前仅校验状态为草稿，但状态字段本身可被篡改或未来状态机扩展后绕过。 | 删除前查询 `c_mes_purchase_receipt` 是否存在关联记录，存在则禁止删除。 |
| ORDER-B09 | 🟠 P1 | 批量删除 `removeByIds` 的状态校验与单笔删除不一致 | 单笔删除 `removeWithItems` 只校验状态，批量删除也仅校验状态；但都没有校验下游单据。应统一校验。 | 统一封装删除前置检查，包含状态、下游单据、存在性。 |
| ORDER-B10 | 🟡 P2 | 金额计算使用 `RoundingMode.HALF_UP`，但币种/精度未统一 | 不同币种精度不同，当前统一 2 位小数，在日元等 0 精度币种场景下会出错。 | 增加币种精度配置，或按业务币种动态计算。 |
| ORDER-B11 | 🟡 P2 | 订单行 `amount` 由后端重算，但 `taxAmount` 和 `totalAmount` 在行级别未保存 | 订单行缺少行级税额和含税金额，在按行对账时无法直接查看。 | 在订单行增加 `taxAmount` 和 `totalAmount` 字段。 |

### 2.3 采购入库模块边界异常

#### 2.3.1 `MesPurchaseReceipt.java` / `MesPurchaseReceiptItem.java`

| 风险编号 | 等级 | 风险点 | 边界异常说明 | 修复建议 |
|----------|------|--------|--------------|----------|
| RECEIPT-B01 | 🔴 P0 | `purchaseOrderId` 允许为 `null`（数据库未 NOT NULL），但后端 `validateReceipt` 要求非空 | 如果直接通过数据库或旧数据写入，可能出现主表无订单但明细行有数量的异常数据。 | 数据库增加 `purchase_order_id NOT NULL` 约束，或业务上明确允许无订单入库。 |
| RECEIPT-B02 | 🔴 P0 | `supplierId` 在前端为必填，但后端校验冗余，且未与订单供应商一致性校验 | 用户可选择与订单不同的供应商，导致财务对账异常。 | 后端保存时校验 `supplierId` 与采购订单 `supplierId` 一致；不一致时报错。 |
| RECEIPT-B03 | 🟠 P1 | `warehouseId` 允许任意仓库，未校验仓库是否启用/存在 | 边界情况下可写入已禁用仓库，导致库存统计遗漏。 | 校验仓库存在且状态可用。 |
| RECEIPT-B04 | 🟠 P1 | 入库行 `orderQuantity` 可手工输入为 0 或负数 | 当前前端 `min: 0` 允许 0，但 `orderQuantity` 应为订单数量，应只读或从订单带出。 | 入库行 `orderQuantity` 从订单行反写，不可编辑。 |
| RECEIPT-B05 | 🟠 P1 | 质检结果 `qcResult` 为可选，但字典值 `1/2/3` 未明确业务含义 | 未选质检结果时，系统无法判断是否可以入库；不合格物料也可能被入库。 | 增加必填校验，或默认「待检」并限制待检物料不能审核入库。 |

#### 2.3.2 `MesPurchaseReceiptServiceImpl.java`

| 风险编号 | 等级 | 风险点 | 边界异常说明 | 修复建议 |
|----------|------|--------|--------------|----------|
| RECEIPT-B06 | 🔴 P0 | 累计入库校验使用 `materialId` 作为 Map Key，但**入库物料可以不在订单行中** | 如果入库行包含订单未采购的物料，校验会跳过，导致超量约束失效；更可能入库错误物料。 | 强制校验入库行物料必须在订单行中存在；否则报错。 |
| RECEIPT-B07 | 🔴 P0 | 累计入库校验未考虑并发 | 两个并发入库单同时保存时，都基于当前历史量计算，可能同时通过校验，导致总入库量超过订单数量。 | 对采购订单行或库存表加乐观锁/数据库行锁，或使用唯一索引 + 预占数量模式。 |
| RECEIPT-B08 | 🔴 P0 | 编辑时强制 `entity.setStatus("1")` 重置为草稿，但单据可能已审核 | 已审核入库单编辑后变成草稿，但库存已增加，状态与库存不一致。 | 已审核/已入库状态禁止编辑，只能红冲。 |
| RECEIPT-B09 | 🟠 P1 | 删除入库单未校验状态，草稿删除后库存无影响，但「已审核」删除逻辑缺失 | 当前 `removeWithItems` 只校验草稿，但未来若状态扩展为已审核，删除不会回滚库存。 | 删除前必须校验状态为草稿；已审核单据需先红冲。 |
| RECEIPT-B10 | 🟠 P1 | 入库保存后没有更新库存，但也没有任何审核动作 | 草稿入库单永远不会自动更新库存，库存台账永远是空的；如果用户误以为保存即入库，会导致账实不符。 | 明确区分「保存草稿」与「审核入库」；审核动作触发库存更新。 |
| RECEIPT-B11 | 🟠 P1 | 历史入库量累计使用 `BigDecimal` 的 `add`，未处理 `null` 值 | 虽然代码用 `merge` 做了 null 处理，但如果某行 `receiptQuantity` 为 `null`，会按 0 处理，可能导致校验通过但实际入库量遗漏。 | 入库行保存时强制 `receiptQuantity` 非空且 `> 0`。 |
| RECEIPT-B12 | 🟡 P2 | `remark` 长度校验仅在后端，但数据库 `VARCHAR(500)` 与前端 `maxlength=500` 一致 | 边界情况下，中文字符在数据库中占 1~3 字节，取决于字符集，500 个字符可能超出字节限制。 | 明确使用 `utf8mb4` 并统一按字符长度校验。 |
| RECEIPT-B13 | 🟡 P2 | `qcResult` 白名单使用 `new HashSet<>(Arrays.asList("1", "2", "3"))` 硬编码 | 如果字典值扩展，需要同步修改代码，维护成本高。 | 从字典配置读取合法值，或定义常量枚举。 |

#### 2.3.3 `receipt/index.vue` / `ReceiptDrawer.vue` / `receipt.data.ts`

| 风险编号 | 等级 | 风险点 | 边界异常说明 | 修复建议 |

## 3. 跨模块边界异常风险

### 3.1 申请 → 订单：无引用关系，边界状态无法追溯

- 采购订单没有记录来源申请行，导致无法校验「已转订单数量 ≤ 申请数量」。
- 边界异常：同一张申请被多次转成订单，可能超出原申请数量。
- **风险等级：🔴 P0**
- **修复建议**：订单行增加 `sourceApplyId` / `sourceApplyItemId`，保存时回写申请行的 `orderedQty`。

### 3.2 订单 → 入库：订单状态可绕过，超量入库

- 入库单校验订单状态必须为 `3`（已确认）或 `4`（部分到货），但订单状态本身可被篡改。
- 边界异常：订单状态被改为已确认后，多次入库可超过订单数量；并发场景下尤为明显。
- **风险等级：🔴 P0**
- **修复建议**：对订单行增加 `arrived_qty` 字段，入库时原子更新并校验；使用数据库行锁或乐观锁。

### 3.3 入库 → 库存：完全脱节，任何库存边界都失效

- 入库单保存后库存不更新，导致负库存、超量出库、库存台账错误等边界条件无法判断。
- **风险等级：🔴 P0**
- **修复建议**：入库审核后，在事务中更新 `c_mes_inventory` 并写入 `c_mes_inventory_ledger`。

### 3.4 状态机缺失导致的状态越界

- 所有模块的状态字段都可被前端任意传入，后端没有统一状态机校验。
- 边界异常：用户可将「已审批」改回「草稿」，或将「已入库」改回「草稿」。
- **风险等级：🟠 P1**
- **修复建议**：定义每个模块的合法状态流转图，所有状态变更通过专门接口，并在 Service 层统一校验。

### 3.5 重复提交与幂等性缺失

- 所有新增/编辑接口都没有幂等机制。
- 边界异常：网络超时后用户重复点击，可能产生重复单据；批量导入时也可能重复。
- **风险等级：🟠 P1**
- **修复建议**：新增接口支持客户端生成唯一幂等键（如 `idempotencyKey`），或基于单号唯一索引兜底；批量导入做去重校验。

### 3.6 并发下唯一单号冲突

- 单号唯一性依赖数据库唯一索引，但代码在 `saveWithItems` 中先做 `selectCount` 再插入。
- 边界异常：高并发下两个请求同时通过 `selectCount` 后同时插入，导致后者抛出唯一索引冲突。
- **风险等级：🟠 P1**
- **修复建议**：数据库唯一索引是必要兜底，但应提前生成单号并加锁，或使用分布式 ID + 预校验。

## 5. 审计结论

从产品边界异常视角看，当前 JeecgBoot MES 采购管理模块存在以下关键问题：

1. **🔴 库存联动缺失是最大的边界风险**：入库单保存后库存不更新，导致所有库存相关边界条件（负库存、超量入库、账实不符）都无法防护。
2. **🔴 跨模块引用缺失导致状态越界**：申请、订单、入库之间没有引用关系，无法防止重复转单、超量入库、入库未采购物料等异常。
3. **🟠 状态机缺失导致任意状态可篡改**：所有状态字段都可被前端传入，缺少统一状态机和白名单校验。
4. **🟠 并发与幂等未考虑**：高并发下可能出现单号冲突、超量入库、重复单据等问题。
5. **🟡 前端边界校验不完整**：行 key 重复、状态字典错误、普通 Input 代替选择器等问题影响异常场景下的用户体验。

建议优先修复 P0 级问题，尤其是入库物料存在性校验、库存联动、订单-入库数量原子控制，否则模块上线后将面临真实的库存数据混乱和账实不符风险。
