## 一、审计目标与范围

本次审计从性能压测视角，对 MES 采购管理模块进行代码静态审查，重点评估以下场景的性能风险：

1. 列表查询（分页 + 字典翻译）
2. 批量导入（Excel 导入）
3. 大批量主子表保存（新增/编辑）
4. 库存台账查询（大数据量时间范围查询）
5. 大数据量导出（Excel 导出）

检查是否存在：N+1 查询、全表扫描、缺少分页、大数据量导出 OOM、大事务、批处理未优化、索引缺失等典型性能问题。

---

## 二、总体结论

| 检查维度 | 结论 | 风险等级 |
|---|---|---|
| 列表查询分页 | 所有分页接口均使用 `Page` + `QueryWrapper`，默认 pageSize=10，具备分页能力 | 低 |
| 列表查询排序 | 均按 `create_time`/`record_date` 倒序，命中索引需验证 | 中 |
| 字典翻译 | 大量 `@Dict`/`dictTable` 字段，依赖 JeecgBoot 字典切面，高并发下可能触发缓存穿透或 N+1 | 中 |
| 批量导入 | 四个模块均未提供 `/importExcel` 接口，无法压测 | 高 |
| 主子表保存 | 明细行采用 `for` 循环逐条 `insert`，存在批量保存性能瓶颈 | 高 |
| 库存台账查询 | 已按 `record_date`/`material_id`/`warehouse_id` 建立索引，但缺少复合索引优化 | 中 |
| 大数据量导出 | 导出阈值分别为 1000/5000，阈值内使用 AutoPoi 全量加载，存在 OOM 风险 | 中 |
| 大事务/长锁 | 主子表保存、批量删除均在一个事务内，明细过多时锁时间长 | 中 |
| 并发幂等 | 无分布式锁/Token 幂等，高并发下依赖数据库唯一索引兜底 | 高 |

**结论**：当前模块在常规业务数据量（主表 < 10 万、明细 < 50 万）下可正常运行；但在高并发、大批量、大数据量导出/导入场景下存在明显性能瓶颈，需重点优化。

## 三、各模块性能风险分析

### 3.1 采购申请模块

**相关代码**：
- `MesPurchaseApplyController.java`
- `MesPurchaseApplyServiceImpl.java`
- `MesPurchaseApplyMapper.java`
- `c_mes_purchase_apply` / `c_mes_purchase_apply_item`

#### 3.1.1 列表查询 `/list`

```java
public Result<IPage<MesPurchaseApply>> queryPageList(MesPurchaseApply entity,
        @RequestParam(name = "pageNo", defaultValue = "1") Integer pageNo,
        @RequestParam(name = "pageSize", defaultValue = "10") Integer pageSize, HttpServletRequest req) {
    QueryWrapper<MesPurchaseApply> qw = QueryGenerator.initQueryWrapper(entity, req.getParameterMap());
    qw.orderByDesc("create_time");
    return Result.ok(service.page(new Page<>(pageNo, pageSize), qw));
}
```

| 检查项 | 结果 | 说明 |
|---|---|---|
| 分页 | ✅ 已分页 | 使用 MyBatis-Plus `Page` |
| 默认页大小 | ✅ 10 | 合理，但前端可传大值（如 10000） |
| 排序字段索引 | ⚠️ 需确认 | `create_time` 是否单独建索引未在脚本中明确，但通常 MyBatis-Plus 逻辑删除字段 `del_flag` 与 `create_time` 组合查询 |
| 字典翻译 | ⚠️ 有风险 | `status` 使用 `@Dict(dicCode="mes_purchase_apply_status")`，列表每页 10 条仅 1 次字典查询，可接受；但 JeecgBoot 字典切面若未命中缓存会查库 |
| 全表扫描风险 | ✅ 低 | 带 `del_flag` 过滤 + 分页 |

**风险点**：
- 如果用户通过接口恶意传入 `pageSize=100000`，Service 层无上限校验，可能导致单次查询加载大量数据。
- `QueryGenerator` 自动生成的 `LIKE` 查询（如 `code` 模糊匹配）如果前缀无 `%`，可走索引；如果前后都有 `%`，会全表扫描。

#### 3.1.2 按 ID 查询 `/queryById`（含明细）

```java
public MesPurchaseApply queryWithItems(String id) {
    MesPurchaseApply apply = baseMapper.selectById(id);
    if (apply != null) {
        LambdaQueryWrapper<MesPurchaseApplyItem> qw = new LambdaQueryWrapper<>();
        qw.eq(MesPurchaseApplyItem::getApplyId, id).orderByAsc(MesPurchaseApplyItem::getLineNo);
        apply.setItems(itemMapper.selectList(qw));
    }
    return apply;
}
```

| 检查项 | 结果 | 说明 |
|---|---|---|
| N+1 查询 | ❌ 存在 | 1 次主表 + 1 次子表，严格说不是 N+1（N 为 1），但主子表未一次性 JOIN 查询 |
| 明细数量 | ⚠️ 无上限 | 一个申请单理论上可无限添加明细行，一次性加载全部明细 |
| 索引 | ✅ 子表 `idx_item_apply_id` 存在 | |

**风险点**：
- 对于单个单据，明细行通常 < 100 条，风险可控。但如果业务允许一个申请单包含上千条明细，按 ID 查询会加载大量数据，建议增加明细分页或限制。

#### 3.1.3 新增/编辑保存（大批量主子表）

```java
private void saveItems(MesPurchaseApply entity) {
    for (MesPurchaseApplyItem item : entity.getItems()) {
        item.setApplyId(entity.getId());
        itemMapper.insert(item);
    }
}
```

| 检查项 | 结果 | 说明 |
|---|---|---|
| 批量插入 | ❌ 逐条插入 | 每个明细行一次 INSERT，网络 RTT + 数据库日志开销大 |
| 事务 | ✅ 已加 `@Transactional` | 但事务时间长，明细多时长锁表 |
| 明细数量上限 | ❌ 无上限 | 用户可一次性提交上万条明细 |
| 索引维护成本 | ⚠️ 高 | 每插入一行都要维护 `idx_item_apply_id` |

**性能估算**：
- 假设 1000 条明细，逐条插入约 1000 次网络往返 + 1000 次 SQL 解析，TP99 可能 > 5s。
- 建议改为 MyBatis-Plus `saveBatch` 或 `insertBatchSomeColumn` 批量插入。

#### 3.1.4 导出 Excel `/exportXls`

```java
public ModelAndView exportXls(MesPurchaseApply entity, HttpServletRequest req) {
    long total = service.count(new QueryWrapper<>());
    if (total > QUERY_ALL_MAX) throw new JeecgBootException("申请超过" + QUERY_ALL_MAX + "条，请使用分页导出");
    return super.exportXls(req, entity, MesPurchaseApply.class, "采购申请");
}
```

| 检查项 | 结果 | 说明 |
|---|---|---|
| 导出上限 | ✅ 1000 条 | 阻止大导出 |
| 导出方式 | ⚠️ 全量加载 | `super.exportXls` 会一次性查询所有数据到内存，1000 条可接受，但字段多（含字典翻译）时仍可能 OOM |
| 字典翻译导出 | ⚠️ 有风险 | `@Excel(dicCode=...)` 会触发字典查询，1000 条主表数据可能多次查字典 |

#### 3.1.5 批量导入

| 检查项 | 结果 | 说明 |
|---|---|---|
| 导入接口 | ❌ 未提供 | 无 `/importExcel` |
| 导入模板 | ❌ 未提供 | 无 `/importExcelTemplate` |

**风险点**：无法通过 Excel 批量导入，业务上如果用户需要一次性导入大量申请单，只能通过新增接口，进一步放大逐条插入的性能问题。

private void saveItems(MesPurchaseOrder entity) {

### 3.3 采购入库模块

**相关代码**：
- `MesPurchaseReceiptController.java`
- `MesPurchaseReceiptServiceImpl.java`
- `MesPurchaseReceiptMapper.java`
- `c_mes_purchase_receipt` / `c_mes_purchase_receipt_item`

#### 3.3.1 列表查询 `/list`

与采购申请/订单类似，分页、排序、字典翻译均一致。

#### 3.3.2 按 ID 查询（含明细）

1 次主表 + 1 次子表。

#### 3.3.3 新增/编辑保存（大批量主子表 + 关联校验）

```java
public void saveWithItems(MesPurchaseReceipt entity) {
    validateReceipt(entity);
    // ... 保存主表
    saveItems(entity);
}

private void validateReceipt(MesPurchaseReceipt entity) {
    // 1. 查询采购订单
    MesPurchaseOrder order = purchaseOrderMapper.selectById(entity.getPurchaseOrderId());
    // 2. 查询订单所有明细行
    List<MesPurchaseOrderItem> orderItems = purchaseOrderItemMapper.selectList(oqw);
    // 3. 查询历史入库单
    List<MesPurchaseReceipt> existingReceipts = baseMapper.selectList(rqw);
    // 4. 如果存在历史入库单，查询所有历史入库明细行
    List<MesPurchaseReceiptItem> historyItems = itemMapper.selectList(hiqw);
    // ... 逐行校验
}

private void saveItems(MesPurchaseReceipt entity) {
    for (MesPurchaseReceiptItem item : entity.getItems()) {
        item.setReceiptId(entity.getId());
        itemMapper.insert(item);
    }
}
```

| 检查项 | 结果 | 说明 |
|---|---|---|
| 明细逐条插入 | ❌ 存在 | 与申请/订单一致 |
| 关联订单查询 | ⚠️ 两次查询 | 查订单主表 + 订单明细 |
| 历史入库查询 | ⚠️ 可能多次 | 先查历史入库单，再查历史入库明细（存在历史入库时） |
| 累计入库校验 | ✅ 功能正确 | 但实现方式是内存聚合，历史入库多时内存占用大 |
| 大事务 | ⚠️ 存在 | 整个保存 + 校验在一个事务内 |
| 锁竞争 | ⚠️ 高 | 同一采购订单并发入库时，历史入库查询可能产生幻读，详见 08 号并发安全报告 |

**性能估算**：
- 假设一个采购订单已产生 100 次入库，每次入库 10 条明细，历史入库明细共 1000 条。
- 每次新增入库单需要：1 次订单主表 + 1 次订单明细 + 1 次历史入库单 + 1 次历史入库明细（1000 条）+ 本次明细插入。
- 历史入库明细加载到内存做聚合，数据量大时 OOM 风险增加。

**优化建议**：
- 使用 SQL 聚合 `SUM(receipt_quantity)` 替代内存聚合。
- 在 `c_mes_purchase_receipt_item` 上建立 `(receipt_id, material_id)` 复合索引，加速历史入库数量汇总。
- 使用批量插入替代逐条插入。

#### 3.3.4 导出 Excel

上限 1000 条，全量加载。

### 3.4 库存台账模块

**相关代码**：
- `MesInventoryLedgerController.java`
- `MesInventoryLedgerServiceImpl.java`
- `MesInventoryLedgerMapper.java`
- `c_mes_inventory_ledger`

#### 3.4.1 列表查询 `/list`

```java
public Result<IPage<MesInventoryLedger>> queryPageList(MesInventoryLedger entity,
        @RequestParam(name = "pageNo", defaultValue = "1") Integer pageNo,
        @RequestParam(name = "pageSize", defaultValue = "10") Integer pageSize, HttpServletRequest req) {
    QueryWrapper<MesInventoryLedger> qw = QueryGenerator.initQueryWrapper(entity, req.getParameterMap());
    qw.orderByDesc("record_date").orderByAsc("material_id");
    return Result.ok(service.page(new Page<>(pageNo, pageSize), qw));
}
```

| 检查项 | 结果 | 说明 |
|---|---|---|
| 分页 | ✅ 已分页 | 默认 10 条 |
| 排序 | ✅ 按 `record_date` 倒序 + `material_id` 正序 | |
| 索引 | ⚠️ 部分 | 脚本建立了 `idx_ledger_date`、`idx_ledger_material`、`idx_ledger_warehouse`，但缺少复合索引 |
| 字典翻译 | ⚠️ 有风险 | `materialId`、`warehouseId` 均为表字典，列表时可能触发 JOIN 或多次查询 |
| 全表扫描风险 | ✅ 低 | 常用查询条件均有索引 |

**风险点**：
- 台账数据量通常最大，可能达到千万级。当前索引为单列索引，如果查询条件为 `material_id + record_date` 范围，单列索引可能无法最优利用。
- 建议建立复合索引：`(material_id, record_date)`、`(warehouse_id, record_date)`。

#### 3.4.2 查询全部 `/queryAll`

阈值 5000 条，超过则抛异常。对于台账模块，5000 条上限相对合理，但仍需警惕前端恶意调用。

#### 3.4.3 导出 Excel `/exportXls`

阈值 5000 条，全量加载。台账字段含 `materialId`、`warehouseId` 表字典，5000 条数据字典翻译可能成为瓶颈。

**风险点**：
- 5000 条数据一次性加载到内存，如果字段多、字典翻译缓存未命中，可能导致：
  - 数据库字典查询压力骤增
  - 服务端内存占用过高
  - 导出响应时间长，甚至超时

## 四、数据库索引检查

### 4.1 采购申请/订单/入库主表

| 表名 | 主键 | 唯一索引 | 普通索引 | 备注 |
|---|---|---|---|---|
| `c_mes_purchase_apply` | `id` | `uk_apply_code_del(code, del_flag)` | 无 | `code` 单独唯一索引可支持编码查询 |
| `c_mes_purchase_order` | `id` | `uk_po_code_del(code, del_flag)` | 无 | 同上 |
| `c_mes_purchase_receipt` | `id` | `uk_receipt_code_del(code, del_flag)` | 无 | 同上 |

**风险点**：
- 列表查询按 `create_time` 倒序 + `del_flag` 过滤，当前未建立 `(create_time, del_flag)` 或 `(del_flag, create_time)` 索引，数据量大时排序可能 filesort。
- 建议增加：
  - `INDEX idx_main_del_time (del_flag, create_time)` 用于列表排序
  - `INDEX idx_main_status (status)` 用于状态筛选

### 4.2 采购申请/订单/入库明细表

| 表名 | 主键 | 普通索引 | 备注 |
|---|---|---|---|
| `c_mes_purchase_apply_item` | `id` | `idx_item_apply_id(apply_id)` | |
| `c_mes_purchase_order_item` | `id` | `idx_item_po_id(order_id)` | |
| `c_mes_purchase_receipt_item` | `id` | `idx_item_receipt_id(receipt_id)` | |

**风险点**：
- 入库模块需要按 `receipt_id + material_id` 汇总历史入库数量，建议增加复合索引 `idx_item_receipt_material(receipt_id, material_id)`。
- 如果按物料查询明细（如订单物料查询），建议增加 `idx_item_material_id(material_id)`。

### 4.3 库存台账表

| 表名 | 主键 | 普通索引 | 备注 |
|---|---|---|---|
| `c_mes_inventory_ledger` | `id` | `idx_ledger_material(material_id)`、`idx_ledger_warehouse(warehouse_id)`、`idx_ledger_date(record_date)` | |

**风险点**：
- 缺少复合索引，常见查询场景如：
  - 按物料 + 日期范围查询：建议 `idx_ledger_material_date(material_id, record_date)`
  - 按仓库 + 日期范围查询：建议 `idx_ledger_warehouse_date(warehouse_id, record_date)`
  - 按日期 + 物料汇总：建议 `idx_ledger_date_material(record_date, material_id)`

## 五、典型性能风险汇总

| 风险编号 | 风险描述 | 涉及模块 | 影响 | 建议处理 | 优先级 |
|---|---|---|---|---|---|
| PERF-001 | 主子表明细逐条 INSERT，无批量优化 | 申请、订单、入库 | 大批量保存时 RT 高、数据库压力大 | 使用 `saveBatch` 或 XML 批量插入；限制单次明细数量上限（如 500） | 高 |
| PERF-002 | 列表查询 `pageSize` 无上限校验 | 全部 | 用户可恶意传入超大 pageSize，导致 OOM/慢查询 | Service 层增加 `pageSize <= 1000` 校验 | 高 |
| PERF-003 | 导出 Excel 全量加载到内存 | 全部 | 阈值内数据仍可能 OOM，尤其是字典字段多 | 采用流式导出（SXSSF）或分页导出；降低阈值 | 中 |
| PERF-004 | 入库校验历史入库量采用内存聚合 | 入库 | 历史入库多时内存占用大、RT 高 | 改为 SQL `SUM` 聚合 | 高 |
| PERF-005 | 表字典字段翻译可能触发 N+1 或大量 JOIN | 订单、入库、台账 | 高并发列表查询字典查库压力大 | 确保字典数据已缓存；减少表字典字段；或使用 SQL 一次性 JOIN |
| PERF-006 | 主表列表排序无索引覆盖 | 申请、订单、入库 | 数据量大时 filesort 慢查询 | 增加 `(del_flag, create_time)` 复合索引 | 中 |
| PERF-007 | 库存台账缺少复合索引 | 台账 | 大表 + 时间范围查询慢 | 增加 `(material_id, record_date)` 等复合索引 | 高 |
| PERF-008 | 批量导入功能缺失 | 全部 | 无法通过批量导入压测，用户只能走单条新增 | 补充 `/importExcel` 并实现批量插入 | 高 |
| PERF-009 | 大事务长锁 | 申请、订单、入库 | 明细多时事务长，锁表时间长 | 限制单次保存明细数量；批量插入减少事务时间 | 中 |
| PERF-010 | 无并发幂等控制 | 全部 | 高并发重复提交导致数据库唯一索引冲突重试 | 增加 Token 幂等或分布式锁 | 高 |

## 六、压测场景设计建议

### 6.1 压测目标接口

| 模块 | 接口 | 压测场景 | 关注指标 |

## 七、结论与交付建议

### 7.1 结论

从性能压测视角看，MES 采购管理模块在当前代码实现下：

- **列表查询**：已具备基础分页能力，但缺少 pageSize 上限校验和排序索引优化。
- **主子表保存**：存在明细逐条插入、无明细数量上限、大事务长锁等明显性能瓶颈，**不适合大批量主子表保存**。
- **批量导入**：功能缺失，无法开展批量导入压测。
- **库存台账**：索引设计偏简单，数据量大时存在慢查询风险，需要补充复合索引。
- **大数据量导出**：阈值内全量加载，字段多/字典多时有 OOM 风险，建议使用流式导出。
- **高并发写入**：无幂等控制，依赖数据库唯一索引兜底，存在并发冲突和重试成本。

### 7.2 阻塞项（必须修复后再压测）

1. **PERF-001 主子表明细逐条插入**：必须改为批量插入，否则 100 行以上明细保存接口无法通过压测。
2. **PERF-002 pageSize 无上限**：必须增加服务端校验，否则列表查询接口存在被恶意压垮风险。
3. **PERF-004 入库历史数量内存聚合**：必须改为 SQL 聚合，否则历史入库多时有 OOM 和慢查询风险。
4. **PERF-008 批量导入缺失**：如需压测导入场景，必须先补充实现。

### 7.3 建议后续工作

1. 研发修复上述阻塞项后，由测试组使用 JMeter 或自研压测平台执行 6.1 场景。
2. 在 10 万/50 万数据量级下验证列表查询、导出、主子表保存的 TP99 和错误率。
3. 使用 MySQL `EXPLAIN` 分析慢 SQL，确保关键查询无全表扫描、无 filesort。
4. 监控 JVM 内存和 GC，确认导出场景无 OOM。
5. 在压测报告中补充 JVM、数据库、Redis 等资源监控图表，形成完整性能基线。
