# 铁拳团 9 号 · 交付测试组 —— MES 生产制造模块（mes-manufacturing）性能压测评估报告

> 审计视角：性能压测（只查不改代码）
> 审计范围：`jeecg-boot/jeecg-boot-module/project-mes/src/main/java/org/jeecg/modules/mes/manufacturing/`（bom / order / picking / completion 四包）+ 建表 SQL `project-mes/db/V7.0.0 ~ V7.0.3`
> 技术栈：MyBatis-Plus 3.5.12 + MySQL（InnoDB / utf8mb4）+ AutoPoi
> 审计日期：2026-07-16

---

## 一、总体结论

manufacturing 模块整体属于"轻量级 CRUD"实现，**基础规范做得不错**：列表全部分页、导出/全量查询有 1000 条上限、批量删除走 `IN`、主子表查询按主外键精确匹配、无显式 N+1 循环查库、无"每次全表 SUM 累计校验"。

但存在**一个必须先解决的可用性地基问题（P0）**：picking / completion 两个模块的**实体与 Mapper 表名与建表 SQL 不一致（缺 `c_` 前缀）**，导致这两套功能实际指向一张不存在/未建索引的表——在它之下谈索引优化没有意义。其余风险集中在**索引缺失**与**主子表大批量写性能**两个层面，多为 P1/P2。

风险分布：**P0 × 1，P1 × 5，P2 × 4**。

## 二、六个审计维度逐项核查

### 1）列表查询：分页 / 模糊查询 / 索引

**分页 —— 合格 ✅**
四个列表接口（bom/order/picking/completion 的 `/list`）全部使用 `service.page(new Page<>(pageNo, pageSize), qw)`，物理分页齐全，无一次性 `list()` 全表返回。

**QueryGenerator 模糊查询 —— 有全表扫描风险 ⚠️**
四个 Controller 均用 `QueryGenerator.initQueryWrapper(entity, req.getParameterMap())` 自动组装条件。实体中 `code`、`remark` 等 String 字段未加 `@QueryField` 限定，QueryGenerator 对 String 字段默认生成 **`LIKE '%keyword%'` 双侧通配**，**无法走任何 B-Tree 索引**，数据量大时必全表扫描。这是 JeecgBoot 通用痛点，本模块未做规避。

**索引 —— 严重缺失 ⚠️（逐表核对建表 SQL）**

| 表 | 已建索引 | 缺失的关键索引 |
|---|---|---|
| `c_mes_bom` | 主键、`uk_bom_product_version(product_id,version,del_flag)` | `code` 无独立索引（仅模糊查/唯一校验用，靠 code 等值查会扫）；`status`、`create_time`（列表默认 `orderByDesc(create_time)`）无索引 |
| `c_mes_bom_item` | 主键、`idx_item_bom_id(bom_id)` | 基本够用 ✅ |
| `c_mes_production_order` | 主键、`uk_prod_order_code(code,del_flag)` | **`product_id`、`bom_id`、`status`、`create_time` 全无索引** |
| `c_mes_production_picking` | 主键、`uk_picking_code(code,del_flag)` | **`production_order_id` 无索引（关联订单查询的高频字段）**、`status`、`create_time` 无索引 |
| `c_mes_production_picking_item` | 主键、`idx_item_picking_id(picking_id)` | 基本够用 ✅ |
| `c_mes_completion_receipt` | 主键、`uk_completion_code(code,del_flag)` | **`production_order_id` 无索引**、`status`、`create_time` 无索引 |
| `c_mes_completion_receipt_item` | 主键、`idx_item_completion_id(receipt_id)` | 基本够用 ✅ |

**结论**：列表排序字段（`create_time`）、状态筛选字段（`status`）、外键关联字段（`production_order_id` / `product_id` / `bom_id`）普遍缺索引，叠加 `LIKE '%..%'` 模糊查，列表在数据量上到几万级即会明显变慢。

### 2）批量导入：是否逐条 save

**结论：本模块实际未提供 Excel 导入功能（无逐条 save 性能问题，但有功能缺口）ℹ️**
- 四个 Controller **均未重写 `importExcel`、也未暴露 `/importExcel` 端点**，即前端无导入入口。
- 父类 `JeecgController.importExcel()` 内部用的是 **`service.saveBatch(list)`（MyBatis-Plus 批量插入，非逐条）**，源码注释明确标注"批量插入 400 条 1592ms vs 循环 1947ms"。因此即便后续开放导入，**只要走基类 `saveBatch` 就不会出现逐条 save**。
- **需提醒**：若未来给 BOM 这种主子表结构开放导入，基类 `saveBatch` 只批量插主表，**子表不会自动级联**，且 `saveBatch` 默认每批 1000 条 flush——大文件需自行分批 + 关闭 `needSave` 的 AutoPoi 落库（基类 `params.setNeedSave(true)` 会再存一份到 AutoPoi 临时表，大数据量时是额外开销）。

### 3）大批量主子表保存：BOM 几百行子项的保存性能

**结论：逐条 INSERT + 先删后插，几百行时性能差（P1）⚠️**
- `MesBomServiceImpl.saveItems()`：`for (item : items) { itemMapper.insert(item); }` —— **逐条 INSERT**。BOM 子项几百行时，一次保存 = 主表 1 条 + 子表 N 条 INSERT，**N 次网络往返 + N 次 redo/binlog**，几百行约数百毫秒到秒级。
- `updateWithItems()` 采用**先删后插**模式：先 `itemMapper.delete(bom_id=?)` 删全部旧子项，再循环逐条 INSERT 新子项。编辑一次几百行 BOM = **1 次批量 DELETE + N 次单条 INSERT**，且 DELETE + INSERT 会让 InnoDB 产生大量页分裂/标记删除，**自增碎片与写放大明显**。
- picking / completion 的 `saveItems()` 同样是逐条 INSERT（领料/入库行通常比 BOM 子项少，风险略低，但同根因）。
- **正向点**：三者都有 `@Transactional(rollbackFor = Exception.class)`，先删后插在事务内，不会出现"删了没插上"的中间态；子表 `bom_id/picking_id/receipt_id` 均有索引，DELETE 走索引高效。

### 4）N+1 查询：列表页是否循环查子表/关联表

**结论：无 N+1，合格 ✅**
- 列表 `/list` 只查主表（`service.page`），**未在结果循环里逐个查子表或订单**。
- 子表查询统一收口在 `queryWithItems(id)`（`queryById` 详情接口），单条主表 + 一次 `itemMapper.selectList(bom_id=?)` 按外键查全部子项，**1+1 两条 SQL**，无循环。
- `removeByIds` 批量删除：`selectBatchIds` 一次 `IN` 查出后在**内存循环**校验状态，再 `delete ... in (...)` 批量删子表，**无逐条查库**。
- 唯一的跨表查询是 picking/completion 的 `validate()` 里 `orderMapper.selectById(productionOrderId)` —— **按主键单查，O(1)，非 N+1**。

### 5）大数据量导出：是否有数量限制

**结论：有限制（1000 条），合格但偏保守 ✅/P2**
- 四个 `/exportXls` 均在导出前 `if (service.count() > QUERY_ALL_MAX=1000) throw 异常`，**有效防住了 OOM / 全表导出打爆内存**。
- 但用的是父类普通 `exportXls()`（一次性 `service.list()` 全量加载进内存再写 Excel），**1000 条上限是为了适配这种全量加载**。父类其实提供了 `exportXlsForBigData()`（`IExcelExportServer` 分批分页导出，可支撑万级），**本模块未启用**。
- `/queryAll` 同样有 1000 条上限兜底，合格。
- **建议**：上限由 1000 提升 + 切换 `exportXlsForBigData` 分批导出，兼顾"大数据量可用"与"内存安全"。

### 6）关联查询：领料/入库关联订单效率 + 累计数量校验 SQL

**关联订单查询 —— 按主键高效，但外键无索引（P1）⚠️**
- picking/completion 保存时 `orderMapper.selectById(productionOrderId)` 按**主键**查订单，高效 ✅。
- **但反向"按订单查其所有领料单/入库单"的场景**（如订单详情联查、订单进度统计）只能 `WHERE production_order_id = ?`，而 `c_mes_production_picking.production_order_id` 与 `c_mes_completion_receipt.production_order_id` **均无索引**，订单下的领料/入库记录一多即为全表扫描。

**累计数量校验 SQL —— 本模块未做全表 SUM，但也因此存在业务缺口（P2）ℹ️**
- **性能视角是好的**：picking 的 `validate()` 只校验"订单状态是否草稿"，completion 只校验"本次入库数量 ≤ 订单计划数量"（`item.receiptQty > order.planQty`），**都没有 `SELECT SUM(quantity) ... GROUP BY` 的累计校验 SQL**，因此不存在"每次保存全表 SUM"的性能杀手。
- **但需提示（属功能正确性而非性能）**：completion 仅比较"单次入库 vs 计划总量"，**未校验"历史累计已入库 + 本次 ≤ 计划"**，可超计划反复入库；picking 同样无"累计领料 vs BOM 应领用量"校验。若后续补这块业务校验，**切忌用"每次全表 SUM"**，应：
  - 方案 A（推荐）：在订单/物料上加**冗余累计字段**（如 `c_mes_production_order.completed_qty` 已存在，领料侧可加 `picked_qty`），保存时 `UPDATE ... SET xxx = xxx + ?` 原子累加，校验读冗余字段（O(1)）；
  - 方案 B：若坚持实时 SUM，务必先给 `production_order_id` 建索引，把 SUM 收敛到"该订单的少量行"，而非全表。

## 三、风险清单（按优先级）

### P0 —— 致命（先修这个，否则索引分析无意义）

| # | 风险 | 位置 | 说明 |
|---|---|---|---|
| P0-1 | **表名映射不一致，picking/completion 指向错误表** | `MesProductionPicking`/`MesCompletionReceipt` 实体 `@TableName("mes_production_picking")`/`@TableName("mes_completion_receipt")`；`MesProductionPickingMapper`/`MesCompletionReceiptMapper` 注解 SQL 用 `mes_production_picking`/`mes_completion_receipt`；而建表 SQL 是 `c_mes_production_picking`/`c_mes_completion_receipt` | 实体与 Mapper 均缺 `c_` 前缀（bom/order 用的是带 `c_` 的正确表名）。后果：这两套功能实际打向一张**未建表/未建索引**的表，运行即报表不存在或落到无索引的旧表，所有查询/写入性能与正确性都无法保证。**必须先统一表名（实体 `@TableName` + Mapper 注解 SQL 全部对齐到 `c_mes_*`），本报告其余针对这两表的索引建议才有落地前提。** |

### P1 —— 高（数据量上来即出问题）

| # | 风险 | 位置 | 影响 | 修复建议 |
|---|---|---|---|---|
| P1-1 | **外键 `production_order_id` 无索引** | `c_mes_production_picking`、`c_mes_completion_receipt` 建表 SQL | "按订单查领料单/入库单"、订单进度统计全表扫描 | `ALTER TABLE ... ADD INDEX idx_picking_order_id(production_order_id); ADD INDEX idx_completion_order_id(production_order_id);` |
| P1-2 | **主子表保存逐条 INSERT** | `MesBomServiceImpl.saveItems`、`ProductionPickingServiceImpl.saveItems`、`CompletionReceiptServiceImpl.saveItems` | BOM 几百行时保存数百毫秒~秒级，N 次网络往返 | 改用 MyBatis-Plus `IService.saveBatch(list)` 或 `insertBatch`（JDBC `rewriteBatchedStatements=true`），把 N 条合并为分批批量 INSERT |
| P1-3 | **编辑"先删后插"写放大** | 三个 `updateWithItems` | 一次编辑 = 批量 DELETE + N 次单条 INSERT，页分裂/碎片 | 配合 P1-2 改批量插；更优是"差异比对"（只插新增、只删移除、只更新变更），避免全量删插 |
| P1-4 | **常用筛选/排序字段无索引** | `c_mes_production_order(status,create_time,product_id,bom_id)`、`c_mes_bom(status,create_time)`、picking/completion `(status,create_time)` | 列表按状态筛选 + `orderByDesc(create_time)` 排序在大表上 filesort + 扫表 | 建 `(status, create_time)` 复合索引；`create_time` 单列索引支撑默认排序 |
| P1-5 | **String 字段默认 `LIKE '%..%'` 模糊查全表扫描** | 四列表 `QueryGenerator.initQueryWrapper`，`code`/`remark` 等 | 关键字搜索无法走索引，数据量大必慢 | 对 `code` 等精准字段用 `@QueryField(queryType=EQ)` 或改前缀匹配 `LIKE 'kw%'`（可走 `uk_xxx_code` 索引）；`remark` 类长文本考虑全文索引或不参与模糊查 |

### P2 —— 中（体验/扩展性）

| # | 风险 | 位置 | 影响 | 修复建议 |
|---|---|---|---|---|
| P2-1 | **导出仅 1000 条上限，未启用分批导出** | 四 `/exportXls` 用普通 `exportXls`（全量加载内存） | 业务数据超 1000 即导不出，硬阻断 | 切换父类 `exportXlsForBigData()`（`IExcelExportServer` 分页分批），上限提至万级 |
| P2-2 | **缺 Excel 导入功能（且无逐条风险但需注意主子表）** | 四 Controller 均未暴露 `/importExcel` | 业务无法批量初始化 BOM/订单 | 开放导入时：主表走基类 `saveBatch`；BOM 子表需自行级联批量插；大文件关闭 AutoPoi `needSave` |
| P2-3 | **累计数量校验缺失（业务正确性，非性能）** | `CompletionReceiptServiceImpl.validate`、`ProductionPickingServiceImpl.validate` | 可超计划入库/无累计领料控制 | 补校验时用**冗余累计字段原子累加**（读 O(1)），勿用每次全表 SUM；若实时 SUM 先建 `production_order_id` 索引 |
| P2-4 | **`selectDeletedByCode` 逻辑删除复用查全列** | 四 Mapper `@Select("SELECT * ... WHERE code=? AND del_flag=1")` | `SELECT *` 回表 + 无法覆盖索引 | 改 `SELECT id, create_by, create_time`（resurrect 只需这几列），可命中 `uk_xxx_code` 覆盖索引免回表；picking/completion 该 SQL 还缺 `LIMIT 1`（bom/order 有），建议补上 |

## 四、优先修复路线（给开发的落地顺序）

1. **（P0-1）先统一 picking/completion 表名**（实体 `@TableName` + Mapper SQL 加 `c_` 前缀）——这是一切的前提。
2. **（P1-1/P1-4）补索引**：`production_order_id`（两张表）、`(status, create_time)` 复合索引、`create_time` 单列。一条 `ALTER` 即可，收益立竿见影。
3. **（P1-2/P1-3）主子表写优化**：`saveItems` 改 `saveBatch` 批量插；编辑改差异比对，消除先删后插写放大。
4. **（P1-5）收敛模糊查询**：`code` 改等值/前缀匹配，避免双侧 `LIKE`。
5. **（P2-1）导出升级**：切 `exportXlsForBigData` 分批导出，放宽 1000 条限制。
6. **（P2-3）补累计校验**：用冗余字段原子累加而非全表 SUM。

## 五、量化预估（供压测基线参考）

| 场景 | 现状 | 数据量阈值（开始明显劣化） | 优化后目标 |
|---|---|---|---|
| 列表按状态+时间排序 | 无索引 filesort | ~5 万行 | 走复合索引，10 万级 < 100ms |
| 按订单查领料/入库单 | 外键无索引全表扫 | ~1 万行单据 | 走索引，毫秒级 |
| BOM 保存（300 子项） | 300 次单条 INSERT | 单次即 ~500ms-1s | saveBatch 分批，< 150ms |
| BOM 编辑（300 子项） | 删 300 + 插 300 | 单次即 ~1s+，碎片累积 | 差异比对后批量，< 200ms |
| code 关键字搜索 | `LIKE '%kw%'` 全表扫 | ~5 万行 | 前缀匹配走索引，< 50ms |

> 注：以上为基于 InnoDB 一般经验的量级预估，非实机压测值；建议以 10 万级订单 / 30 万级单据 / 单 BOM 500 子项为基线做一轮真实压测标定。
