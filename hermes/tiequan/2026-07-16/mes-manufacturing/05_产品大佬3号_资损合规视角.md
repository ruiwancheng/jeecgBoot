## 一、审计结论速览

本模块整体处于"**业务单据录入**"阶段，底层字段（BigDecimal、审计字段、逻辑删除、唯一索引）做得相对规范，**但围绕"钱、量、库存"的核心风控几乎全部缺失**。最严重的问题是：**数量只做了"单次数值合法"校验，完全没有"累计/业务上限"校验**，且**领料与完工入库全程不触碰库存台账**——这在 MES 场景下属于直接的资损与账实不符风险。

| 维度 | 结论 | 最高等级 |
|------|------|----------|
| 1) 数量校验 | 完工入库仅校验单次≤计划量，**无累计校验**（同类问题 e84c96d 已在采购模块修复，本模块漏改）；领料**完全无 BOM 标准用量校验** | **P0** |
| 2) 库存联动 | 领料不扣库存、完工入库不增库存，**库存台账(purchase/ledger)与本模块完全无调用** | **P0** |
| 3) 数据一致性 | 删除订单/BOM **不检查是否已被领料单/入库单/订单引用**，导致悬空 | **P1** |
| 4) 审计追溯 | 创建/修改人字段齐全，但关键操作（入库、领料）**无状态流转、无审核留痕、无操作日志** | **P1** |
| 5) 价格金额 | 数量用 BigDecimal（正确），但**前端 InputNumber 用 JS number 浮点**，且本模块无金额字段 | **P2** |

## 二、P0 风险（直接资损 / 必须立即修复）

### P0-1 完工入库缺少"累计入库量"校验，可超计划多入库【数量校验】

**位置**：`completion/service/impl/CompletionReceiptServiceImpl.java` `validate()` 方法（第 123-132 行）

**现状代码**：
```java
if (order.getPlanQty() != null && item.getReceiptQty().compareTo(order.getPlanQty()) > 0)
    throw new JeecgBootException("第" + (i+1) + "行入库数量不能超过计划数量(" + order.getPlanQty() + ")");
```

**问题**：只校验了"**本次单张入库单**某一行的入库数量 ≤ 订单计划数量"，**没有汇总同一生产订单的历史入库记录**。

**攻击/资损场景**：
- 订单 A 计划生产 100 件。
- 第 1 张入库单入 100 件（校验通过，100 ≤ 100）。
- 第 2 张入库单再入 100 件（**依然校验通过**，因为只比单次 100 ≤ 100）。
- 结果：同一订单累计入库 200 件，**超出计划 100 件**，仓库实物与账务全部失真，直接造成库存虚增 / 成本虚增的资损。

**重要佐证（同类问题已在别处修复，本模块漏改）**：
提交 `e84c96d`「P0-004 累计历史入库量校验——防止同一订单多次入库超量」**只修了采购模块** `purchase/receipt/MesPurchaseReceiptServiceImpl.java`，其修复方式是：
> 汇总同订单+同物料所有历史入库记录，校验 (历史总量+本次) ≤ 采购量；编辑时排除自身单据。

**本模块（manufacturing/completion）存在完全相同的缺陷，但该修复并未同步过来。** 这是典型的"修了一个、漏了一片"。

**修复建议**：
- 参照 `e84c96d` 采购模块的写法，在 `validate()` 中：
  1. 按 `productionOrderId` 查出该订单所有非删除入库单（编辑时 `ne(id, 自身ID)` 排除自身）；
  2. 汇总这些单据的明细，按 `materialId` 得到 `historyQtyMap`；
  3. 逐行校验 `historyQty + 本次receiptQty ≤ order.planQty`，超限则报"累计入库量(X)超过计划数量(Y)，历史已入库 Z"。
- 注意明细行 `materialId` 与订单 `productId` 的对应关系（当前未校验入库物料必须是订单产品，见 P1-3）。

### P0-2 生产领料完全无 BOM 标准用量校验，可无限超领【数量校验】

**位置**：`picking/service/impl/ProductionPickingServiceImpl.java` `validate()` 方法（第 112-131 行）

**现状**：领料校验仅做了：
- 数量非空且 > 0；
- 订单存在、订单为草稿状态、领料仓库非空。

**完全缺失**：
- 没有读取订单关联的 BOM（订单有 `bomId` 字段，但领料时根本不查）；
- 没有计算"BOM 标准用量 = 子项 quantity × 计划数量(或考虑 lossRate 损耗率)"；
- 没有汇总该订单的"历史累计领料量"；
- 因此**任何物料、任何数量都能领**，哪怕领的物料根本不在 BOM 里。

**资损场景**：
- 订单生产 1 台设备，BOM 标准用料是螺丝 4 颗，但可领 40000 颗；或领一颗与 BOM 无关的贵重芯片。
- 物料被大量超领流出，库存被掏空，且无任何拦截 → **直接物料资损**。

**修复建议**：
1. 通过 `order.getBomId()` 查出 BOM 及子项（`MesBomItem`，含 `quantity` 用量、`lossRate` 损耗率）；
2. 计算每个子项物料的"应领上限 = BOM用量 × 订单计划数量 × (1+损耗率)"；
3. 汇总该订单历史领料量（编辑时排除自身），校验 `历史累计 + 本次 ≤ 应领上限`；
4. 校验领料物料必须存在于 BOM 子项中（或明确的替代料 `isSubstitute` 白名单），否则拦截。

### P0-3 领料不扣库存、完工入库不增库存，库存账实完全脱节【库存联动】

**位置**：
- `picking/service/impl/ProductionPickingServiceImpl.java`（整个 save/update/remove 流程）
- `completion/service/impl/CompletionReceiptServiceImpl.java`（整个 save/update/remove 流程）

**现状**：
- 全模块（manufacturing）搜索**没有任何对库存台账的调用**。库存台账 `MesInventoryLedger` 仅存在于 `purchase/ledger/`，只被采购模块使用。
- 生产领料保存后，**原材料库存没有扣减**；
- 完工入库保存后，**产成品库存没有增加**；
- 删除/修改领料单、入库单时，也**没有反向冲销库存**。

**问题判定**：这是**业务设计漏洞**（除非产品定位就是"纯单据登记、库存靠人工另一本账"，但即便如此，系统内采购入库会进台账、生产出库/完工却不进台账，**台账本身已失去完整性**，账实必然对不上）。

**资损场景**：
- 采购入库 1000 件原料进台账 → 生产领料 1000 件做工单，但台账不扣 → 台账显示还有 1000 件，实际已领空 → 再据"账面有货"重复采购/重复承诺交付 → **资金积压或违约**。
- 完工不入库 → 成品账上无货 → 销售环节无法正确发货。

**修复建议**（需产品先确认库存模型）：
- 明确库存联动的触发点：建议在"单据审核/确认"动作时（而非草稿保存时）进行库存增减；
- 领料：对 `MesInventoryLedger` 做**出库**记录并扣减对应仓库物料库存；
- 完工入库：做**入库**记录并增加对应仓库成品库存；
- 删除/红冲单据时生成反向流水，保证可追溯、可回滚；
- 库存操作与单据保存放在**同一事务**，并加库存充足性校验（领料量 ≤ 当前可用库存）。

## 三、P1 风险（数据一致性 / 审计合规）

### P1-1 删除订单不检查是否已有领料/入库记录，产生数据悬空【数据一致性】

**位置**：`order/service/impl/ProductionOrderServiceImpl.java` `removeById()`(第54行) / `removeByIds()`(第57-64行)

**现状**：删除订单仅校验 `status == "1"`（草稿），**不检查该订单是否已被领料单、完工入库单引用**。

**问题**：草稿订单也可能已经建过领料单/入库单（因为领料/入库校验的是"订单为草稿"）。删除订单后，`mes_production_picking.production_order_id`、`mes_completion_receipt.production_order_id` 成为**指向已删除订单的悬空外键**，单据查询、统计、对账全部错乱。

**修复建议**：删除订单前，校验是否存在引用它的领料单或入库单（未删除的），存在则禁止删除并提示"该订单已存在领料/入库记录，请先处理相关单据"。

---

### P1-2 删除 BOM 不检查是否被生产订单引用，产生数据悬空【数据一致性】

**位置**：`bom/service/impl/MesBomServiceImpl.java` `removeWithItems()`(第85行) / `removeByIds()`(第95-105行)

**现状**：删除 BOM 仅校验 `status == "1"`，**不检查是否有生产订单的 `bom_id` 指向它**。

**问题**：删除被引用的 BOM 后，订单的 `bomId` 悬空；后续若想按 BOM 领料/算成本，取不到 BOM 明细，业务中断。

**修复建议**：删除 BOM 前，校验 `c_mes_production_order` 中是否存在引用该 BOM 且未删除的订单，存在则禁止删除。

---

### P1-3 完工入库未校验"入库物料必须属于订单产品"，可张冠李戴【数据一致性】

**位置**：`completion/service/impl/CompletionReceiptServiceImpl.java` `validate()`（第 123-132 行）

**现状**：明细行只校验 `materialId` 非空，**不校验它等于订单的 `productId`**（或订单产品的合法范围）。完工入库的本质应是"该订单的产成品入库"，但目前可挂任意物料 ID，把别的料入到本订单头上，数量统计与成本归集全错。

**修复建议**：校验每行 `materialId` 与 `order.getProductId()` 一致（或产品约定的可入库物料集合），不一致则拦截。

---

### P1-4 关键操作（入库/领料）无状态流转、无审核留痕【审计追溯】

**位置**：两个 Service 的 `saveWithItems()` / `updateWithItems()`

**现状**：
- 保存时 `entity.setStatus("1")`，**强制写死为"草稿"**；
- SQL 字典里定义了完整状态（完工入库：1草稿/2已入库；领料：1草稿/2已审核出库；订单：1~7 完整状态机），但**代码里没有任何把状态从"1"推进到"2"的动作**，也没有审核接口、没有审核人/审核时间字段；
- 也就是说单据永远停在草稿，"已入库""已审核"状态是**死数据**，无法区分"录入中"与"已生效"，更谈不上"谁在什么时候把货入进/领出了库"的审计轨迹。

**审计字段本身**：`createBy/createTime/updateBy/updateTime` 四张主表+明细表均有，且 `saveItems()` 会填充（明细在更新场景走"先删后插"，**明细的历史创建人会被重置**，见下）。

**修复建议**：
- 增加"提交/审核/入库确认"动作接口，推进状态机并记录 `auditBy/auditTime`；
- 对"入库确认""领料出库"等关键动作写操作日志（操作人、时间、单据号、数量、前后库存）；
- 修复明细更新"先删后插"导致 `createBy/createTime` 被重置的问题（编辑时应保留原有创建痕迹，或改为增量更新）。

---

### P1-5 主从表 del_flag 不一致，逻辑删除可能失效或误删【数据一致性】

**位置**：
- 实体：`MesProductionPickingItem`、`MesCompletionReceiptItem` 均带 `@TableLogic private Integer delFlag;`
- SQL DDL：`V7.0.2` 的 `c_mes_production_picking_item`、`V7.0.3` 的 `c_mes_completion_receipt_item` **均没有 `del_flag` 列**。

**问题**：实体声明了逻辑删除字段，但明细表 DDL 没有该列。MyBatis-Plus 逻辑删除会尝试更新 `del_flag`，**列不存在将直接 SQL 报错**（或在某些静默配置下行为异常）。主表有 `del_flag`、明细没有，主从删除行为也不一致（Service 里明细是物理 `delete`）。

**修复建议**：DDL 为两张明细表补齐 `del_flag INT DEFAULT 0`，并统一主从均为逻辑删除（或明确明细物理删除、去掉实体 `@TableLogic`）。

---

### P1-6 表名前缀不一致，存在"建了A表、用B表"的隐患【数据一致性 · 待确认】

**位置**：
- picking / completion 的实体 `@TableName` 与 Mapper SQL 用的是 **`mes_production_picking` / `mes_completion_receipt`**（无 `c_` 前缀）；
- 而 SQL DDL（V7.0.2 / V7.0.3）建的是 **`c_mes_production_picking` / `c_mes_completion_receipt`**（有 `c_` 前缀）；
- 对比 order/bom：实体、Mapper、DDL 三处**统一用 `c_` 前缀**，唯独 picking/completion 两张表前缀错位。

**问题**：若 Flyway 实际执行了 V7.0.2/V7.0.3，则数据库里是 `c_` 前缀表，而代码访问的是无前缀表 → **运行期报表不存在**；反之若数据库里是无前缀表，则 DDL 脚本无效。无论哪种，都是必须核实的隐患。（注：此点需结合实际库表确认，属"只查不改"范畴，如实上报。）

**修复建议**：统一 picking/completion 的实体、Mapper、DDL 三处表名前缀（与 order/bom 保持一致用 `c_`），并核对线上实际表名。

## 四、P2 风险（精度 / 健壮性）

### P2-1 数量字段前端用 JS number（浮点），存在精度丢失风险【价格金额/精度】

**位置**：
- 后端：数量字段（`planQty/receiptQty/quantity/lossRate`）均为 `BigDecimal`，DDL 为 `DECIMAL(18,4)` —— **正确**。
- 前端：`CompletionReceiptDrawer.vue`、`PickingDrawer.vue` 的 `InputNumber` 绑定的是普通 JS number，`(v:number)`，金额/数量经 JSON 序列化传输。

**问题**：本模块**无单价/金额字段**，故无直接金额精度问题；但数量（尤其 4 位小数）经 JS 浮点往返，极端值（如 0.0001、超大数）可能出现浮点尾差，最终以带误差数值落库。

**修复建议**：前端数量录入限制小数位（`:precision="4"`），关键数量以字符串传输或后端 `BigDecimal` 直接接收并 `setScale(4)` 归一，避免浮点中间态。

---

### P2-2 唯一索引依赖 (code, del_flag)，逻辑删除复用单号有并发/脏数据边角风险【健壮性】

**位置**：四张主表 `UNIQUE INDEX uk_xxx_code (code, del_flag)` + Service 的 `selectDeletedByCode` + `resurrect` 复活逻辑。

**现状**：删除的单据说 `del_flag=1`，新增同单号时先查"是否有未删除同号"再"复活已删同号记录"。逻辑可行，但：
- `del_flag` 只有 0/1 两个值，**同号被删除多次会产生多条 del_flag=1 的记录**，`uk(code,del_flag)` 对 (code,1) 也会冲突 → 二次删除同号单会触发唯一键冲突；
- "先 selectCount 再 insert"存在并发窗口，虽用 `DuplicateKeyException` 兜底（好），但 resurrect 路径无并发保护。

**修复建议**：唯一索引改为只对 `code`（配合删除时把 code 改写为 `code_删除时间戳`），或保留现状但明确"同号仅允许删除一次"的限制并加并发测试。

---

### P2-3 数量上限无区间校验，极端大值可入库【健壮性】

**位置**：各 `validate()` 仅校验 `> 0`，未校验上限。

**说明**：入库单 P0-1 已要求"≤计划量"形成自然上限；但领料在未引入 BOM 校验前，数量无任何上界，可录入天文数字。引入 P0-2 的 BOM 上限校验后即可覆盖，此项随之消解。

## 六、给产品的一句话总结

> 本模块把"单据能录进去"做出来了，但**"录进去的数量对不对、货有没有真的进出库"这两件最值钱的事目前是裸奔状态**：完工入库可超计划反复入、领料可无视 BOM 随意超领、且这两个动作都不碰库存台账。建议优先补齐 P0-1/P0-2 的累计数量防线（可直接抄采购模块 e84c96d 的作业），并与产品确认库存联动模型后落地 P0-3，否则账实不符和物料资损只是时间问题。
