## 二、P0 风险（必须立即修复）

### P0-1 并发下“先查后插”导致唯一约束被击穿或产生脏数据

**涉及文件：**
- `MesBomServiceImpl.java` L46-62
- `ProductionOrderServiceImpl.java` L29-38
- `ProductionPickingServiceImpl.java` L51-67
- `CompletionReceiptServiceImpl.java` L51-67

**问题描述：**
四个 ServiceImpl 均采用“先 `selectCount` 查重 → 再 `selectDeletedByCode` 复活/插入”的非原子模式。数据库唯一索引为 `(code, del_flag)` 复合唯一索引，这意味着：

1. **场景 A：并发新增同 code**  
   线程 1 和线程 2 同时通过 `selectCount` 校验（都看到 0），然后同时执行 `super.save()`。其中一个会触发 `DuplicateKeyException` 并提示“编号已存在”，这是**可接受**的兜底。但如果两个线程都进入 `old != null` 分支（即该 code 曾被删除），会同时执行 `resurrect` + `itemMapper.delete` + `saveItems`，由于 `resurrect` 的 SQL 带 `del_flag=1` 条件，只有一条能成功，另一条会**静默更新 0 行**，随后继续执行 `saveItems` 导致**子表重复插入**（因为旧子项已被先删，但两个事务都会插入新子项）。

2. **场景 B：并发“删除+新增”同 code**  
   线程 1 删除某 code（`del_flag=1`），线程 2 同时新增同 code。线程 2 的 `selectCount` 可能在线程 1 提交前看到旧记录（del_flag=0），也可能在线程 1 提交后看到 0。若线程 2 进入 `selectDeletedByCode` 时线程 1 尚未提交，会查不到 `old` 而执行 `super.save()`，最终与线程 1 的删除产生**主键冲突或逻辑混乱**。

**修复建议：**
- 将“查重-复活/插入”改为数据库层原子操作：使用 `INSERT ... ON DUPLICATE KEY UPDATE`（MySQL）或 `MERGE INTO`，把唯一索引改为 `code` 单列唯一（不含 `del_flag`），已删除记录用 `version` 或 `id` 区分历史。
- 若保留现有复合索引，必须在 `selectDeletedByCode` 上加 `FOR UPDATE` 行锁，并确保事务隔离级别为 `REPEATABLE READ` 以上。
- 为 `saveWithItems`/`updateWithItems` 增加分布式锁（key = code），防止同一 code 并发操作。

### P0-2 状态机形同虚设：仅拦截草稿状态，后续状态无流转控制

**涉及文件：**
- `MesBomServiceImpl.java` L126-137
- `ProductionOrderServiceImpl.java` L76-85
- `ProductionPickingServiceImpl.java` L133-144
- `CompletionReceiptServiceImpl.java` L135-146

**问题描述：**
所有 `checkStatus` 方法仅校验 `status != "1"`（草稿）时禁止编辑/删除，但**没有任何状态流转方法**（如审核、下达、取消、关闭）。这意味着：

- **BOM**：状态只有 1(草稿)/2(生效)/3(失效)，但代码里没有任何地方将状态从 1 改为 2 或 3。`saveWithItems` 和 `updateWithItems` 强制 `setStatus("1")`，**即使用户想提交审核，保存后仍是草稿**。BOM 生效后无法被新订单引用的问题无法暴露，因为 BOM 永远到不了生效状态。
- **生产订单**：状态字典定义了 1-7（草稿/已审核/已下达/执行中/已完工/已关闭/已取消），但 Service 里只有草稿校验。**订单取消后（status=7）仍可被领料单/入库单引用**，因为 `ProductionPickingServiceImpl.validate()` 只校验 `!"1".equals(order.getStatus())`，即“仅草稿状态可领料”。这意味着已审核、已下达、执行中的订单反而不能领料，与业务逻辑完全相反。
- **领料单/入库单**：同样只有草稿/已审核（或已入库）两态，但无状态流转入口。

**修复建议：**
- 补充状态机枚举与流转校验，例如 `OrderStatus` 定义合法流转路径：`1→2→3→4→5→6/7`。
- 修正领料/入库的订单状态校验：领料应允许 `3(已下达)`、`4(执行中)`；入库应允许 `4(执行中)`、`5(已完工)` 前。
- 增加 `cancel`/`close`/`audit` 等状态变更接口，并在这些接口中做前置校验（如已领料的订单不可直接取消）。

### P0-3 主子表不一致：子表无逻辑删除，主表删除后子表物理残留

**涉及文件：**
- `MesBomServiceImpl.java` L85-91
- `ProductionPickingServiceImpl.java` L90-96
- `CompletionReceiptServiceImpl.java` L90-96
- `MesBomItem.java`（无 `@TableLogic`）
- `MesProductionPickingItem.java` L69-71
- `MesCompletionReceiptItem.java` L69-71
- SQL：`V7.0.0__mes_bom_init.sql`、`V7.0.2__mes_production_picking_init.sql`、`V7.0.3__mes_completion_receipt_init.sql`

**问题描述：**
- **BOM 子表**：`MesBomItem` 实体**没有 `@TableLogic` 注解**，数据库表 `c_mes_bom_item` 也**没有 `del_flag` 字段**。`removeWithItems` 执行 `itemMapper.delete(delQw)` 是**物理删除**，`updateWithItems` 也是先物理删除再插入。这导致：
  1. 主表逻辑删除后，子表记录被物理删除，看似无残留，但**若删除主表时发生并发插入子表**（见 P0-1），会出现主表已删、子表新插入的脏数据。
  2. 无法追溯历史 BOM 版本，物理删除后审计困难。
- **领料/入库子表**：虽然有 `@TableLogic` 和 `del_flag`，但 `removeWithItems` 调用 `itemMapper.delete(delQw)` 时，MyBatis-Plus 的 `delete` 方法配合 `@TableLogic` 会执行**逻辑删除**（UPDATE del_flag=1），这是正确的。但 `updateWithItems` 同样先逻辑删除再插入，会产生**大量已删除的历史子项记录**，长期运行导致子表膨胀。

**修复建议：**
- 为 `c_mes_bom_item` 增加 `del_flag` 字段和 `@TableLogic` 注解，统一主子表删除策略。
- 所有子表改为逻辑删除，主表删除时同步逻辑删除子表（带 `del_flag`）。
- 若必须物理删除，需在 Service 层增加“主表存在性校验”后再删子表，防止脏数据。

### P0-4 BOM 失效后仍可被新订单引用，且订单与 BOM 无强制关联

**涉及文件：**
- `ProductionOrderServiceImpl.java` L66-74
- `OrderDrawer.vue` / `order.data.ts` L26

**问题描述：**
- `order.data.ts` 中 `bomId` 字段为 `Input`（普通输入框），**非必填**，用户可随意填写任意字符串，也可留空。
- `ProductionOrderServiceImpl.validate()` 只校验 `planQty > 0` 和日期前后关系，**不校验 `bomId` 是否存在、是否有效、是否过期**。
- 即使 `bomId` 填写了真实 BOM ID，也没有任何校验该 BOM 的状态（草稿/生效/失效）或 `expiryDate` 是否已过。

**修复建议：**
- 前端将 `bomId` 改为 `JSearchSelect`（绑定 `c_mes_bom` 字典），必填，且只能选状态为“生效”的 BOM。
- 后端 `validate()` 增加：若 `bomId` 非空，必须查询 BOM 存在且 `status='2'`（生效）且 `expiryDate` 为空或大于当前日期。

## 三、P1 风险（高优先级修复）

### P1-1 前端“保存”按钮无防重复提交机制

**涉及文件：**
- `BomDrawer.vue` L78-88
- `OrderDrawer.vue` L35-45
- `PickingDrawer.vue` L70-80
- `CompletionReceiptDrawer.vue` L74-84

**问题描述：**
四个 Drawer 的 `handleSubmit` 均通过 `setDrawerProps({ confirmLoading: true })` 显示 loading，但：
- 用户在网络延迟时**连续快速点击“确定”**，可能触发多次 `saveOrUpdateXxx` 请求。
- 后端虽有 `selectCount` 查重，但在并发下仍可能产生重复数据（见 P0-1）。
- 没有 `disabled` 状态绑定，也没有请求级别的幂等 key（如 UUID）。

**修复建议：**
- 前端在 `handleSubmit` 入口增加 `if (submitting) return; submitting = true;` 标志位。
- 为每次表单打开生成唯一 `requestId`，提交时携带，后端基于 `requestId` 做幂等去重（Redis SETNX）。

### P1-2 数量边界校验存在绕过空间

**涉及文件：**
- `BomDrawer.vue` L13：`:min="0.01"`，但 `@change` 事件在输入非法值时可能不触发
- `PickingDrawer.vue` L13：同上
- `CompletionReceiptDrawer.vue` L13、L16：`planQty` 的 `:min="0"`，允许输入 0；`receiptQty` 的 `:min="0.01"`
- `MesBomServiceImpl.java` L117-118
- `ProductionOrderServiceImpl.java` L70
- `ProductionPickingServiceImpl.java` L126-127
- `CompletionReceiptServiceImpl.java` L126-129

**问题描述：**
- **BOM 子项数量**：前端 `:min="0.01"`，后端 `quantity <= 0` 拦截。看似完整，但前端 `InputNumber` 的 `@change` 在输入 `-5` 或 `0` 时，如果用户直接失去焦点而非按回车，`change` 事件可能不触发，值仍保持非法，但提交时后端会拦截。这是**可接受**的，但用户体验差（提交后才报错）。
- **完工入库 `planQty`**：前端 `:min="0"`，允许 0；后端 `CompletionReceiptServiceImpl.validate()` **不校验 `planQty`**，只校验 `receiptQty`。这意味着入库明细可以保存 `planQty=0` 或负数，与订单计划数量脱节。
- **领料数量**：前端 `:min="0.01"`，后端 `quantity <= 0` 拦截。但**未校验领料数量是否超过 BOM 用量 × 订单计划数量**，可能超领。

**修复建议：**
- 前端所有数量字段统一使用 `:min="0.01"`，并在表单提交前增加 `validate()` 级别的自定义校验。
- 后端 `CompletionReceiptServiceImpl.validate()` 增加 `planQty > 0` 校验。
- 后端领料单增加“累计领料数量 ≤ BOM 用量 × 订单计划数量”校验。

### P1-3 入库数量上限校验不严谨

**涉及文件：**
- `CompletionReceiptServiceImpl.java` L128-129

**问题描述：**
`receiptQty.compareTo(order.getPlanQty()) > 0` 仅校验**单行**入库数量不超过订单计划数量，未校验**多行累计**或**历史累计**入库数量。例如：
- 订单计划 100，第一次入库 60，第二次入库 60，两行分别校验都通过，但累计 120 > 100。
- 同一订单多次创建入库单，没有累计入库数量校验。

**修复建议：**
- 在 `validate()` 中查询该订单历史所有入库单的 `receiptQty` 总和，加上本次提交的总和，不得超过 `planQty`。

### P1-4 订单编号唯一性校验与并发冲突

**涉及文件：**
- `ProductionOrderServiceImpl.java` L29-38

**问题描述：**
与 P0-1 类似，但订单的 `selectDeletedByCode` 在 `old != null` 时会执行 `resurrect`，而 `resurrect` 的 SQL 未在 Mapper 中展示（根据 BOM 推断结构类似）。若并发下两个线程同时复活同一已删除订单，只有一个成功，但 `super.save()` 分支的 `DuplicateKeyException` 兜底可靠。问题在于：**`resurrect` 成功后，`completedQty` 会被重置为 0**（因为 `save()` 中 `entity.setCompletedQty(BigDecimal.ZERO)`），导致历史完工数量丢失。

**修复建议：**
- 复活已删除订单时，保留原有 `completedQty`，或在业务上禁止复活已删除订单，强制使用新编号。

### P1-5 前端编辑时子表数据加载异常被静默吞掉

**涉及文件：**
- `BomDrawer.vue` L62-69
- `PickingDrawer.vue` L54-61
- `CompletionReceiptDrawer.vue` L58-65

**问题描述：**
`queryXxxById` 失败时 `catch (e) { /* fallback */ }` 完全静默，用户看到空白子表但不知原因，可能误操作保存空数据。

**修复建议：**
- 捕获异常后至少 `console.error` 并 `message.error('加载子表数据失败')`。

### P1-6 前端 `removeLine` 保留最后一行，与后端“至少一个子项”校验重复但粒度不一致

**涉及文件：**
- `BomDrawer.vue` L75
- `PickingDrawer.vue` L67
- `CompletionReceiptDrawer.vue` L71

**问题描述：**
前端 `if (items.value.length > 1)` 阻止删除最后一行，后端也校验 `items.isEmpty()`。但前端保护可被绕过（如直接修改 `items` 引用），建议后端保留校验，前端增加提示。

**修复建议：**
- 前端在尝试删除最后一行时 `message.warning('至少保留一行')`。

## 四、P2 风险（建议优化）

### P2-1 字段命名不一致：前端 `isAlternative` vs 后端 `isSubstitute`

**涉及文件：**
- `BomDrawer.vue` L19、L46、L58
- `MesBomItem.java` L30
- `V7.0.0__mes_bom_init.sql` L24

**问题描述：**
前端使用 `isAlternative`，后端实体和数据库使用 `isSubstitute`。由于 JeecgBoot 的 JSON 序列化默认按字段名映射，**前端传的 `isAlternative` 无法自动绑定到 `isSubstitute`**，导致替代料标志永远为 null 或默认值。

**修复建议：**
- 统一命名为 `isSubstitute`，或在前端提交前做字段映射转换。

### P2-2 BOM 生效/失效日期未做先后校验

**涉及文件：**
- `MesBomServiceImpl.java` L107-124
- `bom.data.ts` L25-26

**问题描述：**
未校验 `expiryDate` 是否早于 `effectiveDate`，与生产订单的日期校验（L71-72）不对等。

**修复建议：**
- `validateBom()` 增加：`if (expiryDate != null && effectiveDate != null && expiryDate.before(effectiveDate)) throw ...`

### P2-3 异常提示信息硬编码在代码中，不利于国际化与统一维护

**涉及文件：**
- 四个 ServiceImpl 中所有 `throw new JeecgBootException("...")`

**修复建议：**
- 抽取为常量类或使用 `MessageSource` 支持 i18n。

## 五、总结与修复优先级建议
