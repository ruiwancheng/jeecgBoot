# MES 生产制造模块（mes-manufacturing）架构全局视角审计报告

> 铁拳团成员 4 号：研发风控组 — 架构全局视角
> 审计范围：`jeecg-boot/jeecg-boot-module/project-mes/src/main/java/org/jeecg/modules/mes/manufacturing/`（bom / order / picking / completion 四包，共 26 个 Java 文件）+ `project-mes/db/V7.0.0~V7.0.3` 四份建表 SQL
> 审计方式：只读静态审查，未改动任何代码
> 技术栈基线：JeecgBoot 3.9.2 + Spring Boot 3.5.5 + Java 17 + MyBatis-Plus（jakarta 命名空间）

---

## 一、总体结论

四个子模块呈现出**两种明显不同的代码风格**，应为两轮（或两人）开发拼接而成：

| 维度 | bom / order（A 风格） | picking / completion（B 风格） |
|---|---|---|
| 表名 | `c_mes_bom` / `c_mes_production_order`（带 `c_` 前缀，与 SQL 一致 ✅） | 实体/Mapper 用 `mes_production_picking` / `mes_completion_receipt`，SQL 建的是 `c_mes_production_picking` / `c_mes_completion_receipt`（**不一致 ❌**） |
| 主子表 | BOM 有子表（`MesBomItem`）；order 为单表 | picking / completion 均为主子表 |
| 实体字段 | 简洁（无冗余 name/code 字段） | 冗余 `productionOrderCode`、`warehouseName`、`materialCode`、`materialName` 等 |
| `items` 映射 | `MesBom.items` 用 `transient` | picking/completion 用 `@TableField(exist = false)` |
| 主表 `del_flag` | `c_mes_bom` / `c_mes_production_order` **有** `del_flag` | SQL 有，但实体缺字段（见 P0-2） |

整体分层骨架（controller/service/mapper/entity）是清晰的，未发现 controller 直调 mapper 的硬伤；但存在 **P0 级表名不匹配** 和 **P0 级主子表字段/类型不一致**，属于"跑不起来/插不进数"级别的问题，必须优先修复。

## 二、P0 风险（阻断性，必须立即修复）

### P0-1 picking / completion 实体 `@TableName` 与建表 SQL 表名不一致 —— 运行即报表不存在

**现象**：
- 实体与 Mapper SQL 写的是：`mes_production_picking`、`mes_production_picking_item`、`mes_completion_receipt`、`mes_completion_receipt_item`
- 建表 SQL（V7.0.2 / V7.0.3）建的是：`c_mes_production_picking`、`c_mes_production_picking_item`、`c_mes_completion_receipt`、`c_mes_completion_receipt_item`

**证据**：
- `picking/entity/MesProductionPicking.java:17` → `@TableName("mes_production_picking")`
- `picking/entity/MesProductionPickingItem.java:16` → `@TableName("mes_production_picking_item")`
- `picking/mapper/MesProductionPickingMapper.java:12,15` → `SELECT * FROM mes_production_picking ...` / `UPDATE mes_production_picking ...`
- `completion/entity/MesCompletionReceipt.java:16`、`MesCompletionReceiptItem.java:16`、`MesCompletionReceiptMapper.java:12,15` 同样缺 `c_` 前缀
- `db/V7.0.2__mes_production_picking_init.sql:2,16`、`db/V7.0.3__mes_completion_receipt_init.sql:2,17` → `CREATE TABLE c_mes_production_picking ...`

已用全仓搜索确认：**不存在任何创建 `mes_production_picking` / `mes_completion_receipt`（无 `c_` 前缀）表的脚本**，且 project-mes 全模块（basic/purchase/sales/manufacturing 的 bom、order）统一使用 `c_mes_` 前缀，唯独这 4 个实体例外。

**影响**：picking / completion 两个模块所有 CRUD 上线即报 `Table 'xxx.mes_production_picking' doesn't exist`，功能完全不可用。

**修复建议**（二选一，推荐 A）：
- A. 改实体与 Mapper：`@TableName("c_mes_production_picking")` 等 4 处实体 + 2 处 Mapper 的 `@Select/@Update` 表名，统一加 `c_` 前缀（与全模块约定一致）；
- B. 改 SQL 去掉 `c_` 前缀 —— 不推荐，会破坏 project-mes 统一的 `c_mes_` 命名约定。

### P0-2 picking / completion 主子表实体字段与 SQL 建表字段大面积不一致

#### P0-2a 子表缺 `del_flag`，主表 SQL 有 `del_flag` 但实体/逻辑删除不一致

- `db/V7.0.2:16` `c_mes_production_picking_item`、V7.0.3 `c_mes_completion_receipt_item` **均未建 `del_flag` 列**，但实体 `MesProductionPickingItem.java:69-71`、`MesCompletionReceiptItem.java:69-71` 却声明了 `@TableLogic private Integer delFlag;`
  - 影响：MyBatis-Plus 逻辑删除开启时，对子表的 `delete/update/select` 会自动拼 `del_flag` 条件，SQL 直接报 `Unknown column 'del_flag' in 'where clause'`。
  - 对比：`bom` 子表 `c_mes_bom_item`（V7.0.0:17-28）同样**没有** `del_flag`，其实体 `MesBomItem` 也**没有** `delFlag` 字段 —— 说明正确做法是子表不带逻辑删除（物理删除），picking/completion 子表多画蛇添足地加了 `@TableLogic`。
- 主表方向相反：`c_mes_production_picking`、`c_mes_completion_receipt` SQL **建了** `del_flag` 且实体也有 `@TableLogic`（一致 ✅），但 `resurrect` 逻辑依赖 `del_flag=1` 能查到已删记录（见 P0-2c 子问题）。

#### P0-2b completion 子表 `plan_qty` 字段实体缺失

- `db/V7.0.3:22` `c_mes_completion_receipt_item` 建了 `plan_qty DECIMAL(18,4)`，但实体 `MesCompletionReceiptItem` 只有 `receiptQty`，**没有 `planQty` 字段**。
  - 影响：DB 列成为死字段；且 `CompletionReceiptServiceImpl.validate()` 第 128 行用 `order.getPlanQty()` 做上限校验，而非明细行自己的 `plan_qty`，设计意图（行级计划量）未落地。

#### P0-2c picking/completion 主表实体有而 SQL 没有的冗余字段

- `MesProductionPicking` 实体有 `productionOrderCode`、`warehouseName` 字段（`MesProductionPicking.java:38,46`），Mapper `resurrect` 也 update 了 `production_order_code`、`warehouse_name`，但 `db/V7.0.2` 建表**没有这两列** → resurrect SQL 执行即报 `Unknown column`。
- `MesCompletionReceipt` 同样问题：`productionOrderCode`、`warehouseName`（`MesCompletionReceipt.java:37,45`）在 `db/V7.0.3` 无对应列；另外 SQL 建了 `product_id` 列（V7.0.3:6），实体却无 `productId` 字段。
- `MesProductionPickingItem` / `MesCompletionReceiptItem` 实体的 `materialCode`、`materialName`、`unitId`、`remark` 在建表 SQL 中**均无对应列** → MyBatis-Plus 全字段 insert（`saveItems` 走 `itemMapper.insert(item)`）会报 `Unknown column 'material_code' ...`。

> 说明：B 风格（picking/completion）明显是从某个带冗余快照字段的模板（类似 purchase 模块）复制而来，但建表 SQL 是按精简模型设计的，两者从未对齐。这是与 P0-1 同源的"复制粘贴后未联调"问题。

**修复建议**：以建表 SQL 为准反向裁剪实体（删除 `productionOrderCode/warehouseName/materialCode/materialName/unitId/remark` 及子表 `@TableLogic delFlag`），或以实体为准补 SQL（加列 + 子表 `del_flag`）。**二者必须对齐一次**，建议由模块 owner 确认哪份是"真实需求"，再统一。同时补齐 `MesCompletionReceiptItem.planQty`。

### P0-3 跨模块引用通过 Mapper 直查，而非 Service 接口（服务边界破坏）

任务重点核查项"completion 引用 order 是否通过 service 接口"——**答案是否定的，且 picking 也存在同样问题**：

- `picking/service/impl/ProductionPickingServiceImpl.java:11,33` `@Autowired private MesProductionOrderMapper orderMapper;`，第 116 行 `orderMapper.selectById(entity.getProductionOrderId())`
- `completion/service/impl/CompletionReceiptServiceImpl.java:16,33` 同样 `@Autowired private MesProductionOrderMapper orderMapper;`，第 116 行 `orderMapper.selectById(...)`

**影响**：
1. 绕过 `IProductionOrderService` 可能存在的业务校验/缓存/数据权限切面；
2. order 模块内部表结构或逻辑变更时，picking/completion 被隐性耦合，无法通过接口契约感知；
3. 若未来拆微服务，Mapper 直查无法平滑切换为 Feign 调用。

**修复建议**：改为注入 `IProductionOrderService`，用 `orderService.getById(...)` 替代 `orderMapper.selectById(...)`。在 `IProductionOrderService` 上补充语义化方法（如 `MesProductionOrder checkAndGetDraft(String id)`），把"订单存在且为草稿"这一校验收敛到 order 模块内部。

## 三、P1 风险（结构性/规范性，应尽快修复）

### P1-1 四个模块代码高度重复，未抽任何公共基类/工具类

以下为**逐字符级重复**的代码（四个 ServiceImpl / Controller 中各出现 4 次）：

| 重复代码块 | 出现位置 | 建议抽取 |
|---|---|---|
| `getCurrentUsername()`（Shiro 取登录人，catch 返回 "system"） | 4 个 ServiceImpl 均有（bom:152 / order:87 / picking:159 / completion:161） | 抽到 `mes.common.util.MesAuthUtil` 或公共基类；JeecgBoot 已有 `LoginUser.getCurrentUser()` 可复用 |
| `checkStatus(entity, action)` + `checkStatus(id, action)` 两个重载 | 4 个 ServiceImpl | 抽 `AbstractMesDocServiceImpl<T>` 泛型基类 |
| `saveItems(...)` 主子表明细保存（设 lineNo/审计字段/循环 insert） | bom/picking/completion 三份近乎一致 | 泛型化为 `<M,I> void saveItems(M main, List<I> items, BiConsumer<I,String> fkSetter, BaseMapper<I> itemMapper)` |
| `resurrect`（按 code 查已删→复活）模式 | 4 个 ServiceImpl + 4 个 Mapper 各一份 | Mapper 层可用 `@Select` 模板化；Service 层抽 `saveOrResurrect` 骨架方法 |
| Controller 的 `queryPageList/queryById/add/edit/delete/deleteBatch/queryAll/exportXls` 八件套 | 4 个 Controller 几乎逐行相同（仅权限串/提示语不同） | 抽 `MesBaseController<T, S extends IService<T>>`，权限串用常量或注解模板 |
| `QUERY_ALL_MAX = 1000` 常量 + `count()>MAX` 抛异常 | 4 个 Controller | 收敛到基类常量 |
| `validate(...)` 中"编号非空/长度≤50/备注≤500/数量>0/明细非空/行号回填" | 4 份 | 抽 `MesValidateUtil` 通用校验 + 各模块差异部分保留 |

**评估**：四个模块相似度约 85%，属于"适度抽取收益很大"的情形。建议抽 1 个 `AbstractMesDocServiceImpl`（主子表 CRUD 骨架）+ 1 个 `MesBaseController` + `MesAuthUtil/MesValidateUtil` 两个工具类即可，不必过度设计。当前不抽的后果是：任何一处公共逻辑（如登录人获取、状态校验文案）改一处要同步改 4 份，极易漏改。

---

### P1-2 主子表外键仅有普通索引，无数据库级外键约束，且主子表删除一致性靠应用层保证

- 建表 SQL 中 `c_mes_bom_item.bom_id`、`c_mes_production_picking_item.picking_id`、`c_mes_completion_receipt_item.receipt_id` 均只有 `INDEX idx_item_xxx`，**无 FOREIGN KEY 约束**。
  - 说明：JeecgBoot 系项目通常不加物理外键（靠应用层保证），这一点可接受；但需在报告中明确这是"应用层保证一致性"的既定策略，而非遗漏。
- 应用层保证目前**有缺口**：
  - `MesBomServiceImpl.removeWithItems` / picking / completion 都是"先删子表再删主表"，在同一 `@Transactional` 内，OK ✅；
  - 但 `removeByIds` 批量删除时，子表删除用 `delQw.in(..., list)`，主表用 `super.removeByIds(list)`，若 list 中包含非本模块数据或部分失败，存在主表删了子表没删的窗口（虽在事务内，但逻辑删除主表 + 物理删除子表的混用使回滚语义不一致，见 P1-3）。

### P1-3 主子表删除策略混用：主表逻辑删除（`@TableLogic`）vs 子表物理删除（`itemMapper.delete`）

- 主表 `MesBom`/`MesProductionOrder`/`MesProductionPicking`/`MesCompletionReceipt` 均 `@TableLogic delFlag` → `removeById` 是逻辑删（`UPDATE del_flag=1`）；
- 子表均通过 `itemMapper.delete(qw)` → 物理删（`DELETE FROM`）。
- 影响：
  1. 主表"删除"后子表数据**永久丢失**，若需恢复主表（resurrect 之外的场景）子表已无法找回；
  2. `resurrect` 流程（如 `MesBomServiceImpl:50-59`）在复活主表前**物理删除了旧子表**（`itemMapper.delete`），再插入新子表 —— 逻辑自洽，但进一步坐实"子表无历史"的设计；
  3. 与 P0-2a 呼应：picking/completion 子表实体加了 `@TableLogic` 但 SQL 无列，说明最初想给子表也做逻辑删，做到一半放弃了。
- 建议：明确主子表删除策略并固化——要么主从均逻辑删（子表加 `del_flag` 列），要么主从均物理删（主表去 `@TableLogic`）。当前"主逻辑删 + 子物理删"的混合态需要在文档中写明取舍。

### P1-4 权限编码风格不统一，且与菜单注册存在命名不一致风险

- Controller 权限串：bom 用 `mes:bom:*`，order 用 `mes:productionOrder:*`（驼峰），picking 用 `mes:productionPicking:*`，completion 用 `mes:completionReceipt:*`。
  - JeecgBoot 主流约定为全小写冒号分隔（如 `mes:production:order:list` 或 `mes:production_order:list`），驼峰式权限串（`mes:productionOrder:list`）与系统内其他模块不一致，且 Linux/部分数据库对大小写敏感性不同，存在授权匹配隐患。
- 菜单注册（`MesMenuRegistry.java:74-77`）中组件名 `MesProductionPicking`/`MesCompletionReceipt` 与权限串 `mes:productionPicking:*` 对应，SQL 授权脚本（V7.0.2:37、V7.0.3:39）也按 `mes:productionPicking:%` 授权 —— 三者目前自洽，但与 bom 的 `mes:bom:*` 风格混用。
- 另外 `deleteBatch` 权限（`mes:bom:deleteBatch` 等）在 JeecgBoot 默认权限模型中通常不单列，建议核对菜单 SQL 是否真实下发了 `deleteBatch`/`export` 按钮权限，否则前端按钮会一直隐藏。

### P1-5 `MesProductionOrder` 无子表却承担"完工数量"字段，与 completion 模块存在数据一致性缺口

- `c_mes_production_order.completed_qty`（V7.0.1:8）由谁回写？当前 `CompletionReceiptServiceImpl` 只校验 `receiptQty <= planQty`（按整张订单的 `planQty` 校验，而非累计），**未回写 `completed_qty`**，也未校验"累计入库 ≤ 计划量"。
- 影响：同一订单可多次完工入库，每次都不超过 `planQty` 但累计远超计划，`completed_qty` 永远是 0，订单状态机（字典里定义了 7 态：草稿/已审核/已下达/执行中/已完工/已关闭/已取消）**无任何代码驱动流转**，状态字段实质是死字段。
- 建议：本报告只负责架构视角提示——状态机与数量回写属于业务逻辑缺失，需业务组确认是否本期实现；至少应在 completion 入库时累加回写 `completed_qty` 并按阈值推进订单状态。

## 四、P2 风险（建议优化，不阻断）

### P2-1 命名规范基本符合约定，个别可打磨

- ✅ 符合 JeecgBoot 约定：`IMesBomService`/`MesBomServiceImpl`、`IProductionOrderService`/`ProductionOrderServiceImpl`、`IProductionPickingService`/`ProductionPickingServiceImpl`、`ICompletionReceiptService`/`CompletionReceiptServiceImpl` 均为 `I<X>Service` + `<X>ServiceImpl`；Mapper 均 `<X>Mapper extends BaseMapper<X>`；Controller 均 `extends JeecgController<T, IService>`。
- ⚠️ 命名不一致点：
  - BOM 用了模块前缀 `MesBom`（`IMesBomService`/`MesBomServiceImpl`），而 order/picking/completion 未带 `Mes` 前缀（`IProductionOrderService` 而非 `IMesProductionOrderService`）。同模块内两套命名前缀并存，建议统一（推荐全部带 `Mes` 前缀，与实体类名对齐）。
  - 包名 `bom/order/picking/completion` 为单词式，与类名 `Production*`/`Completion*` 不完全对应（order 包下是 `ProductionOrder`，completion 包下是 `CompletionReceipt`），属可接受的简写，但建议在包级 README 中说明映射。
- ⚠️ `IProductionPickingService`/`ICompletionReceiptService` 显式声明了 `removeByIds(Collection<?>)`（picking:17 / completion:17），而 `IMesBomService` 没有（靠 `IService` 继承）；`IProductionOrderService` 是空接口 `{}`。同类接口的抽象层次应拉齐。

### P2-2 实体日期字段类型与 SQL `DATETIME` 的语义偏差

- 实体中 `effectiveDate/expiryDate/startDate/endDate/pickDate/receiptDate` 均为 `java.util.Date` + `@JsonFormat(pattern="yyyy-MM-dd")`，SQL 为 `DATETIME`。日期语义用 `DATETIME` 存储虽不报错，但建议改 `DATE` 类型或实体注明只取日期部分，避免时分秒脏数据。
- `createTime/updateTime` 用 `DATETIME` + `yyyy-MM-dd HH:mm:ss` ✅ 正常。

### P2-3 `update-begin/end` 注释标记使用过度且格式不统一

- 所有 26 个 Java 文件均以 `//update-begin---author:ruiwancheng---date:2026-07-16---for: MES生产制造-XXX-----------` 开头、以对应 `update-end` 结尾 —— 按 CLAUDE.md 约定，该标记用于"修改痕迹"，而当前是**整文件新增**，把 update-begin/end 当文件头尾版权块用，属于误用（正确做法是仅在"修改已有代码"的代码段包裹）。
- 格式细节：`for:` 后有的有空格（`for: MES生产制造`）有的无；横线数量不统一（`-----------` vs `---`）；`---date:` 前后分隔符有的三个横杠有的两个。虽然不影响运行，但与 CLAUDE.md 中定义的模板（`//update-begin---author:作者 ---date:YYYY-MM-DD  for：【bug号/需求号】修改说明-----------`）不完全一致。
- 建议：新增文件不需要 update-begin/end 包裹；后续增量修改再按规范打点。此条仅规范提示，不强制返工。

### P2-4 jakarta 命名空间使用规范 ✅

- 所有 Controller 均 `import jakarta.servlet.http.HttpServletRequest;`（如 bom:9、order:8、picking:8、completion:8），无 `javax.servlet` 残留；Swagger 注解用 `io.swagger.v3.oas.annotations.*`（OpenAPI v3）✅；未发现 `springfox` 旧依赖。符合 Spring Boot 3.x 基线。

### P2-5 其他零散项

- `MesBom.items` 用 `transient` 修饰（`MesBom.java:41`），而 picking/completion 用 `@TableField(exist = false)`。`transient` 会导致 JSON 序列化丢失 items（Jackson 默认不序列化 transient），**`queryWithItems` 返回的 BOM 明细前端可能拿不到**——建议 BOM 也改 `@TableField(exist = false)`（picking/completion 的写法是对的）。此条介于 P1/P2 之间，若前端 BOM 明细展示异常则升 P1。
- `MesProductionOrder.bomId` 无 `@Dict` 注解（`MesProductionOrder.java:32`），前端展示 BOM 名称需自行联查；`@Excel(name="BOM")` 导出的是 ID 而非名称。
- `CompletionReceiptServiceImpl.validate()` 第 128 行用整张订单 `planQty` 校验每行 `receiptQty`，多行明细时每行都允许 ≤ 计划量，累计可超计划——业务校验逻辑漏洞（与 P1-5 同源）。
- 四个 ServiceImpl 中 `(Collection<String>) (Collection<?>) list` 的强转（如 bom:97、picking:102、completion:102）有未检查转换警告，建议加 `@SuppressWarnings("unchecked")` 或改泛型签名。
- `selectDeletedByCode` 在 bom/order 用 `LIMIT 1`（`MesBomMapper:10`），picking/completion 未加 LIMIT（`MesProductionPickingMapper:12`），若历史删除多条同 code 记录会返回多行（MyBatis 取首行或报 TooManyResults），建议统一加 `LIMIT 1`。
- 索引设计：主表 `uk_xxx_code(code, del_flag)` 联合唯一索引支持"同 code 逻辑删后可重建"的 resurrect 模式 ✅ 设计合理；子表仅 `bom_id/picking_id/receipt_id` 单列索引 ✅ 够用；缺少 `production_order_id` 索引（picking/completion 主表按订单查询会全表扫）建议补充。
