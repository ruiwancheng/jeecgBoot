## 0. 总体结论

本模块整体处于"单用户草稿单据"设计水平：**所有写操作均无锁、无版本号、无幂等机制**，事务仅使用 `@Transactional(rollbackFor = Exception.class)` 默认配置（REQUIRED + READ COMMITTED），大量"先查后改"（check-then-act）代码在 MySQL 默认隔离级别下存在确定的并发窗口。

最严重后果集中在三处：

1. **完工入库超量校验形同虚设（P0）**——只校验"本次入库数量 ≤ 订单计划数量"，**完全没有累计校验**，`completedQty` 字段从不更新，同一订单可无限次、无限量入库，无需并发即可超量。
2. **生产订单状态/完工数量被全字段覆盖（P0）**——编辑接口 `updateById` 用前端提交的全字段实体直接覆盖数据库行，未来若有审核/报工流程并发写入 `status`/`completed_qty`，会被静默回退（lost update）。
3. **复活已删单据的 `resurrect` 逻辑存在双活竞态（P0）**——`selectDeletedByCode` 未加锁，两个并发新增相同编码的请求可同时走上"复活"或"新增"分支，产生两条 del_flag=0 的同编码单据或主键覆盖。

另外确认了一个**表名不一致的致命隐患（P0）**：实体 `@TableName("mes_production_picking")` / `@TableName("mes_completion_receipt")`，而 SQL 建的是 `c_mes_production_picking` / `c_mes_completion_receipt`（BOM 与 Order 一致，均为 `c_mes_*`）。**picking 与 completion 两个包的所有 SQL 将打到不存在的表上，模块根本跑不起来**——这虽非并发问题，但意味着 picking/completion 从未被真实流量验证过，其并发缺陷从未暴露。

## 1. 事务隔离检查

| 检查项 | 现状 | 评价 |
|---|---|---|
| `@Transactional` 覆盖 | 4 个 ServiceImpl 的 save/update/remove 系列方法均有 `@Transactional(rollbackFor = Exception.class)` | ✅ 覆盖面够 |
| 传播级别 | 全部默认 `REQUIRED`，无 `REQUIRES_NEW` / `NESTED` | ⚠️ 当前无嵌套调用场景，暂未构成问题；未来若在领料/入库事务中调用订单状态推进，需谨慎 |
| 只读事务 | `queryWithItems`、Controller 的 list/queryById/queryAll/export 均未声明 `@Transactional(readOnly = true)` | P2：查询走默认读写事务（或非事务），Druid 连接池无法路由只读库，也无 `readOnly` 优化提示 |
| 长事务 | 写事务内包含：多次 `selectCount`、跨表校验（`orderMapper.selectById`）、逐行 `itemMapper.insert` 循环（`saveItems` 是 N 次单条 insert，非 batch） | P1：明细行数大时事务持有时间线性增长；RR 隔离级别下 gap lock 持有更久，加剧编码唯一索引上的并发冲突概率 |
| 隔离级别 | 未显式指定，跟随 MySQL 默认 REPEATABLE READ | ⚠️ RR 下 `selectCount` 的 gap lock 可部分缓解幻读，但代码中的 check-then-act 均为普通快照读，**快照读不产生锁**，见第 2 节 |

**发现：**

- **P2-1**：`ProductionOrderServiceImpl.save` 等 4 个新增方法在事务内先 `selectCount`（活跃记录）再 `selectDeletedByCode`（已删记录）再 insert/resurrect，整个链路无锁，且事务随明细行数变长。建议将"编码查重"彻底交给数据库唯一约束（直接 insert 捕获 `DuplicateKeyException`——代码已部分这么做），删除前置 `selectCount`，缩短事务。
- **P2-2**：`queryWithItems`（主子表两次查询）无事务，主表读出后、子表查询前主表被并发删除/复活，会组装出"已删除主表 + 旧子表"的脏数据视图。建议加 `@Transactional(readOnly = true)` 利用 RR 一致性视图。

## 2. 数据竞态（check-then-act）

### 2.1 【P0】完工入库数量校验：既不累计也不并发安全

`CompletionReceiptServiceImpl.validate()` 第 128 行：

```java
if (order.getPlanQty() != null && item.getReceiptQty().compareTo(order.getPlanQty()) > 0)
    throw new JeecgBootException("第" + (i+1) + "行入库数量不能超过计划数量(" + order.getPlanQty() + ")");
```

问题有三层，层层致命：

1. **无累计校验**：只比对"本次 ≤ 计划"，不查历史入库单累计，也不读/不更新 `order.completedQty`。同一订单提交两张各 100% 计划量的入库单，两张都通过——**串行就超量，不需要并发**。
2. **并发窗口**：即使补上"累计 + 本次 ≤ 计划"的校验，按当前写法（`orderMapper.selectById` 快照读 → Java 比较 → insert），两个并发请求读到同一 `completedQty` 快照，同时通过校验，提交后超量。典型 TOCTOU。
3. **`completedQty` 是死字段**：`MesProductionOrder.completedQty` 在 `save` 时初始化为 0 后，全模块没有任何代码更新它（只有 `resurrect` 会原样写回）。入库不回写完工数量，订单永远停留在"已完工 0"，状态机（字典里定义了"已完工=5"）无数据驱动。

**修复建议：**
- 在 `c_mes_production_order` 上用**原子累计**回写：
  ```sql
  UPDATE c_mes_production_order
  SET completed_qty = completed_qty + #{qty}
  WHERE id = #{orderId} AND del_flag = 0
    AND completed_qty + #{qty} <= plan_qty
  ```
  影响行数为 0 即抛"超量入库"异常——把校验下推为数据库原子操作，天然免疫并发。
- 或在事务内 `SELECT ... FROM c_mes_production_order WHERE id = ? FOR UPDATE` 锁定订单行后再校验+回写（悲观锁串行化同一订单的入库）。

### 2.2 【P0】单据编码查重 selectCount → save 竞态（四包全中）

4 个 Service 的新增方法同一模式（以 `ProductionOrderServiceImpl.save` 第 29–37 行为例）：

```java
if (baseMapper.selectCount(qw) > 0) throw ...;          // 快照读，无锁
MesProductionOrder old = baseMapper.selectDeletedByCode(...); // 快照读，无锁
if (old != null) { ...resurrect... } else { try { super.save } catch (DuplicateKeyException) ... }
```

- 唯一索引是 `(code, del_flag)`（MySQL 联合唯一索引下，同 code 只能有一条 del_flag=0 + 一条 del_flag=1）。
- 并发场景 A（双新增）：T1、T2 同 code，`selectCount` 均为 0，`selectDeletedByCode` 均为 null，双双 `insert` → 一个成功一个 `DuplicateKeyException`。代码已捕获此异常，**该路径兜底有效**。
- 并发场景 B（一增一复活/双复活，**无兜底**）：已存在一条 del_flag=1 的同 code 记录。T1、T2 同时 `selectDeletedByCode` 命中同一行 → 双双走 resurrect 分支 → 两条 `UPDATE ... WHERE id=#{id} AND del_flag=1`（order/bom 有 del_flag=1 条件，后到的影响 0 行但**代码不检查影响行数**，`resurrect` 返回 void，T2 静默"成功"）；而 picking/completion 的 `resurrect` SQL **连 `AND del_flag=1` 都没有**（见 `MesProductionPickingMapper` 第 15–18 行、`MesCompletionReceiptMapper` 第 15–18 行），T2 会把 T1 刚复活的行**整行覆盖**，T1 事务随后提交即产生 lost update。更糟的是 picking/completion 的 resurrect 分支先 `itemMapper.delete(旧子表)` 再 insert 新子表，两个并发事务交错执行 delete/insert，会出现**子表双份明细或明细全丢**。

**修复建议：**
- `resurrect` 改为 `UPDATE ... WHERE id=#{id} AND del_flag=1` 并**检查影响行数**，为 0 则抛出"单据编码并发冲突，请重试"；
- `selectDeletedByCode` 加 `FOR UPDATE`（把已删行锁住，串行化复活）；
- 或者干脆废弃"复活"设计，删除即物理删/换 code 墓碑值，新增只走 insert + 唯一索引兜底。

### 2.3 【P1】编辑时编码查重 selectCount → updateById

`updateById` / `updateWithItems` 中 `selectCount(code = X AND id != mine) > 0` 后 `super.updateById(entity)`：

- 并发编辑两张单据互换成对方编码：T1 把 A 改成 B 的 code，T2 把 B 改成 A 的 code，两次 `selectCount` 都读不到对方的未提交修改（READ COMMITTED/RR 快照），双双通过 → 提交时唯一索引 `(code, del_flag)` 兜底其中一个报 `DuplicateKeyException`。**但 `updateById` 路径没有 try-catch `DuplicateKeyException`**（只有 save 路径捕获了），异常将以 500 原始堆栈抛出，且事务回滚导致主子表删除已执行的部分整体回滚——数据不错乱，但用户体验差、错误信息误导。
- P1：为 update 路径补 `DuplicateKeyException` 捕获并转业务异常。

### 2.4 【P1】删除前状态校验 checkStatus → removeById

`removeById` / `removeWithItems` / `removeByIds` 均为：`selectById` 读状态 → 判断 `status == "1"` → 执行逻辑删除。

- 与"审核"动作并发时（审核接口目前不存在，但字典已定义 status=2 已审核/已下达等）：T1 读到草稿状态通过校验，T2 并发审核通过，T1 提交删除 → **已审核单据被删**。典型 TOCTOU。
- 当前模块尚无审核接口，状态只有"1"，故定级 P1（预埋炸弹）而非 P0。
- 修复：删除改为条件更新原子化——`UPDATE ... SET del_flag=1 WHERE id=? AND status='1' AND del_flag=0`，检查影响行数，0 行即"状态已变化，删除失败"。MyBatis-Plus 可用 `UpdateWrapper` 一条 SQL 完成。

## 3. 锁机制检查

| 机制 | 现状 |
|---|---|
| 乐观锁 `@Version` | ❌ 全模块 0 处使用；MyBatis-Plus `OptimisticLockerInnerInterceptor` 未见实体配合 |
| 悲观锁 `SELECT ... FOR UPDATE` | ❌ 全模块 0 处（已全文检索 `for update` 确认） |
| 应用层锁 `synchronized` / `Lock` / Redis 分布式锁 | ❌ 0 处 |
| 数据库唯一约束兜底 | ✅ 仅 `(code, del_flag)` 联合唯一索引（且 MySQL 上该设计有固有缺陷，见下） |

**关键更新是否需要锁——需要，清单如下：**

1. **P0**：完工入库回写订单 `completedQty`（当前根本没写）——必须用原子 UPDATE 或订单行锁。
2. **P0**：`resurrect` 复活流程——必须对目标行加锁或校验影响行数。
3. **P1**：订单编辑（`updateById`）——`MesProductionOrder` 应加 `@Version` 字段 + `OptimisticLockerInnerInterceptor`，防止两个用户同时编辑互相覆盖；尤其防止编辑提交把并发的状态流转/完工数量覆盖回旧值（当前 `updateById` 是全字段更新，前端传什么就覆盖什么，**`status` 和 `completedQty` 都会被打回**——见第 5 节 P0-3）。
4. **P1**：领料/入库保存时对订单状态的校验（`validate` 中 `orderMapper.selectById` 后判断草稿）——未来状态机上线后需 `FOR UPDATE` 或条件 UPDATE 原子校验。

**唯一索引设计缺陷（P2）**：`(code, del_flag)` 联合唯一意味着同一 code 最多容忍一条已删记录；第二次删除同 code 单据时（del_flag 从 0→1，但已存在一条 del_flag=1 的同 code 行）会直接 `DuplicateKeyException` 导致**删除失败**。建议：del_flag 存删除时间戳/删除批次号，或用 `(code)` 唯一 + 删除时把 code 改写为 `code#deleted#id`。

## 4. 幂等设计检查

| 接口 | 重复调用后果 | 评级 |
|---|---|---|
| 新增 `/add`（四包） | 同 code 重复提交：第一个成功，第二个走 `selectCount>0` 抛"已存在"或唯一索引兜底 → 基本幂等（但 resurrect 分支并发不幂等，见 2.2）；**前端无防重 token，双击/重试依赖 code 唯一性兜底** | P1 |
| 编辑 `/edit` | 天然幂等（同数据覆盖），但并发编辑互相覆盖无版本控制 | P1 |
| 删除 `/delete` `/deleteBatch` | 重复删除：`checkStatus` 对已删记录 `selectById` 返回 null（逻辑删除后查不到）→ `exist != null` 判断跳过 → `super.removeById` 影响 0 行 → 返回成功。**重复删除幂等** ✅ | 低危 |
| 前端防重复提交 | ❌ 无 `@RepeatSubmit` / token / 请求指纹机制；JeecgBoot 本身不内置，需自行接入 | P1 |

**P1 详述——新增接口非幂等的真实场景**：前端网络超时重试 / 用户双击，两次请求 body 相同（同 code）。若中间无并发删除，第二次被"已存在"拒绝，表现幂等；但若第一次请求实际已成功而响应丢失，用户看到失败后**改 code 重发**，就会产生两张内容相同仅 code 不同的单据（业务重复单）。建议：前端生成一次性 `requestId`/单据号由后端生成（code 改为服务端发号，如规则引擎/Redis INCR 发号），杜绝客户端携带编码重试产生的歧义；或加幂等表/Redis `SET NX` 防重。

## 5. 状态机安全

字典定义了完整状态机（订单：草稿→已审核→已下达→执行中→已完工→已关闭/已取消；领料：草稿→已审核；入库：草稿→已入库），**但代码中没有任何状态流转接口**——save/update 一律 `entity.setStatus("1")` 强制打回草稿。

由此产生三个问题：

- **P0-3【状态回退 / lost update】**：`ProductionOrderServiceImpl.updateById` 第 47 行 `entity.setStatus("1")` + 全字段 `super.updateById(entity)`。场景：订单已被（未来接口或管理员直接改库）置为"已下达=4"，此时用户在前端编辑备注提交 → `checkStatus` 先读状态发现非草稿会拦截……但若状态流转与编辑**并发**发生（T1 读到草稿通过校验，T2 审核下达，T1 提交全字段覆盖），T1 会把 status 从 4 打回 1，`completedQty` 也被前端提交的旧值（甚至 null→0）覆盖。未来审核/报工接口上线之日，就是此雷引爆之时。
  **修复**：编辑只更新业务字段（`UpdateWrapper` 显式 set 允许编辑的列），不触碰 `status`、`completedQty`；流转用独立的条件更新：`UPDATE ... SET status=#{to} WHERE id=#{id} AND status=#{from}`，影响行数 0 即并发冲突。
- **P1**：`validate` 中"仅草稿状态的生产订单可领料/入库"（`ProductionPickingServiceImpl` 第 118 行、`CompletionReceiptServiceImpl` 第 118 行）语义存疑——草稿订单就允许领料入库？应该是"已下达/执行中"才允许。这是业务规则问题，但一旦按业务修正，并发下"校验时是可领料状态、提交时订单已关闭"的 TOCTOU 窗口必须用订单行锁或状态条件更新消除。
- **P2**：当前无状态流转接口，状态机名存实亡，建议要么补齐流转接口（带条件更新），要么删掉多余字典项避免误导。

## 6. 累计字段原子性

- `c_mes_production_order.completed_qty`：全模块**零更新**（仅 save 初始化 0、resurrect 原样写回）。不存在"先查再 set"的代码，是因为**压根没有累计逻辑**——这比写法错误更严重，属于功能缺失，见 2.1 P0。
- 领料侧：`MesProductionPicking` 主表无累计字段，订单上也没有"累计领料量"字段——领料超发无防控（P1 功能缺失：应增加订单/明细级累计领料校验，同样用原子 UPDATE 兜底）。
- **未来实现累计时的正确写法**（写入报告作为规范）：
  ```java
  // 错误：read-modify-write
  // order = selectById(id); order.setCompletedQty(order.getCompletedQty().add(qty)); updateById(order);
  // 正确：数据库原子自增 + 约束下推
  int rows = orderMapper.addCompletedQty(orderId, qty); // SET completed_qty = completed_qty + #{qty} WHERE id AND completed_qty + #{qty} <= plan_qty
  if (rows == 0) throw new JeecgBootException("入库超量或订单状态已变更");
  ```

## 7. 主子表保存并发（delete-all-then-insert 模式）

`updateWithItems`（bom/picking/completion 三包同构）：

```java
super.updateById(entity);            // 更新主表
itemMapper.delete(delQw);            // 物理删除全部旧子行
saveItems(entity);                   // 逐条 insert 新子行
```

- **单事务内**该模式本身可回滚，数据不会脏，但：
- **P1【并发编辑同一单据】**：两个用户同时编辑同一单据，T1、T2 都通过 `checkStatus`（快照读 status=1），T1 删子表插 3 行，T2 删子表插 5 行。RR 下 `itemMapper.delete` 会对 `picking_id = X` 范围加 next-key lock，T2 的 delete 会**等锁**至 T1 提交，然后删掉 T1 刚插的行再插自己的——最终后提交者覆盖先提交者，**先提交用户的修改静默丢失，无任何冲突提示**。主表应加 `@Version` 乐观锁（子表随主表版本），让后到者在 update 主表时即失败。
- **P1【删插窗口内的读】**：`queryWithItems` 无事务（见 1 节 P2-2），在另一会话的"删旧子表→插新子表"窗口内读取，可能读到**空子表**（READ COMMITTED）或旧子表（RR 快照）——JeecgBoot 默认 RR 下普通 SELECT 是快照读，读到旧数据，可接受；但主表已更新 + 子表是旧的组合会造成"主表数量与子表合计不符"的瞬态。建议查询加 `readOnly` 事务包住两次 SELECT，保证同一快照。
- **P2【性能/长事务】**：`saveItems` 逐条 `itemMapper.insert`（非 `saveBatch`/非 foreach 批量 SQL），100 行明细 = 100 次网络往返 + 100 条 redo，事务拉长、锁持有时间变长。建议改 MyBatis-Plus `saveBatch` 或 `<foreach>` 多值 insert。
- **P2【 resurrect 分支的子表删除】**：saveWithItems 的 resurrect 分支先删旧子表再复活主表再插新子表，与 2.2 的并发复活叠加时，可能删掉另一事务刚插入的子表行。

## 8. 风险清单汇总

### P0（必须立即修复）

| # | 位置 | 风险 | 修复要点 |
|---|---|---|---|
| P0-1 | `CompletionReceiptServiceImpl.validate` L128 | 入库无累计校验、不回写 `completedQty`，串行即可超量入库 | 原子 UPDATE `completed_qty = completed_qty + qty` + `WHERE ... <= plan_qty` 约束下推，影响行数校验 |
| P0-2 | 四包 `saveWithItems`/`save` 的 resurrect 分支 | 并发复活同 code 已删单据：双活、lost update、子表被误删；picking/completion 的 resurrect SQL 无 `del_flag=1` 守卫 | resurrect 校验影响行数 + `selectDeletedByCode ... FOR UPDATE`；picking/completion 补 `AND del_flag=1` |
| P0-3 | `ProductionOrderServiceImpl.updateById` L47–50 | 全字段覆盖更新 + 强制 status="1"，并发下回退状态机与完工数量（lost update） | 编辑改为显式列更新，不碰 status/completedQty；加 `@Version` 乐观锁 |
| P0-4 | picking/completion 实体 `@TableName("mes_*")` vs SQL 建表 `c_mes_*` | 表名不匹配，两包功能直接报错不可用，并发缺陷从未被真实流量检验 | 统一表名（属功能缺陷，列入 P0 一并修复） |

## 9. 修复优先级路线图建议

1. **第一步（阻塞性）**：修表名不一致（P0-4），让 picking/completion 能跑起来；
2. **第二步（数据正确性）**：完工入库原子累计 + 超量约束下推（P0-1）；resurrect 加锁与影响行数校验（P0-2）；
3. **第三步（防覆盖）**：主表 `@Version` 乐观锁（P1-3）+ 编辑改显式列更新、不碰 status/completedQty（P0-3）；
4. **第四步（状态机）**：删除/流转改条件更新（P1-2、P1-5），补状态流转接口；
5. **第五步（体验与加固）**：幂等 token、批量 insert、只读事务、唯一索引重构。
