# 铁拳团审计 · 风控总报告

| 项目 | 内容 |
|---|---|
| 审计模块 | mes-manufacturing（BOM管理 / 生产订单 / 生产领料 / 完工入库） |
| 审计日期 | 2026-07-16 |
| 审计团队 | 铁拳团 10 人（产品风控 3 + 研发风控 3 + 交付测试 4） |
| 审计方式 | 静态代码走读（只查不改），主控对最高危 P0 做了源码复核 |
| 对应提交 | c590ead feat: MES生产制造模块——BOM+生产订单+生产领料+完工入库 |

## 一、总体结论

**模块当前不可上线。** 四个子模块中，生产领料（picking）和完工入库（completion）两个模块的实体表名与建表 SQL 不一致，部署后直接报表不存在、功能完全不可用。BOM 和生产订单两个模块虽然能跑通 CRUD，但单据之间没有状态驱动、没有数量回写、没有引用校验，业务闭环断裂——当前状态只能称为"四个电子台账"，不能称为"生产制造管理"。

| 维度 | 结论 |
|---|---|
| 能否部署 | ❌ picking/completion 上线即报表不存在（P0-1） |
| 能否防资损 | ❌ 完工入库可无限超计划、领料可领任意物料任意数量、库存台账不联动（P0-2/3/4） |
| 业务闭环 | ❌ 订单永远草稿、completedQty 永远 0、无状态流转（P0-5） |
| 菜单可用性 | ❌ 菜单权限未注册，所有接口 403（P0-6） |
| BOM/订单基础 CRUD | ✅ 可正常使用（但存在 P1 级引用校验缺失） |

## 二、共识 P0 风险表（必改）

> 共识 = 多名成员独立识别 + 主控源码复核属实。按修复依赖排序。

| # | 风险 | 位置 | 业务影响 | 修复建议 |
|---|---|---|---|---|
| **P0-1** | **picking/completion 表名不一致**：实体 `@TableName("mes_production_picking")` / `@TableName("mes_completion_receipt")`，建表 SQL 却是 `c_mes_production_picking` / `c_mes_completion_receipt`（缺 `c_` 前缀），主从 4 张表全错 | picking/completion 实体 + Mapper + 前端 API 路径 vs V7.0.2/V7.0.3 SQL | 部署后这两模块所有接口报表不存在，功能完全不可用 | 统一为 `c_mes_` 前缀：改 4 个实体 @TableName + 2 个 Mapper 注解 SQL + 检查前端 url（6 人+主控复核） |
| **P0-2** | **完工入库无累计校验**：validate 只比较"本次单行 ≤ 订单计划数量"，不查历史累计。订单计划 100 可开 10 张单各入 100，累计 1000 全放行 | CompletionReceiptServiceImpl.validate() L112-133 | 库存虚增、成本分摊爆炸，"入库数量≤计划数量"的核心规则实际不存在。**与 e84c96d 在采购模块修的 P0-004 同型，manufacturing 漏改** | 照抄 purchase 修复模式：查历史累计 SUM(receiptQty) 排除自身 + 本次 ≤ planQty；加 FOR UPDATE 行锁防并发（5 人共识） |
| **P0-3** | **领料完全不与 BOM 对账**：不校验领料物料是否在订单 BOM 子项内、不限累计领料量（BOM用量×计划数量×(1+损耗率)）；订单 bomId 可空且从未被使用 | ProductionPickingServiceImpl.validate() L112-131 | 可给"自行车"订单领"航空发动机"99999 个，物料管控失效，成本核算失真 | ① 订单保存强制 bomId 非空；② 领料物料必须 ∈ BOM 子项；③ 累计领料 ≤ BOM用量×计划数量×(1+lossRate)×容差（3 人共识） |
| **P0-4** | **库存台账断裂**：领料（出库）/完工入库（入库）均不写 MesInventoryLedger，台账只有采购入库一侧 | ProductionPickingServiceImpl / CompletionReceiptServiceImpl 均未注入台账服务 | 库存账实永远无法对账，资损发生后无法追查 | 在审核时点（见 P0-5）写台账流水；建议补单据行级流水表 c_mes_inventory_flow（2 人，但属资损根基） |
| **P0-5** | **订单无状态机 + completedQty 死字段**：所有单据 save/update 强制 setStatus("1") 永远草稿，无下达/完工/关闭端点；入库从不回写 completedQty | 四个 ServiceImpl + ProductionOrderServiceImpl | 订单从创建到报废永远"草稿"，完工进度永远 0，"这个月哪些订单在产/完工"系统答不出；且"仅草稿订单可领料/入库"的校验方向与真实业务相反 | 补状态机（草稿→已下达→生产中→已完工→已关闭）+ release/finish/close 端点；入库保存/删除回写 completedQty；领料/入库改为仅"已下达/生产中"可操作（4 人共识） |
| **P0-6** | **菜单权限未注册**：V7.0.x SQL 只有 sys_role_permission 授权，没有 INSERT INTO sys_permission 菜单记录 | V7.0.0~V7.0.3 SQL | @RequiresPermissions 全部 403，前端菜单看不到 | 补菜单 SQL（参考 MesMenuRegistry 注册 + SQL INSERT sys_permission）（09 号发现，主控复核属实） |
| **P0-7** | **删除/编辑不校验下游引用**：删 BOM 不查订单引用、删订单不查领料/入库记录，产生悬空外键；编辑不存在的主表 ID 返回"编辑成功"并插入孤儿子项 | 四个 ServiceImpl 的 removeWithItems/updateWithItems | 已下达的 BOM 被子项整体删换，订单按错误清单备料；孤儿单据无法回溯 | 删除前查下游引用存在则拦截；编辑前校验主表存在（4 人共识） |

## 三、共识 P1 风险表（建议改）

| # | 风险 | 影响 | 建议 |
|---|---|---|---|
| P1-1 | 跨模块走 Mapper 直查（picking/completion 直查 order 表） | 破坏服务边界，微服务化时断裂 | 改注入 IProductionOrderService 接口调用 |
| P1-2 | 子表 @TableLogic 与 DDL 缺 del_flag 列矛盾；复活路径物理删旧子行 | 逻辑删除 SQL 报错或审计追溯链断 | item 表补 del_flag 列，复活改逻辑删 |
| P1-3 | Controller 直接暴露 Entity，createBy/updateBy/delFlag 泄露 | 敏感字段随 list/queryAll/exportXls 泄露 | 引入 VO 隔离，或 @JsonIgnore 敏感字段 |
| P1-4 | 前后端字段名不一致 2 处：BOM isSubstitute vs isAlternative；领料 pickDate vs pickingDate | 替代料功能静默失效、领料日期存不上 | 统一前后端字段名 |
| P1-5 | 入库明细 materialId 不校验是否=订单产品 | 可给电机订单入拖鞋，库存账错乱 | 后端强制校验 materialId == order.productId（或白名单） |
| P1-6 | 并发竞态：查重-插入非原子、复活 selectDeletedByCode 无锁双活、(code,del_flag) 唯一索引二次删除冲突 | 并发下同编码双复活/脏数据、二次删除失败 | 唯一索引兜底 + 捕获 DuplicateKeyException；del_flag 删除置时间戳 |
| P1-7 | 前端无防重复提交；订单无"领料/入库"跳转入口，productionOrderId 是纯 Input 手填雪花 ID | 双击产生脏数据；用户操作路径断裂 | 前端加 submitting 锁；订单行操作加领料/入库跳转，表单改 JSearchSelect |
| P1-8 | production_order_id 外键无索引、saveItems 逐条 INSERT、缺 (status,create_time) 复合索引 | 按订单查领料/入库全表扫；BOM 几百行保存秒级 | 补索引；saveItems 改 saveBatch |
| P1-9 | 无审核动作，台账无写入时点；单据永远草稿无法"定稿" | 任何单据随时可改，账实对不上 | 补 audit/unAudit 接口，审核后禁止编辑 |
| P1-10 | 无自动单号，四模块 code 全手工输入 | 多人开单撞号，报错后重填整张单 | 接编码规则（PO+yyyyMMdd+流水），前端留空自动生成 |

## 四、P2 建议项

- 领料/入库列表"生产订单"列显示雪花 ID 而非单号（冗余字段 productionOrderCode 从不回填）
- 前端数量用 JS number 传 BigDecimal，理论上有精度丢失风险（建议 Jackson 序列化为字符串）
- 全模块无单价/金额字段，成本维度资损无法度量（设计级缺口，需明确成本归属边界）
- BOM 版本字段沦为纯文本：code 唯一锁死多版本，无版本历史/失效拦截
- lossRate 无 0-100 范围校验；新增领料/入库默认预填 quantity=1 易误提交
- queryAll 仅按 1000 条硬上限拦截且无状态过滤
- 导出未启用 exportXlsForBigData 分批导出
- MesBom.items 用 transient（picking/completion 用 @TableField(exist=false)），风格混用

## 五、修复优先级（三批次）

### 第一批次：让系统能跑（1 天内）
1. P0-1 表名统一（picking/completion 改 `c_mes_`）— 否则这两模块根本不存在
2. P0-6 菜单权限 SQL 补注册 — 否则所有接口 403
3. P0-2 完工入库累计校验（照抄 purchase e84c96d 模式 + FOR UPDATE）
4. P0-3 领料 BOM 对账（物料 ∈ BOM 子项 + 累计上限）

### 第二批次：让业务闭环（2-3 天）
5. P0-5 订单状态机 + completedQty 回写 + 领料/入库状态校验方向修正
6. P0-7 删除/编辑下游引用校验
7. P0-4 库存台账联动（审核时点写台账）
8. P1-1 跨模块改 Service 接口调用
9. P1-4 前后端字段名统一
10. P1-5 入库物料=订单产品校验

### 第三批次：让系统好用（1 周内）
11. P1-2 子表 del_flag 对齐 + 复活逻辑修正
12. P1-3 VO 隔离敏感字段
13. P1-6 并发兜底（唯一索引 + DuplicateKeyException + del_flag 时间戳）
14. P1-7 前端防重复提交 + 订单跳转领料/入库 + JSearchSelect
15. P1-8 索引补齐 + saveBatch
16. P1-9 审核接口
17. P1-10 自动单号
18. P2 项按需排期
