**审计模块**：mes-manufacturing（bom / order / picking / completion）
**审计日期**：2026-07-16
**审计人**：铁拳团 10 号（测试牛马4号 · 资损对账专项）
**对照基准**：commit e84c96d 在 purchase 模块修复的「累计入库超量校验」同类问题（P0-004）

---

## 一、总体结论

manufacturing 模块的**资损防线基本为零**。purchase 模块在 e84c96d 中已经修复的「累计入库量 vs 订单量」校验，在 manufacturing 的完工入库单里**完全缺失**；领料单与 BOM 标准用量**没有任何对账关系**；库存台账 `MesInventoryLedger` 只有 purchase 模块自己维护，manufacturing 的领料（出库方向）与完工入库（入库方向）**均未写台账**，库存账与业务单据之间没有可对账的数据链路。此外还发现表名不一致（`c_mes_` vs 无前缀）、`@TableLogic` 逻辑删除与物理删除混用导致的**主子表残留**等结构性问题。

## 二、分专题审计发现

### 专题 1：入库累计与订单数量对账（P0）

**代码位置**：`CompletionReceiptServiceImpl.validate()`（第 112–133 行）

**现状代码**：
```java
if (order.getPlanQty() != null && item.getReceiptQty().compareTo(order.getPlanQty()) > 0)
    throw new JeecgBootException("第" + (i+1) + "行入库数量不能超过计划数量(" + order.getPlanQty() + ")");
```

**发现的问题**：

1. **【P0-1】只校验单次入库，不查历史累计** —— 与 e84c96d 修复前 purchase 模块的漏洞完全相同。同一生产订单可以开 N 张入库单，每张都按「单次 ≤ 计划数量」通过校验，累计入库量可无限超发。例如订单计划 100，可分别入库 80、80、80，累计 240 均不被拦截。
   - 对照：`MesPurchaseReceiptServiceImpl` 第 138–172 行已用 `historyQtyMap` 累计历史入库并排除自身（编辑场景），manufacturing 未同步该修复。

2. **【P0-2】`completedQty` 字段成为死字段** —— `c_mes_production_order.completed_qty` 定义了「已完工数量」，实体也有该字段，但**全模块没有任何代码在入库单审核/保存后回写该字段**。订单上的完工数量永远是初始值 0，无法作为对账依据。后续「订单完工数量达标 → 状态 5」的字典定义也无代码驱动。

3. **【P0-3】并发可绕过（即使补上累计校验也一样）** —— 校验逻辑是「先 SELECT 历史单，再 INSERT 新单」的两段式，未加行锁（`SELECT ... FOR UPDATE`）或乐观锁。两个并发请求同时查到「历史累计 = 0」，各自 +80 都通过，最终 160 > 100。purchase 模块的 e84c96d 修复也存在同样并发缺口，manufacturing 抄作业时应一并补齐（如对 `production_order_id` 加锁或使用数据库唯一约束/触发器兜底）。

4. **【P0-4】删除入库单后无累计回减概念** —— 当前既无累计字段回写，自然也无回减。若未来实现 completedQty 回写，必须同步实现 `removeWithItems` / `removeByIds` 中的回减逻辑，否则删除即资损。当前 `removeWithItems` 直接物理删子表 + 逻辑删主表，没有任何钩子。

5. **【P1-1】入库明细行的 `materialId` 与订单产品不校验一致性** —— `validate()` 只查 `materialId` 非空，不校验是否等于订单的 `productId`。可以在 A 产品的订单下给 B 产品入库，张冠李戴。

6. **【P1-2】`item.plan_qty` 明细字段从不赋值** —— `c_mes_completion_receipt_item.plan_qty` 列存在，实体里却没有该字段（`MesCompletionReceiptItem` 无 `planQty`），属于半拉子设计，后续无法做行级对账。

### 专题 2：领料累计对账（P0）

**代码位置**：`ProductionPickingServiceImpl.validate()`（第 112–131 行）

**发现的问题**：

1. **【P0-5】领料数量完全不与 BOM 标准用量对账** —— 领料单保存时只校验 `quantity > 0`：
   ```java
   if (item.getQuantity() == null || item.getQuantity().compareTo(BigDecimal.ZERO) <= 0)
       throw new JeecgBootException("第" + (i+1) + "行领料数量必须大于0");
   ```
   没有：
   - 校验 `materialId` 是否在该订单 BOM 的子项清单里（可领 BOM 外物料，资损敞口）；
   - 校验累计领料量 vs `BOM.quantity × order.planQty × (1+lossRate)`（可无限超额领料，典型资损场景）；
   - 累计历史领料（与专题 1 同型的「单次校验」漏洞，甚至这里连单次上限都没有）。

2. **【P0-6】订单与 BOM 关联形同虚设** —— `c_mes_production_order.bom_id` 允许为 NULL，且没有任何代码在领料时加载 BOM。业务上「订单→BOM→子项标准用量→领料控制」的管控链断裂。

3. **【P1-3】业务上允许超额领料时也应有管控阈值** —— 即使业务允许超领（补料场景），也应设置超领比例上限（如 ≤110%）并记录超领原因。当前是**无上限、无原因、无审批**的三无状态。

### 专题 3：库存台账一致性（P0）

**发现的问题**：

1. **【P0-7】领料/完工入库均不写库存台账** —— 全仓搜证：`IMesInventoryLedgerService` 仅在 purchase 模块内部被引用（`MesInventoryLedgerController` 自身），manufacturing 的 `ProductionPickingServiceImpl` 与 `CompletionReceiptServiceImpl` **均未注入或调用** 台账服务。
   - 领料 = 库存出库 → 无台账流水
   - 完工入库 = 库存入库 → 无台账流水
   - 结果：`c_mes_inventory_ledger` 只能看到采购入库一侧，库存账永远无法与 manufacturing 业务单据对账。资损发生后无法事后追查。

2. **【P1-4】无审核动作，台账无写入时点** —— 字典定义了 `mes_picking_status`（1 草稿 / 2 已审核）与 `mes_completion_status`（1 草稿 / 2 已入库），但 controller 里**没有 audit/approve 接口**，status 只能通过 `updateWithItems` 被前端任意修改（见专题 5）。台账通常应在「审核」时点写入，目前连这个时点都不存在。

3. **【P1-5】`MesInventoryLedger` 为期间汇总结构（beginningQty/inQty/outQty/endingQty + recordDate），非流水表** —— 即使 manufacturing 想接，也缺少按单据行的流水结构（bizId 是单号但数量是期间值），设计上与「单据↔台账逐笔对账」不匹配，需要补一张流水表或改造。

### 专题 4：数量精度（P1）

**发现的问题**：

1. **【P1-6】DB 精度与 Java 类型基本一致，但精度本身偏低** —— 所有数量字段 DB 侧统一 `DECIMAL(18,4)`，Java 侧 `BigDecimal`，无 float/double 混用，这点合格。但 `DECIMAL(18,4)` 整数位只有 14 位，对大数量+小单价场景够用，对纯数量场景（如件数）通常 `DECIMAL(18,2)` 或 `(18,3)` 即可；不是 bug，但需在文档中统一约定。

2. **【P1-7】前端精度丢失风险** —— JeecgBoot 前端 Vue 默认 JSON number 是 IEEE754 double，超过 15~16 位有效数字会丢精度。`DECIMAL(18,4)` 的理论上限 99999999999999.9999（14 位整数 + 4 位小数共 18 位有效数字）已超 double 安全范围。虽然业务上数量很难达到 14 位整数，但若前端用 number 而非 string 传 `BigDecimal` 字段，理论上有丢精度风险。建议 Jackson 对 BigDecimal 序列化为字符串（`spring.jackson.generator.write-bigdecimal-as-plain` + 全局 serializer），前端用字符串接收。

3. **【P2-1】`loss_rate DECIMAL(5,2)` 容量过小** —— `c_mes_bom_item.loss_rate` 最大 999.99%，正常业务损耗率 0~100% 够用，但若有人录 100.00 以上（如超耗场景）无校验。实体 `MesBomItem` 未审计（本文略），建议补范围校验 0–100。

4. **【P2-2】金额字段完全缺失** —— 全模块没有任何单价/金额字段（`unit_price`、`amount` 等）。完工入库单无法核算完工成本，领料单无法核算领料成本，**成本维度资损完全无法度量**。如果业务上制造模块需要做成本核算，这是设计级缺口；如果成本在别的模块核算，应明确接口契约。

### 专题 5：删除/编辑后的数据一致性（P0）

**代码位置**：四个 ServiceImpl 的 `updateWithItems` / `removeWithItems` / `removeByIds`

**发现的问题**：

1. **【P0-8】已审核单据可被编辑** —— `checkStatus` 只校验「草稿状态可操作」，但**没有审核接口**可以把单据从草稿改成已审核（字典里定义了 status=2，却无代码路径设置）。结果：
   - 所有单据永远停留在 status=1（草稿）；
   - `updateWithItems` 里又强制 `entity.setStatus("1")`（CompletionReceiptServiceImpl:77、ProductionPickingServiceImpl:77、MesBomServiceImpl:72、ProductionOrderServiceImpl:47），即使将来加了审核功能，**任何编辑都会把单据打回草稿**，审核结果可被静默抹掉。
   - 这是一个「状态机未实现 + 防御性赋值反成后门」的组合问题。

2. **【P0-9】子表物理删除 vs 主表逻辑删除 → 数据残留/复活失败** ——
   - 主表 `del_flag` 走 `@TableLogic` 逻辑删除；
   - 子表 `c_mes_bom_item` / `c_mes_production_picking_item` / `c_mes_completion_receipt_item` **实体上有 `@TableLogic` 注解，但 DDL 里没有 `del_flag` 列**（见 V7.0.2/V7.0.3 SQL 第 16–27 行）；
   - `removeWithItems` 里 `itemMapper.delete(qw)` 的行为依赖实体 `@TableLogic`：如果 MyBatis-Plus 识别为逻辑删除，会拼 `UPDATE ... SET del_flag=?` 直接 **SQL 报错（列不存在）**；如果被忽略，则物理删除。
   - 更严重的在「复活」路径：`saveWithItems` 里 `old = selectDeletedByCode(...)` 找到已删主单后 `resurrect`，然后**直接 `itemMapper.delete` 删旧子行再插新子行** —— 旧子行被永久物理删除，审计追溯链断。正确做法应是子表也加 `del_flag` 列并逻辑删除。

3. **【P1-8】`uk_*_code (code, del_flag)` 唯一索引 + 逻辑删除的伪唯一陷阱** —— MySQL 中 `(code, del_flag)` 复合唯一索引意味着同一 code 删除一次后（del_flag=1）还可以再新建一条同 code 记录，业务上 code 不复用没问题；但**第二次删除时** `del_flag` 还是 1（实体 `@TableLogic` 默认未指定删除值也是 1），会与已删记录冲突，导致**第二次删除失败**。这是 JeecgBoot 常见坑，需要 del_flag 用时间戳或删除时用唯一值。

4. **【P1-9】删除订单不校验下游单据** —— `ProductionOrderServiceImpl.removeById` 只查自身 status，不查是否存在领料单/入库单。删除一个已有领料记录的订单后，领料单 `production_order_id` 成为**悬挂外键**，对账时无法回溯。

5. **【P1-10】批量删除的 race condition** —— `removeByIds` 先 `selectBatchIds` 校验状态，再删除。两并发请求可同时通过校验（都看到草稿），同时删除，没有问题；但一个是删除、另一个是审核（若将来有审核接口）就可绕过。属于低概率但需要在引入审核功能后重新评估。

### 专题 6：跨模块一致性（P1）

**发现的问题**：

1. **【P1-11】表名前缀不一致** —— `c_mes_bom`、`c_mes_production_order` 有 `c_mes_` 前缀，而 `mes_production_picking`、`mes_completion_receipt` 无前缀（实体 `@TableName` 与 DDL 一致，但风格混乱）。这会导致：
   - DBA 跨模块关联查询时易写错；
   - 若后续做分库分表/读写分离按前缀路由，路由规则需要特殊处理；
   - 与 purchase 模块 `c_mes_inventory_ledger` 也不一致。

2. **【P1-12】订单状态与下游单据状态完全脱钩** ——
   - 领料单/入库单保存时校验 `order.status == "1"`（仅草稿订单可操作）——**这意味着订单一旦下达（status≥3），就不能再领料/入库**！这与实际业务完全相反：正常逻辑应是「草稿订单不能领料，已下达/执行中订单才能领料」。
   - 该判断写反了（或设计就错了），导致流程上必须先把订单改回草稿才能补录领料单，**反过来又依赖「编辑打回草稿」的后门（P0-8）**才能正常工作。
   - 订单「完工后」（status=5）领料单还能不能改？答案：**当前无所谓**，因为订单永远停在 1；若将来状态机补齐，`updateWithItems` 里没校验订单当前状态（只在 save 时校验），编辑已下达订单的领料单没有任何拦截。

3. **【P2-3】无跨模块事件/消息** —— 领料审核应触发库存扣减事件、入库审核应触发库存增加事件。当前没有任何事件机制，后续接台账时需要补。

## 四、修复建议（按优先级）

### P0（立即修复）

**R1 · 同步 e84c96d 修复模式到完工入库**
在 `CompletionReceiptServiceImpl.validate()` 中：
- 加载订单 `bom_id`（若关联）用于校验 `materialId == order.productId`；
- 查询同 `productionOrderId` 且未删除的历史入库单（编辑时 `ne id`），聚合 `receiptQty` 为 `historyQty`；
- 校验 `historyQty + 本次 ≤ order.planQty`；
- **加并发保护**：`SELECT * FROM c_mes_production_order WHERE id = ? FOR UPDATE` 先锁订单行，再做累计校验与插入（purchase 模块的 e84c96d 也建议同步补这一层）。

**R2 · 实现 completedQty 回写与回减**
- 入库单「审核」（需新增 audit 接口，见 R4）时：`UPDATE c_mes_production_order SET completed_qty = completed_qty + ? WHERE id = ?`，并在同 SQL 里 `WHERE completed_qty + ? <= plan_qty` 做数据库层兜底防超；
- 反审核/删除已审核入库单时对应 `completed_qty = completed_qty - ?`；
- 入库行加 `plan_qty` 实体字段并填订单计划值，作为行级对账快照。

**R3 · 领料单接入 BOM 对账**
- 订单保存时强制 `bom_id` 非空（或领料时校验非空）；
- 领料单 validate 中加载 BOM 子项：
  - `materialId` 必须在 BOM 子项内；
  - 累计领料量（含历史，逻辑同 R1）≤ `bomItem.quantity × order.planQty × (1 + lossRate/100)` × 超容许差（建议参数化，默认 110%）；
  - 超限时要求填写超领原因（新增字段）。

**R4 · 补审核状态机**
- 新增 `/audit`、`/unAudit` 接口，将 status 从 1 → 2、2 → 1；
- 去掉 `updateWithItems` 里的 `entity.setStatus("1")`（这是后门）；
- 校验顺序改为：已审核单据禁止编辑/删除（现有 checkStatus 已支持，只要状态能推进到 2 即可生效）；
- 领料审核时点写台账（出库方向），入库审核时点写台账（入库方向）。

**R5 · 修主子表一致性**
- DDL 给三张 item 表加 `del_flag INT DEFAULT 0` 列（与实体 `@TableLogic` 对齐）；
- 或者去掉实体的 `@TableLogic` 并确认 `itemMapper.delete` 是物理删除（二选一，建议前者保留审计）；
- 复活路径禁止物理删旧子行，改为逻辑删 + 新插入；
- `(code, del_flag)` 唯一索引改为：删除时把 `del_flag` 置为记录主键的 hash 或时间戳，避免二次删除冲突（JeecgBoot 通用做法）。

**R6 · 订单删除前校验下游**
`ProductionOrderServiceImpl.removeById/removeByIds` 增加：
