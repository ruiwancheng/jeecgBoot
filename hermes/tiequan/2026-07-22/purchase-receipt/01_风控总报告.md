## 共识 P0（多视角命中）

### P0-1：删除操作并发击穿——已审核入库单可被并发删除（5 视角命中）

- **位置：**
  - `MesPurchaseReceiptServiceImpl.removeWithItems():107-113` — 调用 `checkStatus(id, "delete")`，内部 `baseMapper.selectById(id)` 无 FOR UPDATE
  - `MesPurchaseReceiptServiceImpl.removeByIds():177-191` — 调用 `baseMapper.selectBatchIds(list)` 无 FOR UPDATE
- **根因：** 2026-07-21 采购订单审计 P0-3 报告"编辑/删除并发击穿"后，仅编辑路径加了 `selectByIdForUpdate`，删除路径遗漏。`checkStatus` 方法（line 265-270）读取状态与后续删除之间无锁保护。
- **攻击场景：** 
  1. 操作员 A 点删除草稿入库单 → `checkStatus` 读到 status='1' → 通过
  2. 操作员 B 同时点审核同一入库单 → `auditWithGuard` 原子改 status='2' → 成功，库存已更新
  3. 操作员 A 的删除继续执行 → `itemMapper.delete` + `super.removeById` → 入库单及其明细行被物理删除
  4. **后果：库存已增加（审核副作用已执行），但入库单丢失 → 库存与单据对不上，资损**
- **核实：** ✅ 属实。对比 `updateWithItems`（line 86-88）已正确使用 `selectByIdForUpdate`，`removeWithItems` 和 `removeByIds` 仍是旧写法。
- **修法：**
  1. `removeWithItems`：将 `checkStatus(id, "delete")` 替换为 `baseMapper.selectByIdForUpdate(id)` 并校验状态
  2. `removeByIds`：新增 Mapper 方法 `selectBatchIdsForUpdate`（`SELECT ... WHERE id IN (...) FOR UPDATE`），替换 `selectBatchIds`
  3. 或简化方案：删除操作也走 `auditWithGuard` 同款原子 SQL——Mapper 新增 `deleteWithGuard`（`DELETE FROM ... WHERE id=? AND status='1'`），影响 0 行即报错

## 共识 P1（≥2 视角命中）

### P1-1：`loadOrderItemsForReceipt` 返回 DTO 的 materialCode/materialName 从未赋值（7 视角命中）

- **位置：** `MesPurchaseReceiptServiceImpl.loadOrderItemsForReceipt():295-302` — DTO 构建链
- **核实：** ✅ 属实。DTO `MesPurchaseOrderItemForReceipt` 声明了 `materialCode`（line 27）和 `materialName`（line 30），但 Service 构建 DTO 时仅设置了 itemId/materialId/orderQty/receivedQty/remainQty/unitPrice/taxRate，未设置 materialCode 和 materialName。
- **原因：** `MesPurchaseOrderItem` 实体只有 `materialId`，无 `materialCode`/`materialName`。要填充这两个字段需要 JOIN 物料表 `c_mes_material`。
- **影响：** 前端若直接绑定这两个字段显示，会看到空白列，用户体验差；若前端做二次查询，则多余开销。
- **修法：**
  - **方案 A（推荐）：** DTO 中去掉 materialCode/materialName 字段，前端用 `materialId` + 字典组件渲染（与列表页模式一致）
  - **方案 B：** Service 中额外查询物料表填充这两个字段（增加一次 JOIN/子查询）

### P1-2：`loadOrderItemsForReceipt` 无参数校验（3 视角命中）

- **位置：** `MesPurchaseReceiptController.loadOrderItemsForReceipt():102` — `@RequestParam String orderId`
- **核实：** ✅ 属实。orderId 为 null/空字符串时，Service 查询 `eq(MesPurchaseOrderItem::getOrderId, "")` 返回空列表，Controller 直接 `Result.ok(emptyList)`。前端收到空列表后无法区分"订单无明细"还是"传参有误"。
- **修法：** Controller 或 Service 入口加 `if (!StringUtils.hasText(orderId)) throw new JeecgBootException("订单ID不能为空")`

### P1-3：`audit()` 循环内 N+1 查询订单行单价（4 视角命中）

- **位置：** `MesPurchaseReceiptServiceImpl.audit():139-148` — for 循环内 `purchaseOrderItemMapper.selectList(piQw)`
- **核实：** ✅ 属实。每行入库明细都执行一次 DB 查询（`eq orderId + eq materialId`），10 行入库明细 = 10 次 DB 查询。
- **影响：** 入库行数多时审核接口响应慢，且无谓消耗 DB 连接池。
- **修法：** 循环前一次性加载采购订单全部明细行到 `Map<String, MesPurchaseOrderItem>`（key=materialId），循环内直接 get。

### P1-4：`audit()` 应付未settledAmount 未含税，财务口径偏差（3 视角命中）

- **位置：** `MesPurchaseReceiptServiceImpl.audit():164-167`
- **核实：** ✅ 属实。
  ```java
  ap.setAmount(totalAmount);           // 不含税金额
  ap.setUnsettledAmount(totalAmount);  // 未结金额=不含税金额（未加税！）
  ap.setTaxAmount(totalTax);           // 税额单独记录
  ```
- **影响：** `unsettledAmount` 字段语义上应是"含税未结总额"，当前少了税额部分。若财务模块直接读 `unsettledAmount` 做应付账龄分析，金额会少一个税。
- **修法：** `ap.setUnsettledAmount(totalAmount.add(totalTax))`

### P1-5：`audit()` 同物料多行仅取第一行单价（3 视角命中）

- **位置：** `MesPurchaseReceiptServiceImpl.audit():139-148`
- **核实：** ✅ 属实。代码注释已标注"同物料多行取第一行——后续 order_item_id 关联后再优化"。当采购订单中同一物料存在多行（不同行号、可能不同单价）时，入库审核取到的单价始终是第一行的。
- **影响：** 若同一物料分两行采购、单价不同（如促销价 vs 正常价），入库审核取到的单价与实际不符 → 应付金额偏差。
- **修法：** 入库行增加 `orderItemId` 字段关联到具体采购订单行，审核时按 `orderItemId` 精确取单价。

## 十视角一致肯定

以下实现获全部视角肯定，已形成可推广模式：

- **`auditWithGuard` 原子状态机守卫** — `UPDATE ... SET status='2' WHERE id=? AND status='1'`，影响 0 行即报错，并发安全
- **`atomicReceive` 原子扣减** — 单 SQL `received_qty + qty <= quantity` 防止超收，替代旧的"先汇总→比较→插入"三步非原子操作
- **`selectByIdForUpdate` 编辑行锁** — 编辑路径已正确使用 FOR UPDATE 防并发击穿
- **`validateReceipt` 多层校验** — 订单存在→状态允许入库→物料归属→累计超量→质检白名单→行号自动编排，覆盖完整
- **事务边界完整** — `@Transactional(rollbackFor = Exception.class)` 覆盖所有写操作，审核副作用（库存+应付）在同一事务内
- **订单状态回写** — `markPartiallyReceived` + `markFullyReceived` 双重推进，`markFullyReceived` 用 `NOT EXISTS` 判断全部到货
- **借尸还魂模式** — resurrect 保留历史 ID/创建人/创建时间，软删除记录复用时审计链不断
