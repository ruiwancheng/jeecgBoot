**P0-1 的攻击场景可复现性分析：**

```
时间线:
T1: 操作员A点删除 → checkStatus(id, "delete") → SELECT 读 status='1' → 通过
T2: 操作员B点审核 → auditWithGuard → UPDATE SET status='2' WHERE id=? AND status='1' → 成功
    → 库存已增加 (atomicReceive)，应付账款已生成
T3: 操作员A的删除继续 → itemMapper.delete(明细) + super.removeById(主表) → 入库单被逻辑删除
结果: 库存+1, 应付+1, 但入库单已删除 → 库存与单据对不上 → 资损
```

**并发窗口真实存在，P0 判定正确。** 两个操作都对同一条 status='1' 的记录等效竞争。

## 四、问题 3：采购申请 P0 对比采购订单修复模式是否一致？

### 结论：模式高度一致，但修复未同步，严重度升级合理

| 问题 | 采购订单 (原始) | 采购订单 (修复后) | 采购申请 (当前) | 模式一致？ |
|------|:--:|:--:|:--:|:--:|
| 编辑并发 | `checkStatus`(普通SELECT) | `selectByIdForUpdate` + `setStatus(null)` | `checkStatus`(普通SELECT) + `setStatus("1")` | ✅ **同一漏洞** |
| 删除并发 | `checkStatus`(普通SELECT) | `selectByIdForUpdate` | `checkStatus`(普通SELECT) | ✅ **同一漏洞** |
| 敏感字段注入 | 无置null | saveWithItems/updateWithItems 开头置 null | 无置null | ✅ **同一漏洞** |
| resurrect 并发 | 无校验 | `if (resurrect(entity)==0) throw...` | 无校验 | ✅ **同一漏洞** |

**报告1的升级判定合理：**

- P0-3（敏感字段注入）：采购订单评为 P1，采购申请升级为 P0。**合理** — 采购订单在当时审计时也未加审核端点，风险窗口相似；但考虑到这是第三次发现同一模式（订单→入库→申请），安全债务累积，升级为 P0 可打破"修一处漏三处"的循环。
- P0-4（resurrect 并发）：采购订单评为 P1-2，采购申请升级为 P0。**合理** — resurrrect 不校验影响行数会导致并发复活时明细行互相覆盖，数据静默错乱比并发编辑更难发现。

## 五、问题 4：采购入库删除 P0 是否与增量审计 P2-1 一致？

### 结论：描述同一问题，严重度判定矛盾

**事实比对：**

| 维度 | 报告2 P0-1 | 报告3 P2-1 |
|------|------|------|
| 文件 | `MesPurchaseReceiptServiceImpl.java` | `MesPurchaseReceiptServiceImpl.java` |
| 行号 | L.107-113 | L.107-113 |
| 问题描述 | 删除操作并发击穿 | removeWithItems 未使用 FOR UPDATE 行锁 |
| 攻击场景 | 审核+删除并发→库存已增但单据被删 | 并发删除+审核→auditWithGuard 影响0行 |
| 后果评估 | 库存与单据对不上，**资损** | 实际影响有限（低频操作） |
| 严重度 | **P0** | **P2** |
| 修复建议 | 3 行改法（同报告3） | 3 行改法（同报告2） |

**交叉验证判定：P0 是正确的评级。**

理由：
1. **事实相同**：两份报告发现的是同一个代码问题（L.107-113 同一段代码），修复方案相同
2. **P0 评级依据更充分**：
   - 采购订单模块对同类问题评为 P0（且已修复）
   - 采购申请模块对同类问题评为 P0
   - `auditWithGuard` 审核端点已存在（L.117-172），删除+审核并发不是理论风险而是**实际可达**
   - 后果是财务影响（库存与单据不一致），不仅仅是"并发缺口"
3. **报告3 的降级理由不成立**："删除和审核通常不会同时发生"——但同一模块的编辑+审核并发被报告3认为是 P0 级别（已修），编辑和删除对审核的并发竞争窗口完全相同。不能因为"删除比编辑少见"就降级。
4. **报告3 的 P2-1 自身描述矛盾**：一方面说"同一 commit 内编辑/删除对称操作不一致"（承认不对称），一方面评为 P2。对称操作不一致属于审计分类标准中的"真实 bug"，应是 P0/P1。

**判定：报告2的 P0-1 和报告3的 P2-1 是同一个问题。报告3的 P2 严重度偏低，应升级为 P0 以与报告2保持一致。**

## 六、问题 5：修复优先级是否正确？

### 报告1（采购申请）优先级：正确 ✅

```
P0-1 编辑原子守卫  ← 最高优先级（一旦加审核端点就激活）
P0-2 删除原子守卫  ← 同上
P0-3 敏感字段置null ← 照抄3行代码
P0-4 resurrect 校验 ← 照抄1行代码
```

**评价：** 四个P0全是照抄采购订单已修代码，修复成本极低（~20行代码），优先级排最高是正确的。

### 报告2（采购入库）优先级：基本正确，建议微调

```
P0-1 删除加 FOR UPDATE       ← 最高优先级 ✅
P1-1 DTO 字段清理            ← 建议与 P0-1 同批修
P1-4 应付含税                ← 财务口径，建议升级优先级
P1-2 参数校验 / P1-3 N+1     ← 顺手修
P1-5 入库行关联订单行ID       ← 下迭代
```

**建议微调：** P1-4（应付未settledAmount未含税）直接影响财务数据正确性，虽不影响功能运行，但**业务数据错误**。建议从 P1 升级为至少与 P1-1/P1-2 同批处理。

### 报告3（采购订单增量）优先级：P2-1 应升级

```
P2-1 收货删除无锁  ← 应升级为 P0（见第五部分分析）
P3-1 子表逐条调API ← P3 正确
P3-2 子查询缺索引  ← P3 正确
```

**建议：** P2-1 升级为 P0 后，与采购入库 P0-1 合并为同一个修复 task（两个模块的删除路径统一加 FOR UPDATE）。

## 七、补充发现（三份报告之外）

在代码逐行核实过程中发现以下报告未覆盖的问题：

### 补充-1：采购入库 `saveWithItems` 同样缺少 `@RequestBody` 防护

- **位置：** `MesPurchaseReceiptServiceImpl.saveWithItems()` L.57-78
- **现象：** 报告2确认 `updateWithItems` 已置 null `delFlag/createBy/createTime/status`（L.91-92），但 `saveWithItems` 未做同样处理
- **风险：** 攻击者可在新建入库单 JSON 中注入 `"delFlag": 1`，导致入库单创建即进入已删除状态
- **影响程度：** 中等（新建操作通常无敏感动机，但安全边界应一致）
- **建议：** `saveWithItems` 开头加 `entity.setDelFlag(null)`

### 补充-2：采购申请 `saveWithItems` 同样缺少 `@RequestBody` 防护

已在报告1的 P0-3 中覆盖（报告1明确指出 saveWithItems 和 updateWithItems 均缺少）。

### 补充-3：三模块的 `checkStatus` 设计模式不一致

| 模块 | checkStatus 实现 | 调用点 |
|------|------|------|
| 采购订单 | **已删除** — 直接内联 `selectByIdForUpdate` | edit(L.82) / delete(L.109) |
| 采购入库 | 仍存在，两个重载：Entity版(L.257) + String版(L.265) | edit(L.83 via Controller) / delete(L.108) |
| 采购申请 | 仍存在，两个重载：Entity版(L.139) + String版(L.147) | edit(L.73) / delete(L.90) |

**建议：** 采购入库和采购申请删除 `checkStatus` 辅助方法，直接内联 FOR UPDATE 模式（与采购订单对齐）。`checkStatus` 的存在容易让后续开发者误以为"状态校验已经安全了"，实际只是普通 SELECT。
