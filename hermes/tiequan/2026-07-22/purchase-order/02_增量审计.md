## 五、新发现问题

### 🔴 P2-1（新）：收货入库 `removeWithItems` 未使用 FOR UPDATE 行锁

- **位置：** `MesPurchaseReceiptServiceImpl.java` L.107-113
- **现象：** 收货入库的 `updateWithItems` 已正确使用 `selectByIdForUpdate`（L.86），但同一文件中的 `removeWithItems` 仍用旧式 `checkStatus(id, "delete")` → `baseMapper.selectById(id)`，无 FOR UPDATE 锁
- **对比：** 采购订单模块的 `removeWithItems` 已使用 FOR UPDATE（`MesPurchaseOrderServiceImpl.java` L.109），收货模块修复时只修了编辑路径，忘了删除路径
- **影响：** 并发删除+审核时，草稿入库单可被删+同时被审核 → 审核在删除之后执行时，`auditWithGuard` 的 WHERE 已不满足（记录已被逻辑删除），影响 0 行 → 报错。**实际影响有限**（删除和审核通常不会同时发生），但严格说是并发缺口
- **建议：** 三行改法：
  ```java
  // L.107-113 改为：
  public void removeWithItems(String id) {
      MesPurchaseReceipt exist = baseMapper.selectByIdForUpdate(id);
      if (exist == null) throw new JeecgBootException("入库单不存在");
      if (!"1".equals(exist.getStatus())) throw new JeecgBootException("非草稿状态入库单禁止删除");
      ...
  }
  ```
- **评级：P2**（低频操作 + 状态校验已有部分保护，但同一 commit 内编辑/删除对称操作不一致）

### 🟡 P3-1（新）：`OrderItemsSubTable` 逐条调物料API，性能可优化

- **位置：** `OrderItemsSubTable.vue` L.53
- **现象：** `ids.map(id => queryMaterialById({ id }))` 对每个物料逐一发起 HTTP 请求
- **影响：** 10 行物料 = 10 次请求，大订单详情展开延迟明显
- **建议：** 后端 `queryWithItems` 返回物料名称/规格/单位（或新增批量查询端点），前端去掉逐条查询
- **评级：P3**（性能优化建议，非功能缺陷）

### 🟡 P3-2（新）：`markFullyReceived` 的 NOT EXISTS 子查询缺少专用索引

- **位置：** `MesPurchaseOrderMapper.java` L.30
- **SQL：** `NOT EXISTS (SELECT 1 FROM c_mes_purchase_order_item WHERE order_id = #{id} AND received_qty < quantity)`
- **现象：** V9.5.0 SQL 只建了 `idx_po_create_time` 和 `idx_po_status`（在 `c_mes_purchase_order` 表），`c_mes_purchase_order_item` 表如果没有 `(order_id)` 索引，该子查询在小数据量下无感，万级数据后性能退化
- **建议：** 下一版 SQL 加 `CREATE INDEX IF NOT EXISTS idx_poi_order_id ON c_mes_purchase_order_item(order_id)`（用 INFORMATION_SCHEMA 守卫做 MySQL 5.7 兼容）
- **评级：P3**（当前数据量下无影响，预防性优化）
