# 01_风控总报告 — 采购申请模块（单 Agent 10 视角审计）

**审计日期：** 2026-07-22
**审计对象：** `project-mes` 采购申请全栈（Entity×2 / Mapper×2 / ServiceImpl / Controller，共 6 个 Java 文件）
**执行方式：** 单 Agent 多视角切换（3 产品 + 3 研发 + 4 测试视角）
**定级方式：** 代码逐行审查 + 采购订单 P0 同类问题对照

## 总体结论

**采购申请模块代码结构与采购订单高度相似，但缺失采购订单审计后的 4 项 P0 修复。** 核心问题：编辑/删除使用"先查后写"非原子模式（采购订单 P0-3 同类）、编辑强制回写 `status="1"`（采购订单 P0-3 同类）、`@RequestBody` 直绑实体无敏感字段过滤（采购订单 P1-8 同类）、resurrect 不校验影响行数（采购订单 P1-2 同类）。

**好消息是：** 借尸还魂模式、编号唯一双保险、校验规则（日期/数量/物料）、权限注解、事务边界——这些基础功扎实，与采购订单审计时的肯定项一致。

**坏消息是：** 采购订单审计已修完的 4 个 P0/P1 问题在采购申请中全部复现。这些修复并未同步到采购申请模块。此外采购申请缺少审核端点，主流程在状态机层面断通。

## 共识 P0（代码确认属实）

### P0-1：编辑无原子守卫 + 强制回写草稿状态（与采购订单 P0-3 完全相同）

- **位置：** `MesPurchaseApplyServiceImpl.updateWithItems()` L71-85
- **核实：** ✅ 属实。流程为：
  1. L73 `checkStatus(entity, "edit")` → `SELECT ... WHERE id=?` 读状态（非原子）
  2. L75 `entity.setStatus("1")` → **强制将 status 写回 "1"（草稿）**
  3. L80 `super.updateById(entity)` → 无 `WHERE status='1'` 守卫
- **风险：** 一旦未来添加审核端点（将 status 改为非 "1"），编辑请求可与审核并发竞跑：审核先改 status→已确认，编辑随后 `updateById` 将全部字段（含 status="1"）覆盖回去→已确认的申请被静默退回草稿。**当前虽无审核端点，这是潜伏缺陷——审核端点一旦加上就立刻激活。**
- **修法：** 照抄采购订单修复方案：
  1. 编辑改 `selectByIdForUpdate`（FOR UPDATE 行锁）+ 原子读 status
  2. `entity.setStatus(null)` 而非 `entity.setStatus("1")`，防止覆盖已有状态
  3. Mapper 加 `selectByIdForUpdate` 方法

### P0-2：删除无 FOR UPDATE 锁（与采购订单 P0-3 完全相同）

- **位置：** `MesPurchaseApplyServiceImpl.removeWithItems()` L87-95
- **核实：** ✅ 属实。流程为：
  1. L90 `checkStatus(id, "delete")` → `SELECT` 读状态（非原子）
  2. L93-94 删明细 + 删主表，无 `WHERE status='1'` 守卫
- **风险：** 与 P0-1 同理——审核端点加入后，审核与删除并发可导致已确认申请被删。
- **修法：** 照抄采购订单修复：`selectByIdForUpdate` + 行锁读状态 + 原子判断。

### P0-3：`@RequestBody` 直绑实体，敏感字段可被客户端注入（与采购订单 P1-8 同类，安全视角升级为 P0）

- **位置：** `MesPurchaseApplyController.add()` L55-57、`edit()` L60-62
- **核实：** ✅ 属实。
  - Controller 的 `add(@RequestBody MesPurchaseApply entity)` 和 `edit(@RequestBody MesPurchaseApply entity)` 直接将 JSON 请求体反序列化为实体对象
  - `saveWithItems()` 和 `updateWithItems()` 中**未对 `delFlag`、`createBy`、`createTime` 做置 null 处理**
  - 采购订单已在 `saveWithItems` 和 `updateWithItems` 中加了这三行：`entity.setDelFlag(null); entity.setCreateBy(null); entity.setCreateTime(null);`
- **风险：** 攻击者可在 JSON 请求体中注入 `"delFlag": 1` 使新建申请直接进入已删除状态，或注入 `"createBy": "admin"` 伪造创建人。
- **修法：** 在 `saveWithItems()` 和 `updateWithItems()` 开头加敏感字段置 null（照抄采购订单的三行写法）。

### P0-4：resurrect 不校验影响行数，并发复活可重复插明细（与采购订单 P1-2 同类，并发视角升级为 P0）

- **位置：** `MesPurchaseApplyServiceImpl.saveWithItems()` L62
- **核实：** ✅ 属实。`baseMapper.resurrect(entity)` 无返回值检查。
  - 采购订单已修复为 `if (baseMapper.resurrect(entity) == 0) throw new JeecgBootException("...")`
- **风险：** 两个请求同时用同一已删除编号创建申请：
  1. 请求 A：`selectCount(active)=0` → `selectDeletedByCode` 找到旧记录
  2. 请求 B：`selectCount(active)=0` → `selectDeletedByCode` 找到同一条旧记录
  3. A 先执行 `resurrect`（del_flag 0→成功，影响 1 行）
  4. B 再执行 `resurrect`（del_flag 已为 0，WHERE del_flag=1 条件不满足→影响 0 行→静默成功）
  5. A 删旧明细 + 插新明细，B 也删明细（删掉 A 刚插的）+ 插新明细
  6. **最终：A 的明细被 B 覆盖，A 的用户看到的是 B 的数据。**
- **修法：** `resurrect` 调用后检查返回值，影响 0 行时抛异常。

## 视角一致肯定

以下设计/实现获得多视角一致肯定，与采购订单审计结论一致：

1. **借尸还魂模式正确** — `saveWithItems` 中 `selectDeletedByCode` → `resurrect` 保留旧 ID/创建人/创建时间，审计链完整
2. **编号唯一双保险** — 先查活跃记录（MP 正常查询），再查软删除记录（原生 SQL），最后 catch DuplicateKeyException
3. **事务边界完整** — `@Transactional(rollbackFor = Exception.class)` 覆盖所有写操作
4. **校验规则到位** — 单号非空+长度、需求日期≥申请日期、物料非空、数量>0、行号自动编号
5. **权限注解齐全** — 所有 Controller 方法有 `@RequiresPermissions`
6. **queryAll 有 1000 条上限保护**
7. **导出有 1000 条上限保护**
8. **批量删除用 `super.removeByIds` 而非循环 `this.removeById`**（已修）
9. **日期范围校验** — `requiredDate.before(applyDate)` 正确拒绝
