## 二、草案评估：三层降级方案

### 草案架构

```
Layer 1: Hook (硬门控)     ← exec 层面强制，不可绕过
Layer 2: Command (用户触发)  ← 用户决定何时执行
Layer 3: Rule (参考知识)     ← 知识库，非约束
```

### 2.1 逐层评价

#### Layer 1 — Hook（硬门控）✅ 正确

当前 10 个 hook 脚本覆盖：
- `pre-commit-check.sh` — git commit 前拦截（检查 orca-review 完成、文件边界、危险模式）
- `pre-write-check.sh` — Write/Edit 前拦截（文件边界检查）
- `pre-plan-check.sh` — Skill 调用前拦截（检查前置条件）
- `block-dangerous.sh` — 危险 Bash 命令拦截
- `session-start.sh` / `session-end.sh` — 会话生命周期

**评价**：这层完全正确。Hook 是唯一不依赖 AI 记忆的机制——exec 层在工具调用前执行，无论上下文多长都生效。草案"不动 hooks"的决策是英明的。

**建议增强**：考虑在 `pre-commit-check.sh` 中加入一个简单检查——当前会话是否执行过 `/verify`？如果没有，拦截并提示。这能把最关键的防失忆逻辑从"AI 记忆"下沉到"脚本强制"。

#### Layer 2 — Command（用户触发）⚠️ 有风险，但方向正确

草案将 `/verify` `/plan` `/orca-review` `/quality-gate` `/done` 归为用户触发命令。

**风险识别**：
- 用户触发依赖用户记得。而"记得"正是当前系统的痛点。
- 但草案的隐含假设是正确的：**用户比 AI 更适合做"何时执行"的决策**。用户知道自己改了代码、部署了、准备提交了。AI 只能靠模式匹配猜测。

**缓解措施**：
1. `pre-commit-check.sh` 已经拦截 git commit——如果 hook 增强了 verify 检查，用户即使忘记也会被拦住。
2. CLAUDE.md 的"关键规则"表（4 条核心原则）应保留作为"建议"而非"强制"。这 4 条不是触发条件，是工作哲学。
3. 可以考虑在 CLAUDE.md 末尾加一行简短提醒而非详尽触发表：
   ```
   > 💡 改完代码记得 /verify，通过记得 commit+push。
   ```
   一行话不会稀释注意力，但覆盖了 80% 的遗忘场景。

#### Layer 3 — Rule（参考知识）✅ 方向正确，不需要"缩水"

草案将 code-style / frontend / debugging 等保持为知识库。

**评价**：这层实际上不需要"缩水"——当前 19 个 rules 文件就是参考知识，它们的价值在于 AI 遇到具体问题时的精确检索，不在于被全部记住。关键调整是：

- ✅ 去掉 rule 文件中的"强制""必须自动执行"措辞
- ✅ 保留所有技术规范内容（代码模式、踩坑记录、组件用法）
- ❌ 不需要删除 rule 文件或精简内容

**code-style.md 的 150 行不是问题**——它是 AI 写代码时的参考手册，不是需要记住的触发条件。新会话加载这些规则后，AI 在遇到"怎么写 ServiceImpl"时自然会参考，不需要"强制触发"。

## 三、评审问题逐一回答

### Q1: 这个分层是否过度简化？有没有中间地带？

**结论：分层本身不过度简化，但实施方式有中间地带。**

三层模型在架构上是完备的——Hook(exec) → Command(interactive) → Rule(knowledge) 覆盖了从硬件到软件的所有执行层面。不存在"第四层"。

**中间地带在于"砍掉什么"的粒度：**

| 草案方案 | 中间地带建议 |
|----------|------------|
| workflow.md: 砍掉全部 14 条防失忆触发 | **保留 2-3 条最关键触发转为 Hook 增强** + 其余转为"常见失忆点"参考（非触发） |
| CLAUDE.md: 砍掉"写完代码自动 /verify"等描述 | **保留 4 条关键规则作为工作哲学**（改表述：从"必须自动"→"建议执行"） |
| deploy-quality-gate.md: 去掉"自动执行"措辞 | **保留流程描述，改触发措辞**：从"AI 必须自动执行"→"部署完成后，建议执行以下验证流程" |

**具体保留建议**（中间地带）：

```
保留触发 1: git commit 前 → Hook 拦截检查 /verify 是否执行（exec 层，非 AI 记忆）
保留触发 2: /plan 结束后 → CLAUDE.md 保留"建议 orca-review"（一行，非触发表）
保留触发 3: 写完代码 → CLAUDE.md 保留"建议 /verify"（一行，非触发表）
```

这三条覆盖了 80% 的真实遗忘场景，且前两条在 exec 层有硬门控兜底。

### Q2: 砍掉自动触发后，会不会导致用户忘记执行 verify/quality-gate？

**结论：短期可能略有下降，但中期不劣于当前方案。**

**证据链**：

1. **当前 14 条触发条件并不有效**。workflow.md 的 7 条"最常见失忆点"正是因为有触发条件仍然被遗忘才被记录下来的。如果 14 条触发条件真的有效，就不会有"写完代码直接结束，跳过了 /verify"的问题。这说明**触发条件的存在 ≠ 触发条件被遵守**。

2. **Hook 层提供兜底**。`pre-commit-check.sh` 在 git commit 时硬拦截。如果增强为检查 verify 执行状态，即使用户和 AI 都忘了，commit 时也会被拦住。这是比"AI 记得提示"更可靠的机制。

3. **用户记忆曲线**。新用户使用 1-2 周后会形成肌肉记忆——改代码 → /verify → commit → push。这个习惯不依赖 AI 提示，依赖重复行为。14 条触发条件反而可能导致"提示疲劳"——用户习惯性忽略。

4. **风险量化**：
   - 最坏情况：用户连续 3 次忘记 /verify，导致未验证代码 push
   - 缓解：pre-commit-check.sh 拦截（当前已有）+ 建议增强 verify 检查
   - 对比当前：14 条触发条件仍在，但 AI 在长上下文中忽略它们 → 同等风险

**建议**：实施后观察 2 周。如果 /verify 执行率下降 >30%，回滚到中间地带方案（保留 2-3 条关键触发转为 Hook 增强）。

### Q3: Rule 层缩水后，新 AI 会话还能快速理解项目规范吗？

**结论：能，且可能更好。**

**分析**：

1. **Rule 文件内容不变**。草案说的是"去掉自动触发描述"，不是说"删除 rule 文件"。code-style.md 的 150 行、frontend.md 的组件规范、debugging.md 的诊断流程——全部保留。

2. **上下文更干净 = 规范更容易被注意到**。当前 CLAUDE.md 110 行 + workflow.md 215 行（含触发表）被 AI 同时加载。去掉触发表后，workflow.md 缩减到 ~100 行。总上下文从 ~325 行降到 ~210 行，减少了 35% 的"噪声"。剩下的是真正有用的步骤清单和依赖查证。

3. **新会话的实际加载顺序**：
   - CLAUDE.md → 110 行（核心工作流）
   - 19 个 rules 文件 → 全部加载到系统提示词（无论有没有触发描述）
   - 砍掉的只是"如果 X 则必须 Y"的触发语言，不影响规范内容

4. **一个被忽视的优势**：去掉自动触发后，AI 不会在每次回复末尾机械地输出"下一步请运行 /verify"。这种机械输出在 10 轮对话后变成纯粹的噪声。减少噪声 = 提高关键信息的信噪比。

**实证**：对比 LLM 在"50 条指令"和"10 条指令"下的指令遵循率，几乎所有研究都表明指令遵循率随指令数量递减。19 个 rules 文件已经够多了，不需要在 CLAUDE.md 和 workflow.md 中重复强调。

## 五、具体改动建议（逐文件）

### 5.1 CLAUDE.md 改动

**草案方案**：
- ❌ 砍掉"写完代码自动 /verify"等自动触发描述

**建议改动**：
```diff
- > ⚠️ 写完代码必须自动 /verify。verify 通过必须 commit+push。本地后端在线必须 curl 实测。
- > 完整防失忆触发表见 `.claude/rules/workflow.md`。
+ > 💡 改完代码建议 /verify，通过后 commit+push。本地后端在线时 /verify 会 curl 实测。
```

4 条关键规则保持不变（先分析再改、改完必验证、验证必实测、简单精准），但"改完必验证"的解释从"自动跑"改为"建议执行"。

### 5.2 workflow.md 改动

**草案方案**：
- ❌ 砍掉"防失忆触发表"（14 条自动触发规则）

### 5.3 deploy-quality-gate.md 改动

**草案方案**：
- ❌ 去掉"部署后自动执行"措辞

**建议改动**：
```diff

+ **集中部署完成后，建议执行以下质量验证流程**（用户手动触发或通过 /quality-gate 命令）。
```

保留完整的执行流程、分级细则、链路匹配、报告模板——这些是 deploy-quality-gate.md 的核心价值。只改触发措辞，不改流程内容。

### 5.4 pre-commit-check.sh 增强（新增建议）

在 pre-commit-check.sh 中增加 verify 检查逻辑：

```bash
# 检查当前会话是否执行过 /verify
# 如果 staged 有 Java/Vue 变更但无 verify 记录，警告但允许跳过（非阻断）
# 这个检查不依赖 AI 记忆——是 exec 层面的硬检查
```

**注意**：这个增强超出了草案范围，但它是"把最重要的防失忆逻辑从 AI 记忆下沉到 Hook"的关键一步。

### 5.5 rules 文件无改动 ✅

19 个 rules 文件保持原样。它们的价值在于技术参考，不在于触发条件。

## 六、总体评价

### 评分（5 分制）

| 维度 | 评分 | 说明 |
|------|:--:|------|
| 架构合理性 | 5/5 | 三层模型完备，Hook(exec)→Command(interactive)→Rule(knowledge) 覆盖所有执行层面 |
| 问题诊断准确性 | 5/5 | "长上下文稀释 LLM 注意力"是真实问题，不是规则写得不好 |
| 实施粒度 | 3/5 | 砍得太彻底。建议保留 2-3 条关键触发转为 Hook 增强，7 条失忆点转为参考 |
| 风险意识 | 4/5 | 识别了核心风险（用户忘记），但缓解措施不够具体 |
| 可逆性 | 5/5 | 纯文案改动，回滚成本为零 |

**综合**: **4.4/5 — 方向正确，建议增加中间地带后实施。**

### 终极建议

**按这个顺序实施**（渐进式，每步可回滚）：

```
Step 1: 不改 workflow.md，先在 pre-commit-check.sh 增强 verify 检查
        → 验证 Hook 能否覆盖 80% 遗忘场景（观察 2 周）
        
Step 2: 如果 Hook 有效 → 砍 workflow.md 触发表，保留 7 条失忆点为参考
        → 验证 AI 行为是否退化（观察 1 周）

Step 3: 如果无退化 → 改 CLAUDE.md 和 deploy-quality-gate.md 的触发措辞
        → 完成三层降级

Step 4: 如果 Step 1 验证 Hook 不足以覆盖 → 保留 2-3 条关键触发在 CLAUDE.md
        → 中间地带方案
```

这样避免了一次性大改动导致不可预见的退化，每步都有数据支撑下一步决策。
