# /new 命令记忆卡片优化 — 方案评审

> 评审日期：2026-07-22
> 评审人：Claude Code（架构评审视角）

---

## 一、方案摘要

**问题：** `/new` 创建的新终端拿到记忆卡片后，仍然问"你要我做什么？"——用户感觉没有"续接"感。

**方案：** 三个改动（~10行）：
1. 记忆卡片模板加"🤖 恢复指令"头部
2. `--inject` 内容改为"恢复指令 + 记忆卡片"
3. "下一步"从描述性改为可执行格式

---

## 二、逐项分析

### 2.1 根因判断是否准确？

**部分准确，但不完整。**

方案将根因归结为"卡片是参考文档而非行动指令"。这个判断抓住了**次要原因**，但漏掉了**主要原因**。

**主要原因在 `new.md` 第 31 行：**

```markdown
消化完后回复ready，等待用户指令。不要主动做任何事。
```

这句话是 `--inject` 注入的 preamble，它**明确命令 AI 等待**。AI 严格遵循了这条指令——它不是在"误解"卡片，而是在**正确执行 preamble**。新终端问"你要我做什么？"不是 bug，是当前设计的预期行为。

**设计张力：** `/new` 的设计意图是"干净的指挥中心，等你下命令"；但用户的使用场景是"接续上一个终端，直接继续干活"。两者的期望冲突了。

**真正的根因链：**
```
用户期望"续接" → /new 设计是"等待" → preamble 写"不要主动做任何事"
→ AI 严格等待 → 用户感觉"全新终端，没有续接感"
```

卡片格式（参考文档 vs 行动指令）是这个链条的**下游结果**，不是根因。即使不改卡片格式，只把 preamble 从"等待用户指令"改成"继续当前任务"，AI 的行为就会立刻改变。

**结论：根因判断漏掉了 preamble 这一层。** 方案的三项改动中，改动 1 和 2 实际上是在修复 preamble 问题（通过把指令塞进卡片），但没有直接承认和修改 `new.md` 中那条"不要主动做任何事"的指令。

### 2.2 方案能否真正解决"新终端感觉全新"的问题？

**能部分解决，但有遗漏。**

| 改动 | 效果评估 |
|------|---------|
| 1. 卡片加"🤖 恢复指令"头部 | ✅ 有效——卡片从纯参考变为带指令 |
| 2. `--inject` 含恢复指令 | ✅ 有效——直接告诉 AI 继续工作 |
| 3. "下一步"可执行化 | ⚠️ 有条件有效——取决于上一个 AI 的总结质量 |

**遗漏点：**

- **`new.md` 第 31 行的 preamble 没提要改。** 如果那条"等待用户指令"不改，新的注入内容会和它冲突——一头说"立即执行"，另一头说"不要主动做任何事"。AI 面对矛盾指令时行为不可预测。

- **卡片"下一步"质量不可控。** 如果上一个终端在复杂任务的中间（比如刚 brainstorm 完还没 plan），AI 写的"下一步"可能是"进入 /plan 阶段"——这对新 AI 来说仍然不够具体。方案依赖人工写高质量的"下一步"，但这是 AI 自动生成的。

- **没有解决"续接"和"等待"两种场景的分野。** 用户有时候真的想要一个干净的指挥中心（比如上一个终端已经乱了，只想重新开始），有时候想要续接。方案把 `/new` 固定为"续接"模式，丢掉了"等待"模式的用途。

### 2.3 有没有更根本的解决方案？

**有，三个方向：**

#### 方向 A：最小改动——只改 preamble（1 行）

不碰卡片模板，只把 `new.md` 第 31 行的注入 preamble 从：
```
消化完后回复ready，等待用户指令。不要主动做任何事。
```
改为：
```
你是上一个会话的延续。阅读卡片了解上下文后，直接继续"当前会话→下一步"中的工作。
如果卡片中没有明确的下一步，则回复："记忆卡片已消化，当前进度是XXX。请告诉我要继续做什么？"
```

**优点：** 1 行改动，根因直达，不引入新复杂度。
**缺点：** 卡片本身的"下一步"可能不够具体，AI 仍然需要用户补充。

#### 方向 B：区分两种模式（推荐）

`/new` 保持现有行为（干净指挥中心，等待指令）。
新增 `/new --continue` 或 `/continue` 命令：
```
/delegate "继续当前工作：{从cleanup-context提取的任务描述}"
```
复用 `/delegate` 的完整工作流 preamble（brainstorm→plan→implement→verify），
工人拿到的不只是"继续"，还有完整的工作纪律。

**优点：** 
- 两种场景都覆盖（等待 vs 续接）
- 复用现有 `/delegate` 机制，不造新轮子
- Worker 拿到完整工作流，不会因为"不知道怎么做"而卡住

**缺点：** 多了一个命令需要维护。

#### 方向 C：统一 `/new` 和 `/delegate`

两者本质是同一机制：
```
记忆卡片 + --inject 注入 + 新终端 = 基础能力
preamble 不同 = 行为不同（等待 vs 执行）
```

可以合并为一个底层命令 + preamble 参数：
```
/delegate <任务>     → preamble=worker（执行任务）
/delegate --continue → preamble=continue（续接当前工作）
/new                 → preamble=idle（等待指令，保留现有行为）
```

**优点：** 消除重复，维护一套机制。
**缺点：** 改动范围大，需要重写两个命令。

#### 推荐

**短期（立刻做）：** 方向 A（1 行改 preamble）+ 方案的改动 3（"下一步"可执行化）。总改动 ~3 行，直接解决 80% 的问题。

**中期（积累反馈后）：** 方向 B。等用户使用改进后的 `/new` 一段时���，确认"续接"和"等待"两种场景都真实存在，再决定是否分叉。

### 2.4 边界 case 分析

| 边界场景 | 风险 | 建议 |
|---------|------|------|
| **上一个 AI 写了模糊的"下一步"** | 新 AI 拿到"下一步：采购申请需要加审核端点"，不知道具体改哪个文件、什么接口路径 | 改动 3（可执行化"下一步"）的值就在此——模板约束 AI 必须写具体路径和操作，降低此风险 |
| **任务在 brainstorm 中途** | 新 AI 看到"正在做：需求分析"，直接跳到写代码 | "🤖 恢复指令"应含阶段判断：如果"正在做"是 brainstorm/plan，则继续分析不要写代码 |
| **任务已完成但卡片没更新** | 新 AI 重复做已完成的工作，导致冲突 | 卡片加"完成检查点"字段，列出已写入的文件和已运行的验证 |
| **多项目上下文** | 上一个终端在 MES 项目，新终端可能在另一个项目 | 卡片加"当前项目"字段（已有 progress.md 追踪），恢复指令首行确认项目上下文 |
| **Orca 不可用（降级路径）** | 用户手动复制卡片到新终端，但卡片里的恢复指令不会被 `--inject` 的 preamble 强化 | 降级路径的提示文字也要对齐——告诉用户"粘贴后新 AI 会自动继续"，而不仅是"这是记忆卡片" |
| **连续多次 `/new`** | 每次生成新卡片，"下一步"越来越模糊，信息逐级衰减 | 卡片加"接力次数"计数器，≥3 次时提示用户"建议人工介入确认方向" |
| **卡片里"下一步"与 preamble 矛盾** | Preamble 说"立即执行"，但卡片"下一步"说"等用户确认后再改" | "🤖 恢复指令"应该给优先级规则：卡片中的约束（如"先确认再改"）优先于恢复指令的"立即执行" |

## 三、综合结论

### 方案评分

| 维度 | 评分 | 说明 |
|------|:--:|------|
| 问题定位 | ⚠️ 部分 | 抓住了卡片格式问题，漏了 preamble 根因 |
| 方案有效性 | ✅ 可行 | 三项改动方向正确，但需补充 preamble 修改 |
| 方案完整性 | ⚠️ 有遗漏 | 未覆盖降级路径、多阶段任务、接力衰减 |
| 复杂度 | ✅ 低 | ~10行改动，风险可控 |
| 可逆性 | ✅ 高 | 纯模板改动，随时可回滚 |

### 判定：有条件通过（Adjust）

方案方向正确，建议以该方案为基础，做以下补充后实施：

1. **P0-必改：同步修改 `new.md` 第 31 行 preamble**——把"等待用户指令"替换为恢复指令，否则新模板和旧 preamble 矛盾。
2. **P1-建议：加阶段感知**——"🤖 恢复指令"中区分当前阶段：brainstorm/plan 阶段 → 继续分析不要写代码；implement/verify 阶段 → 直接继续执行。
3. **P2-建议：加接力计数器**——防止多次 `/new` 后信息逐级衰减。
4. **P2-建议：降级路径对齐**——Orca 不可用时的提示文字也要反映"续接"语义。

### 与现有机制的关系

| 命令 | 当前行为 | 改后行为 |
|------|---------|---------|
| `/new` | 新指挥中心，等待指令 | 新指挥中心，**自动续接**（如果卡片有明确的下一步） |
| `/delegate <任务>` | Worker 执行具体任务 | 不变 |
| `/cleanup-context` | 生成记忆卡片 | 卡片模板增强（含恢复指令头部） |

**注意：** 改后 `/new` 和 `/delegate` 的行为会更接近。如果发现用户困惑两者的区别，届时考虑方向 B（分叉 `/new` 和 `/new --continue`）。

## 四、回复建议（给方案提出者）

根因判断基本正确但少了一层——**preamble 里的"不要主动做任何事"才是 AI 等待的直接原因**。卡片格式是次要因素。

方案的三项改动方向对，但建议**优先级调整**：先改 preamble（1 行，立刻见效），再改卡片模板（巩固效果）。不要反过来——改了卡片不改 preamble，新旧指令冲突，AI 行为不可预测。

另外建议考虑一个场景：用户在 brainstorm 中途执行 `/new`，新 AI 应该继续分析还是直接写代码？你的"🤖 恢复指令"需要区分这两种情况。
