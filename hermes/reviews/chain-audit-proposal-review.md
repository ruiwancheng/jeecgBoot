## 一、总体判断：方案方向正确，建议批准实施

今天的00_交叉验证报告已经用事实证明了链路视角的必要性：

- **采购申请→订单是断的**：申请无审核端点、订单无"从已审核申请生成"的接口 → 链路走不通
- **DTO字段空值**：loadOrderItemsForReceipt 返回 materialCode/materialName 为空 → 三个模块各自审计都没发现
- **严重度判定不一致**：同一段代码的删除无锁问题，入库审计评 P0，增量审计评 P2 → 交叉验证才纠偏

这些不是"哪个模块写得不好"的问题，而是"模块之间没接上"的问题。现有的10人铁拳团天然看不全——每个人只读一个模块的代码。加第11视角是正确的补位，不是锦上添花。

**判定：PASS（有条件批准），以下为详细分析和条件。**

## 二、问题1：6个检查维度是否完整？

### 逐维度评价

| # | 维度 | 评价 | 说明 |
|:--:|------|:--:|------|
| 1 | 状态机衔接 | ✅ 核心维度 | 今天已证实：采购申请 status='2'(已审核) 存在，但审核端点不存在——画了状态但走不到 |
| 2 | 接口衔接 | ✅ 核心维度 | 订单需要"从已审核申请生成"的API，跨模块依赖 |
| 3 | 数据契约 | ✅ 核心维度 | materialCode/materialName 空值就是典型契约不匹配 |
| 4 | 逆向流程 | ✅ 必要 | 入库审核失败后库存要不要回滚？中间失败的处理往往比正向更容易漏 |
| 5 | 跨模块事务边界 | ✅ 必要 | 入库审核要同时写库存+应付，事务边界在哪里？ |
| 6 | 字典/常量一致性 | ✅ 必要 | 三个模块的 status 字典值是否一致？'1' 在申请里是"草稿"还是"待审核"？ |

### 建议增加的维度

#### 维度7：权限衔接（建议增加）

**问题：** 上游模块写入的数据，下游模块的读取权限是否对等？

**示例：** 采购员创建了申请（权限 `mes:purchase:apply:add`），审核后生成订单。但订单列表页的权限 `mes:purchase:order:list` 只授权给采购经理角色 → 采购员看不到自己申请生成的下游订单 → 业务流程断裂。

**检测方法：** 比对链路上相邻模块的 Controller `@RequiresPermissions` 值，检查是否有权限缺口。

**增加理由：** 今天三份审计报告都没有提权限问题——因为每个模块单独看，权限都是"该有的都有"。只有站在链路视角才能发现"你有的权限和我需要的不一致"。

**建议优先级：** 与6个原始维度同级。

#### 维度8：时序依赖（建议增加，可作为维度4的补充）

**问题：** A 模块的状态变更后，B 模块何时、以什么方式感知？

**示例：** 申请审核通过后，是同步调订单生成接口，还是异步消息？如果是异步，延迟窗口内订单列表是否应该出现"申请已审但订单未生成"的中间态？

**检测方法：** 检查上游 Service 中是否调用了下游模块的 API（同步）还是发送了事件（异步），在报告中标注时序假设。

**建议优先级：** 作为维度4（逆向流程）的子项，不单独成维度。

### 不缺失的维度（有人可能问，但不需要）

| "缺失"候选 | 为什么不需要 |
|-----------|------------|
| 性能衔接 | 属于性能压测（测试牛马3号），不在链路审计范围 |
| UI一致性 | 不同模块的页面风格统一是前端规范问题，不是链路问题 |
| 部署顺序 | 已在 deploy-quality-gate.md 覆盖（SQL扫描），不重复 |

### 维度完整性判定：6→7

建议在方案中增加"权限衔接"作为第7维度，其余6个维度保持不变。总计7维，不膨胀。

## 三、问题2："不读代码细节"是否可行？

### 先澄清"代码细节"的定义

这个问题的关键是定义边界。我理解方案说的"不读代码细节"是指：
- **不读：** Service 实现逻辑（if-else分支、for循环体、具体的数值计算）
- **要读：** Controller 方法签名 + 参数/返回类型 + 注解、DTO 类字段定义、Entity 字段定义 + `@Dict` 注解、Mapper 接口方法签名、状态常量/枚举值

### 链路审计需要读什么才能完成7个维度的检查？

| 维度 | 需要读的代码 | 是否属于"细节"？ | 是否可避免？ |
|------|------------|:--:|:--:|
| 状态机衔接 | Entity status 字段 + 状态常量/字典 + Controller `audit` 方法签名 | ❌ 接口层 | ✅ 可控 |
| 接口衔接 | Controller `@PostMapping/@GetMapping` 路径 + 参数 | ❌ 接口层 | ✅ 可控 |
| 数据契约 | DTO 类字段名+类型 vs 下游 Entity 字段名+类型 | ❌ 结构层 | ✅ 可控 |
| 逆向流程 | Service 中 `delete/rollback` 方法存在性 + 上游调用点 | ⚠️ 需要读 Service 方法名 | ✅ 表面层 |
| 事务边界 | Service 方法上的 `@Transactional` + Mapper 中的 `FOR UPDATE` | ❌ 注解+SQL关键词 | ✅ 可控 |
| 字典一致性 | `@Dict(dicCode="...")` 注解值 vs SQL INSERT 字典值 | ❌ 注解+SQL字符串 | ✅ 可控 |
| 权限衔接 | `@RequiresPermissions` 注解值 | ❌ 注解层 | ✅ 可控 |

**结论：需要读的都是"接口表面层"——方法签名、注解、DTO字段、Enum值。** 这些不需要深入Service实现逻辑。方案说的"不读代码细节"应该是指不读业务逻辑实现，这个区分是合理且可行的。

### 如何做到既准确又低成本？

**核心策略：用 code-review-graph MCP 工具替代人工翻代码。**

链路审计Agent的工作流建议：

```
Step 1: 从 business-chains.json 读取链路定义 → 得到模块列表
Step 2: 用 query_graph_tool 批量查询各模块的 Controller 端点签名
        → query_graph_tool(pattern="file_summary", target="MesPurchaseApplyController.java")
Step 3: 用 query_graph_tool(pattern="callers_of") 追踪跨模块调用
        → 从上游 Service 找是否调了下游 Controller/Service
Step 4: 用 traverse_graph_tool 从上游 Controller 出发，深度2遍历
        → 自动发现 DTO→Entity 的字段传递链
Step 5: 对 Step 2-4 的输出做7维对照检查
Step 6: 仅当图谱信息不足以判定时，才 Read 具体文件（降级兜底）
```

**耗时估算：**
- Step 1-2：~30秒（图谱查询，不走文件IO）
- Step 3-4：~60秒（traverse + callers_of）
- Step 5：~60秒（AI分析结构化输出）
- Step 6：~30秒（兜底Read，大多数情况不需要）
- **总计：~3分钟**（与方案估算的3-5分钟吻合）

### 但有一个准确性的坑

**图谱可能不是最新的。** 如果开发者刚改完代码还没提交，或者图谱的增量更新漏了某些文件，链路审计Agent读到的接口签名可能和实际代码不一致。

**缓解措施：**
1. 链路审计Agent启动前，先调 `build_or_update_graph_tool`（增量更新，~10秒）
2. 关键判定（如"某端点不存在"）必须 Read 实际文件二次确认——不能纯靠图谱

## 四、问题3：有没有过度设计？有没有更简单的替代方案？

### 先评价方案本身的复杂度

| 维度 | 评价 |
|------|------|
| 新增Agent数 | 1个 |
| 新增报告 | 1份（链路审计报告） |
| 触发条件 | full级变更 + 命中链路 |
| 耗时 | 3-5分钟 |
| 依赖 | code-review-graph MCP（已有）|
| 需要改动的文件 | 铁拳团SKILL.md（加1个Agent定义）+ 报告模板 |

**这不是过度设计。** 加1个Agent、1份报告、3-5分钟——这是铁拳团最小的增量单元。

### 三个"更简单"的替代方案及为什么不选

#### 替代A：扩展现有Agent的提示词（不新增Agent，只改prompt）

**做法：** 让现有的10个Agent在审计时多读一个上下游模块的Controller代码。

**为什么不选：**
- 10个Agent并行，每个都读上下游 → 总文件读取量翻倍，但信息重复
- 每个Agent只从自己视角看上下游，不会产生"链路走通了吗？"这个整体判断
- 今天的三模块审计已经证明：即使10个人都读了一个模块的代码，也没人发现链路断裂

#### 替代B：把交叉验证报告（00_交叉验证报告.md）标准化

**做法：** 每次多模块审计后自动生成交叉验证报告，作为第11份输出。

**为什么不选：**
- 交叉验证是"事后缝合"——10个人各写各的，第11人来找矛盾
- 链路审计是"事前贯通"——1个人从头走到尾，主动找断裂
- 交叉验证只能发现"两个Agent对同一事实判断不一致"，不能发现"两个Agent都没看到的事实"
- 今天 DTO 字段空值就是典型案例——三个模块没人提不是因为判断不一致，是因为压根没人看跨模块的字段传递

**但交叉验证不应被替代。** 它解决的是"多Agent共识一致性"问题，和链路审计互补。

#### 替代C：静态契约文件（不跑AI，只维护一份接口契约文档）

**做法：** 在 `business-chains.json` 中声明上下游接口契约（DTO字段映射、状态码对应表），Agent只检查合规性。

**为什么不选：**
- 契约文件本身需要维护，且会和代码不同步（链路注册表腐烂问题）
- AI审计可以自动发现"代码实际在传什么"，契约文件只能检查"规定应该传什么"
- 契约文件的维护成本可能超过AI审计的3-5分钟

**但契约文件可以作为链路审计的输出物。** 即：链路审计Agent分析完之后，自动更新 `business-chains.json` 中的契约声明。这样下次审计有基线可对比。

### 判定：方案没有过度设计，反而是最小可行增量

## 五、问题4：链路审计和模块审计结果冲突怎么办？

### 冲突类型分析

冲突不是"同一个事实你说对错我说对"——链路审计和模块审计看的是不同层次：

| 场景 | 模块审计说 | 链路审计说 | 哪个对？ |
|------|----------|----------|:--:|
| DTO字段映射 | "Service 逻辑正确，字段赋值没问题" | "从订单传到入库时 materialCode 是 null" | **链路对** — 模块审计只看了自己模块的赋值代码，没追踪数据从哪来 |
| 审核端点存在性 | "申请模块功能完整" | "申请没有审核端点，订单无法从已审核申请生成" | **链路对** — 模块审计看的是"模块内部自洽"，链路审计看的是"外部可调" |
| 状态码定义 | "status 字段用 Integer，字典正确" | "申请的 status='2' 在订单里被当成 '1' 处理了" | **链路对** — 字典值本身没错，但跨模块的语义映射错了 |
| Service逻辑bug | "save() 没有校验必填字段" | "从链路看这个字段在下游必填，上游应该校验" | **不冲突** — 模块审计发现的是实现缺陷，链路审计发现的是设计缺口，两者叠加 |

### 冲突解决规则

```
规则1: 链路审计发现在模块审计范围内的问题 → 降级为"参考"，以模块审计为准
       原因：模块审计读了完整代码，链路审计只读了接口表面层

规则2: 链路审计发现跨模块衔接问题 → 升级为"决定性"，覆盖模块审计的"无问题"判定
       原因：模块审计没有跨模块视角，其"无问题"判定不适用于跨模块场景

规则3: 两者对同一代码段的严重度判定不一致 → 取高者
       原因：今天 P0 vs P2 的案例已证实，不同视角的严重度判断基于不同的影响面假设，
             链路视角通常能看到更大的影响面 → 严重度更高

规则4: 无法判定谁对的 → 标记"需人工复核"，不自动合并
```

### 落实方式

链路审计报告的每条发现，必须标注"信息来源"：
- `[来源: Controller签名]` → 高置信度
- `[来源: 图谱traverse]` → 中置信度（需要确认图谱是最新的）
- `[来源: read文件确认]` → 高置信度
- `[来源: 推断/猜测]` → 低置信度，降级为P2

这样当冲突发生时，可以根据置信度决定以哪个为准。

## 六、问题5：还有没有其他漏洞？

### 漏洞1：链路审计的触发时机有缺口

**当前方案：** 仅在 full 级变更时触发（Entity/Service/Mapper/SQL变更）

**缺口：** 链路断裂不一定需要 full 级变更。比如：
- 只改了 Controller 的 `@RequiresPermissions` 值（standard级）→ 下游模块权限断裂，不触发链路审计
- 只改了前端路由（standard级）→ 菜单跳转断裂，不触发链路审计

**建议：** 链路审计的触发条件从"full级"改为"变更涉及 business-chains.json 中任意链路的 ≥2 个模块"。不依赖变更分级，独立判断。

### 漏洞2：缺少"链路自愈"建议

**当前方案：** 链路审计只标断点和隐患

**缺口：** 用户拿到报告后需要自己判断"在哪个模块修"。比如"申请→订单是断的"，到底是在申请模块加审核端点，还是在订单模块加直接生成接口？两个做法都能接通链路，但架构影响不同。

**建议：** 链路审计报告的每个断点，附加一行"建议修复位置"（在A模块修 / 在B模块修 / 两个都要修），给出理由（如"在A模块加审核端点更符合业务语义，因为审核是对申请的审批行为"）。

### 漏洞3：链路审计结果没有反馈到链路注册表

**当前方案：** 审计报告是一次性产物

**缺口：** 下次部署时的 deploy-quality-gate 看不到上次链路审计的结果。如果审计发现"申请→订单接口缺失"，这是已知缺陷，下次部署申请模块时应该提醒"链路仍有未修复断点"而不是重新审计。

**建议：** 链路审计报告更新 `business-chains.json` 中的 `chains.<name>.health` 字段：

```json
"采购链路": {
  "health": {
    "lastAudit": "2026-07-22",
    "status": "broken",          // "healthy" | "degraded" | "broken"
    "openGaps": [
      "申请无审核端点",
      "入库DTO缺少materialCode/materialName"
    ]
  }
}
```

deploy-quality-gate 读取 `health.status`，`broken` 时自动提醒但不阻塞（影子模式）。

### 漏洞4：循环链路未覆盖

**当前方案：** 假设链路是单向的（申请→订单→入库→台账）

**缺口：** 实际业务中存在循环：
- 退货→重新入库→重新销售（销售链路的反向）
- 部分收货→剩余数量回写到订单→再次收货（采购链路内循环）
- 生产退料→退回库存→再次领料（生产链路内循环）

单向遍历会漏掉回环中的状态不一致。

**建议：** 链路审计Agent在遍历时，额外检查：如果下游有"反向操作"的端点（如退货、退料），是否在上游有对应的状态回退逻辑。

### 漏洞5：Agent设计中没有定义其"角色名"

**小问题但容易漏：** 方案说"第11视角"，但没有给这个Agent起名字。

**建议：** 命名为"链路人1号 — 端到端链路贯通视角"，与现有10个Agent的命名规范保持一致。角色定位：不是产品/研发/测试任一梯队，是独立于三梯队之外的"架构集成"角色。

## 七、综合判定与实施建议

### 判定：有条件批准

| 条件 | 说明 | 是否阻塞实施？ |
|------|------|:--:|
| 增加第7维度"权限衔接" | 补齐维度缺口 | 否，可v1.1补充 |
| 明确"不读细节"的边界定义 | 避免Agent过度简化或过度深入 | **是，v1.0必须** |
| 链路审计触发条件改为"跨≥2模块" | 而非仅full级 | **是，v1.0必须** |
| 建立冲突解决规则 | 防止两个审计互相打架 | **是，v1.0必须** |
| 审计结果回写 health 字段 | 非阻塞 | 否，可v1.1补充 |
| 给Agent起名 + 定义角色 | 命名规范 | 否，实施时顺手做 |

### 推荐实施步骤

```
Phase 1 (v1.0, 本次实施):
  1. 铁拳团SKILL.md 新增"链路人1号"Agent定义（7个维度+边界定义）
  2. 报告模板新增链路审计报告（文件名: 13_链路审计报告.md）
  3. 触发条件：变更涉及 business-chains.json 中任意链路 ≥2 模块
  4. 冲突解决规则写入 audit-classification.md

Phase 2 (v1.1, 收集数据后):
  5. 链路审计结果回写 business-chains.json health 字段
  6. deploy-quality-gate 读取 health 状态提醒
  7. 循环链路检测
```

### 一句话总结
