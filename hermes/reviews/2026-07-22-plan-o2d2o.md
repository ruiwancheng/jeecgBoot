# plan 评审 — O2D2O 链路实施方案（order→delivery→outbound）

> **评审视角：** 架构/实现可行性 — 文件清单、自动vs手工取舍、并发幂等、遗漏联动、与已有校验的冲突
> **评审对象：** 销售订单→发货单→出库单链路 2 项新增改动
> **日期：** 2026-07-22
> **代码基准：** `MesSalesOrderServiceImpl.release()` / `MesDeliveryNoteServiceImpl.sign()` / `MesSalesOutboundServiceImpl.audit()` 当前实现

---

## 评审结论

**方案方向正确，但需要补 4 个实现细节后可通过。**

核心逻辑（下达自动生成发货单 + 签收联动应收）与出库模块已有的 `audit()` 模式（原子改状态→副作用→下游联动）一致，可行性高。但存在 4 个待明确点：① 文件清单不完整（至少需 6-7 个文件）；② 多发货单场景下"已有则跳过"的幂等判断规则模糊；③ sign 联动应收时未说明如何处理"一出库单多次签收"的并发；④ **发现了前置缺陷**：出库审核 `audit()` 中首次部分出库就无条件将发货单状态 2→3，导致 sign 可被提前调用——这个缺陷若不修，sign 联动应收的实施意义打折。

### 遗漏 2：多发货单场景下"已有则跳过"的判断规则模糊

草案描述"已有发货单则跳过"，但当前系统**支持同一订单创建多个发货单**（`checkDeliveryQty` 已聚合所有未取消发货单的已发量）。需要明确：

| 场景 | 预期行为 | 幂等判断 |
|------|---------|---------|
| 首次下达（无任何发货单） | 创建草稿发货单，明细=全部订单行 | ✅ 明确 |
| 下达生成后用户删除了发货单 | 再次下达？还是 skip？ | ⚠️ 建议 skip——用户主动删除说明"不需要"，自动重建违反用户意图 |
| 已有 1 个草稿发货单（上次自动生成还没处理） | **跳过**（不重复创建） | ⚠️ 需按 `salesOrderId + status='1'` 查 |
| 已有 1 个已提交/已出库发货单（部分发货） | 创建**新的**草稿发货单，明细=剩余未发量 | ⚠️ 此时"已有"=草稿态才跳过，已提交不跳过 |
| 全部已发货（无剩余量） | 不应创建（数量=0） | ⚠️ 需先判断是否有剩余 |

**建议的幂等规则：**
```java
// 查询该订单是否已有草稿态发货单
LambdaQueryWrapper<MesDeliveryNote> dnQw = new LambdaQueryWrapper<>();
dnQw.eq("sales_order_id", orderId).eq("status", "1");
if (baseMapper.selectCount(dnQw) > 0) return; // 已有未处理的草稿，跳过
// 否则汇总已发货量，计算剩余→生成新发货单
```

### 遗漏 3：sign 联动应收时需处理"一出库单多签收"并发

草案描述"找到关联出库生成的AR(AR-出库code)→update status"。实际需处理：

**a) 一个发货单可能对应多个出库单。** 当前 `MesSalesOutbound` 表有 `deliveryNoteId` 字段，sign 时应查出该发货单关联的**所有出库单**，再逐一查对应应收。

**b) AR 是否存在不确定。** 出库 `audit()` 中 AR 生成用 `DuplicateKeyException` 静默吞异常（L.143），意味着 AR 可能因并发插入失败而实际不存在。sign 时应检查 AR 是否存在，缺失时报错而非静默跳过。

**c) AR 状态更新需原子守卫。** 应新增 Mapper 方法：
```java
@Update("UPDATE c_mes_receivable SET status = '2', update_by = #{updateBy}, update_time = #{updateTime} WHERE id = #{id} AND status = '1'")
int confirmWithGuard(@Param("id") String id, @Param("updateBy") String updateBy, @Param("updateTime") Date updateTime);
```
防并发 sign 重复确认。

**建议的 sign 实现骨架：**
```java
// 1. 原子改状态（已有 signWithGuard）
int rows = baseMapper.signWithGuard(id, username, now);
if (rows == 0) throw ...;
// 2. 查该发货单的所有已审核出库单
List<MesSalesOutbound> obs = outboundMapper.selectByDeliveryNoteId(id, "2"); // status=已审核
// 3. 逐一出库单找 AR 并确认
for (MesSalesOutbound ob : obs) {
    MesReceivable ar = receivableMapper.selectBySourceBillId(ob.getId());
    if (ar == null) throw new JeecgBootException("应收记录缺失，签收前请确认出库[" + ob.getCode() + "]");
    int arRows = receivableMapper.confirmWithGuard(ar.getId(), username, now);
    if (arRows == 0) throw new JeecgBootException("应收[" + ar.getCode() + "]状态已变更，请刷新");
}
```

### 风险 4（前置缺陷）：部分出库后发货单状态过早变更为 '3'，sign 可被提前调用

**位置：** `MesSalesOutboundServiceImpl.audit()` L.124-126

**现状：**
```java
// 3. 联动更新发货单状态 待出库(2)→已出库(3)
if (e.getDeliveryNoteId() != null) {
    deliveryNoteMapper.updateStatus(e.getDeliveryNoteId(), "3", "2", username, now);
}
```

**问题：** 这段代码在**每次**出库审核后**无条件**将发货单状态 2→3。`updateStatus` 的返回值被**忽略**（不判断 rows==0）。场景：
```
发货单A: 物料X qty=10, 物料Y qty=5
出库单1: 物料X actualQty=10 → 审核 → delivery status 2→3 ✓
出库单2: 物料Y actualQty=5  → 审核 → delivery status 2→3 失败(已是3，oldStatus=2不匹配)
                                              → 但 rows==0 未被检查，静默成功
→ sign 在只有 X 出库后即可调用，Y 还未出库！
```

**影响：** 若 sign 联动应收，而此时只出了部分物料，应收确认的金额 = 出库单1的金额（仅物料X），缺失物料Y的应收。客户签收后应付金额对不上。

**建议：** 仿照订单 `shipWithGuard`（L.164-171 的 `allShipped` 判断），发货单状态 2→3 应改为**条件判断**：汇总该发货单所有出库的实出量，与发货数量逐行比较，全部足量才置 3。修复代码：
```java
// 判断该发货单是否全部出库完成
boolean allOutbounded = checkAllOutbounded(e.getDeliveryNoteId());
if (allOutbounded) {
    deliveryNoteMapper.updateStatus(e.getDeliveryNoteId(), "3", "2", username, now);
}
// 否则保持 status='2'（待出库，允许继续出库）
```

**这是 sign 联动应收的前置条件修复——应先修此缺陷，再做 sign→AR。**

## 💡 优化建议

### 建议 1：release 事务边界需明确

`release()` 当前只有一行 `releaseWithGuard`。新增发货单自动生成后，整个操作需要在**同一事务**内完成：
```java
@Override @Transactional(rollbackFor = Exception.class)
public void release(String id) {
    // 1. 原子状态变更（已有）
    String username = getCurrentUsername(); Date now = new Date();
    int rows = baseMapper.releaseWithGuard(id, username, now);
    if (rows == 0) throw ...;
    // 2. 自动生成发货单（新增）
    generateDraftDeliveryNote(id, username, now);
}
```
如果 ② 失败抛异常 → 事务回滚 → 订单状态回到 '2'。这是正确的业务语义（下达失败不应该部分成功）。

---

### 建议 2：release 自动生成应 refer 出库模块的已有模式

出库模块的 `saveWithItems` 已经证明以下模式可用：
- `FOR UPDATE` 锁订单 → 防并发
- `getNextCode(MES_BIZ_CODE.XXX)` → 自动编码
- `借尸还魂` → 编码复用
- `saveItems` 逐行 INSERT

release 自动生成发货单时，可直接调用 `MesDeliveryNoteServiceImpl.saveWithItems()`（通过注入 Service 而非 Mapper），复用已有的校验 + 编码逻辑 + 事务管理，减少重复代码。

---

### 建议 3：sign 不应处理库存（职责清晰）

草案未提及库存，出库 `audit()` 已扣库存。sign 是"客户收到货"的确认，不涉及实物移动。✅ 无需额外处理。但如果未来增加"签收时发现破损→退货"场景，库存调整应在退货模块独立处理，sign 本身不应混合退货逻辑。

---

### 建议 4：发货单 sign 后考虑是否需要联动更新订单状态为"已签收"

当前订单状态机：草稿(1)→已审核(2)→已下达(3)→已发货(4)→已关闭(5)/已取消(6)。没有"已签收"状态。如果业务上需要区分"已发货"和"客户已签收"，需新增状态 '7' 或在 delivery note 签收时保持订单状态不变。当前方案选择不更新订单状态，这在"发货≠签收"的业务模型下是正确的——订单状态追踪到"已发货"为止，签收属于物流确认。
