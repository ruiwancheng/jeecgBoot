## 一、方案方向是否正确？有没有过度设计？

### 方向：✅ 正确

"假绿灯"问题的根因判断准确。当前 gen-tests 的 2 类测试 + 8 条自定义规则全部是**单端点维度**——每个测试只调用一个 API，验证一个 Controller 方法的输入输出。这就像检查每个汽车零件合格，但从不把车开出车库。采购链路的 7 个真实 bug（审核缺失、DTO 空值、编辑无锁、删除无锁、敏感字段注入、resurrect 并发、反审核缺失）全部是**跨操作场景**——需要 B 操作在 A 操作之后执行才能暴露。单端点测试对这类问题确实 100% 盲区。

### 过度设计风险：⚠️ 存在

方案的 3 个改动点中，第 3 步（生成端到端链路测试）的野心过大：

```
创建申请→审核→加载到订单→创建订单→审核→加载到入库→创建入库→审核→验证库存→验证应付→反审核
```

这是一个 **11 步的完整业务流程测试**。自动生成这种测试面临的挑战：

1. **状态转移知识不在注解层**：gen-tests 的核心能力是"从 Controller 注解推导测试"。但链路测试需要的知识（"申请审核后状态变为'已审核'""只有'已审核'的申请才能生成订单"）存在于 ServiceImpl 的 if-else 分支里，Controller 注解上没有任何线索。

2. **每步输出是下步输入**：步骤 2（审核）需要步骤 1（创建）返回的 ID。步骤 4（生成订单）需要步骤 2 改变的状态。自动生成的代码必须正确解析 JSON 响应、提取字段、拼装到下一个请求。这已经不是"模板生成"而是"程序合成"。

3. **错误传播雪崩**：如果步骤 3 失败，步骤 4-11 全失败。测试报告显示 9 个 FAIL，但实际上只有 1 个根因。调试效率比单端点测试差一个数量级。

### 建议：分两期

- **第一期（立即可做）**：生成 **2-3 步的"微链路"测试**（详见第四节替代方案）
- **第二期（数据驱动）**：等第一期跑出误报率数据后，再决定是否扩展到完整链路

## 二、链路测试生成是否可行？自动生成的难度在哪？

### 可行性：⚠️ 有条件可行

自动生成链路测试的输入源和难度分析：

| 需要的信息 | 来源 | 自动化难度 |
|-----------|------|:--:|
| 链路有哪些步骤 | `business-chains.json` 的 `chains.<name>.flow` | 🟢 低（已有结构化数据） |
| 每步对应哪个 API | `chains.<name>.criticalPaths` + Controller 扫描 | 🟡 中（criticalPaths 目前只有采购链路有数据，销售/生产链路为空） |
| 步骤间的数据传递 | 前一步的响应 JSON + 后一步的请求参数 | 🔴 高（需要理解 JSON 结构、字段映射） |
| 状态转移条件 | 无结构化来源，需读 ServiceImpl 代码 | 🔴 高（当前 gen-tests 不读 ServiceImpl） |
| 测试数据（供应商/物料/仓库） | 无，需预置种子数据 | 🟡 中（可以硬编码已知 ID） |
| 逆向流程（反审核/取消） | `chains.<name>.flow` 未声明 | 🔴 高（需要知道"哪些操作可逆"） |

### 核心难点排序

1. **状态转移建模**（最难）：gen-tests 只知道"有个 PUT /apply/audit 端点"，不知道"调它之前必须调 POST /apply/add 且 add 返回的 status 必须是'待审核'"。这个知识在 `MesPurchaseApplyServiceImpl.audit()` 的守卫条件里。当前 gen-tests 不读 ServiceImpl。

2. **响应-请求字段映射**：步骤 1 返回 `{result: {id: "abc123"}}`，步骤 2 需要 `{id: "abc123"}`。自动生成器需要理解"步骤 1 的 `result.id` 对应步骤 2 请求体的 `id` 字段"。这实际上要求 gen-tests 变成一个轻量的 API 编排引擎。

3. **错误定位**：11 步的链式测试，第 8 步失败时，是人去排查还是 AI 去排查？当前单端点测试的"失败→读报错→定位"流程在链路测试中会成倍复杂。

## 三、会不会和现有模块测试重复？怎么避免冗余？

### 会重复，而且重复不是坏事，但不能无脑重复

当前 `purchase.test.js` 的结构是：

```
1.1 查询空列表 → 1.2 空code被拦截 → 1.3 正常新增 → 1.4 重复编码被拦截 → 1.5 列表查询 → 1.6 按ID查询 → 1.7 编辑 → 1.8 删除
2.1 空供应商被拦截 → 2.2 正常新增 → 2.3 列表查询 → 2.4 日期校验 → 2.5 queryById
3.1 不存在订单被拦截 → 3.2 草稿订单入库被拦截 → 3.5 空仓库被拦截
4.1 台账列表 → 4.2 台账queryAll
```

如果新增的链路测试又做一遍"新增申请→校验空code→校验重复code"，那就是**冗余**——这些断言单端点测试已经覆盖了。

### 避免冗余的策略

**链路测试只做"单端点测试做不到的事"**：

| 测试层面 | 测什么 | 不测什么 |
|---------|--------|---------|
| 单端点测试（现有） | 单个 API 的输入校验、边界值、权限 | — |
| 链路测试（新增） | **跨步骤的状态一致性、数据传递正确性、副作用验证** | 不重复单端点已有的输入校验 |

具体来说，链路测试的每个步骤只断言"链路特有"的事：

```
步骤: 创建申请 → 断言: 返回 status='待审核'，不重复测空code/空items
步骤: 审核申请 → 断言: status 变为 '已审核'，不重复测不存在的ID
步骤: 生成订单 → 断言: 订单关联了申请ID、明细行数量一致
步骤: 审核订单 → 断言: 订单 status='已审核'，申请 status 未变
步骤: 入库     → 断言: 入库单关联订单ID、可收数量已扣减
步骤: 审核入库 → 断言: 库存增加、应付生成
步骤: 反审核   → 断言: 库存扣回、应付取消、状态回退
```

**关键设计原则：链路测试的 assert 不包含"code=200"或"必填校验"——这些留给单端点测试。链路测试只 assert 跨步骤的状态变化和数据传递。**

### 与铁拳团链路审计（链路人1号）的关系

链路人1号是**静态分析**——读 Controller 签名、Entity 注解，判断"接口是否存在""类型是否匹配"。不实际调 API。

链路测试是**动态验证**——实际调 API，判断"数据真的流过去了"。

两者互补：
- 链路审计发现"入库 DTO 缺少 materialName 字段" → 静态分析能发现
- 链路测试发现"审核入库后库存没增加" → 只有动态验证能发现

**但二者有信息重叠**。链路审计的 7 个维度（状态机衔接、接口衔接、数据契约等）已经覆盖了链路测试的部分断言。建议：链路测试的断言设计应**优先覆盖链路审计无法静态判定的场景**（如运行时事务行为、实际数据库状态）。

## 四、有没有更简单的替代方案？

### 替代方案 A：微链路测试（推荐 ✅）

不生成 11 步的完整链路测试，只生成 **2-3 步的"邻接模块测试"**：

```
# 不是这样（11步）:
创建申请→审核→生成订单→创建订单→审核→加载→创建入库→审核→验证库存→验证应付→反审核

# 而是这样（每段2-3步，独立文件）:
purchase-apply-order.chain.test.js:    创建申请 → 审核 → 验证可被订单加载
purchase-order-receipt.chain.test.js:  创建订单 → 审核 → 验证可被入库加载
purchase-receipt-finance.chain.test.js: 创建入库 → 审核 → 验证库存+应付
```

**优势：**
- 每段独立运行，失败不传播
- 生成难度大幅降低（只需知道相邻两个模块的接口）
- 可以渐进式覆盖——先做申请→订单，再做订单→入库
- 与 `business-chains.json` 的 `criticalPaths` 数组天然对齐

### 替代方案 B：增强现有单端点测试的"上下文断言"（更简单）

不新增测试文件，在现有单端点测试中追加"链路上下文"步骤：

```javascript
// 在 purchase.test.js 的 1.8 删除申请 之前插入:
// [CHAIN] 审核后验证下游可加载
r = await api('PUT', '/mes/purchase/apply/audit', { id: applyId });
assert(r.code === 200, '[CHAIN] 审核申请成功');
// 验证：已审核的申请可以被订单加载
r = await api('GET', '/mes/purchase/order/loadApplyItems?applyId=' + applyId);
assert(r.code === 200 && r.result?.length > 0, '[CHAIN] 已审核申请可加载到订单');
```

**优势：** 零新文件、零新工具、改动量最小。缺点是会让现有测试文件变长。

### 替代方案 C：只做"关键路径"测试（最小化）

只测 `business-chains.json` 中 `criticalPaths` 数组里的端点组合。目前只有采购链路有 3 条 criticalPath：

```json
"criticalPaths": [
  "POST /mes/purchase/receipt/add → 校验订单存在+状态+超量",
  "PUT /mes/purchase/receipt/audit → 原子扣减+库存更新+应付生成",
  "POST /mes/purchase/order/add → 供应商校验+金额重算"
]
```

每条 criticalPath 生成一个测试——3 个测试覆盖采购链路的核心风险点。成本最低，收益集中。

### 对比

| 方案 | 开发量 | 维护成本 | 覆盖度 | 假绿灯风险 |
|------|:--:|:--:|:--:|:--:|
| 原方案（完整链路） | 🔴 高 | 🔴 高 | 🟢 高 | 🟢 低 |
| **A: 微链路测试** | 🟡 中 | 🟡 中 | 🟡 中 | 🟡 中 |
| B: 上下文断言 | 🟢 低 | 🟢 低 | 🟡 中 | 🟡 中 |
| C: 关键路径 | 🟢 低 | 🟢 低 | 🔴 低 | 🔴 高 |

**推荐 A + C 组合：** 先对已有 criticalPaths 的链路生成微链路测试，跑 2 周看假绿灯率变化，再决定是否扩展到完整链路。

## 五、其他漏洞

### 5.1 R009 不应该是"规则"——它是不同类别的东西

R001-R008 都是"单端点维度的断言模板"（传入 X → 期望 Y）。链路测试是"多步骤编排 + 跨步骤断言"，结构和生成逻辑完全不同。把 R009 塞进 `gen-tests-rules.json` 会让规则文件承担两种不同职责。

**建议：** 链路测试配置独立存储，例如在 `business-chains.json` 的每个链路下增加 `chainTests` 配置：

```json
"采购链路": {
  "chainTests": {
    "enabled": true,
    "segments": [
      {
        "name": "申请→订单",
        "steps": ["createApply", "auditApply", "verifyOrderLoadable"],
        "assertions": ["statusTransition", "dataPassThrough"]
      }
    ]
  }
}
```

### 5.2 测试数据依赖未解决

链路测试需要预置的参考数据：供应商 ID、物料 ID、仓库 ID、有效的字典值。当前 `purchase.test.js` 硬编码了 `temp_s_001`、`m001`、`wh001`——这些在生产环境可能不存在。

**建议：** 在 gen-tests SKILL.md 中增加"测试数据引导"步骤——在生成链路测试前，先从对应 Controller 的 `queryAll` 接口获取第一条可用数据作为测试参数。或者在链路测试文件头部声明依赖数据：

```javascript
// @test-data-deps: supplierId=第一个供应商, materialId=第一个物料, warehouseId=第一个仓库
```

### 5.3 执行时间没有估算

单端点测试跑完采购模块约 30 秒（22 个断言）。11 步的完整链路测试（含等待、数据准备、清理）预估需要 3-5 分钟。如果 4 条链路都生成，测试总时间从 2 分钟变成 15-20 分钟。

**建议：** 链路测试默认不跑，只在 full 级变更时触发（与 `deploy-quality-gate.md` 的分级策略对齐）。日常开发中跑单端点测试就够了。

### 5.4 测试隔离问题

链路测试会创建真实数据。如果测试中途失败，残留数据可能影响下次运行（如"编码已存在"导致步骤 1 失败）。

**建议：** 所有链路测试使用带时间戳的唯一编码（如 `CHAIN-TEST-{timestamp}`），并在文件顶部声明 `beforeAll` 清理逻辑（按编码前缀批量删除）。或者支持 `--cleanup-only` 模式。

### 5.5 gen-tests 定位漂移

gen-tests 当前是"纯生成工具"——从 Controller 代码生成测试，不执行测试。加了链路测试后，gen-tests 的行为边界的模糊了：它需要"理解业务含义"（"审核"意味着状态从 A 变成 B），这超出了"从注解推导"的范畴。

**建议：** 链路测试的生成逻辑应独立于 gen-tests 的注解推导逻辑。gen-tests 继续做它擅长的事（单端点测试），链路测试的生成作为一个**独立的生成阶段**或甚至**手动维护的模板 + 参数填充**。

## 附录：如果只做最小可行版（MVP）

MVP 范围：**一段微链路测试 + 一条 criticalPath + 一个模块对**

目标：验证"链路测试能否发现单端点测试发现不了的问题"

具体做法：
1. 手写一个 `purchase-order-receipt.chain.test.js`（不做自动生成）
2. 覆盖 `POST /receipt/add → 校验订单存在+状态` 这条 criticalPath
3. 步骤：创建订单 → 审核 → 创建入库（正常） → 创建入库（超量，期望拦截）
4. 跑 2 周，统计"链路测试发现了多少单端点测试漏掉的问题"
5. 数据达标后，再投入 gen-tests 自动生成

**这样做的理由：** 先证明链路测试有价值，再投入工程化。避免花 3 天做自动生成，结果发现链路测试的增量价值没有想象中大。

---

*评审结论：方案方向正确但范围过大。建议缩小到微链路测试 + 先手动验证价值 + 数据驱动扩展。R009 不应放入 gen-tests-rules.json。*
