# 评审输入：/decompose 命令设计方案

## 背景

用户在 JeecgBoot 项目中开发模块时，遇到大型任务管理痛点：
1. 单次 brainstorm/plan 把整个大功能塞进单个上下文，token 暴涨触发限制
2. orca-review 每次加载 ~150K tokens 上下文（22 rules + 3 CLAUDE.md + 70 skills）
3. 开发环境被搞崩（多 worker 并发改同模块、Maven 编译锁死、DevTools 热重载叠加 OOM、Vite 缓存污染）

用户选择方案 A（手动切片 + 串行标准工作流），并提出关键调整：
- **不按"后端到前端"分层切**（中间状态无法手工验证）
- **按"端到端可手工验证"切**（每个切片能立刻在浏览器里走一遍）
- **一步步手工验收**，把控质量

## 草案：垂直切片（Vertical Slicing）方案

### 核心拆分原则

> 每个切片 = 一个端到端可手工走通的最小业务场景
> 从数据库到前端都通，能在浏览器里点一遍看到结果。

### 主动警告的反模式（5 条）

| 反模式 | 为什么不能用 |
|--------|-------------|
| ❌ "先做完所有 Entity" | 用户看不到结果，无法验收 |
| ❌ "先做完所有 Service" | 没有 Controller 调用，等于白做 |
| ❌ "先做完所有 Vue 列表" | 没有增删改，只是花瓶页面 |
| ❌ "先做完所有后端接口" | 没有前端页面，等于不可用 |
| ❌ 按"代码文件类型"分片 | 任何一片都跑不通 |

### 切片 4 个必备要素

1. **业务名 + 用户操作路径**
   - 例："新建订单" — 浏览器点"新建"→ 填客户+物料 → 保存 → 列表出现新行
2. **验收标准（UI 上能看到什么）**
   - 例："列表页显示新订单，客户名/总金额正确" — 而不是 "Service 返回 Page<XxOrder>"
3. **依赖关系**
   - 例："依赖切片 1（订单主表已存在）"
4. **风险等级**（高/中/低）
   - 高 = 改 Entity / SQL / 状态机
   - 中 = 改 Service / Controller
   - 低 = 改 Vue / 加字段

### 示例：销售订单模块 → 切 6 片

1. 📦 新建订单（最小闭环）：列表→新建→填客户+物料→保存→列表出现。中风险
2. 🔍 订单查询/筛选：列表→输入条件→列表过滤。低风险
3. ✏️ 订单编辑：列表→点击行→编辑→保存。中风险。依赖 1
4. 🗑️ 订单作废（带确认）：列表→点击作废→确认→状态变更。中风险。依赖 1
5. 🔄 订单审核流：提交→审核→通过/驳回。高风险（状态机）。依赖 1, 4
6. 📋 订单物料明细（主子表）：详情页→添加物料行→保存。高风险（主子表 SQL）。依赖 1

### 关键设计点

1. **首个切片必须能跑通最小闭环**：打开页面 → 新建一条 → 列表看到
2. **风险片单独成片**：状态机、SQL 改动、Entity 改动单独评审
3. **依赖关系显式列出**：不按顺序做会失败，命令会强制提醒
4. **每片完成后强制 commit**（`slice-<N>-<业务名>`），崩了回退到上一个 commit 锚点

### 拟落地的产出物

1. `.claude/commands/dev/decompose.md` — `/decompose <大任务>` 命令文件
2. `.claude/skills/decompose/SKILL.md` — 拆分方法论、模板、反模式清单

## 待评审问题

1. **拆分原则是否完整**：4 个必备要素够不够？是否需要补充"工作量评估"、"rollback 策略"？
2. **反模式清单覆盖度**：5 条反模式是否覆盖了典型错误？还有没有其他常见反模式（如"按周/天分片"、"按用户角色分片"）？
3. **切片粒度评估**：销售订单示例的 6 片是合适的粒度吗？会不会太细（切片 2、3 单独成片可能过碎）？或者太粗（切片 6 主子表可能过于复杂）？
4. **执行流程设计**：每片强制 commit + 健康检查是否合理？要不要在命令里内嵌 verify 步骤？是否需要状态持久化（记录已完成切片）？
5. **风险等级标准**：高/中/低的判定标准（Entity/SQL/状态机=高）是否合理？是否需要更细粒度？
6. **现有命令集成**：和 `/brainstorm`、`/plan`、`/orca-review`、`/verify`、`/done` 的衔接是否自然？
