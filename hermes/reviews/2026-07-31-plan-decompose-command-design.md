## 总体评价：方案方向正确，5 个关键补充 + 2 个风险警示

垂直切片拆分大型任务是正确的策略。草案的核心洞察——"按端到端可手工验证切，不按代码文件类型切"——精准命中痛点。以下按 6 个问题维度逐项评审。

---

## 一、拆分原则完整性

### 现有 4 要素评估

| 要素 | 覆盖度 | 评价 |
|------|:--:|------|
| 业务名 + 用户操作路径 | ✅ | 必需，定义 What |
| 验收标准（UI 可见） | ✅ | 必需，定义 Done |
| 依赖关系 | ✅ | 必需，定义 Order |
| 风险等级 | ✅ | 必需，定义 Review 深度 |

### ⚠️ 缺失要素：建议补充 2 项

#### 5. 预期工作量（估算，非承诺）

**为什么需要：** 用户用 `/decompose` 是为了"把大任务切成能管理的小片"。如果用户看不到每片大概多大，就无法判断切片是否合理——可能切片 1 需要 2 小时、切片 6 需要 2 天，但都被标记为"一片"。

**建议：** 用 T 恤尺码（S/M/L/XL），不是人天：
- S = 预计 1-2 次 AI 交互完成（如加一个字典下拉）
- M = 预计 3-5 次交互（如新增一个 CRUD 端点）
- L = 预计 5-10 次交互（如主子表+物料选择+成本计算）
- XL = 需要进一步拆分（/decompose 递归）

**理由：** 人天估算在 AI 辅助开发中意义不大（AI 写代码快但审核慢），交互次数更贴近实际体验。

#### 6. Rollback 策略（可选，高风险片必填）

**为什么需要：** 草案说了"崩了回退到上一个 commit 锚点"，但没说回退后怎么恢复**数据**——如果切片 3 的 SQL 迁移脚本已经执行、切片 5 发现设计错误需要回退，仅仅是 `git reset --hard` 不够，数据库迁移不可逆。

**建议：** 风险=高 的切片必须写一句 rollback 策略：
- "回退：git reset --hard slice-2 + 手动 DROP 新表"（DDL 新增）
- "回退：git reset --hard slice-1，数据库无影响"（仅代码改动）
- "回退：git reset --hard slice-4，数据迁移脚本需手工逆向"（有数据变更）

### 结论

4 要素 → **6 要素**（+ 预期工作量 + Rollback 策略）。工作量必填，rollback 仅高风险片必填。

## 二、反模式清单覆盖度

### 现有 5 条的评估

| # | 反模式 | 命中率 | 评价 |
|---|--------|:--:|------|
| 1 | "先做完所有 Entity" | 高 | 经典错误，必须警告 |
| 2 | "先做完所有 Service" | 高 | 同上 |
| 3 | "先做完所有 Vue 列表" | 中 | 前端可能犯 |
| 4 | "先做完所有后端接口" | 高 | 后端优先原则的误用 |
| 5 | 按"代码文件类型"分片 | 高 | 最抽象的反模式，应排第一 |

### ⚠️ 建议补充 3 条反模式

#### 6. ❌ "第一个切片把数据库全建好"

**为什么不能用：** 比"先做完所有 Entity"更隐蔽——表面上是"端到端"，实际上把 10 张表的 DDL 塞进切片 1。后续切片如果用不到某些表，这些表就是未经验证的"僵尸 schema"，字段设计错误要到几片之后才发现（那时已有数据）。

**正确做法：** 每个切片只建自己需要的表/字段。切片 1 建 1-2 张核心表，后续切片通过增量 SQL 加字段/加表。

#### 7. ❌ "按菜单结构分片"

**为什么不能用：** 菜单是一级/二级/三级页面的树形划分，不等同于业务场景。一个"采购订单"菜单下可能包含：新建订单、审核订单、订单查询、订单报表——应该是 4 个切片。反过来，"订单审核"可能需要同时改采购订单和销售订单（共享审核状态机）——不能按菜单分开。

**正确做法：** 以**用户操作流**为切片单位，不以菜单树为切片单位。

#### 8. ❌ "第一个切片做权限和菜单"

**为什么不能用：** 权限/菜单在没有功能页面时是不可验证的——你不知道权限码是否真的保护了正确的端点、菜单是否真的跳到了正确的页面。这是"基础设施先行"思维在垂直切片中的残留。

**正确做法：** 权限/菜单在每个切片中随功能一起交付。切片 1 做"新建订单"时同步注册这个功能的菜单+权限，切片 2 做"订单查询"时补充查询权限。**基础设施跟功能走，不单独成片。**

### 结论

5 条 → **8 条反模式**。建议按严重度排序，第 5 条（按代码文件类型）排第一，因为最抽象、最易犯。

## 三、切片粒度评估

### 销售订单 6 片分析

| 切片 | 内容 | 风险 | 粒度判断 | 评审意见 |
|------|------|:--:|:--:|------|
| 1. 新建订单 | 最小闭环 | 中 | ✅ 合适 | 基准片，独立可验证 |
| 2. 查询/筛选 | 列表过滤 | 低 | ⚠️ 过碎 | 见下方分析 |
| 3. 订单编辑 | 行编辑 | 中 | ⚠️ 过碎 | 见下方分析 |
| 4. 订单作废 | 状态变更 | 中 | ✅ 合适 | 独立业务操作 |
| 5. 审核流 | 状态机 | 高 | ✅ 合适 | 高风险应单独评审 |
| 6. 物料明细 | 主子表 | 高 | ✅ 合适 | SQL+Entity 改动大 |

### 切片 2 和 3 的合并建议

**切片 2（查询/筛选）+ 切片 3（订单编辑）→ 合并为"订单管理（查询+编辑）"**，理由：

1. **编辑依赖查询**：编辑前必须能在列表里找到要编辑的行。切片 3 标注"依赖 1"，但实际操作中用户新建完订单后，下一步就是"点进去看看+改改"，查询和编辑是同一个交互流的两个步骤，不适合拆开。

2. **粒度失衡**：切片 1（新建，包含表单+保存+列表刷新）的工作量远大于切片 2（加几个搜索框）。把搜索框单独成片导致 6 片中有一半是"中/低风险的小片"，commit 数量膨胀但每片信息量低。

3. **代码改动少**：查询/筛选在 JeecgBoot 中只是 `searchFormSchema` 加 3-5 个字段定义，5 分钟改完。单独 commit 后几乎立即进入下一片，commit 锚点的价值不大。

**合并后的 5 片方案：**

1. 📦 新建订单（最小闭环）— 中风险
2. 🔍✏️ 订单管理（查询+筛选+编辑）— 低风险。依赖 1
3. 🗑️ 订单作废（状态变更）— 中风险。依赖 1
4. 🔄 订单审核流（状态机）— 高风险。依赖 1, 3
5. 📋 订单物料明细（主子表）— 高风险。依赖 1

### 粒度判断标准（建议固化到技能）

| 判断维度 | 太细的信号 | 太粗的信号 | 合适 |
|----------|-----------|-----------|------|
| 代码改动量 | <3 个文件 | >10 个文件 | 3-8 个文件 |
| 独立可验证 | 验证依赖前一片的 UI | 验证时需要同时测 3+ 个独立场景 | 一个操作路径串起来 |
| 风险混合度 | 纯低风险 | 高+低风险混在同一片 | 同等级或相邻等级 |

### 结论

6 片 → **建议合并为 5 片**。切片 2+3 合并，其余保持不变。固化为"粒度三判断"标准放入技能。

## 四、执行流程设计

### 现有设计评估

| 设计点 | 评价 | 说明 |
|--------|:--:|------|
| 每片强制 commit | ✅ 合理 | commit 是 Git 原生锚点，不需要额外状态文件 |
| commit 命名 `slice-<N>-<业务名>` | ✅ 合理 | 清晰、可搜索、与 Git bisect 兼容 |
| 崩了回退到上一个 commit | ✅ 合理 | `git reset --hard` 是最小摩擦的恢复手段 |

### ⚠️ 需要补充的 3 个设计点

#### 1. 状态持久化

**问题：** 用户干了 3 片后下班，明天回来——怎么知道做到哪了？纯靠 commit message 可搜（`git log --oneline --grep="slice-"`），但不够直观。而且用户可能在切片 3 内部（改了一半没 commit）就中断了。

**建议：** 命令在执行时维护一个轻量状态文件 `.claude/decompose-state.json`（放在 `.claude/` 目录，不仅限于当前项目，可以作为通用机制）：

```json
{
  "task": "销售订单模块",
  "totalSlices": 5,
  "currentSlice": 3,
  "sliceHistory": [
    {"n": 1, "name": "新建订单", "commit": "abc123", "completedAt": "2026-07-31T10:30:00"},
    {"n": 2, "name": "订单管理", "commit": "def456", "completedAt": "2026-07-31T11:45:00"}
  ],
  "dirty": false
}
```

- `dirty: true` = 用户中断在切片中途（有未提交改动），恢复时 AI 先展示当前状态
- 重入时：`/decompose --resume` 读状态文件，从中断点继续
- 完成后自动清理状态文件

**为什么不放在 memory 或 hermes/：** hermes/ 是工程产物目录，状态文件是运行时的临时数据；memory 是持久记忆，不适合记录"进行到一半"的临时状态。

#### 2. 每片内置 verify

**问题：** 草案说"每片完成后强制 commit"，但没说 commit 之前要做什么验证。如果 commit 了但代码编译不过，锚点就是坏的——回退到这个锚点后仍需修编译错误。

**建议：** 每片流程内嵌验证步骤，不是可选的：

```
切片 N 执行流程：
  1. 实现代码（brainstorm → plan → [orca-review] → 写代码）
  2. /verify（强制，编译+curl，不过不 commit）
  3. git add + git commit -m "slice-<N>-<业务名>"
  4. 健康检查（可选，仅高风险片）：
     - mvn compile 二次确认（防止 DevTools 热加载掩盖问题）
     - 检查是否有未跟踪的关键文件（git status --short）
  5. 更新 decompose-state.json
  6. 输出：✅ 切片 N 完成 | 下一片：<名称> | /decompose --next 继续
```

**关键：** `/verify` 嵌入为切片内的必做步骤，不是切片外的独立命令。这样每个 commit 锚点都有质量保证。

#### 3. orca-review 触发规则

**问题：** 现有 orca-review 对"小改动（≤3 文件，无新 Entity/Service）"免评（见 orca-review SKILL.md 第 143 行）。但切片模式下，低风险片（切片 2）恰好就是这种小改动——如果免评，评审链条就断了。

**建议：** 切片模式下的评审策略：

| 切片风险 | orca-review | 理由 |
|:--:|:--:|------|
| 高 | **强制**（完整 plan 评审） | Entity/SQL/状态机，评审投入产出比高 |
| 中 | **强制**（轻量 code-review） | 有 Service 逻辑，快速扫权限/空值/并发 |
| 低 | **可选**（用户决定） | ≤3 文件纯前端改动，评审成本 ~150K tokens |

注意：这里**不沿用** orca-review 的免评规则。切片模式下中风险片包含 Service/Controller 改动，orca-review 的"小改动免评"是针对独立小任务的（如改一个样式），不适用于切片流中的关键片。

### 结论

执行流程补充 3 点：+ 状态持久化（decompose-state.json）+ /verify 内嵌 + 切片模式专用评审规则。

## 五、风险等级标准

### 现有标准评估

| 等级 | 标准 | 评价 |
|:--:|------|------|
| 高 | Entity / SQL / 状态机 | ✅ 合理——这些改动影响数据库和业务规则，回滚代价大 |
| 中 | Service / Controller | ✅ 合理——逻辑改动，回滚代价中等 |
| 低 | Vue / 加字段 | ⚠️ "加字段"的归类有歧义 |

### ⚠️ "加字段"的归类问题

草案把"加字段"归为低风险，但这取决于**加什么字段**：

- 加一个 `remark` 字段（VARCHAR，无索引）→ 低风险 ✅
- 加一个 `unit_price` 字段（DECIMAL）+ 所有涉及金额计算的地方 → **高风险** 🔴（涉及金额 = 资损风险）
- 加一个外键字段 + 修改 JOIN 查询 → **中风险** 🟡

**建议：** "加字段"不作为独立风险类别，而是拆入现有三级：

| 字段改动类型 | 风险等级 |
|-------------|:--:|
| 字符串/文本字段，纯展示 | 低 |
| 外键/关联字段 | 中（涉及 JOIN 查询变更） |
| 金额/数量/状态字段 | 高（涉及计算逻辑或状态机） |

### 风险等级的"一票升级"规则

**建议补充：** 任一条件满足，整片风险升级：

- 涉及 ≥2 个模块目录 → 升级一级
- 涉及金额计算 → 直接定为高
- 涉及并发/锁 → 直接定为高
- 新表 DDL → 直接定为中（即使其他都是低风险）

### 结论

风险标准整体合理。补充"加字段"的细分 + "一票升级"规则。

## 六、现有命令集成

### 与现有工作流的衔接分析

```
现有流程：/brainstorm → /plan → [orca-review] → 写代码 → /verify → /done

/decompose 插入点：
  /brainstorm（整体需求澄清）
    ↓
  /decompose（拆分大任务为切片）  ← 新增
    ↓
  for each 切片：
    /plan（切片级实施计划）
      ↓
    [orca-review]（高风险+中风险）
      ↓
    写代码
      ↓
    /verify（切片级验证）
      ↓
    git commit（锚点）
    ↓
  /done（整体完成检查）
```

### 逐命令衔接评估

| 衔接点 | 现状 | 问题 | 建议 |
|--------|------|------|------|
| brainstorm → decompose | 无衔接 | brainstorm 产出验收标准，decompose 需要这些标准来切片 | decompose 命令第一步：读取最近的 brainstorm 结论（从会话上下文或 hermes/prd/），基于验收标准推导切片 |
| decompose → plan | 无衔接 | plan 现在默认"整个任务一起 plan"，需要适应切片模式 | decompose 的每片输出应包含"本片的计划要点"，plan 命令增加 `--slice` 参数或自动检测 decompose-state.json |
| orca-review | 部分冲突 | orca-review 的"小改动免评"与切片流的中风险片冲突 | 见上文"四-3"，采用切片专用评审规则 |
| verify | 无冲突 | verify 原本就是按变更内容推导验证，切片模式天然吻合 | 见上文"四-2"，verify 内嵌为切片的必做步骤 |
| done | 需要适配 | done 现在检查的是"所有改动都在项目目录+标记完整"，没有考虑切片流的完整性 | done 增加切片流检查：所有切片 commit 是否存在、状态文件是否标记完成、是否有遗漏的切片 |

### ⚠️ 关键风险：orca-review 的 token 成本累积

**问题：** 当前 orca-review 每次启动独立 Claude 会话加载 ~150K tokens 上下文（22 rules + 3 CLAUDE.md + 70 skills）。如果 5 个切片中 4 个需要评审（1 高 + 3 中 = 4 次），总评审成本 = 4 × 150K = **600K tokens**。这还不算评审内容本身。

**这不是否决理由，但需要在设计中显式告知用户：**

- 在 `/decompose` 输出中，对需要 orca-review 的切片标注 "⚠️ 本片需要外部评审（预计 ~150K tokens）"
- 提供 `--skip-review` 选项让用户在低风险片跳过评审（用户主动选择，非 AI 默认跳过）
- 建议：如果用户选方案 A（手动切片+串行）就是为了控制质量，那评审成本是可接受的——这本来就是"质量换 token"的取舍

### 结论

集成整体自然。需要补充：brainstorm→decompose 的上下文传递、decompose→plan 的参数适配、done 的切片完整性检查、评审 token 成本显式披露。

## 两个非阻塞风险警示

### 风险 A：命令文件膨胀

`/decompose` 如果按草案设计，命令文件会包含：切片拆分步骤、反模式检查、粒度判断、验证内嵌、状态管理……这些不是"通用工作流"，而是带有**强领域知识**的操作（如何判断切片粒度？什么算反模式？）。

**按 skill-command-boundary.md 的判定标准**，以下内容属于技能（换项目需要改）：
- 5 种/8 种反模式的具体定义 → SKILL.md
- 风险等级判定标准（Entity=高） → SKILL.md
- 粒度判断标准（3-8 个文件） → SKILL.md

### 风险 B：切片内"端到端"的定义可能被稀释

"端到端可手工验证"的准确含义是：**做完切片后，打开浏览器，走一遍用户操作路径，看到预期结果。** 但如果切片依赖前一片的数据库表，验证时需要前一片的数据——这时"可手工验证"实际上依赖前一片的环境没有被破坏。

**比如：** 切片 5（审核流）依赖切片 1 的表和数据。如果切片 4 的代码改动引入了一个 bug 导致数据损坏，切片 5 验证时看到的"审核失败"可能是切片 4 的 bug，不是切片 5 的问题。

**这不是设计缺陷，但需要在技能文档中写明：**
- 每片验证时，先确认依赖的切片功能正常（快速冒烟）
- 如果依赖切片异常，先修依赖切片，再继续当前切片
- 这是垂直切片的固有属性——依赖链越长，调试越需要追溯上游
