# Harness 测试体系改进方案评审输入（2026-07-28）

## 背景
jeecgBoot MES 项目 harness 测试体系实战暴露问题：盘点单模块交付时 API 测试 14/14 + E2E 12/12 全绿，但人工测试发现 4 个 bug（物料显示ID/账面数取值有误/审核未生效/明细过多）。用户认为测试体系"实际使用效果不理想"，我做了复盘并提出改进方案，请做方案级评审。

## 复盘结论（4 bug × 4 盲区）
1. 物料显示ID → API测试只断言数值不断言显示值（渲染层盲区）
2. 账面数取值有误 → 测试payload是手工想象构造，与前端真实发送形状不同
3. 审核未生效 → 新模块只有API测试没有E2E完整业务流
4. 明细过多 → P0修复把零库存行全纳入快照，数据正确但UX灾难（自动化测不出）

## 现状数据
- 后端35个Controller，API测试覆盖约12个(34%)，finance 9个Controller 0测试
- E2E 5个spec共12用例，11个是"页面能打开"级，只有1个真实业务流
- testing.md写"E2E用浏览器登录不设Token"，实际用token注入（规则与现实矛盾）
- /gen-tests Bug反哺闭环从未真正跑过（僵尸）
- done.md/finish.md要求/test-api、/test-all必过，但实际关键路径是/verify→pre-commit-gate→部署，测试在路径外
- 测试清理用execSync调mysql，Windows引号问题导致残留→下次跑挂→失信→弃用螺旋
- 2个purchase链路测试预存在失败没人修（破窗）

## 改进方案（待评审）

### P0：把测试钉进关键路径
- 定义"关键套件"：不追60%覆盖率，改为"每模块业务流测试（创建→审核→状态）必须全绿"（约8个API套件+核心E2E）
- pre-deploy-check hook 增加跑关键套件，红则提示（先影子模式警告，2周后转阻断）

### P1：新模块测试模板（/plan固定一栏）
新模块交付三件套：
1. API业务流测试（harness/tests/xxx.test.js）
2. 1条E2E完整业务流（创建→编辑→审核→结果页，含显示值断言：物料列必须显示编码不是ID）
3. 关键payload从浏览器DevTools抓包保真

### P1：环境自愈
- 清理统一"写SQL文件→mysql执行文件"（绕开Windows引号），抽共享helper
- 所有测试强制唯一编码（时间戳后缀）

### P2：规则对齐+破窗
- testing.md改写：token注入合法化、覆盖目标改"关键业务流100%"
- 2个chain测试修或隔离
- /gen-tests：用一次或删

## 待评审问题
1. "关键套件钉进部署门禁"会不会太重？每次部署跑API+E2E全量约5-10分钟，业务方能接受吗？还是应该只跑API（~2分钟）E2E留给重大变更？
2. 影子模式2周转阻断合理吗？还是直接阻断？（项目目前只有1个客户在生产）
3. 新模块三件套模板会不会导致"为了过门而写的水测试"（比如E2E只测空流程）？如何防止模板化敷衍？
4. 放弃60%覆盖率目标改"关键业务流100%"，会不会让测试范围越缩越小？需要配套什么机制防止退化？
5. 有没有遗漏的改进点？比如：渲染层断言除了E2E还有没有更轻的手段（组件测试/Vitest截图对比）？测试数据管理（seed/fixture）要不要体系化？
