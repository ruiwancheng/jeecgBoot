### 2.0（P0 硬冲突）主线与场景 1 结构冲突 —— 信息该放哪？

**这是最大的设计问题，必须解决后再写正文。**

#### 问题

当前场景 1 副标题是「从想法到代码提交」，完整链路为：

```
/brainstorm → /plan → orca-review → 写代码 → /verify → /pre-commit-gate → git commit → /done
```

完善方案要在两个地方同时加内容：
- **主线章节**：完整端到端链（含 push/部署/deploy-verify/交付/session-wrap）
- **场景 1 补步骤 8-10**：推送/部署/部署后验证

这导致三个后果：

| 后果 | 说明 |
|------|------|
| **信息重复** | 推送/部署/验证三个动作在主线章节和场景1各写一遍，业务人员看到两处描述同一件事会困惑 |
| **场景 1 副标题撒谎** | 「从想法到代码提交」变成了「从想法到交付验收」，已超出原设计范围 |
| **场景 1 步骤膨胀** | 从 7 步变 10 步，场景 1 作为"最高频"场景负担过重——不是每次开发都要部署 |

#### 建议方案

**推荐 B**（信息分层，避免重复）：

```
主线章节（新增）
  └─ 端到端全链路命令序列（每步三要素）
     ├─ 开发阶段 → 详见场景 1（步骤 1-7）
     ├─ 推送部署阶段 → 详见本小节（git push → 部署控制台 → /deploy-verify）
     ├─ 交付验收 → 客户确认动作
     └─ 每日收尾 → /session-wrap

场景 1（修改）
  └─ 副标题：「从想法到代码提交（开发阶段）」
  └─ 保留步骤 1-7 不变
  └─ 步骤 7 末尾加一行引导：「👉 代码已提交？继续看「主线章节 - 推送部署」」
  └─ 不补步骤 8-10
```

**放弃方案 A**（两处都写全）：场景 1 和主线章节同时写推送/部署/验证，业务人员看两遍重复内容，维护时改两处。
**放弃方案 C**（只在场景 1 加）：主线章节约等于空壳，达不到"端到端命令链"的设计目标。

### 2.1 `/pre-commit-gate` 已内置视觉检查，主线中 `/visual-check` 重复

#### 证据

`commands/quality/pre-commit-gate.md` L42：

```
### 4. 视觉门控（非 skip 级）
变更的 Vue 页面 → Orca browser 截图 → 与基线对比。
```

#### 问题

完善方案的主线链是：`/verify → /visual-check → /pre-commit-gate → git commit`

如果非 skip 级变更，`/pre-commit-gate` 内部已经做了一次 Orca 截图+基线对比。主线中单独加 `/visual-check` 等于**同一个页面截图两次**，浪费时间且令业务人员困惑"为什么两个命令做同一件事"。

#### 建议

两个选择：

| 选择 | 主线链 | 适用场景 |
|------|--------|---------|
| **简化为一段** | `/verify → /pre-commit-gate → git commit` | 日常开发（推荐，pre-commit-gate 已含视觉） |
| **分拆用 --skip-visual** | `/verify → /visual-check → /pre-commit-gate --skip-visual → git commit` | 想单独先看截图确认再安全检查时 |

推荐第一种。在主线章节的 `/pre-commit-gate` 步骤说明中注明"此命令已包含页面截图对比"，避免用户困惑"我是不是漏了 /visual-check"。

**`/visual-check` 的独立价值不在主线，而在以下场景：**
- 场景 7（部署验证）—— 已正确列出
- 排查 UI 问题（"帮我看看采购订单页有没有异常"）—— 不是主线流程
- 首次建立基线（"帮我给所有页面建基线"）—— 一次性操作

### 2.2 `/plan` 已强制嵌入 orca-review，主线不宜将其列为独立步骤

#### 证据

`commands/dev/plan.md` L38-44 明确规定：

> **无论 delegate 还是直接模式，任何代码改动（Java/Vue/TS/SQL）都必须先 orca-review。**
> 直接模式+代码改动 ≠ 免评。

#### 问题

完善方案的主线链将 orca-review 列为独立步骤（`(大改动 orca-review)`）。但实际执行中：
- 业务人员输 `/plan` 后，AI 内部自动触发 orca-review
- 如果业务人员看到主线写着"大改动才跑 orca-review"，小改动时可能会想"我不需要评审"—— 但 plan 命令强制要求**所有代码改动都评审**，小改动也不例外

业务人员不需要知道 orca-review 的存在——这是 AI 内部的质检步骤，不是用户操作。

#### 建议

主线的每一步应该只包含"用户输入什么命令"，不要混入 AI 内部步骤。主线链改为：

```
/brainstorm → /plan → 写代码 → /verify → /pre-commit-gate → git commit → ...
```

在 `/plan` 步骤的"AI 做什么/看到什么算通过"中说明 AI 会自动调外部评审终端。业务人员看到的信号是"AI 说评审通过，可以开始写代码"。

**特殊场景**：`/orca-review` 命令本身不存在——它是 `dev:orca-review` 技能（在 `/plan` 内部调用）。当前指南场景 1 第 3 步写 `/orca-review` 存在歧义：如果用户真的输入 `/orca-review`，这是一个有效的 skill 调用（`orca-review` 技能存在），但其效果和 `/plan` 内部的 orca-review 重复。建议保持一致——要么全部作为 `/plan` 内部步骤（主线 + 场景1），要么保留为独立可选步骤且说明"等同于让 AI 再检查一遍方案，通常 /plan 已经自动做了"。

### 2.3 部署控制台操作缺少"这步不在 Claude Code 里"的明确标示

#### 问题

完善方案的主线链中「部署控制台「开始部署」」是唯一需要业务人员**离开 Claude Code 终端、打开浏览器**的操作。此前所有步骤都在对话窗口里完成，这步突然切换工具，业务人员可能：

1. 以为在 Claude Code 里输入"部署控制台 开始部署"就能触发部署
2. 打开浏览器后不知道要看什么才算"部署成功了"
3. 部署中（3-8 分钟）不知道是等着还是可以做别的

#### 建议

主线章节中部署控制台这一步，必须包含以下四要素（当前方案只给了三要素模板）：

| 要素 | 内容示例 |
|------|---------|
| **你做什么** | 打开浏览器 → 输入 `http://100.122.125.106:3101` → 点击「开始部署」按钮 |
| **这不是 Claude Code 命令** | ⚠️ 这步在浏览器里操作，不是在对话窗口输入命令 |
| **看到什么算通过** | 页面显示部署进度条 → 最终显示「部署完成」绿色提示 |
| **等多久** | 首次 5-8 分钟，后续 3-5 分钟。可以切回对话窗口继续工作，部署在服务端后台运行 |
| **卡住了怎么办** | 看本节「故障速查」→ 部署控制台连不上 / 部署报错 |

### 2.4 缺少首次部署的 bootstrap 说明

#### 问题

`/deploy-verify` 依赖 `.last-deploy-commit` 文件做 diff 基准。首次部署时这个文件不存在：
- `deploy-verify.md` 说"若 `.last-deploy-commit` 不存在 → 使用 HEAD~1（首次）"
- 但 HEAD~1 在新项目首次推送时可能不是正确的比较基准（取决于 git 历史）
- 业务人员不知道 `.last-deploy-commit` 是什么、是否需要手动创建

#### 建议

部署操作小节加一行说明：

> **首次部署**：`.last-deploy-commit` 文件自动创建，你不需要手动操作。`/deploy-verify` 会用最近一次提交作为比较基准。

或更简单：在主线"部署控制台"步骤的"AI 做什么"中说明：

> AI 在部署完成后自动记录本次部署的 commit，下次 `/deploy-verify` 自动对比变更。

### 2.5 权限码生效确认缺失

#### 问题

新增菜单和权限码（`sys_permission` 表 INSERT）后，JeecgBoot 的 Shiro 权限缓存不会自动刷新。业务上表现为：部署成功 → 用户登录 → 看不到新菜单 → 以为部署失败。

这不是 `/deploy-verify` 能发现的问题（API 测试用 admin 账号，admin 默认有全部权限）。但真实用户（非 admin 角色）登录后看不到新菜单是常见事故。

#### 建议

主线"交付"步骤加一条（或作为部署操作小节的"部署后必验"）：

> **权限码确认**：部署后让非 admin 角色的用户登录 → 确认能看到新菜单 → 确认能操作新按钮。如果看不到，运行 `admin:restart-backend` 清除权限缓存。

### 2.7 `/done` 命令在主线中位置不明确

#### 问题

当前场景 1 第 7 步是 `/done`（完成检查 → 输出选项：提交/继续编辑/暂不提交）。完善方案的主线链中没有 `/done`，直接是 `/pre-commit-gate → git commit`。

`/done` 的独特价值是**决策环节**——它不是检查工具，而是"帮业务人员判断现在是否可以提交"。如果主线没有 `/done`，业务人员需要自己判断"是不是该提交了"。

#### 建议

主线链在 `/pre-commit-gate` 后加 `/done`：

```
/verify → /pre-commit-gate → /done → git commit → git push → 部署控制台 → /deploy-verify → 交付 → /session-wrap
```

`/done` 的"AI 做什么"：检查 verify 通过 + 测试通过 → 输出选项（提交/继续编辑/暂不提交）。业务人员选择"提交"后，AI 自动执行 git commit 和后续步骤。

**或者反过来**——如果主线已经明确了"做完验证就推送部署"，可以去掉 `/done` 的决策意义，让 `/done` 只在场景 1 中作为"开发阶段收尾"存在。这两种设计都合理，但**必须选一个，不能主线没 `/done`、场景 1 有 `/done`，让业务人员不知道什么时候该用哪个**。

建议保持 `/done` 在主线中，因为它的"给你选项，不替你做决定"哲学是 harness 设计的核心原则（铁律 6）。

### 2.8 部署失败的回退路径缺失

#### 问题

整个指南（含完善方案）没有任何"部署失败了怎么办"的内容。`deployment-architecture.md` 有故障排查表，但指南正文没有引用。

业务人员部署失败后的真实反应：反复点「开始部署」按钮 → 更糟 → 放弃 → 打电话找人。

#### 建议

部署操作小节的故障速查部分至少覆盖三条：

| 现象 | 可能原因 | 你该做什么 |
|------|---------|-----------|
| 部署进度卡住超过 10 分钟 | Less 编译死锁 | 等——脚本自动重试 3 次。超过 15 分钟刷新页面重试 |
| 部署完成但页面没变化 | 浏览器缓存 | Ctrl+F5 强制刷新 |
| 部署控制台打不开 | Windows 端口转发断开 | 输入 `帮我排查部署控制台连接问题` |

### 2.9 服务端 vs 客户端两种部署路径未区分

#### 问题

当前指南快速启动包含两种模式：
- `/start`：服务端（本地跑全部服务）
- `/client-start`：客户端（后端连服务端，本地只跑前端）

两种模式的部署路径完全不同：
- **服务端**（`/start`）：本地改代码 → 本地编译 → 本地验证 → `/deploy-verify` 直连本地后端。**不需要 git push、不需要部署控制台。**
- **客户端**（`/client-start`）：本地改代码 → 本地验证前端 → git push → 部署控制台部署后端 → `/deploy-verify` 连服务端。**需要完整推送部署链路。**

完善方案的主线链隐含假设是**客户端模式**（需要 push + 部署控制台）。如果业务人员在服务端用 `/start` 启动后按主线操作，会发现：
- git push 不需要（改了直接生效）
- 部署控制台不需要（本地编译即生效）
- `/deploy-verify` 比较的是本地 `.last-deploy-commit`，不是服务端的

#### 建议

主线章节开头加一句限定：

> 以下主线适用于**客户端开发模式**（`/client-start` 启动）。如果你用 `/start` 在服务端直接开发，修改代码后本地编译即生效，跳过 git push 和部署控制台步骤，直接运行 `/deploy-verify`。

## 三、建议 💡

以下不阻塞方案通过，但可提升指南的傻瓜程度和维护性。

### 3.1 主线每步加"卡住了？"指向

当前方案要求"卡住指向场景编号"。建议统一用符号而非编号（编号会随章节增删变动）：

```
/brainstorm → /plan → ... → /session-wrap
   ↓卡住?         ↓卡住?
  场景2 debug    场景3 环境检查
```

每步只挂一个最可能的卡住原因。比罗列全部场景更精准。

### 3.2 "git push" 对业务人员过于技术化

"git push" 是开发者术语。业务人员不需要知道什么是 git push，只需要知道"把代码发到服务器"。主线中可以用业务语言：

| 技术术语 | 业务语言 |
|---------|---------|
| git commit | 保存代码修改 |
| git push | 发送代码到服务器 |
| git rebase | （不出现，AI 自动处理） |

"/git-commit" 命令内部已包含"询问是否推送"，主线可以不单独列出"git push"步骤——改为在 commit 步骤说明"AI 会问是否推送到服务器，选择'是'"。

### 3.3 部署操作小节按业务语言重写按钮用途

`deployment-architecture.md` 的按钮说明偏技术：

| 现在 | 建议改为（业务语言） |
|------|---------------------|
| 自动分析 git diff 选模式 | 智能判断——改了什么自动选最快方式 |
| 仅前端 | 只更新页面（3 分钟）——只改了页面样式/文字时用 |
| 仅后端 | 只更新接口（5 分钟）——只改了业务逻辑时用 |
| 强制全量 | 全部重建（8 分钟）——不确定改了什么时用这个，最保险 |

### 3.4 主线应引用"环境与 MCP 启动检查清单"

主线链中多个命令（`/visual-check`、`/pre-commit-gate`、`/deploy-verify`）依赖 Orca 运行。主线章节开头加一句：

> 开始前先跑一次「快速诊断箱」：输入 `帮我检查开发环境`。确认 Orca 状态正常后再开始主线流程。

### 3.5 `/session-wrap` 触发时机补充

当前方案将其放在主线末尾（每日）。但实际使用中：
- 开发到一半被叫去开会 → 该跑 `/session-wrap` 吗？
- 一天改了 3 个需求 → 每个需求跑一次 `session-wrap` 还是一天一次？

建议在主线章节末尾加注：

> `/session-wrap` 什么时候跑：每天收工时跑一次。中途不需要。如果开发中途要交给别人继续，用 `/cleanup-context` 生成记忆卡片而不是 `/session-wrap`。
