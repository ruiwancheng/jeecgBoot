## 2. 逐项评审

### 2.1 改动一：部署后自动执行 ❌ 方向对，但缺关键防护

**方案：** 部署→自动 git diff→查链路注册表→命中链路自动跑鹰眼团+铁拳团→汇总报告

**评审：**

- ✅ 把"可选提示"变成"自动执行"解决了当前最大痛点：遗忘
- ✅ 部署后是合理的触发时机——代码已上线，验证"实际跑的是对的"

**必须调整：**

- ❌ **git diff 基准错误** — 方案用 `HEAD~1` 做 diff 基准，但集中部署 + 多人并行场景下，两次部署之间可能有多个 commit。A 的部署刚启动，B push 了 commit，最终部署包含 B 的代码但审计只看了 A 的 diff。必须用 `.last-deploy-commit` 作为 diff 基准（部署完成后更新此文件）

- ❌ **缺少变更分类** — git diff 分不出"改按钮文字"和"改金额计算逻辑"。前端文案变更也触发 10 分钟全链路审计，团队会在第三次等待后关掉自动审计。必须加文件类型 × 变更范围的最小过滤：

```
*.vue(模板文字) → SKIP
*.vue(脚本逻辑) → 仅前端测试
*.java(Entity)  → 全链路
*.java(Controller) → API测试 + 审计
*.sql(DDL)      → 全链路 + 审计
```

- ❌ **缺少失败策略** — 审计发现 P0 后部署继续还是回滚？方案没说。这是整个方案最大的决策点，决定方案是"摆设"还是"门控"

- ❌ **缺少逃生舱** — 生产 P0 hotfix 不能等 10 分钟审计。必须设计 `--skip-audit` 旁路 + 事后补偿审计 + 旁路使用频率监控

### 2.2 改动二：业务链路注册表 ⚠️ 核心思路对，实施细节缺失

**方案：** `hermes/business-chains.json` 定义采购链路 apply→order→receipt→ledger，改任意节点触发全链路回归

**评审：**

- ✅ 链路语义比"文件数"精确得多——这才是解决"分级测试只看文件数"的正确方向
- ✅ JSON 格式对业务人员可读，PM 可以维护链路定义

**必须调整：**

- ❌ **无 Schema 校验** — JSON 多一个逗号 → 解析失败 → 静默 fallback 到"无链路命中" → 0 测试执行，部署正常完成，开发者以为一切正常。这是最危险的静默失效场景。部署流水线第一步必须是 `jsonschema validate`

- ❌ **手动维护必然腐烂** — 新增"采购退货"模块（也改订单表），没更新 JSON → 退货改动不触发链路。三个月后 JSON 和实际代码脱节，自动门控形同虚设

- ❌ **未考虑多开发者并发编辑** — 两人同时加链路 → git merge conflict → 冲突标记留在 JSON → 解析崩溃

- ❌ **缺少链路与文件的自动校验** — 理想情况：CI 定期跑"JSON 中引用的文件路径是否真实存在？文件路径是否被至少一条链路覆盖？"没有这个，腐烂是必然的

**建议：** 链路注册表不应是纯手动 JSON。应有一个生成脚本：扫描模块目录 → 自动检测 Controller/Service/Mapper 的引用关系 → 生成候选链路 → 人工确认后写入 JSON。这是"降低维护成本"的关键。

### 2.3 改动三：可读质量报告 ✅ 无争议，但格式须结构化

**方案：** 可读质量报告替代 50 行日志

**评审：**

- ✅ 这是无争议的改进——没有人反对更可读的报告
- ⚠️ 但报告格式必须结构化（Markdown + 固定章节），否则连续 10 次部署后无法对比趋势

**建议：** 报告模板固定为：

```markdown
# 部署质量报告 — YYYY-MM-DD HH:MM

## 部署概况
- 变更文件: N 个
- 命中链路: [采购: apply→order→receipt→ledger]
- 审计耗时: X 分钟

## P0 新发现 (阻塞)
- [ ] xxx

## P0 遗留 (不阻塞，已记录)
- [ ] xxx (自 2026-07-20 起)

## 测试结果
- API: 12/12 ✓
- E2E: 5/5 ✓

## 判定: PASS / NEEDS WORK / BLOCKED
```

## 3. 综合风险分析

| 风险 | 等级 | 说明 |
|------|:--:|------|
| 链路注册表腐烂 → 静默跳过审计 | 🔴 极高 | JSON 失效 = 自动门控形同虚设，且开发者不会察觉 |
| git diff 基准错误 → 漏审代码 | 🔴 高 | 多人集中部署的常态场景 |
| 前端文案改触发全链路 → 团队关掉审计 | 🔴 高 | 每次 10 分钟等待，容忍度约 3 次 |
| P0 去重缺失 → 报告噪声 → 没人看 | 🟡 中 | "狼来了"效应，两周后审计报告沦为摆设 |
| 测试文件过时 → 假阴性 | 🟡 中 | 旧测试全通过，新接口裸奔 |
| 测试数据污染生产 | 🟡 中 | E2E 创建真实订单、消耗单号、触发告警 |
| 审计成为部署瓶颈（10min 同步等待） | 🟡 中 | 紧急 hotfix 场景不可接受 |
| Token 成本不可控 | 🟢 低 | 可预估：~50K token/次 × 5 次/天 = ~$5/天 |
| 鹰眼团测试文件无人维护 | 🟡 中 | "现成的测试"现在可能是现成的，三个月后不是 |

## 4. 遗漏场景清单

| # | 遗漏 | 严重度 |
|:--:|------|:--:|
| 1 | **并发部署竞态** — 部署流水线 A 和 B 同时触发，共享 `.last-deploy-commit` | P0 |
| 2 | **与 quality-gate 关系未定义** — 审计结果是映射到 BLOCKED 还是只 WARN？ | P0 |
| 3 | **无影子模式过渡** — 直接上线阻塞模式，误报直接阻挡部署 | P0 |
| 4 | **无反馈闭环** — P0 修复后如何验证？同类问题是否反复出现？ | P1 |
| 5 | **ESL 成本未量化** — 10 人审计每次 50K token，月成本需提前算清 | P1 |
| 6 | **审计结果去重** — 历史 P0 和新 P0 混在一起，无法区分"本次引入"vs"已知遗留" | P1 |
| 7 | **审计和测试的并行/串行调度** — 改 3 个模块时是串行(30min)还是并行(10min×3 倍 token)？ | P2 |
| 8 | **多语言项目** — 链路注册表只考虑 Java 文件？Vue 文件怎么映射到链路？ | P2 |

## 5. 判定结论：有条件通过（Conditional Pass）

**方案方向正确，"手工验收 4 小时 vs 自动化 10 分钟"是真实且重要的痛点。但"只改 workflow.md + 一个 JSON"是对实施复杂度的严重低估——实际上需要 7+ 项基础设施支撑。**

### 必须补的 3 个硬要求（缺一不可上线）

| # | 要求 | 理由 |
|:--:|------|------|
| **H1** | **变更分级过滤** — 不是所有 git diff 都值得跑审计。文件类型 × 变更范围的最小过滤（模板文字改→跳过，Entity 改→全链路）。不补 = 第三周被关掉 | 防止"改个文案等 10 分钟" |
| **H2** | **失败策略 + quality-gate 映射** — 审计 P0 → 部署行为是什么？（阻塞/告警/忽略），P0 遗留 → 不阻塞但提醒。必须与已有 quality-gate PASS/NEEDS WORK/BLOCKED 对齐 | 决定方案是门控还是摆设 |
| **H3** | **影子模式过渡 2 周** — 审计自动执行但先不阻塞部署，积累误报率、真实发现问题率、Token 消耗数据。2 周后评审数据再决定是否开启阻塞模式 | 防止误报阻塞部署导致方案被关 |

### 建议补的 4 个软要求（可上线后迭代）

| # | 要求 | 理由 |
|:--:|------|------|
| S1 | `.last-deploy-commit` 替代 `HEAD~1` 做 diff 基准 | 修复多人并发部署漏审 |
| S2 | `business-chains.json` 加 JSON Schema 校验 + CI 定期链路覆盖审计 | 防止注册表腐烂 |
| S3 | P0 指纹去重（问题描述+文件+代码片段哈希） | 区分新 P0 vs 遗留 P0 |
| S4 | `--skip-audit` 紧急旁路 + 使用频率监控 | 生产 hotfix 不等待 |

### 明确的"不要做"

| 不要做 | 原因 |
|------|------|
| 不要一开始就阻塞部署 | 没有误报率数据，阻塞 = 盲飞 |
| 不要让测试数据污染生产库 | 必须加 `created_by = 'auto_quality_gate'` 标记 + 测试后清理 |
| 不要把 JSON 当数据库用 | 链路超过 20 条后 JSON 的维护成本指数增长，尽早考虑结构化存储（SQLite 或 YAML） |
| 不要假设测试永远是"现成的" | 必须加测试时效性校验：测试上次通过时间 + 覆盖的 API 版本号 |
