# Orca Review: 集中部署后自动质量门控方案

**评审日期:** 2026-07-22
**评审人:** Claude Code (orca-review)
**结论: 有条件通过（Conditional Pass）** — 方向正确，实施门槛被严重低估，必须补 3 项硬要求 + 4 项软要求后才能上线

## 1. 方案理解

阅读了以下上下文文件确认现有体系：`workflow.md`（开发流程+防失忆+分级测试）、`quality-gate-criteria.md`（PASS/NEEDS WORK/BLOCKED 三级判定）、`security-gate-checklist.md`（P0/P1 安全扫描）、`quality-escalation.md`（缺陷升级规则）、`engineering-artifacts.md`（产物目录规范）、`tiequan-report-retention.md`（审计报告留存）、`audit-classification.md`（审计反馈分类）、`testing.md`（测试标准）、`deep-inspect-schedule.md`（巡检调度）、`jeecg-tiequan-audit/SKILL.md`（10 人并行审计 ~7 分钟/模块）。

---

## 2. 逐项评审

### 2.1 改动一：部署后自动执行

**方案：** 部署→自动 git diff→查链路注册表→命中链路自动跑鹰眼团+铁拳团→汇总报告

- ✅ 把"可选提示"变成"自动执行"解决了最大痛点：遗忘
- ❌ **git diff 基准错误** — `HEAD~1` 在多人并行部署时漏审中间 commit，必须用 `.last-deploy-commit`
- ❌ **缺少变更分类** — 改按钮文字也触发 10 分钟全链路，团队容忍度约 3 次后关掉
- ❌ **缺少失败策略** — 审计 P0 → 部署继续还是回滚？这是决定方案是"门控"还是"摆设"的核心决策
- ❌ **缺少逃生舱** — 生产 P0 hotfix 不能等 10 分钟审计

### 2.2 改动二：业务链路注册表

**方案：** `hermes/business-chains.json` 定义采购链路，改任意节点触发全链路回归

- ✅ 链路语义比"文件数"精确——解决分级测试痛点
- ❌ **无 Schema 校验** — JSON 多一个逗号→解析失败→静默 fallback→0 测试执行，最危险失效模式
- ❌ **手动维护必然腐烂** — 新增"采购退货"不更新 JSON，三个月后 JSON 与代码脱节
- ❌ **缺少链路覆盖审计** — CI 应定期检查"所有 Controller 是否被至少一条链路覆盖"

### 2.3 改动三：可读质量报告

- ✅ 无争议改进
- ⚠️ 必须固定结构（变更概况→P0 新发现→P0 遗留→测试结果→判定），否则无法趋势对比

## 3. 综合风险矩阵

| 风险 | 等级 | 说明 |
|------|:--:|------|
| 链路注册表腐烂 → 静默跳过审计 | 🔴 极高 | JSON 失效 = 门控形同虚设，无人察觉 |
| git diff 基准错误 → 漏审代码 | 🔴 高 | 多人集中部署的常态场景 |
| 前端文案改触发全链路 → 团队关掉审计 | 🔴 高 | 容忍度约 3 次 |
| P0 去重缺失 → 报告噪声 → 没人看 | 🟡 中 | "狼来了"效应，两周后报告被忽略 |
| 测试文件过时 → 假阴性 | 🟡 中 | 旧测试全通过，新接口裸奔 |
| 测试数据污染生产 | 🟡 中 | E2E 创建真实订单、消耗单号、触发告警 |
| 10min 同步等待 → 部署瓶颈 | 🟡 中 | hotfix 场景不可接受 |
| Token 成本 | 🟢 低 | ~50K × 5 次/天 ≈ $5/天 |

## 5. 判定结论：有条件通过（Conditional Pass）

**方案方向正确，"手工验收 4 小时 vs 自动化 10 分钟"是真实且重要的痛点。但"只改 workflow.md + 一个 JSON"是对实施复杂度的严重低估——实际上需要 7+ 项基础设施支撑。**

### 必须补的 3 个硬要求（缺一不可上线）

| # | 要求 | 不补的后果 |
|:--:|------|------|
| **H1** | **变更分级过滤** — 模板文字改→跳过，Entity 改→全链路 | 第三次"改文案等 10 分钟"后方案被关 |
| **H2** | **失败策略 + quality-gate 对齐** — 审计 P0 → BLOCKED 还是 WARN？P0 遗留不阻塞 | 不确定方案是门控还是摆设 |
| **H3** | **影子模式过渡 2 周** — 只审计不阻塞，积累误报率+真实发现率+Token 消耗数据 | 误报直接挡部署 → 方案被关 |

### 建议补的 4 个软要求（可上线后迭代）

| # | 要求 | 理由 |
|:--:|------|------|
| S1 | `.last-deploy-commit` 替代 `HEAD~1` 做 diff 基准 | 修复多人并发部署漏审 |
| S2 | JSON Schema 校验 + CI 定期链路覆盖审计 | 防止注册表腐烂 |
| S3 | P0 指纹去重（描述+文件+代码哈希） | 区分新 P0 vs 遗留 P0 |
| S4 | `--skip-audit` 紧急旁路 + 使用频率监控 | hotfix 不等待 |

### 明确的"不要做"

| 不要做 | 原因 |
|------|------|
| 不要一开始就阻塞部署 | 没有误报率数据，阻塞 = 盲飞 |
| 不要让测试污染生产库 | 必须加 `created_by='auto_quality_gate'` 标记 + 测试后清理 |
| 不要把 JSON 当数据库用 | 链路超 20 条后维护成本指数增长，尽早考虑结构化存储 |
| 不要假设测试永远是"现成的" | 必须加测试时效性校验：上次通过时间 + 覆盖的 API 版本号 |
